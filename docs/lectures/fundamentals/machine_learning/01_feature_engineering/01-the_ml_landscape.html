Lectures / Machine learning / Feature engineering

The machine learning landscape

Before any algorithm, the map. Where each method sits, what it assumes, and where the bias-variance trade-off lives. This is the lecture every later lecture refers back to when it says "trade complexity for generalisation".

Lecture 1 of 62 Reading time, 45 minutes Part I: foundations
Step 1

The 30-second version

Machine learning is the discipline of building functions $\hat{f}$ that approximate an unknown true function $f$ from a finite sample of data, in a way that generalises to data the function has not yet seen. Three paradigms differ in what kind of signal the data carries: supervised learning has labelled examples and approximates $\mathbb{E}[Y \mid X]$, unsupervised learning has no labels and looks for structure inside $X$ alone, reinforcement learning has rewards instead of labels and learns by interaction. Across all three, the work is the same six-stage pipeline: prepare features, split data, fit a model, tune hyperparameters, evaluate honestly, explain what was learned. The single trade-off that runs through every stage is between bias (a simple model misses real structure) and variance (a complex model fits the noise). Everything else in this course is local detail on top of that frame.

Feynman test Machine learning is curve-fitting that knows it has to work on the next observation, not just the ones in front of it. You have a sample $\{(x_i, y_i)\}$ and you want a function $\hat{f}$ such that, for some new $x^*$ drawn from the same distribution, $\hat{f}(x^*)$ is close to the unknown $y^*$. Every method in this course is a different way to constrain the space of functions you search over so that the one you pick generalises rather than memorises. The constraint is the algorithm; the data is the input; generalisation is the test.
What's beyond the syllabus A standard ML course treats algorithms as the subject and the pipeline as scaffolding. In credit risk practice the order is reversed: the pipeline is the subject, because every modelling decision is auditable end-to-end and a model that scores well in cross-validation but fails a Population Stability Index check at deployment is a failed model regardless of its AUC. The reordering here is deliberate. Stages 1-2 (feature engineering, splitting) are roughly half the work, the modelling stage is a quarter, and tuning, evaluation, and interpretation are the other quarter. Most lecture courses invert those weights.
Where this sits in the ML world This lecture is the world map for the rest of the course. Every later lecture is either "stage $k$ of the pipeline" or "a position on the bias-variance axis". Lecture 2 (feature transformation) is the first concrete stage. Lectures in 03_supervised_learning are all bias-variance trade-offs against different function classes. Lectures in 06_hyperparameter_tuning are explicit moves along the bias-variance axis. Lecture 36 (regression diagnostics) reads off the residuals what stage you got wrong. Holding the map in your head turns the rest of the course from a list into a system.
Step 2

Why this matters

Three reasons to begin with the map rather than with an algorithm. First, the choice of model is not the most important decision in an ML project; it is the third or fourth. Picking XGBoost over logistic regression matters less than choosing the right target variable, less than holding out a meaningful test set, and less than treating missingness honestly. Every senior modeller has seen a project where a junior analyst tuned XGBoost for a week on a target that was leaking the answer; every project review where this is caught starts by walking back up the pipeline and pointing at stage 1. If you cannot draw the pipeline from memory before you fit anything, you do not yet have a project.

Second, constraints flow backwards. In a regulated setting the interpretability requirement at stage 6 dictates the model class at stage 3, which dictates the feature engineering at stage 1. A bank that needs to defend every PD model feature to its supervisor cannot use a 200-feature gradient-boosted model with three layers of target encoding, no matter how good its AUC; the loss of explanatory transparency makes the model unsupportable under SREP. The pipeline view exposes this dependency before a week of work is wasted in the middle of it.

Third, most production ML failures are pipeline failures, not model failures. Models drift not because the algorithm degraded but because the input distribution shifted (covariate shift, label shift, or concept drift in the underlying $f$). The pipeline view is the only honest way to spot the failure: a model that suddenly underperforms is almost always being asked questions about a different population than the one it was trained on. Stage 5 (monitoring as part of evaluation) is where this is caught; stage 1 is where it has to be re-engineered.

Vignette from the field A PD model on a SME book scored AUC 0.83 on holdout, sailed through validation, and was put into production. Within six months its observed default rate diverged sharply from its expected. The post-mortem found the feature "months since incorporation" had been winsorised at the 99th percentile in training, which silently capped a fast-growing segment of the new portfolio at the training cap and removed all variation in that feature for them. Stage 1 (feature transformation) caused the failure; stage 5 (monitoring) detected it; stage 3 (the model) was blameless. None of this is unusual.
Step 3

The mental model

Hold this picture in your head. A machine learning project is a directed graph of six stages, with three modelling families fanning out at the third node and a feedback edge from monitoring back to feature engineering. Each stage produces an artefact (a feature table, a split index, a fitted model, a tuned model, a metric, an explanation) that is the input to the next. Each stage has its own failure mode; the failure modes do not commute, which is why the order matters.

Three things are worth pointing to on the diagram. The monitoring loop is what turns a one-shot academic exercise into a production system: real data drifts, the population that the model is asked about changes, and stage 5 detects the change before stage 6's explanations become misleading. The three-family fan at stage 3 is what people usually mean by "ML": the rest of the diagram is the support structure. The bias-variance axis at the bottom is not a separate concept attached to the pipeline; it is the single dimension along which every algorithmic choice in the pipeline trades off. Reading this lecture is reading the axis.

Step 4

The detail

The three paradigms

The first axis on the world map is what kind of signal the data provides about the function being learned.

Supervised learning has paired observations $(x_i, y_i)$ for $i = 1, \ldots, n$, where $x_i \in \mathcal{X}$ is a feature vector and $y_i \in \mathcal{Y}$ is a label. The objective is to estimate the conditional expectation

$$\hat{f}(x) \approx \mathbb{E}[Y \mid X = x]$$

for classification with $\mathcal{Y} = \{0, 1, \ldots, K-1\}$ or regression with $\mathcal{Y} = \mathbb{R}$. Almost every model in the credit risk modeller's day-to-day is supervised: PD models (binary classification with $Y$ = default indicator), LGD models (bounded regression with $Y \in [0, 1]$), EAD models (regression with a mass point at the limit). Lecture sub-module 03 covers the seven supervised algorithms.

Unsupervised learning has only the feature vectors $x_i$ and no labels. The objective is to find structure inside $X$: low-dimensional manifolds, clusters of similar observations, anomalies relative to a learned density. Two distinct goals share the unsupervised umbrella. Compression reduces the dimension while preserving as much information as possible (principal component analysis, autoencoders); the output is a transformed feature set that feeds back into stage 1. Clustering partitions observations into groups with no labels (k-means, DBSCAN, hierarchical); the output is a discrete cluster index that is itself a feature. Lecture sub-module 04 covers the two canonical methods.

Reinforcement learning has no fixed dataset at all. An agent interacts with an environment, takes actions, observes states, and receives scalar rewards; it learns a policy $\pi: \mathcal{S} \to \mathcal{A}$ that maximises expected discounted future reward. This course does not cover reinforcement learning; it is included on the map because excluding it leaves a hole in the taxonomy, and because algorithmic trading and dynamic pricing are reinforcement problems even when they are usually solved with supervised approximations.

Two recent additions Two further paradigms have become standard in the last decade and do not fit cleanly into the original three. Self-supervised learning generates its own labels from the structure of $X$ (predict the next word, predict a masked patch of an image, predict whether two augmentations of the same image are the same); it is supervised learning with a free label generator. It is the foundation of every modern large language model. Semi-supervised learning sits between supervised and unsupervised: a small labelled set plus a much larger unlabelled one, exploited together. Both are practical refinements of the supervised paradigm rather than fundamentally new objects, and the lectures in sub-module 03 build the tools needed to understand either later.

The six-stage pipeline, lecture by lecture

Each stage corresponds to one or more sub-modules. Reading this list is reading a compressed table of contents for the rest of the course.

Stage 1, feature engineering, is the conversion of raw data into a numerical feature table that an algorithm can consume. Lecture 2 of this sub-module covers transformation (scaling, binning, encoding categorical variables, handling outliers); lecture 3 covers dimensionality reduction (PCA, LDA, t-SNE) where compression preserves information; lecture 4 covers feature selection (filter, wrapper, embedded methods) where the goal is to drop columns. The output of this stage is a clean, numerical matrix $X \in \mathbb{R}^{n \times p}$ and a target vector $y \in \mathbb{R}^n$ for supervised problems.

Stage 2, train and test split, partitions the data into disjoint subsets used at different points in the pipeline. The training set is used to fit parameters; the validation set is used to choose hyperparameters; the test set is used once at the end to estimate generalisation. Sub-module 02 covers basic, stratified, k-fold, and time-series splits and pipelines, which are the unit of leakage prevention.

Stage 3, fit a model, is where the function class is chosen and its parameters estimated by minimising a loss on the training set. Sub-module 03 covers the seven canonical supervised methods (KNN, decision trees, SVM, naive Bayes, ensemble methods, causal models, conformal prediction); sub-module 04 covers the two unsupervised methods (k-means, PCA); sub-module 05 covers neural networks. Each method is a different choice of function class and a different position on the bias-variance axis.

Stage 4, tune hyperparameters, is where the knobs that are not directly fitted (number of trees, depth of a tree, regularisation strength, learning rate) are chosen by searching over the validation set. Sub-module 06 covers grid, random, Bayesian, and genetic search.

Stage 5, evaluate, is where the tuned model is held up against a metric that matches the business question. Sub-module 07 splits this into four lectures: relative model performance (AIC, BIC), regression diagnostics (residual plots, RMSE, MAE, $R^2$), classification metrics (confusion matrix, ROC, AUC, Gini), and forecasting (Ljung-Box, backtesting). Monitoring after deployment is a sustained version of stage 5 and is where the feedback loop in the diagram fires.

Stage 6, interpret, is where the question shifts from "how well does it score" to "why did it make that prediction". Sub-module 08 covers white-box vs black-box framing, model-specific methods (coefficients, odds ratios, tree importance), and model-agnostic methods (permutation importance, partial dependence plots, SHAP, LIME).

The bias-variance decomposition, derived

The bias-variance trade-off is the single most important formula in this course because it is the only one that applies to every algorithm. Derive it once and the rest of the course slots into it.

Suppose the true relationship is $y = f(x) + \varepsilon$ where $\varepsilon$ has zero mean and variance $\sigma^2$, independent of $x$. We fit an estimator $\hat{f}(x)$ from a training sample. The expected squared prediction error at a fixed $x$, averaged over training samples and over the noise, is

$$\mathbb{E}\left[(y - \hat{f}(x))^2\right] = \mathbb{E}\left[(f(x) + \varepsilon - \hat{f}(x))^2\right].$$

Expanding the square and using $\mathbb{E}[\varepsilon] = 0$ and the independence of $\varepsilon$ from $\hat{f}(x)$,

$$\mathbb{E}\left[(y - \hat{f}(x))^2\right] = \mathbb{E}\left[(f(x) - \hat{f}(x))^2\right] + \mathbb{E}\left[\varepsilon^2\right].$$

The second term is $\sigma^2$, the irreducible noise. The first term decomposes further by adding and subtracting $\mathbb{E}[\hat{f}(x)]$,

$$\mathbb{E}\left[(f(x) - \hat{f}(x))^2\right] = \left(f(x) - \mathbb{E}[\hat{f}(x)]\right)^2 + \mathbb{E}\left[(\hat{f}(x) - \mathbb{E}[\hat{f}(x)])^2\right].$$

The first term on the right is the squared bias: how far the average prediction is from the truth. The second is the variance: how much the prediction wobbles across training samples. Combining,

$$\boxed{\mathbb{E}\left[(y - \hat{f}(x))^2\right] = \underbrace{\left(f(x) - \mathbb{E}[\hat{f}(x)]\right)^2}_{\text{Bias}^2} + \underbrace{\mathbb{E}\left[(\hat{f}(x) - \mathbb{E}[\hat{f}(x)])^2\right]}_{\text{Variance}} + \underbrace{\sigma^2}_{\text{Noise}}.}$$

Three observations. The noise term is irreducible: no algorithm can drive it below $\sigma^2$, and chasing it indicates overfitting. Bias and variance trade against each other: a constant predictor $\hat{f}(x) \equiv \bar{y}$ has zero variance and large bias; a nearest-neighbour predictor with $k = 1$ has zero bias on the training set and large variance on the test set. The minimum of total error is interior: the U-shape of test error against model complexity is a direct consequence of the formula, with the minimum somewhere between the constant predictor and the interpolating one.

No free lunch

Wolpert's no free lunch theorem (1996) states, informally, that averaged over all possible data-generating distributions, every algorithm has identical expected performance. There is no universally best classifier; there is only an algorithm well-matched to the problem at hand. Practically this means three things. First, algorithm choice is data-conditional: tree ensembles tend to win on tabular data with mixed feature types and modest signal-to-noise, neural networks win on images and language, linear models win when the truth is approximately linear and the sample is small. Second, benchmarking matters: the only way to know which algorithm fits your data is to try several with comparable effort spent on each. Third, inductive bias is the algorithm: the assumptions an algorithm makes about the shape of $f$ are what gives it an advantage on data that happens to satisfy those assumptions and a disadvantage on data that does not.

A common misreading No free lunch is sometimes quoted to argue that all algorithms are equivalent in practice. They are not. The theorem averages over all possible distributions, the vast majority of which are pathological and never occur in real data. On real-world data certain classes of algorithm reliably outperform others (gradient-boosted trees on tabular credit data, transformers on text). The theorem rules out a universal best algorithm; it does not rule out an empirically best algorithm for a given problem domain.

Performance, capacity, and the empirical pattern

One last piece of vocabulary. The capacity of a model class is its ability to fit complex functions; formally, it is measured by Vapnik-Chervonenkis dimension or by Rademacher complexity, but intuitively it is "how many distinct functions can this class express". Low capacity (linear, shallow trees) gives high bias; high capacity (deep networks, very deep trees) gives high variance. The same machine, fit on the same data, lands at different points on the bias-variance axis depending on capacity. Two patterns recur and are worth memorising. For a fixed sample size, optimal capacity is interior: increasing capacity past the sweet spot starts overfitting (the bottom-left corner of the U-curve becomes the bottom-right). For a fixed model, increasing sample size lets you push capacity higher safely: more data shrinks the variance component of the formula, and you can afford a more expressive model. This is why neural networks won the 2010s: more data plus more compute moved both knobs in the right direction at once.

Step 5

Pitfalls

Three failure modes recur across every project and trip up every modeller eventually. The pipeline view makes each of them visible at the stage where it has to be prevented.

Leakage Information from the test set seeps into training, inflating test performance and producing a model that will not generalise. The classic source is feature engineering computed on the full dataset before splitting (target encoding, scaling parameters, missing-value imputation). The fix is to make the feature engineering itself part of the split: fit transformations on the training fold only, apply them to the test fold without re-fitting. This is what scikit-learn pipelines are for, and the reason lecture 2_02 spends a whole session on them.
Overfitting on the validation set The validation set is meant to choose hyperparameters once. In practice, modellers iterate: try a model, look at validation performance, change the model, look again. Each iteration is a Bonferroni-style multiple comparison against the validation set, and validation performance becomes optimistic. The fix is a three-way split (train, validate, test) where the test set is touched exactly once, at the end. Cross-validation makes the trick more efficient but does not change the principle.
Forgetting deployment A model that scores AUC 0.85 on a clean test set can score 0.65 on next month's portfolio because the population has shifted. The pipeline view treats monitoring as part of stage 5, not as a separate concern: the model must be evaluated against the population it is asked about, not against the population it was trained on. Population Stability Index (PSI) and characteristic stability are the standard tools; the absence of either in a model document is a red flag.
Step 6

Synthesis and what's next

You now have the world map. Three paradigms (supervised, unsupervised, reinforcement) classify the kind of signal the data carries. Six stages (feature engineering, splitting, fitting, tuning, evaluating, interpreting) shape the workflow. One trade-off (bias-variance) runs through every stage and every algorithmic choice. One impossibility result (no free lunch) explains why algorithm selection is data-conditional. Three failure modes (leakage, validation overfitting, drift) are the failures every production project has to defend against.

What this lecture deliberately did not do. It did not write a single line of model-fitting code; that begins next lecture. It did not derive any algorithm; algorithms start in sub-module 03. It did not say which algorithm is best for any given problem; that is the no-free-lunch point. It gave you the frame, not the contents. Every following lecture fills in one cell of the frame.

Lecture 2, feature transformation, is the first concrete stage. Raw data is rarely in a form an algorithm can consume directly: scales differ, categoricals need numerical encoding, outliers distort distance-based methods, and skewed distributions break linear models' assumptions. Transformation is the first place the pipeline view earns its keep, because every transformation has to be fit on the training set alone if leakage is to be avoided.
