Pipelines

A pipeline turns several preprocessing steps and a model into one object that can be fit, predicted, persisted, and cross-validated atomically. It is the only construction that makes the leakage rule automatic, and the same object that ships to production.

Lecture 6 of 62 Reading time, 40 minutes Part I: foundations
Step 1

The 30-second version

A pipeline is a composite scikit-learn estimator that chains a sequence of transformers (and optionally a final model) into a single object exposing the usual fit, transform, and predict interface. The composition is a list of (name, estimator) tuples; calling fit on the pipeline calls fit_transform on each step in turn, threading the output of one into the input of the next, and finally fit on the terminal estimator. Calling predict calls transform on every step (no re-fitting) before predict on the terminal model. This single behavioural rule (fit propagates, transform does not) is what operationalises the leakage rule from lecture 5: the statistics learned during training (means, standard deviations, one-hot vocabularies, target encodings) are captured inside the fitted transformer objects, and applied to test or production data without ever seeing the target. A pipeline also accepts a ColumnTransformer as one of its steps, which lets different columns receive different treatments (scaling on numeric, one-hot on categorical) in parallel. The fitted pipeline can be passed wholesale to GridSearchCV, which re-fits every step inside every fold, and pickled wholesale as the artefact that goes to production. There is no separately maintained preprocessing script.

Feynman test A model rarely consumes raw database columns directly. Before it sees a feature matrix, several things have to happen: missing values are filled in, numeric columns are put on a common scale, categoricals are turned into numbers, perhaps some columns are dropped. Each of these steps has parameters (the mean used to impute, the standard deviation used to scale, the list of categories used to one-hot) that have to be learned from data and then frozen. A pipeline is the object that holds those frozen parameters together with the model, so that when a new row arrives in production, exactly the same arithmetic is applied to it as was applied to the training rows. Without a pipeline, you are keeping that bookkeeping in your head, which is where leakage hides.
What's beyond the syllabus Pipelines are often taught as a tidiness device, a way to write fewer lines of code. The real reason to use them is governance. A regulator does not ask to see your notebook, they ask for the artefact that scores a customer. If preprocessing lives in a separate script and the model in a pickled file, you have two things to version, two things to test, and two places where they can drift apart. A single pipeline pickle collapses that surface area: one object, one hash, one provenance record. The leakage benefit is what wins arguments in the team; the governance benefit is what wins arguments with model risk management.
Where this sits in the ML world The pipeline is the connective tissue between lecture 2 (the individual transformations) and every supervised method in sub-module 03 (the models that consume the transformed matrix). It is also the only sensible input to grid search, because the search has to re-fit preprocessing per fold; without the pipeline abstraction, leakage in cross-validation is silent and routine.
Step 2

Why this matters

Three reasons the pipeline is not optional in serious work. First, the leakage rule is structural, not procedural. Lecture 5 introduced the rule that any transformer with learned parameters must be fit on training data only. In a script that loads the full dataset, imputes the mean, scales, and then splits, that rule is violated and the violation is invisible. The training set's reported performance is inflated by an amount that depends on how much information the leaked statistic carries (very little for a single mean, materially more for a target encoding). A pipeline removes the procedural step that can be skipped. The order of operations inside pipeline.fit(X_train, y_train) is enforced by the library, not by the analyst's memory.

Second, cross-validation without pipelines is leaky by default. If you scale your features once before passing them to cross_val_score, every fold's training portion has already been contaminated by statistics from that fold's validation portion. The bias is small per fold but compounds across folds and across hyperparameter settings, and the model that wins the grid search is often the one that benefits most from the leak. Passing the pipeline to the cross-validator (rather than the model alone) makes the cross-validator re-fit every step on every training fold; preprocessing parameters never see the held-out portion. This is the single most common silent error in applied machine learning.

Third, the deployable artefact has to include preprocessing. The production system receives a raw row from the database, not a preprocessed feature vector. If preprocessing lives outside the model object, the production system has to reproduce it, and any divergence (a different sklearn version, a different default, a missed step) shows up as a serving-time bug. Pickling the entire pipeline captures both the fitted transformers and the fitted model in one file with one signature. Treating that file as the deployable unit removes a whole class of train-serve skew.

Vignette from the field A behavioural PD model performed well in validation, with cross-validated AUC stable across folds and bootstrap iterations. In the first month of live scoring, the daily prediction distribution drifted upward by about 0.05 in mean probability. The cause was traced to a numerical feature that had been Yeo-Johnson transformed in the training notebook using a fitted lambda; the production scoring code re-fit the transformer on each daily batch (a default copy-paste from the notebook). The team's fix was not a better deployment script but a structural one: the pipeline pickle was made the only artefact, with the production code reduced to pipeline.predict_proba(row). Drift then became something to monitor, not something to introduce.
Step 3

The mental model

Picture a pipeline as a row of black boxes connected end-to-end, with a single switch at the front marked "fit" or "transform" (or "predict" for the final box). When the switch is set to fit, each box learns its parameters from whatever comes through and passes its output downstream. When the switch is set to transform, the boxes apply their already-learned parameters without changing them. The same row of boxes handles training and inference; only the switch position differs.

Three things to read off the diagram. The ColumnTransformer is itself a single step within the outer pipeline, which means the whole composition is still one object that takes raw rows in and predictions out. The branches inside the ColumnTransformer operate on disjoint column groups in parallel; they do not share state, but their outputs are concatenated column-wise before the next step. The amber bar at the bottom is the same rule from lecture 2: the difference is that here the rule is enforced by the architecture rather than by the analyst's discipline.

Step 4

The detail

Pipeline composition

A Pipeline is constructed from a list of (name, estimator) tuples. The names are arbitrary strings (used later to address hyperparameters in grid search) and the estimators are any scikit-learn-compatible objects implementing fit and transform, with the final step optionally being a predictor (implementing fit and predict). Every step except the last must be a transformer; the last may be a transformer or a predictor.

The behavioural rule is simple. Calling pipeline.fit(X, y) iterates through the steps in order, calling fit_transform(X, y) on each transformer and passing the output to the next; on the final step, it calls fit(X, y). Calling pipeline.predict(X) calls transform(X) on every step (without re-fitting) and predict(X) on the last. Calling pipeline.transform(X) calls transform(X) on every step (only valid if the final step is also a transformer). The composition itself is an estimator, so it has its own fit, predict, score, get_params, and set_params; it can be nested inside another pipeline or a meta-estimator like GridSearchCV without special handling.

The make_pipeline shortcut constructs a pipeline from a sequence of estimators without explicit names, auto-generating names from the lower-cased class name. It is convenient for short pipelines where the names are not needed later for parameter addressing. For anything that will be tuned or documented, the explicit tuple form is preferable: a name like ("scale", StandardScaler()) reads clearly in a stack trace, whereas "standardscaler" reads less clearly and changes if you swap the scaler.

ColumnTransformer

Real feature matrices contain columns of different types. A scaler is appropriate for numeric columns and meaningless for categorical ones; a one-hot encoder is the reverse. The ColumnTransformer applies different transformations to different columns in parallel and concatenates the results column-wise. Its constructor takes a list of (name, transformer, columns) triples, where columns is a list of column names, a list of integer indices, or a selector like make_column_selector(dtype_include="number").

The remainder argument controls what happens to columns not mentioned in any triple: "drop" (the default) discards them, "passthrough" appends them unmodified to the output, and a transformer object applies that transformer to all the unmentioned columns. The make_column_transformer shortcut, analogous to make_pipeline, auto-generates names from class names. The result of a fitted ColumnTransformer is a single matrix (numpy array or pandas DataFrame, controlled by set_config(transform_output="pandas")) whose columns are the concatenation of the sub-transformer outputs in the order the triples were listed.

The ColumnTransformer is itself a single step inside the outer pipeline. A typical structure has a per-type sub-pipeline (imputer then scaler for numeric, imputer then one-hot for categorical) inside each branch of the ColumnTransformer, with the ColumnTransformer itself as the only preprocessing step in the outer pipeline, followed by the final estimator. This three-level nesting (outer pipeline, ColumnTransformer, inner per-type pipelines) is the canonical layout for tabular work and the one to default to.

Pipelines and cross-validation

The whole point of putting the pipeline together is that it can be passed wholesale to cross_val_score, cross_validate, or GridSearchCV as if it were a single model. The cross-validator splits the data, calls pipeline.fit(X_train_fold, y_train_fold) on each training fold (which re-fits every transformer's learned parameters from scratch), then calls pipeline.predict(X_val_fold) on the held-out fold (which applies the just-fitted transformers without re-fitting). No preprocessing statistic from the validation fold leaks into the training fold. This is the leakage-safe behaviour that is impossible to guarantee without the pipeline abstraction.

Hyperparameter addressing inside a pipeline uses the double-underscore convention. A parameter called alpha on a step named "model" is referred to as "model__alpha" in the grid search parameter dictionary; a parameter n_neighbors on a step "knn" inside a ColumnTransformer step "prep" is "prep__knn__n_neighbors". This lets the grid search tune preprocessing choices (number of imputed components, scaler choice, one-hot drop strategy) alongside model hyperparameters, with the cross-validation safety guarantee covering both.

Pipelines and persistence

A fitted pipeline is a Python object containing fitted transformer state (means, standard deviations, category lists, learned lambdas) and the fitted model. Pickling it with joblib.dump(pipeline, "model.pkl") captures all of that in one file; loading with joblib.load("model.pkl") restores the object ready to score new data. The deployment contract reduces to "load the pickle, call predict or predict_proba on a raw row". There is no separately maintained feature-engineering code.

Two practical conditions make this safe. First, the production environment must match the training environment closely enough for the pickle to load: same scikit-learn major version, same Python major version, same numpy. A version mismatch is one of the more common production incidents; the standard mitigation is to pin versions in the deployment image and check the loaded pipeline's __sklearn_version__ attribute on startup. Second, the input row at scoring time must have the same column names and dtypes as the training matrix; the pipeline raises if a column is missing or named differently. The pipeline's feature_names_in_ attribute, set during fit, is the contract that the scoring system has to satisfy.

Worked example

The following pipeline imputes missing values, scales numeric columns, one-hot encodes categorical ones, and fits a logistic regression as the final step. It is the canonical layout described above (outer pipeline holding a ColumnTransformer holding per-type inner pipelines).

import pandas as pd
from sklearn import set_config
from sklearn.compose import ColumnTransformer, make_column_selector
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import GridSearchCV, train_test_split
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

set_config(transform_output="pandas")

# X is a DataFrame with mixed numeric and categorical columns; y is a binary target
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=42
)

numeric_pipeline = Pipeline(steps=[
    ("impute", SimpleImputer(strategy="median")),
    ("scale", StandardScaler()),
])

categorical_pipeline = Pipeline(steps=[
    ("impute", SimpleImputer(strategy="constant", fill_value="missing")),
    ("onehot", OneHotEncoder(handle_unknown="infrequent_if_exist", min_frequency=0.01)),
])

preprocess = ColumnTransformer(transformers=[
    ("num", numeric_pipeline, make_column_selector(dtype_include="number")),
    ("cat", categorical_pipeline, make_column_selector(dtype_include="object")),
])

pipeline = Pipeline(steps=[
    ("preprocess", preprocess),
    ("model", LogisticRegression(max_iter=1000, solver="liblinear")),
])

# Tune both preprocessing and model hyperparameters; preprocessing is re-fit per fold
param_grid = {
    "preprocess__num__impute__strategy": ["median", "mean"],
    "model__C": [0.1, 1.0, 10.0],
}

search = GridSearchCV(pipeline, param_grid, cv=5, scoring="roc_auc", n_jobs=-1)
search.fit(X_train, y_train)

# The fitted artefact is one object containing preprocessing and model
best_pipeline = search.best_estimator_
test_auc = best_pipeline.score(X_test, y_test)

import joblib
joblib.dump(best_pipeline, "pd_model.pkl")

Three details earn their inclusion. The handle_unknown="infrequent_if_exist" setting on the one-hot encoder gives a deployment-safe behaviour for unseen categorical levels (see lecture 2 on the dummy variable trap and rare-label encoding). The double-underscore parameter names in the grid let the search tune the numeric imputer strategy and the logistic regression regularisation strength simultaneously, with the cross-validation guaranteeing both are evaluated without leakage. The single joblib.dump call at the end persists the whole composition; the next code that touches it is a one-line load and predict in production.

Step 5

Pitfalls

Three failure modes account for most pipeline-related incidents, and one is a subtle misuse rather than an outright bug.

Preprocessing outside the pipeline, then cross-validating the model Fit a scaler on the full dataset, transform once, then pass the transformed matrix and a bare model into cross_val_score. The cross-validation is now leakage-contaminated even though it looks correct: every training fold has been pre-scaled with statistics that included the validation fold. The reported score is optimistic, the bias is fold-dependent, and the model that wins a downstream grid search is often the one that benefits most. The fix is to put the scaler inside the pipeline and pass the pipeline (not the bare model) to the cross-validator.
Fit-then-transform anti-pattern Call pipeline.fit(X_train) and then pipeline.fit_transform(X_test) by mistake. The second call re-fits every transformer's parameters on the test set, replacing the training statistics with test statistics. The test score is then computed against a model that has effectively seen the test inputs. The fix is to remember that after fit the only methods you should call on the pipeline are transform, predict, predict_proba, or score; never fit or fit_transform again until the next training cycle.
Pickle portability across versions A pipeline pickled with scikit-learn 1.3 may fail to load under 1.5, or load with subtly different default behaviour. The failure mode at training time is loud (an import error); at scoring time it is silent (the default value of a parameter changed and the predictions shift). The fix is to pin the scikit-learn version in the deployment image, store the training version as metadata alongside the pickle, and check the version on load. For long-lived production models, prefer ONNX or PMML export over raw pickle, which decouples the artefact from a specific library version at the cost of more complex tooling.
Hidden state in custom transformers A custom transformer that holds state in module-level globals or class attributes rather than instance attributes will not pickle correctly, will not behave correctly under cross-validation (because the state is shared across folds), and will fail in obscure ways inside GridSearchCV with n_jobs > 1. The fix is to follow the scikit-learn convention: all learned parameters are stored on self as attributes with trailing underscores (self.mean_, self.categories_), set during fit and read during transform. A passing call to check_estimator on the custom class catches most of these.
Step 6

Synthesis and what's next

A pipeline is the object that holds preprocessing and modelling together, exposes a single fit-predict interface, and enforces the leakage rule structurally. The composition is a list of named steps where every step except the last is a transformer and the last is optionally a predictor. A ColumnTransformer is the standard pattern for applying different transformations to different column types in parallel, and is itself a single step inside the outer pipeline. Passing the pipeline (not the bare model) to cross-validation makes preprocessing re-fit per fold; passing the pipeline to GridSearchCV with double-underscore parameter names tunes preprocessing and model jointly. Pickling the fitted pipeline produces the artefact that ships to production; the deployment contract is a single load and predict call. Underneath all of this is the same rule from lecture 2 and lecture 5, now enforced by architecture rather than discipline.

What this lecture deliberately did not do. It did not introduce model selection or hyperparameter tuning beyond the example with GridSearchCV; the search strategies, the choice of scoring metric, and the diagnostic of the resulting CV curve are lecture 21. It did not introduce any specific model; the algorithms start in sub-module 03 with k-nearest neighbours. It did not address monitoring, drift detection, or re-fit triggers; those are stage 6 of the pipeline from lecture 1 and are covered later.

The next lecture, k-nearest neighbours, introduces the first proper supervised model. It is also the first algorithm whose performance materially depends on having the preprocessing right (KNN distance is dominated by whichever feature has the largest scale), which makes it the natural place to see a pipeline used in earnest.
