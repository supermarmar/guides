Course companion

Business intelligence

A seventeen-lecture course on the layer between the warehouse and the decision. Business intelligence is the discipline of turning a governed data model into an interface a non-analyst can interrogate without asking you first. The course teaches the general principles (dimensional models as query contracts, evaluation context, the freshness triangle, interaction state, row-level access) and implements every one of them in Power BI, because that is the tool the audience actually has. Each lecture then maps the same idea onto Tableau, Looker, Qlik, and the SQL or dbt equivalent, so the knowledge survives a change of vendor. Examples build one credit-risk portfolio model throughout: a loan-book fact table with customer, product, date, and branch dimensions.

The BI stack

Every BI tool ever built is the same four layers stacked on a warehouse, wrapped in three concerns that cut across all of them. Learn the layers and the tool becomes an implementation detail. The diagram maps the seventeen lectures onto that stack.

How to use this

Lectures are sequenced as prerequisites of the next, and the dependency is real rather than editorial: evaluation context (07) is incomprehensible without the relationship graph (04), and every performance lecture assumes the storage model (05). Status badges show what is built (built) or planned.

Every lecture is written in three registers, in the same order, so the general knowledge and the vendor knowledge stay separable in your head.

Lecture anatomy

The principle states the idea in vendor-neutral terms, usually with a SQL or relational-algebra formulation, because SQL is the lingua franca that outlives every BI product. The implementation builds it in Power BI with the real interface, real DAX, and the real failure modes. The portability map closes each lecture with a table showing the same concept in Tableau, Looker or LookML, Qlik, and a dbt or SQL metrics layer, with an explicit note where the mapping genuinely breaks down rather than pretending the tools are equivalent.

Read the principle sections alone and you have a tool-agnostic BI course. Read all three and you can build the thing on Monday.

Part I: what BI is and what a semantic layer does

Framing the discipline

  • plannedWhat business intelligence is for: decision support, the self-service bargain, and the tool landscape
  • plannedThe semantic layer: metrics as a governed contract, headless BI, and why one definition of "default rate" beats forty

Lecture 01 argues that BI exists to shorten the distance between a question and a defensible number, and that most BI failures are organisational rather than technical. Lecture 02 introduces the single idea the rest of the course elaborates: a semantic model is a published contract mapping business vocabulary onto physical tables. Power BI calls it a semantic model, Looker calls it LookML, dbt calls it the semantic layer, and Cube calls it a data model. Framing this early keeps the DAX-heavy middle of the course from reading as vendor trivia.

Part II: modelling

The model is the product

  • plannedDimensional modelling for BI: grain, facts, conformed dimensions, the date table, hierarchies, slowly changing dimensions
  • plannedRelationships and filter propagation: cardinality, cross-filter direction, ambiguity, bridge tables, role-playing dimensions
  • plannedStorage modes and the freshness triangle: import, DirectQuery, dual, aggregations, incremental refresh

Lecture 03 is the applied twin of data engineering lecture 08: the warehouse-side lecture designs the star, this one designs it for a query engine that must answer in under a second while a slicer moves. Lecture 04 covers the material most Power BI users never learn properly, and reframes filter propagation as what it actually is, a directed graph over a join network, which is why many-to-many and bidirectional filtering produce ambiguity rather than magic. Lecture 05 presents the choice between cached and pushdown execution as a three-way trade between freshness, latency, and cost that every tool resolves with the same vocabulary under different names.

Part III: transformation

Shaping data on the way in

  • plannedThe transformation layer: Power Query and M, profiling, unpivoting, query folding, and the push-it-upstream rule

Power Query is a declarative transformation language with pushdown, which makes it a peer of dbt models and SQL views rather than a peer of Excel formulas. The lecture teaches the shaping vocabulary (promote headers, unpivot, merge, custom columns, type enforcement) alongside the discipline that matters more: query folding, how to verify it, and the rule that a transformation belongs as far upstream as it can be pushed. Cross-references dbt and analytics engineering for the case where the answer is to stop transforming in the BI tool entirely, and pandas core for the same operations expressed imperatively.

Part IV: the calculation language

Evaluation context and the measure

  • plannedEvaluation context: row context, filter context, context transition, and what CALCULATE actually does
  • plannedMeasures, calculated columns, and calculated tables: choosing where a calculation lives and what it costs
  • plannedTime intelligence: the date spine, year-to-date, period-over-period, moving windows, semi-additive measures
  • plannedAdvanced patterns: iterators, ranking and top-N, virtual tables, disconnected tables, what-if parameters, dynamic segmentation

Lecture 07 is the hinge of the course. Almost everything people find hard about DAX reduces to one idea: a measure is a function from a filter context to a scalar, and there are exactly two ways context is created and one way it is transformed. Taught properly, this transfers directly to SQL window frames, Looker's symmetric aggregates, and the MDX heritage the whole field inherited. The remaining three lectures are applications of it. Lecture 08 makes the storage-versus-compute trade explicit, since a calculated column costs memory in every refresh while a measure costs CPU on every query. Lecture 09 shows why a proper date dimension is the precondition for all time comparison, and lecture 10 covers the patterns that separate a competent model from a good one. Readers who know groupby and pivot semantics already hold most of the intuition and should read 07 as a translation exercise.

Part V: the report

Encoding, interaction, and design

  • plannedVisual encoding under interaction: chart selection, KPI tiles, small multiples, tables versus charts, geospatial
  • plannedInteraction and report state: filter pane, slicers, cross-filtering, drill-down and drill-through, tooltips, bookmarks, navigation
  • plannedReport and dashboard design: the four report archetypes, layout and Gestalt principles, colour, accessibility, mobile
  • plannedIn-report analytics: binning, outliers, clustering, key influencers, decomposition trees, natural-language query, and their statistical limits

Lecture 11 assumes the encoding fundamentals from data analysis lecture 05 and adds what changes when the reader can filter: a chart that is honest at the full grain can mislead badly at a filtered one, and small-multiple and tile design has to survive every slicer state. Lecture 12 treats a report as a state machine, which is the framing that makes bookmarks, drill-through, and interaction rules coherent instead of a list of features. Lecture 13 covers information design and the four archetypes worth distinguishing (dashboard, analytical, operational, educational), each with a different reader, refresh cadence, and density budget. Lecture 14 is deliberately sceptical: the one-click analytics features are useful, and they are also unsupervised methods with assumptions the interface hides, so it cross-references statistics and machine learning for what key influencers and clustering are actually computing.

Part VI: production

Making it fast, safe, and maintainable

  • plannedPerformance engineering: columnar compression, cardinality reduction, storage versus formula engine, variables, aggregations, diagnosis
  • plannedSecurity: row-level and object-level security, perspectives, dynamic rules, sensitivity labels, and testing access
  • plannedBI operations: workspaces, deployment pipelines, gateways and refresh, lineage and impact analysis, usage monitoring, BI as code

Lecture 15 explains why a column with 4 million distinct values costs more than a table with 400 million rows, which is the same dictionary-encoding argument as Parquet and columnar formats, then gives a diagnostic order of operations rather than a list of tips. Lecture 16 treats row-level security as a data-modelling problem with a testing obligation, because an untested security role is an unproven one, and maps Power BI roles onto warehouse-native policies. Lecture 17 is the operational close: environments, promotion, scheduled and incremental refresh, gateway topology, lineage and impact analysis before a breaking change, and the argument for version-controlled BI artefacts. It leans on orchestration, observability and contracts, governance and privacy, and the CI/CD material in software engineering.

Prerequisites and adjacent courses

The course assumes SQL at the level of data engineering lecture 05 and no prior Power BI. Dimensional modelling is developed from scratch in lecture 03, but readers who have done data engineering lectures 07 and 08 will move faster. No statistics beyond descriptive summaries is needed until lecture 14.

The natural companions are data analysis, which covers the same describe-and-visualise work in Python for cases where a report is the wrong deliverable, and data engineering, which builds the warehouse this course consumes. The relationship is worth stating plainly: data engineering owns everything below the semantic model, this course owns the semantic model and everything above it, and the boundary between them is exactly the argument in lecture 06 about where a transformation belongs. Applied use of all three sits in the credit risk track, where portfolio monitoring, IFRS 9 staging movement, and A-IRB model performance reporting are BI problems wearing a regulatory hat.
