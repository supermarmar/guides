Version control with git

Git is a content-addressed file system with a version-control interface bolted on top. Learning the commands without the data model gives you a tool that works most of the time and terrifies you the rest. This lecture builds the model first (objects, refs, the DAG of commits), then derives the everyday commands and the branching workflows from it.

Step 1

The 30-second version

Git (Linus Torvalds, 2005) is the distributed version-control system that every modern software-engineering team uses. The interface is famously prickly: more than 150 subcommands, an internal vocabulary borrowed from no one else's tool, and error messages that improve nothing. The remedy is to stop learning git as a command list and start learning it as a data model. The data model has three pieces. First, every file you have ever committed is stored as a blob, addressed by the SHA-1 hash of its contents. Second, every snapshot of the project is a tree of named blobs, and every snapshot in history is a commit that points to a tree and to one or more parent commits. Third, a branch is just a label that points at a commit, and the history of the project is the directed acyclic graph (DAG) of commits reachable from those labels.

Once that model is in place, the commands fall out of it. git add writes blobs and stages them; git commit creates a new commit pointing at a new tree and at the current branch's commit as parent, and then moves the branch label forward by one. git branch foo creates a new label; git checkout foo moves HEAD to point at it; git merge bar creates a commit with two parents, the current branch and the named one. The phrases that frighten new users, "rebase", "cherry-pick", "force-push", "rewriting history", are all small operations on the DAG that become obvious once you can see the DAG.

The everyday workflow on a team is the same shape on every git host (GitHub, GitLab, Bitbucket, Azure DevOps). Clone the repository, create a branch for the change, commit work to that branch, push the branch to the remote, open a pull request (or merge request, depending on the host), accept review feedback, merge. The variant that matters at the team level is the branching model (trunk-based, GitHub Flow, Git Flow), which decides how many branches are alive at once and how long they live for. The empirical answer, in the 2023 Accelerate State of DevOps report, is that trunk-based with short-lived feature branches correlates with high performance; long-lived branch models correlate with low performance.

Feynman test A git repository is a database of immutable objects, plus a small set of mutable pointers. The objects are blobs (file contents), trees (folder structure), and commits (snapshots with parents). The pointers are refs: branch names, tags, HEAD. Every git operation either adds an object to the database, moves a ref, or both. If you can hold that distinction, you can predict what every git command will do before you run it.
What's beyond the syllabus Git's data model is so cleanly content-addressed that it has been repurposed as a general-purpose object store: GitHub deploys static sites from it, Hugging Face stores models in it, Nix uses the same hashing idea for package identity. The deep insight is that content-addressed storage, where the name of a thing is the hash of its contents, gives you deduplication, integrity checking, and distributed consistency for free. The reason git push can synchronise two repositories quickly is that both sides agree on the names of every object they have ever seen.
Step 2

Why this matters

The first reason is that git is the universal medium of collaboration in software. Every modern developer survey (Stack Overflow, GitHub State of the Octoverse, JetBrains State of Developer Ecosystem) puts git's usage above 90% among professional developers, and there is no second-place tool in sight. Mercurial, Bazaar, Perforce, Subversion, Fossil all exist and have their adherents, but a candidate at a modern engineering team is expected to know git the way they are expected to know how to use a keyboard. The minimum competence bar has been raised to a position the bar did not occupy ten years ago.

The second reason is that fluency with git is what makes the rest of the engineering workflow comfortable. A team that can move work between branches confidently, that can rebase a series of commits before review, that can git bisect to find the commit that introduced a regression, can build a workflow in which mistakes are recoverable. A team that fears git, that commits everything to main because branching is "complicated", forfeits all of those affordances. The fear-driven workflow is the source of most of the merge conflicts, lost work, and force-pushed history that teams complain about; the engineering work is to make the workflow boring.

The third reason is that git literacy is the prerequisite for the next three lectures. Code review (Lecture 13) is a workflow on top of git branches. Continuous integration (Lecture 14) is automation triggered by git events. Auto-generated documentation (Lecture 15) is keyed on git tags. None of those work if the team's git practice is "we usually push directly to main and hope". The investment in this lecture is the investment that makes the rest of the part-IV curriculum possible.

Step 3

The mental model

Objects: blob, tree, commit

The git object database lives in .git/objects. It stores three kinds of objects, each addressed by the SHA-1 (or, increasingly, SHA-256) hash of its content.

A blob is the contents of a single file at a point in time. Two files with identical contents share one blob; renaming a file in a commit does not change the blob, only the tree that references it. A tree is a list of (mode, name, hash) entries: it is git's representation of a folder. A tree is recursive: each entry in a tree either points to a blob (a file in this directory) or to another tree (a subdirectory). A commit is a small text record that names a tree (the snapshot at this commit), one or more parent commits, the author and committer (name, email, timestamp), and a message.

commit a8b7c6d...
    tree    1f2e3d4...    # the folder structure at this commit
    parent  9876543...    # the previous commit
    author  Mario Ervedosa <mario@example.com> 1715000000 +0100
    committer Mario Ervedosa ...

The commit is the unit of history. Following the parent pointers backwards traverses the history of the project; following them forwards is not possible directly, which is why git logs walk backwards from the current commit. A commit can have zero parents (the first commit in a repository, known as the root commit), one parent (a normal commit), or two or more parents (a merge commit). The history of the project is therefore a directed acyclic graph: directed because parent pointers have direction, acyclic because each commit is created with parents already in place, never the reverse.

Refs: branches, tags, HEAD

The object database is immutable: once a commit is created, its contents and hash do not change. The mutable part of git is the set of refs in .git/refs. A ref is a small file containing a hash; the file's name is how the ref is referred to. A branch is a ref under refs/heads/: main is the file refs/heads/main, containing the hash of the latest commit on that branch. A tag is a ref under refs/tags/: v1.0.0 is the file refs/tags/v1.0.0, conventionally pointing at a specific release commit. A remote-tracking branch is a ref under refs/remotes/origin/, recording what your local copy knows about the remote's branches.

HEAD is the special ref that names the current branch. Usually HEAD contains the literal text ref: refs/heads/main (a symbolic reference); a commit operation reads the branch HEAD points to, creates a new commit with that branch's tip as parent, and updates the branch to point at the new commit. A "detached HEAD", which scares new users, simply means HEAD contains a commit hash directly rather than a branch name; you can commit in that state, but your commits are not on any branch and will be garbage-collected if you switch away without naming them.

The three-tier working area

Git's interface presents three places a file can live, between the database and the editor. The working tree is the files on disk that you edit. The index (also called the staging area) is a binary file at .git/index that records what the next commit's tree will look like; it sits between the working tree and the repository. The repository is the object database itself. The commands move content between these tiers: git add moves working-tree changes into the index; git commit moves index contents into a new commit in the repository; git checkout moves repository contents (a commit's tree) into the working tree and the index.

Index. The proposed contents of the next commit. git add writes to it; git commit reads from it. The index lets you stage some hunks for commit while leaving others out, which is the entire purpose of having an explicit staging step.
Fast-forward. A merge that does not need a merge commit: if the target branch's tip is an ancestor of the source branch's tip, the target's pointer can simply be moved forward along the existing chain. Fast-forward merges keep history linear; non-fast-forward merges produce a diamond shape.
Step 4

The detail

The daily commands

Most days, a working developer uses a small subset of git's surface. The list below covers about 90% of the activity on a normal week.

# Set-up
git clone git@github.com:org/repo.git
cd repo

# Branching and switching
git switch -c feature/calibrate-pd        # new branch from current HEAD
git switch main                            # back to main
git branch -d feature/calibrate-pd         # delete a merged branch

# Inspecting state
git status                                 # what is staged, what is not
git diff                                   # unstaged changes
git diff --staged                          # staged but uncommitted
git log --oneline --graph --decorate -20   # recent history

# Recording changes
git add path/to/file
git add -p                                 # interactive hunk staging
git commit -m "feat: add PD calibration"
git commit --amend                         # rewrite the last commit
                                           #   (only before push)

# Remote synchronisation
git fetch                                  # download remote refs
git pull --rebase                          # fetch + rebase local on top
git push -u origin feature/calibrate-pd    # push and track

# Recovering
git restore --staged path/to/file          # unstage
git restore path/to/file                   # discard working-tree change
git reset --hard HEAD~1                    # destructive: discard last commit

Two patterns are worth special attention. The interactive add (git add -p) walks through every change hunk by hunk and lets you stage some and not others; it is the difference between committing exactly the change you want and committing whatever happens to be in the file. The git pull --rebase form, rather than the default merge, keeps history linear when you pull in upstream changes; the team's setting git config --global pull.rebase true makes it the default.

Merging versus rebasing

The branch in the diagram above was integrated with main via a merge commit M, which has two parents. The alternative is a rebase: replay the commits from the feature branch on top of the current tip of main, producing new commit objects with new hashes but the same diffs. The history that results is linear, as though the feature work had always been done after the current state of main.

# merge: keep history accurate, accept a diamond shape
git switch main
git merge feature/calibrate-pd

# rebase: keep history linear, rewrite the feature branch
git switch feature/calibrate-pd
git rebase main
git switch main
git merge feature/calibrate-pd      # this merge is now fast-forward

The choice between them is the longest-running argument in version-control culture. The two camps agree on one rule: never rebase commits that have been shared, because rebasing produces new hashes and anyone who has pulled the old hashes will be confused when they reappear under new names. Within that rule, the typical modern workflow is: rebase your own feature branch before opening the pull request (clean history, no merge bubbles), and use a merge (or squash-merge) for the final integration into main. The "Squash and merge" button on GitHub does exactly this: it collapses the feature branch's commits into one and fast-forwards main onto it, producing a one-commit-per-feature history on the trunk.

Branching strategies

Three branching models account for most teams.

Trunk-based development (paulhammant.com/trunkbaseddevelopment): all developers commit to main, with feature branches that live no more than a day or two. CI runs on every push; the trunk is always releasable. Feature flags are used to hide unfinished work in production. The DORA studies (Forsgren, Humble, Kim, Accelerate, 2018) found this model is the strongest predictor of high engineering performance.

GitHub Flow (Scott Chacon, 2011): a long-lived main, plus short-lived feature branches that exist for the duration of one pull request. The branch is merged and deleted when the PR lands. This is the default on GitHub and the right starting point for most teams.

Git Flow (Vincent Driessen, 2010, nvie.com/posts/a-successful-git-branching-model): a long-lived main for production, a long-lived develop for integration, plus feature/, release/, and hotfix/ branches. Designed for products with scheduled releases. Heavyweight for fast-moving teams; Driessen himself published an addendum in 2020 noting that "if your team is doing continuous delivery of software, I would suggest to adopt a much simpler workflow".

Useful rescue operations

The most frightening git operations are also the ones that recover the situation when something has gone wrong.

git reflog is the answer to "I rebased and lost my commits". The reflog records every place HEAD has been for the last 90 days, including hashes of commits that are no longer reachable from any branch. git reset --hard <hash> on a reflog entry puts you back where you were.

git bisect is the answer to "which commit introduced this bug?". You tell git a known-good commit and a known-bad commit; git checks out the midpoint and asks you to test it; you mark it good or bad; git checks out the next midpoint. In ten steps you have searched a thousand-commit history.

git bisect start
git bisect bad                # current commit is broken
git bisect good v1.2.0        # this old release worked
# git checks out the midpoint; run your test
git bisect good   # or bad, depending on result
# ... repeats until the culprit is found
git bisect reset

git cherry-pick is the answer to "I need this one commit on another branch". It takes a commit by hash, computes the diff, and applies it on top of the current branch. Useful for backporting a bug fix from main to a release branch.

git stash is the answer to "I have uncommitted changes but need to switch branches". It pushes the working-tree changes onto a stack and reverts the working tree to clean; git stash pop reapplies them later. The modern workaround is to use worktrees (git worktree add ../other-checkout other-branch), which lets two branches be checked out at once in different folders.

Common pitfall The single most destructive git command is git push --force against a shared branch. It rewrites the remote's history to match yours and silently invalidates the local copies of every other team member working on that branch. The safer variant is git push --force-with-lease, which refuses to overwrite if someone else has pushed in the meantime. Better still, configure the remote (GitHub, GitLab) to disallow force pushes to main. The team rule should be: force pushes on your own short-lived feature branch are fine; on any shared or long-lived branch, they are forbidden.

The .gitignore and .gitattributes files

Two configuration files shape what git tracks and how. .gitignore lists patterns of files that git should never offer to stage: __pycache__/, *.pyc, .venv/, node_modules/, generated build artefacts, and any local-only configuration. .gitattributes declares per-pattern handling: which files are text and need line-ending normalisation, which files are binary and should not be diffed, which files use a custom merge driver. The pair are committed to git like any other source file.

# .gitignore
__pycache__/
*.pyc
.venv/
.pytest_cache/
.coverage
data/raw/
.DS_Store
.env

# .gitattributes
*.py        text eol=lf
*.md        text eol=lf
*.png       binary
*.parquet   binary
*.ipynb     filter=nbstripout      # see Lecture 10

Worked example: salvaging a tangled feature branch

Worked example: rescuing a feature branch with a bad commit

You have been working on feature/lgd-recalibration for three days, with six commits. The fifth commit accidentally added the entire data/raw/ folder (2GB of parquet files), which is too big to push. The sixth commit, on top of it, contains the actual fix you want to keep. The remote has the first four commits but rejected commits five and six because of the size.

Step 1 (find the offending commit). git log --oneline --stat -10 shows the six commits and the files each changed. The fifth has 18 parquet files in its diff. The hash is e3b0c44.

Step 2 (rebase interactively). git rebase -i HEAD~6 opens an editor showing the six commits. Change the line for commit e3b0c44 from pick to edit. Save and close.

Step 3 (fix the bad commit). git pauses at the bad commit. Remove the files: git rm -r --cached data/raw/. Add the path to .gitignore in this same commit. Amend: git commit --amend --no-edit. Continue the rebase: git rebase --continue.

Step 4 (verify). git log --oneline --stat -6 confirms the parquet files no longer appear. du -sh .git confirms the repo is back to a reasonable size. git status is clean.

Step 5 (force-with-lease push). Because the rebase rewrote local commits and the remote already has different versions of commit five, you need to overwrite. git push --force-with-lease origin feature/lgd-recalibration. The lease ensures you only overwrite if no one else has pushed in the meantime.

The branch is now pushable, the bad commit is gone, the fix is preserved, and the team's pull-request review can proceed. The whole rescue is six minutes once you know the shape of it; without the mental model, it is a panicked half-hour search through Stack Overflow.

Step 5

Synthesis and what's next

Git is a content-addressed object database (blobs, trees, commits) with mutable refs (branches, tags, HEAD) pointing into it. The everyday commands move content between the working tree, the index, and the repository, and update the refs as they go. Branching and merging produce a DAG; rebasing rewrites parts of it; the team's branching model (trunk-based, GitHub Flow, Git Flow) decides how busy the DAG becomes. The frightening commands (reflog, bisect, cherry-pick, stash, force-with-lease) are the recovery toolkit; they are scary until you have used them once with the mental model in mind, and obvious afterwards.

The wider point is that version control is the team's memory. Every change carries the author, the timestamp, and (if the commit message is decent) the reasoning. git blame on a confusing line of code retrieves not just who wrote it but why. The team's commit-message discipline (Conventional Commits, or a similar convention) is therefore not bureaucracy; it is the layer that makes the team's memory useful five years later.
