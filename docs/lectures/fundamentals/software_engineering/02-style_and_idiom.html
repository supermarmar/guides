Style and idiom: PEPs 8, 20, 257, 484

Style is the property of code that determines whether a second person can read it. Python is unusual in having codified its norms as community standards (the PEPs), and unusual again in automating their enforcement (black, ruff, mypy). This lecture is that toolkit, line by line, plus the philosophy underneath.

Lecture 2 of 16 Reading time, 45 minutes Part I: the craft of writing code
Step 1

The 30-second version

Style is how the code is formatted, named, organised, typed, and documented. It is not the same thing as correctness; a program can be correct and unreadable, or readable and wrong. But maintainability, which Lecture 1 named as one of the four properties software is judged on, is almost entirely a question of style. A program that nobody can read is a program that nobody can change, and a program that nobody can change becomes incorrect by drift.

The Python community is unusually well organised in this area. Style is codified in Python Enhancement Proposals (PEPs), short normative documents authored by the language's maintainers. Four PEPs cover almost everything a working engineer needs:

  • PEP 8 (van Rossum, Warsaw, Coghlan; 2001, revised). The style guide proper: indentation, line length, naming, whitespace, imports.
  • PEP 20 (Peters; 2004). The Zen of Python, a 19-line aesthetic creed.
  • PEP 257 (Goodger, van Rossum; 2001). Docstring conventions.
  • PEP 484 (van Rossum, Lehtosalo, Langa; 2014). Type hints.

The second unusual fact is that the modern Python toolchain enforces these rules automatically. Black reformats your code to a canonical layout. Ruff lints and formats at C-extension speed. Mypy and pyright check the type hints. Pre-commit runs the lot before every commit. The setup cost is twenty minutes; the saving compounds for the life of the project.

Feynman test Imagine you write a long letter, then send it to a colleague to finish. If your handwriting changes mid-page, if you mix capitals and lower-case at random, if you sometimes write the date as DD/MM and sometimes MM/DD, your colleague will spend most of their time decoding rather than reading. Style is the convention that lets them read instead. Code style is the same convention for source files, made stricter because the next reader is often you, six weeks later, with no memory of why you wrote what you wrote.
What's beyond the syllabus A common objection is that style is a matter of taste. The empirical record disagrees. Hindle, Barr, Su, Gabel and Devanbu (MSR 2012, "On the naturalness of software") show that real code is highly repetitive, far more so than natural language, and that statistical models of code style improve completion accuracy and defect prediction. Style is not taste; it is the regularity that makes prediction, and therefore reading, cheap.
Step 2

Why this matters

The economic case rests on a single ratio. The read-to-write ratio of code is empirically around ten to one (Martin, Clean Code, 2008, after observing dozens of professional teams). For every line you write, that line will be read by someone, often a future version of you, ten times before it is replaced. Optimising the writing experience at the expense of the reading experience is therefore a bad trade by a factor of ten, on average.

The deeper case is Knuth's. In "Literate programming" (Knuth 1984), he argues that source code has two audiences: the compiler, which must accept it, and the human reader, who must understand it. The compiler will accept almost anything that parses; the human reader is the binding constraint. Knuth's solution, that we should write programs as expository documents from which the machine-readable form is extracted, was always too radical for the mainstream. The watered-down version, that we should write code so that a human reader has a fighting chance, is now textbook orthodoxy. Style is what gives them that chance.

A second consideration is bikeshedding, named after Parkinson's law of triviality (Parkinson 1957). When the substantive decisions in a project are hard, teams gravitate towards the easy decisions, what colour to paint the bikeshed, where to put the brackets, whether single or double quotes. These arguments are infinitely sustainable, because nobody can be definitively wrong. Tools that take the decision out of human hands (black, ruff format) end the argument by simply imposing a choice; the team can then return to the substantive decisions, of which there are usually plenty.

Step 3

The mental model

Treat style as five layers, from the most mechanical to the most subjective. Each layer is enforced by a different tool, and the cost of enforcing it falls as you go down the list:

FormattingWhitespace, line length, where the brackets go, indentation depth. Pure mechanics. Enforced by a formatter: black, ruff format. Zero human judgement after the initial choice of tool.
NamingVariables, functions, classes, modules. Convention is mechanical (snake_case for functions, PascalCase for classes); the substance, "is this name actually good?", is not. Enforced by convention + reviewer.
StructureOrder of imports, module layout, where helpers live, where the entry point is. Enforced by linter / sorter: isort, ruff.
Idiom"The Pythonic way to do X." A list comprehension instead of a manual for-loop append; enumerate instead of an index counter. Enforced by ruff's RUF rules and by reviewers.
TypesPEP 484 annotations that document the interface between functions. Enforced by a type checker: mypy, pyright. Strictly optional in Python but the equivalent of a free unit test.

The order matters. Formatting is non-negotiable and automated; types are negotiable and partial. Most teams start by enforcing formatting and naming, add structure and idiom rules over time, and adopt typing last, often after a particularly painful bug that types would have caught. The layered approach also matches the order in which a reviewer looks at code: the eye notices format first, names second, structure third; idiom and types require slower reading.

Style is necessary, not sufficient A perfectly formatted, fully typed program can still be wrong, brittle, slow, or unmaintainable. Style is the floor, not the ceiling. The discipline of style buys you the right to argue about the substantive properties of the code, because the bikeshed colour is no longer up for debate. It does not, by itself, ensure those properties.
Step 4

The detail

PEP 8: the style guide proper

PEP 8 is the longest of the four PEPs and the one whose rules an engineer should be able to recite without looking up. The document was authored by Guido van Rossum (Python's creator), Barry Warsaw, and Nick Coghlan, and has been revised regularly since 2001. The rules that matter most for day-to-day work are below.

Indentation is four spaces per level, never tabs, never mixed. The choice is arbitrary; the consistency is not. Python uses indentation as a syntactic element, so mixing tabs and spaces is one of the few style errors that can change the meaning of a program. Modern editors should be configured to convert tabs to spaces on save.

Line length is the one PEP 8 rule that almost nobody follows literally. The PEP says 79 characters; the rationale was historical (terminal width). The de-facto standard for new projects is now 88 (black's default) or 100 (Google), with 120 sometimes used for codebases that work in wide editors. The substance matters more than the number: a line that is too long forces the reader to scroll horizontally or wrap awkwardly. Pick a number, write it down in pyproject.toml, let the formatter enforce it, and move on.

Naming conventions are tighter:

Imports go at the top of the file, one per line, grouped into three blocks separated by a blank line: the standard library, third-party libraries, then local modules. Within each block, imports are sorted alphabetically. from X import * is forbidden in production code because it pollutes the namespace and breaks "explicit is better than implicit".

import os
import sys
from pathlib import Path

import numpy as np
import pandas as pd

from src.config import DATA_PATH
from src.pricing import compute_pd

Whitespace rules are mechanical and easily learned: one space around binary operators (x = a + b, not x=a+b); no space inside brackets (foo(x, y), not foo( x, y )); two blank lines between top-level functions and classes; one blank line between methods inside a class. The full list is in PEP 8; black and ruff format will apply it for you.

PEP 20: the Zen of Python, line by line

Tim Peters drafted the Zen at a 1999 Python conference and submitted it as PEP 20 in 2004. It ships with every Python interpreter; import this prints it. The 19 lines are aphoristic, and tone matters: it is half a creed and half a joke. Read line by line, with a working example each, it becomes a checklist for everyday code review.

PEP 257: docstrings

A docstring is a string literal that occurs as the first statement of a module, function, class, or method. It is accessible at runtime as obj.__doc__ and is what help(obj) prints. PEP 257 standardises the format; three flavours are common in practice, and the choice is a project-level decision.

One-line docstrings are for self-evident functions:

def square(x: float) -> float:
    """Return x squared."""
    return x * x

Multi-line docstrings start with a one-line summary, then a blank line, then the rest. Three formats dominate:

Google style

def compute_pd(scores: pd.Series, calibration: dict[str, float]) -> pd.Series:
    """Translate raw scorecard outputs into calibrated PDs.

    Args:
        scores: Vector of raw scorecard outputs in the open unit interval.
        calibration: Mapping from segment label to calibration intercept.

    Returns:
        Series of calibrated probabilities of default, indexed identically
        to ``scores``.

    Raises:
        CalibrationError: If a segment in ``scores`` has no calibration entry.
    """
    ...

NumPy style (common in scientific Python)

def compute_pd(scores, calibration):
    """Translate raw scorecard outputs into calibrated PDs.

    Parameters
    ----------
    scores : pandas.Series
        Vector of raw scorecard outputs in the open unit interval.
    calibration : dict[str, float]
        Mapping from segment label to calibration intercept.

    Returns
    -------
    pandas.Series
        Calibrated probabilities of default.
    """
    ...

Sphinx (reST) style

def compute_pd(scores, calibration):
    """Translate raw scorecard outputs into calibrated PDs.

    :param scores: vector of raw scorecard outputs.
    :type scores: pandas.Series
    :param calibration: mapping from segment label to intercept.
    :returns: calibrated probabilities of default.
    :raises CalibrationError: if a segment has no calibration entry.
    """
    ...

Google style is the most readable in source form and is the default for new projects that use mkdocs-material. NumPy style is preferred in the scientific stack. Sphinx style is the oldest and is still common in older codebases. Within a single project, pick one and never mix.

Docstrings vs comments A docstring documents the interface (what the function does, for callers). A comment explains the implementation (why a particular line of code looks the way it does, for maintainers). The two are not interchangeable. Docstrings are addressed to people who will not read the body; comments are for those who will. A common anti-pattern is to use a long docstring to apologise for a confusing implementation; the right fix is almost always to clarify the implementation, not to lengthen the docstring.

PEP 484: type hints

Python is dynamically typed: a variable's type is decided at runtime, and is not declared. PEP 484, accepted in 2014 and shipped in Python 3.5, adds a syntax for declaring types without changing this. The annotations are not enforced by the interpreter at runtime; they are read by external type checkers (mypy, pyright, pyre) which produce errors at lint time, before the program runs.

Basic syntax annotates parameter and return types:

def add(x: int, y: int) -> int:
    return x + y

def greet(name: str) -> None:
    print(f"Hello, {name}.")

Container types use the built-in collection names with parameter types in brackets (PEP 585, Python 3.9+):

def total(xs: list[float]) -> float:
    return sum(xs)

def lookup(table: dict[str, int], key: str) -> int:
    return table[key]

def pair() -> tuple[str, int]:
    return ("alice", 42)

For values that may be missing, use X | None (PEP 604, Python 3.10+) instead of the older Optional[X]:

def find_user(uid: int) -> User | None:
    ...

For abstract container types where the caller might pass any iterable, use the collections.abc protocols rather than concrete types:

from collections.abc import Iterable, Mapping

def sum_all(xs: Iterable[float]) -> float:
    return sum(xs)

def first_value(m: Mapping[str, int]) -> int:
    return next(iter(m.values()))

Generics let you write a function whose output type depends on its input type:

def first[T](xs: list[T]) -> T:
    return xs[0]

The syntax above is PEP 695, Python 3.12+. Older code uses TypeVar from typing. Protocols (PEP 544) provide structural typing, the Python equivalent of Go interfaces:

from typing import Protocol

class SupportsLength(Protocol):
    def __len__(self) -> int: ...

def report_size(x: SupportsLength) -> None:
    print(f"size is {len(x)}")

Any object with a __len__ method satisfies SupportsLength; you do not need to inherit from it. This is the type-system equivalent of duck typing.

Types are not a substitute for tests A typed program is not, by virtue of typing, a correct program. Types catch a particular family of errors, wrong-type at the boundary, that would otherwise need a test. They do not catch logic errors, performance errors, or anything that lives inside the type. def divide(a: float, b: float) -> float says nothing about division by zero. Lecture 5 (testing) returns to what types do and do not cover.

The toolchain

Modern Python style enforcement is automated. A working configuration involves five tools, all configurable through pyproject.toml and runnable both locally and in CI:

blackOpinionated code formatter. Re-formats files to a canonical layout. No configuration except line length. The original "stop arguing" tool, written by Łukasz Langa in 2018.
isortSorts and groups imports per PEP 8. Now largely subsumed by ruff but still used standalone.
ruffA linter and formatter written in Rust; 10 to 100x faster than the Python alternatives. Implements most of flake8, isort, pyupgrade, and black in one tool. The pragmatic default for new projects (Charlie Marsh, Astral, 2022).
mypy / pyrightStatic type checkers. Mypy is the reference implementation (Lehtosalo, after PEP 484). Pyright is Microsoft's faster alternative, used inside VS Code's Pylance extension. Pick one per project; they disagree at the margins.
pre-commitA framework for running tools at git commit time. Configured in .pre-commit-config.yaml; ensures the local checks match the CI checks. Covered in Lecture 12.

A minimal pyproject.toml configuration that covers all five looks like this:

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "SIM", "N"]
ignore = ["E501"]  # line length handled by ruff format

[tool.ruff.format]
quote-style = "double"

[tool.mypy]
strict = true
python_version = "3.12"
warn_unused_ignores = true

The ruff rule selection above covers (E) PEP 8 errors, (F) pyflakes (unused imports, undefined names), (I) import sorting, (B) bugbear (common bug patterns), (UP) pyupgrade (use modern syntax), (SIM) flake8-simplify (suggest simpler forms), and (N) PEP 8 naming. The full catalogue is hundreds of rules; start with a small selection and grow it as the team's appetite for strictness grows.

Idiom: the patterns the Zen actually rewards

Style guides cover formatting and naming; idiom is the part that is harder to mechanise. A few patterns separate Python written by a beginner from Python written by someone who has internalised the Zen.

Comprehensions over manual loops, when the operation is a transformation or filter:

# Less idiomatic
result = []
for x in xs:
    if x > 0:
        result.append(x * x)

# Idiomatic
result = [x * x for x in xs if x > 0]

Enumerate instead of an index counter:

# Less idiomatic
i = 0
for item in items:
    print(i, item)
    i += 1

# Idiomatic
for i, item in enumerate(items):
    print(i, item)

Unpacking instead of indexing:

# Less idiomatic
first = pair[0]
second = pair[1]

# Idiomatic
first, second = pair

Context managers for resources:

# Less idiomatic
f = open("data.csv")
try:
    data = f.read()
finally:
    f.close()

# Idiomatic
with open("data.csv") as f:
    data = f.read()

F-strings for formatting (Python 3.6+), not % or str.format:

# Idiomatic
name = "alice"
print(f"Hello, {name}.")

Dataclasses or pydantic models for plain data, not bare dictionaries:

from dataclasses import dataclass

@dataclass
class Borrower:
    id: int
    score: float
    segment: str

The list is not exhaustive. The point is that "Pythonic" code rewards two habits: prefer the most direct construct that does the job (the Zen's "one obvious way"), and lean on the language's built-in machinery rather than reinventing it.

Anti-patterns worth naming

Style is partly negative: knowing what to avoid is half the discipline. A short catalogue of the most common failures, in rough order of frequency:

Anti-patternWhy it hurtsWhat to do instead
Bare except:Silently swallows all exceptions, including KeyboardInterrupt and SystemExit; defeats every debugger.Catch a specific exception class. If you must catch all, use except Exception and log.
Mutable default argumentsdef f(x=[]): is evaluated once at definition time; the list is shared across calls.Use None and assign inside: def f(x=None): x = x or [].
Wildcard importsPollutes the namespace; breaks reader's ability to find a name's origin; risks shadowing.Import what you need, explicitly.
Magic numbersAn unnamed constant in the middle of a function is meaningless to the reader and dangerous to change.Name it: MIN_BALANCE = 50.0 at module scope.
Single-letter namesCryptic. Only acceptable as loop indices (i, j) or mathematical variables matching a published formula.Use a descriptive name.
Dead code / commented-out codeConfuses the reader: is this here for a reason?Delete. Version control remembers.
Long parameter listsA function with more than five positional parameters is hard to call and hard to read.Group into a dataclass, or pass keyword-only.
Returning None to signal "missing"Caller forgets to check, gets a TypeError three calls deeper.Either raise or return a sentinel typed as X | None so the type checker flags missed checks.
Worked example: rewriting a function for style

Original (style violations marked):

def CALC(d,r=[]): # PEP 8: name; mutable default if d!=None: # whitespace; "is not None" for i in range(len(d)): # not enumerate x = d[i] if x['s']>0: # cryptic key, magic 0 r.append(x['s']*1.5) # magic number return r

Idiomatic rewrite:

SCALE_FACTOR = 1.5 def scale_positive_scores(items: list[dict] | None) -> list[float]: """Multiply positive scorecard outputs by the scale factor. Args: items: List of dicts, each with key "score". May be None. Returns: List of scaled scores, or an empty list if items is None. """ if items is None: return [] return [item["score"] * SCALE_FACTOR for item in items if item["score"] > 0]

The rewrite fixes nine separate style issues: function naming, mutable default, equality comparison with None, indexed loop, cryptic key name, magic constants, missing type hints, missing docstring, and lack of comprehension. None of the changes affect correctness on the original inputs; all of them affect readability for the next person who touches the function.

Step 5

Synthesis and what's next

Style is the cheapest available improvement to maintainability, the property that Lecture 1 named as the dominant one in the long run. The investment is twenty minutes of toolchain setup (black or ruff format, ruff lint, mypy or pyright, pre-commit) and the standing cost of conforming to the conventions while writing. The payback is every read of every file from that moment forward, multiplied by the read-to-write ratio of roughly ten.

The four PEPs give you most of what you need. PEP 8 covers formatting and naming; PEP 20 articulates the sensibility; PEP 257 standardises docstrings; PEP 484 enables type checking. Tools (black, ruff, mypy, pyright, pre-commit) automate the enforcement. Idiom and anti-patterns are the part you internalise by reading and writing, and through code review (Lecture 14).

From here, Lecture 3 turns to the constructs the style is built on: Python's built-in data types, their idiomatic uses, and the comprehensions and iteration patterns that "explicit is better than implicit" rewards. Lecture 4 turns to text processing with regular expressions. Together, Lectures 2 to 4 cover the file-level craft; Part II then asks how we know any of it is correct.
