Regular expressions

A regex is a tiny language for describing patterns in text. It is the smallest tool that solves a surprisingly large class of problems, and the wrong tool for a surprisingly large class of others. This lecture covers the constructs, the Python API, the underlying theory (regular languages, Thompson's NFA), and the line at which you should stop and reach for a parser.

Lecture 4 of 14 Reading time, 40 minutes Part I: the craft of writing code
Step 1

The 30-second version

A regular expression is a string that denotes a set of strings. Reading a regex is reading its description of all the strings it would match; writing one is writing the description from a set in your head. The engine that compares the regex against an input is small (a few hundred lines of code in its classical form), the language it accepts is well understood (the regular languages of formal-language theory), and the API in any modern language is two or three functions.

Stephen Kleene invented the notation in 1951 as part of his work on neural nets and finite automata. Ken Thompson built the first practical engine into a text editor (QED, 1968), then into grep (1973). Almost every editor, log analyser, configuration tool, and data-cleaning script written since has been a downstream consequence. Two-thirds of the world's industrial text processing is regex-driven; the other third is parsers, and the rest of this lecture is partly about telling them apart.

In Python, the re module is the standard interface. The five functions you will use 95 per cent of the time are re.search, re.match, re.findall, re.finditer, and re.sub. The rest of the API is for compiled patterns, flags, and named groups.

Feynman test A regex is a recipe for "yes" or "no". Given any string, the regex either matches it or does not. The cleverness is that the recipe is itself a string, so we can store, share, modify, and compose recipes the same way we store, share, modify, and compose data. The engine, internally, walks through the input one character at a time, holding a set of states the regex could be in, and asking after each character whether any state is the "accept" one. That is all there is to it.
What's beyond the syllabus Real-world regex engines are not the classical Kleene-Thompson construction. Most (Perl, Python, Ruby, JavaScript, Java) use a backtracking implementation that supports features (backreferences, lookarounds) which classical regex theory cannot express. The trade-off is that pathological patterns can run in exponential time, a class of bug known as ReDoS (regular-expression denial of service). Russ Cox's three-part essay "Regular expression matching can be simple and fast" (2007) is the canonical exposition.
Step 2

Why this matters

Text is the universal data format. Logs, CSV files, JSON dumps, HTML pages, configuration files, source code, emails, chat messages, scraped pages, and most outputs of "machine X talking to machine Y" are sequences of characters that someone else's program produced and someone else's program (yours) has to read. The unifying skill of working with this material is pattern recognition: "show me the lines that look like a phone number", "extract the timestamp from each log entry", "find every occurrence of the word 'todo' in the codebase". Regex is the tool that turns these descriptions into one-liners.

The economic argument is the same as the comprehension argument from Lecture 3: a regex that takes 30 seconds to write replaces a 30-line state machine that takes an hour to write and ten minutes per change to maintain. The cost of not knowing regex is that you reinvent a worse one every time. The cost of knowing it is one afternoon, plus a permanent need for a reference card.

The deeper case is theoretical. Regex matches exactly the regular languages, type 3 in Chomsky's hierarchy (Chomsky 1956). These are the languages a finite-state automaton can recognise: bounded memory, single pass, no nesting. The languages that cannot be recognised this way (balanced parentheses, arbitrarily deep XML, well-formed JSON) require context-free grammars (type 2) or stronger. Knowing where the line is saves you from the most common regex anti-pattern: trying to parse HTML with a regex.

Step 3

The mental model

A regex is built from six kinds of construct. Read every regex by classifying each piece into one of the six categories, in this order:

LiteralA character that stands for itself: a matches a; banana matches banana. The atoms.
Character classA set of literals, any one of which matches one position. [abc] matches a, b, or c; [a-z] matches any lowercase letter; [^0-9] matches anything that is not a digit; \d is shorthand for [0-9].
QuantifierA repetition count attached to the previous atom: x? (0 or 1), x* (0 or more), x+ (1 or more), x{n} (exactly n), x{n,m} (between n and m).
AnchorA zero-width assertion about the position in the input: ^ matches the start of the string (or line, with the MULTILINE flag); $ matches the end; \b matches a word boundary.
AlternationA|B matches A or B. Lowest precedence: cat|dog means "cat or dog", not "ca, t-or-d, og".
GroupParentheses serve two purposes: scoping (limit alternation and quantifiers) and capture (record the matched substring for later use). (cat|dog)s? matches "cat", "dog", "cats", "dogs", and captures the animal.

Every regex is a composition of these six. Reading complicated regexes is the practice of identifying which construct each fragment is. The character . is a one-character class meaning "anything except newline"; the construct \d{3}-\d{4} is "a character class with a fixed quantifier, a literal, another character class with a fixed quantifier"; the construct ^[A-Z][a-z]+\s+[A-Z][a-z]+$ is "anchor, character class, character class plus quantifier, character class plus quantifier, repeat the pattern, anchor".

The hardest part of writing a regex is not the syntax but the specification: what exactly do you intend to match? "An email address" is not a regex specification; it is a famously open question. RFC 5322's grammar for valid email addresses is several pages long. A practical regex for "things that look like email addresses in this dataset" is two lines. The difference matters: the right specification is the smallest one that distinguishes what you want from what you do not want.

When regex is the wrong tool Stop and reach for a parser whenever the language you are matching has arbitrarily nested structure (JSON, XML, HTML), arbitrarily long context dependencies, or formal correctness requirements (compilers, financial protocols). The famous Stack Overflow answer "you can't parse HTML with regex" (2010, Bobince) is correct, in two senses: (a) HTML is context-free, regex is regular; (b) even where it works on small inputs, the resulting code is fragile to changes in input format. Use html.parser, lxml, BeautifulSoup, or a real grammar.
Step 4

The detail

Character classes and shorthands

The character class [...] matches any single character listed; [^...] matches any single character not listed. Inside a class, - denotes a range and ^ at the start denotes negation; other metacharacters lose their special meaning. Ranges follow ASCII (or Unicode) ordering: [a-zA-Z0-9_] matches one "word" character.

Common shorthands save typing. Each has an uppercase negation:

ShorthandEquivalentMatchesNegation
\d[0-9]One digit.\D
\w[A-Za-z0-9_]One "word" character (letter, digit, underscore).\W
\s[ \t\r\n\f\v]One whitespace character.\S
.(any but newline)Any single character. With the DOTALL flag, includes newline.n/a

The Python re module supports Unicode shorthands by default: \w matches any letter from any script, not just ASCII. Pass re.ASCII to restrict.

Quantifiers, greedy and lazy

Every quantifier comes in two flavours. The default is greedy: match as much as possible while still allowing the rest of the pattern to succeed. Append ? to make it lazy: match as little as possible. The difference matters whenever the pattern after the quantifier could appear inside the quantified region.

import re

text = '<b>bold</b> and <i>italic</i>'

re.findall(r'<.+>', text)        # ['<b>bold</b> and <i>italic</i>']   greedy
re.findall(r'<.+?>', text)       # ['<b>', '</b>', '<i>', '</i>']     lazy

Greedy .+ consumes everything to the last >; lazy .+? stops at the first. The lesson is to pick the flavour deliberately. The default greedy behaviour is correct surprisingly often, but the bug it produces (over-matching) is silent and well-disguised.

Anchors and boundaries

Anchors match positions, not characters; they consume nothing.

AnchorMatches at
^Start of string (or start of line with re.MULTILINE).
$End of string (or end of line with re.MULTILINE).
\bWord boundary: between a \w and a \W (or string edge).
\BNot a word boundary.
\A, \ZTrue start/end of string regardless of flag.

The most useful anchor in everyday code is \b. Without it, cat matches "scatter"; \bcat\b matches only the whole word.

Groups: capturing, non-capturing, named

Parentheses do two things: scope (so a quantifier or alternation applies to the enclosed expression) and capture (so the matched substring can be retrieved or referred to later). Three flavours of group:

(abc)        # capturing group, indexed from 1
(?:abc)      # non-capturing group, scope only
(?P<name>abc) # named capturing group (Python syntax)

The convention is: use a non-capturing group whenever you do not need the captured value. The capture has a small cost (the engine remembers the offsets) and clutters the result. Use named groups whenever the position of the capture is not obvious; reading m.group("year") is friendlier than m.group(2).

m = re.match(r'(?P<year>\d{4})-(?P<month>\d{2})-(?P<day>\d{2})', '2026-05-17')
m.group("year")    # '2026'
m.group("month")   # '05'
m.groupdict()      # {'year': '2026', 'month': '05', 'day': '17'}

A backreference matches the same text that was captured earlier in the pattern. The notation is \1 for the first capturing group, \2 for the second, and so on; or (?P=name) for named groups. Backreferences let you express "the same string twice", a feature outside classical regular languages and one of the reasons most engines use backtracking.

# Match repeated words: "the the", "very very"
re.findall(r'\b(\w+)\s+\1\b', text)

Lookaround

Sometimes you want to match a pattern only when it is preceded or followed by another pattern, without including the surroundings in the match. Lookaround assertions are zero-width: they constrain the position without consuming characters.

ConstructMeaningExample
(?=...)Positive lookahead: only if the next characters match ....\d+(?=px) matches a number followed by "px", without capturing "px".
(?!...)Negative lookahead: only if the next characters do not match.foo(?!bar) matches "foo" not followed by "bar".
(?<=...)Positive lookbehind: only if preceded by ....(?<=\$)\d+ matches a number preceded by a dollar sign.
(?<!...)Negative lookbehind: only if not preceded by ....(?<!\\)" matches a quote not preceded by a backslash.

Python's lookbehind requires a fixed width (no variable-length quantifiers). The regex third-party module relaxes this if you need variable-length lookbehind.

The Python re module

The functions you will use most:

import re

# Search anywhere in the string
m = re.search(r'\d+', 'abc123def')        # <Match span=(3, 6) match='123'>
m.group()                                  # '123'

# Match only at the start
re.match(r'\d+', 'abc123')                 # None
re.match(r'\w+', 'abc123')                 # <Match span=(0, 6) match='abc123'>

# Full match required end-to-end
re.fullmatch(r'\d+', '123')                # <Match ...>
re.fullmatch(r'\d+', '123abc')             # None

# All non-overlapping matches
re.findall(r'\d+', 'a1 b22 c333')          # ['1', '22', '333']

# Same, as an iterator of Match objects (use for groups / spans)
for m in re.finditer(r'\d+', 'a1 b22 c333'):
    print(m.group(), m.span())

# Replace
re.sub(r'\d+', 'N', 'a1 b22 c333')         # 'aN bN cN'

# Replace with a function
re.sub(r'\d+', lambda m: str(int(m.group()) * 2), 'a1 b22 c333')
# 'a2 b44 c666'

Two practical habits. First, use raw string literals (r'\d+') for every regex. Without the r prefix, the backslashes are interpreted by Python's string parser first, producing confusing errors. Second, compile patterns you reuse:

EMAIL = re.compile(r'[\w.-]+@[\w.-]+\.\w{2,}')

for line in lines:
    if EMAIL.search(line):
        ...

The cached implementation in re means this is rarely a performance optimisation, but the explicit compile step is clearer to the reader and allows flags to be applied once: re.compile(r'...', re.IGNORECASE | re.MULTILINE).

Common flags

FlagEffect
re.IGNORECASE (re.I)Case-insensitive matching.
re.MULTILINE (re.M)^ and $ match line breaks, not just string edges.
re.DOTALL (re.S). matches newline.
re.VERBOSE (re.X)Allow whitespace and comments inside the pattern for readability.
re.ASCII (re.A)Restrict \w, \d, \s to ASCII (default is Unicode).

The verbose flag is underused and worth knowing. A complicated pattern is much easier to read when broken across lines and commented:

UK_POSTCODE = re.compile(r"""
    ^                                    # start of string
    ([A-Z]{1,2})                         # area:    1-2 letters
    ([0-9][A-Z0-9]?)                     # district: digit + optional letter/digit
    \s*                                  # optional spaces
    ([0-9])                              # sector:  1 digit
    ([A-Z]{2})                           # unit:    2 letters
    $
""", re.VERBOSE | re.IGNORECASE)

Pathological patterns and ReDoS

Python's re module is a backtracking engine. For most patterns this is fine. For a specific family of patterns it is catastrophic. The classic example is (a+)+b on the input aaaaaaaaaaaaaaaaa with no b: the engine tries every way of splitting the as between the inner and outer +, of which there are exponentially many.

The condition is called catastrophic backtracking; the security vulnerability it produces, where an attacker submits a crafted string to a regex on the server, is ReDoS. The defence is twofold. Avoid nested quantifiers when the inner can match a prefix the outer also can ("evil regexes" almost always have this shape). On the server side, use a non-backtracking engine: Google's re2 library (which Russ Cox helped write, available in Python as google-re2) guarantees linear time in the input length, in exchange for not supporting backreferences. For untrusted inputs, this is the safer default.

Six worked examples

# 1. Strip trailing whitespace and collapse internal runs of spaces
re.sub(r'\s+', ' ', text).strip()

# 2. Parse an ISO date
m = re.fullmatch(r'(?P<y>\d{4})-(?P<m>\d{2})-(?P<d>\d{2})', s)

# 3. Extract every quoted string (allowing escaped quotes inside)
re.findall(r'"((?:[^"\\]|\\.)*)"', source)

# 4. Match a "loose" email (good enough for log scraping, not RFC-correct)
re.findall(r'[\w.+-]+@[\w-]+\.[\w.-]+', logs)

# 5. Find Python identifiers (after a function definition)
re.findall(r'\bdef\s+([A-Za-z_]\w*)', source)

# 6. Normalise a phone number to E.164 (UK)
def to_e164(s: str) -> str | None:
    digits = re.sub(r'\D', '', s)
    if digits.startswith('0'):
        return '+44' + digits[1:]
    if digits.startswith('44'):
        return '+' + digits
    return None
Worked example: parsing a log line

The input is one line of an Apache common-log-format access log:

192.168.1.42 - alice [17/May/2026:14:32:01 +0100] "GET /api/v1/score HTTP/1.1" 200 1842

The goal is to extract IP, user, timestamp, method, path, status, and bytes into named groups. The regex, written verbosely:

LOG = re.compile(r""" ^ (?P<ip>\d{1,3}(?:\.\d{1,3}){3})\s+ -\s+ (?P<user>\S+)\s+ \[(?P<ts>[^\]]+)\]\s+ "(?P<method>[A-Z]+)\s+(?P<path>[^\s"]+)[^"]*"\s+ (?P<status>\d{3})\s+ (?P<bytes>\d+) $ """, re.VERBOSE)

Notice three deliberate choices. (1) The IP uses \d{1,3}(?:\.\d{1,3}){3}, a non-capturing group with a fixed quantifier; this is the right shape for "four octets separated by dots" without capturing each one separately. (2) The timestamp is captured as the entire bracketed string; parsing the date itself is a separate concern, handled by datetime.strptime on the captured string. (3) The user agent and referrer are skipped via [^"]* rather than trying to match every detail; a regex that tries to validate everything is harder to maintain than two regexes that handle two concerns.

Step 5

Synthesis and what's next

Regex is the smallest standard tool in the engineer's toolbox that solves a large class of problems: pattern matching, lightweight extraction, search-and-replace, and validation against simple formats. The six constructs (literal, class, quantifier, anchor, alternation, group) compose to express every regular language, and the Python re module gives you the API in five functions. Most working regexes are a dozen characters long; a complicated one that has been through code review is two dozen lines of re.VERBOSE, with comments.

The cost of fluency is one afternoon of practice plus a permanent reference card; the saving is every time you would otherwise have written a state machine by hand. The cost of over-use is reaching for a regex where a parser is the right answer; the discipline is to know the boundary (Chomsky's hierarchy) and to step over it deliberately. For HTML, JSON, and source code, use a parser; for log lines, identifiers, dates, and "does this string look like X", use a regex.
