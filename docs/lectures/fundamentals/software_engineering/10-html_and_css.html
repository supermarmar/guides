HTML, CSS, and the visual layer

Every documentation pipeline, every Markdown engine, every Jupyter renderer, eventually emits HTML and styles it with CSS. This lecture is the practical, working-analyst's view of that stack: the document tree, the cascade, web fonts, SVG, KaTeX, and the syntax-highlighting layer, with attention to the parts that actually break when a doc site goes wrong.

Lecture 10 of 16 Reading time, 50 minutes Part III: documentation
Step 1

The 30-second version

HTML (HyperText Markup Language, Tim Berners-Lee, 1990) is the document model of the web: a tree of nested elements with semantic tags. CSS (Cascading Style Sheets, Håkon Wium Lie, 1994) is the stylesheet language that decorates that tree: selectors target elements, declarations set properties, and a deterministic cascade resolves conflicts. Together they are the rendering target for almost everything in the documentation toolchain. Markdown compiles to HTML; MkDocs and Sphinx emit HTML; the Jupyter notebook displays HTML; a PDF produced by Pandoc started life as HTML. Knowing how the stack works is the difference between a documentation site that you can debug and one that you cannot.

The author of documentation rarely writes HTML or CSS by hand. The Markdown engine writes it for them. What the author does is configure the toolchain (theme, fonts, math, syntax highlighting, custom call-outs) and, when something renders wrong, read the rendered HTML and the applied CSS to diagnose the problem. That diagnostic skill is the goal of this lecture. By the end you should be able to open the browser's developer tools on any documentation page in this course, identify the elements, identify the rules styling them, and change the result.

The five layers that matter in practice are the document tree (HTML structure and semantic elements); the cascade (CSS selectors, specificity, and inheritance); the typographic stack (web fonts and the rules that load them); SVG (the vector-graphics dialect that lives inside HTML, used for the figures in lectures 7 and 8); and the two add-ons that almost every technical site needs, KaTeX for mathematics and Prism (or one of its rivals) for syntax highlighting.

Feynman test A web page is a tree, a stylesheet, and a renderer. The tree (HTML) says what the elements are. The stylesheet (CSS) says how they look. The renderer (your browser) walks the tree, looks up every applicable rule, resolves conflicts by the cascade, and paints the result. If you can describe what happens to the heading <h1>Introduction</h1> on its way from source to screen, you can hold a useful opinion on every layout, font, or syntax-highlighting question.
What's beyond the syllabus The deep reason HTML and CSS endure, after thirty-five years, is that they are declarative. The author describes what the document is, not how to draw it. The browser, the screen reader, the search-engine crawler, the e-reader, and the PDF converter all read the same source and adapt it to their medium. A page that renders well on Chrome usually also renders well in Reader Mode, in Pocket, in EPUB, and as a print PDF, because the same semantic structure carries through. The discipline behind a good documentation site is the same discipline behind a good Markdown source: write the meaning, let the renderer choose the appearance.
Step 2

Why this matters

The first reason is debugging. Every Markdown-to-site pipeline produces HTML that the browser then styles. When a heading is the wrong size, a code block does not highlight, a table overflows the page, or a diagram renders blank, the diagnosis lives in the rendered HTML and the applied CSS. The right-click "Inspect Element" view in any modern browser is the most useful documentation tool you will ever learn. Without HTML literacy, you are reduced to changing settings at random and hoping; with it, you read the page, find the broken rule, and fix it.

The second reason is extension. The MkDocs Material theme is excellent out of the box, but every team eventually wants something it does not ship: a call-out class for a regulatory citation, a print stylesheet that hides the navigation, a custom Mermaid theme that matches the corporate palette. All of these are short pieces of CSS added in one file. A team that cannot read CSS treats the theme as a black box; a team that can extends it in an afternoon. The same applies to Sphinx, Jupyter, and any rendering surface you do not own outright.

The third reason is durability. The MkDocs theme of 2018 is not the MkDocs theme of 2026. Themes deprecate, plugins break, and corporate brand standards change every five years. The asset that survives is the underlying HTML structure: semantic tags, accessible markup, clean section hierarchy. A site whose Markdown produces good HTML can be re-themed in a day. A site whose Markdown depended on theme-specific hacks needs to be rewritten. Lehmann's first law of software evolution applies to documentation: anything that is used must change, and the structures that change cheaply are the ones built on durable foundations.

Step 3

The mental model

The document tree

An HTML document is a tree. The root is the <html> element. Inside it, <head> contains metadata (title, links to stylesheets, font preconnect hints) and <body> contains the visible content. Inside the body, elements nest: a <section> wraps a heading and paragraphs, a <figure> wraps an image and its caption, a <table> wraps rows of cells. The browser parses the source linearly, builds the tree in memory (the DOM, document object model), and from then on every layout and styling decision is made by walking the tree.

The tree has structural elements (containers like section, article, nav, header, footer, main, aside), text-level elements (h1 to h6, p, ul, ol, li, blockquote), and inline elements (strong, em, code, a, span). The structural tags are not decoration; they are how screen readers, search-engine crawlers, and reading-mode tools understand the page. A site whose Markdown engine produces semantically correct HTML is automatically accessible, indexable, and printable; a site whose Markdown produces a wall of <div> tags is none of those things.

The cascade

CSS attaches style to the tree. A CSS rule has a selector and a block of declarations. The selector says which elements the rule applies to; each declaration is a property: value pair. The same property can be set by multiple rules for the same element, and the cascade resolves the conflict.

/* selector { property: value; property: value; } */
section h2 {
    font-size: 1.4rem;
    font-weight: 600;
    color: var(--charcoal);
    margin-block: 2rem 0.5rem;
}

The resolution order for conflicting declarations is, in priority: (1) any rule marked !important, (2) inline styles on the element itself, (3) ID selectors, (4) class and pseudo-class selectors, (5) element selectors. Within the same specificity tier, the later rule wins. This is the specificity hierarchy, and it is the second-most-common source of "why isn't my CSS applying?" bugs. The first is forgetting that some properties (font, colour) are inherited from the parent, while others (margin, padding, border) are not.

Specificity. A four-part score (inline, IDs, classes, elements) computed for every CSS selector; the rule with the higher score wins. Roughly: #hero beats .hero beats section. !important trumps the whole hierarchy and is therefore the last weapon, not the first.
The box model. Every element on the page is a rectangle with four nested boxes: content, padding, border, margin. Setting width: 200px sets the content box only; the padding and border add to the final rendered width unless box-sizing: border-box is in effect. The latter is the modern default and is set globally in almost every modern stylesheet, including the one for this course.

Layout: flexbox and grid

Until 2017, CSS layout was a workaround. Two-column pages were built with floats; centred elements were built with table tricks. The modern answer is two layout modes that solve the problem properly. Flexbox (2012, widely supported by 2016) arranges items in one dimension, with rules for spacing, alignment, and wrapping. CSS Grid (2017) arranges items in two dimensions, with named tracks and explicit placement. The rule of thumb is: a row of items uses flexbox, a page layout with sidebars uses grid. Together they cover every layout this course needs.

/* Three-card row, equal columns, gap between them. */
.cards {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
    gap: var(--s-lg);
}

/* Header bar, items pushed to opposite ends. */
.lecture-header .meta {
    display: flex;
    justify-content: space-between;
    align-items: center;
    gap: var(--s-md);
}
Step 4

The detail

HTML, by structure

The skeleton of every HTML document is fixed: a doctype, a root element, a head with metadata, and a body with content.

<!doctype html>
<html lang="en-GB">
<head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Lecture 9: HTML, CSS, and the visual layer</title>
    <link rel="stylesheet" href="lecture.css" />
</head>
<body>
    <main>
        <section>
            <h1>Heading</h1>
            <p>A paragraph.</p>
        </section>
    </main>
</body>
</html>

The lang attribute on <html> tells the browser the natural language (en-GB here; screen readers and hyphenation rules use it). The two <meta> tags are non-negotiable: the first declares UTF-8 encoding, the second tells mobile browsers not to scale the page to desktop width. The <title> appears in the browser tab and in search results. The <link> attaches the stylesheet.

The semantic tags inside <body> matter more than they look. <header>, <nav>, <main>, <article>, <section>, <aside>, and <footer> tell tools (screen readers, reading-mode plugins, search-engine crawlers) which part of the page is which. A page built entirely of <div> elements is, to all of those tools, indistinguishable from a sheet of paper turned into HTML. The course pages here use one <header>, one <main>, one <footer>, and a <section> per step of the lecture; that structure is what allows Reader Mode to extract the article cleanly.

ElementRoleWhen the renderer reads it
<header>Introductory content for a page or sectionSkipped to "main" content by accessibility tools
<main>The unique primary content of the pageTarget of the "skip to content" link
<article>A self-contained piece of content (a post, a lecture)Reader Mode extracts this
<section>A thematic grouping with its own headingBuilds the page outline
<nav>Navigation blockScreen readers announce as a landmark
<figure> / <figcaption>A diagram or image with its captionCaption announced alongside image alt-text
<blockquote>An extended quotationIndented and stylistically set apart
<code> / <pre>Code inline; preformatted code blockMonospace font, syntax-highlighter target

CSS, by mechanism

A CSS stylesheet has four moving parts: selectors (what to match), declarations (what to set), the cascade (which rule wins), and custom properties (variables that hold reusable values). The last is the part that turns a stylesheet from a list of rules into a design system.

A custom property is declared with a leading double dash and used through the var() function. The course stylesheet declares its palette this way, in the :root selector at the top of the file, so the same purple appears in every component without ever being repeated.

:root {
    --primary:        #5B47E0;
    --charcoal:       #37352F;
    --hairline:       #E8E6E1;
    --r-md:           8px;
    --s-md:           16px;
    --sans:           'Inter', system-ui, sans-serif;
    --mono:           'JetBrains Mono', ui-monospace, monospace;
}

.callout {
    background: var(--primary);
    color: white;
    border-radius: var(--r-md);
    padding: var(--s-md);
    font-family: var(--sans);
}

The benefit is immediate: change the value of --primary in one place, and every component that references it updates. The design tokens for this course (Notion-inspired palette, the 8/12/16 radius scale, the 4-then-8 spacing scale) are all variables of this kind. Dark mode, when added later, is a matter of redefining the variables inside a @media (prefers-color-scheme: dark) block.

Typography and web fonts

Default browser fonts are unattractive and inconsistent across operating systems. The standard solution is a web font: a typeface loaded over the network from a font hosting service (Google Fonts, Adobe Fonts, Bunny Fonts) or self-hosted from the project's own assets. The course uses two: Inter (Rasmus Andersson, 2017) for body text and headings, and JetBrains Mono (JetBrains, 2020) for code.

<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
<link rel="stylesheet"
      href="https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600;700&family=JetBrains+Mono:wght@400;500&display=swap" />

The two preconnect hints tell the browser to open a TCP connection to Google Fonts before the stylesheet is needed; this typically saves 100 to 300 ms on first paint. The display=swap directive tells the browser to render text in a fallback font immediately and swap in the web font when it arrives, rather than leaving the text invisible. Without that flag, slow networks produce the dreaded flash of invisible text (FOIT); with it, you get the milder flash of unstyled text (FOUT), which is the trade most teams prefer.

The pragmatic font stack always includes system fallbacks at the end, so the page is readable even if the web font fails entirely:

font-family: 'Inter', -apple-system, system-ui, 'Segoe UI', Helvetica, sans-serif;

SVG: vectors inside HTML

SVG (Scalable Vector Graphics, W3C 2001) is an XML dialect for vector drawing. It lives inside HTML; the lectures in this course use it for every diagram that is not a Mermaid block. An SVG element has a viewBox (the internal coordinate system), some shapes (rect, circle, path, line), and text. The pipeline figure earlier in this lecture is one of these. The benefits of SVG over a PNG are that it scales to any size without pixellation, is searchable, can be styled with CSS, and is small in bytes for line art.

<svg viewBox="0 0 200 80" xmlns="http://www.w3.org/2000/svg"
     role="img" aria-label="A labelled box">
    <rect x="20" y="20" width="160" height="40"
          fill="var(--tint-lavender)" stroke="var(--primary)"
          stroke-width="2" rx="6" />
    <text x="100" y="46" text-anchor="middle"
          font-family="Inter" font-size="12" fill="#3D2EB5">
        Labelled box
    </text>
</svg>

The role="img" and aria-label attributes make the SVG announce itself sensibly to screen readers. The rx attribute on the rectangle gives a rounded corner. The fill can reference a CSS variable, which means the same SVG palette automatically follows the rest of the design system.

KaTeX: maths rendered in the browser

Native HTML has no mathematical typesetting. KaTeX (Khan Academy, 2014) and the older MathJax (American Mathematical Society, 2009) fill the gap. Both read LaTeX-flavoured maths source and emit HTML and CSS that the browser then renders. KaTeX is faster, smaller, and rendered server-side or in one pass at page load; MathJax is more complete, supports more LaTeX features, but is slower. KaTeX is the right default for almost every documentation site, including this course.

<!-- KaTeX assets, loaded in the head -->
<link rel="stylesheet"
      href="https://cdn.jsdelivr.net/npm/katex@0.16.11/dist/katex.min.css" />
<script defer src="https://cdn.jsdelivr.net/npm/katex@0.16.11/dist/katex.min.js"></script>
<script defer src="https://cdn.jsdelivr.net/npm/katex@0.16.11/dist/contrib/auto-render.min.js"></script>

With the auto-render extension configured to recognise $...$ for inline maths and $$...$$ for display maths, any LaTeX inside those delimiters is rendered automatically when the page loads. The A-IRB capital formula in the Markdown lecture, for example:

$$K = LGD \cdot \left[ \Phi\!\left( \frac{\Phi^{-1}(PD) + \sqrt{R}\,\Phi^{-1}(0.999)}{\sqrt{1-R}} \right) - PD \right]$$

is one LaTeX source line in the Markdown, and KaTeX produces the styled result you see above. The maths renders client-side in a few milliseconds; the source is searchable in the raw HTML. The Sphinx and MkDocs ecosystems each have a configuration switch that turns on KaTeX (or MathJax) for an entire site.

Syntax highlighting

A fenced Markdown code block, by default, renders as plain monospace text. Colourised, language-aware highlighting is a separate step performed by a JavaScript library: Prism (Lea Verou, 2012), highlight.js (Ivan Sagalaev, 2006), or the newer Shiki (Anthony Fu, 2020, Vue ecosystem). Prism and highlight.js run client-side at page load; Shiki runs server-side at build time, producing pre-highlighted HTML, which renders faster and never flashes unstyled.

<link rel="stylesheet"
      href="https://cdn.jsdelivr.net/npm/prismjs@1.29.0/themes/prism.min.css" />
<script defer src="https://cdn.jsdelivr.net/npm/prismjs@1.29.0/prism.min.js"></script>

Prism reads any <pre><code class="language-python">...</code></pre> block on the page and rewrites the inner HTML with one <span> per token, each tagged by syntactic role. The accompanying stylesheet colours the spans. The course can write a one-line custom theme by overriding the CSS variables Prism exposes (--prism-string, --prism-keyword, etc.), keeping syntax colours in step with the rest of the palette.

Common pitfall Syntax-highlighting libraries that run client-side cause a visible flash on first load: the code appears in plain text, then re-paints with colour a few milliseconds later. The fix is one of three options: (1) move highlighting to build time with Shiki or a Pandoc filter; (2) set the code block's background to match the highlighter's theme so the flash is invisible; (3) accept the flash and prioritise smaller bundle size. The trade-off is real; the choice depends on how busy the site's code blocks are.

Responsive design and print stylesheets

A documentation site is read on phones, on laptops, and as PDFs. Two CSS features handle the variation. Media queries let a stylesheet apply different rules depending on the viewport: a navigation column hides below a tablet width; a table switches to a stacked layout on mobile. Print stylesheets are a special media query (@media print) that hides everything that does not belong on paper (navigation, footer, dark backgrounds) and tunes typography for ink.

/* Tablet and narrower: the nav becomes a top bar */
@media (max-width: 900px) {
    .layout { grid-template-columns: 1fr; }
    .sidebar { display: none; }
}

/* Print: hide chrome, use serif body, switch links to footnotes */
@media print {
    .lecture-header, .lecture-footer, nav { display: none; }
    body { font: 11pt/1.45 Georgia, serif; color: #000; }
    a::after { content: " (" attr(href) ")"; font-size: 9pt; }
}

The print-stylesheet trick is the one most documentation teams forget. A lecture page like this one prints to PDF in two clicks if the rules are right, and prints into an ugly mess if they are not. The course stylesheet ships with a minimal print block; the test is to open the print preview pane and confirm the page comes out clean.

Worked example: a custom call-out for regulatory citations

Worked example: adding a "Regulation" call-out class

The course uses several call-out classes (feynman, insight, warn) defined in lecture.css. Suppose the brief is to add a new one, regulation, for inline citations of Basel rules, IFRS 9 paragraphs, or CRR articles. The reader should see a soft yellow background, a green left border, and a small "REG" tag in the top-left corner.

Step 1 (semantic HTML). Decide what the markup looks like in a lecture file. A call-out is a <div> with two classes: the generic callout and the specific regulation. Inside, a <span class="tag"> for the corner badge and the body text.

<div class="callout regulation">
    <span class="tag">Regulation</span>
    The 12-month PD floor of 0.03% is CRR Article 160(1).
</div>

Step 2 (CSS). The generic callout class already sets padding, border-radius, and margins. The job is to override the colours.

.callout.regulation {
    background: var(--tint-yellow);
    border-left: 4px solid var(--success);
    color: var(--charcoal);
}
.callout.regulation .tag {
    background: var(--success);
    color: white;
    font-size: 0.7rem;
    font-weight: 600;
    text-transform: uppercase;
    letter-spacing: 0.05em;
    padding: 2px 8px;
    border-radius: var(--r-xs);
}

Step 3 (verify the cascade). The new .callout.regulation rule has the same specificity as .callout.feynman and the others, so the order in lecture.css matters: define regulation below the generic callout rules. Open the page, right-click the call-out, choose "Inspect", and confirm that the computed background is #FBF1D4 (the resolved value of --tint-yellow).

Step 4 (responsive and print). On narrow screens the call-out should not break the line layout; the existing .callout rule already handles that. In print, the green border should remain visible because it carries information; the existing print stylesheet keeps borders, so nothing extra is needed.

Step 5 (commit and use). One CSS rule, eight lines of code, zero JavaScript. The new call-out is now available across the course; every lecture can cite a Basel rule with one line of HTML.

Step 5

Synthesis and what's next

HTML is the structure, CSS is the presentation, and together they are the rendering target of every documentation pipeline you will ever touch. The author of documentation rarely writes HTML by hand; the Markdown engine, the Sphinx builder, the Jupyter renderer, and the diagram tools all produce it on their behalf. The skill is to read what they produce, debug it when it breaks, and extend it when the toolchain stops short of what the team needs. Five layers carry that responsibility: the document tree, the cascade, the typographic stack, SVG for vector figures, and the KaTeX-and-Prism duo for maths and code colouring.

The deeper point is that the visual layer is just another part of the docs-as-code stack. Custom call-outs are CSS files in the repository. Themes are stylesheet overrides. Brand changes are token edits. The discipline is the same one as for prose and diagrams: text source, version control, pull-request review, CI build. The next lecture turns to the third documentation surface, the Jupyter notebook, where the prose-code-output triple becomes one file and the reproducibility problem comes into sharp focus.
