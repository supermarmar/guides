Jupyter notebooks and the reproducibility problem

A notebook interleaves prose, code, and output in a single file. It is the medium in which most modern data analysis is actually done, and it is also the medium most likely to produce a result no one can reproduce a year later. This lecture covers what a notebook is, why reproducibility is so brittle, and the discipline plus tooling (jupytext, papermill, nbstripout, Quarto, Marimo) that puts the artefact back on a defensible footing.

Step 1

The 30-second version

A Jupyter notebook (Fernando Pérez and Brian Granger, 2014; descended from IPython, 2001) is a JSON file containing an ordered list of cells. A cell is either Markdown prose or executable code; running a code cell produces output (text, tables, plots), which is stored back in the file alongside the source. The file extension is .ipynb. The notebook is opened in a kernel (a Python or R or Julia process), and cells are executed in any order the author chooses. The combination of prose, code, and rendered output in one file is what makes the notebook so useful for exploratory analysis and so hard to treat as a repeatable artefact.

The pathology that makes notebooks problematic is hidden state. A cell that defines x = 1, then x = 2, then is deleted, leaves x bound to 2 in the running kernel; the notebook file no longer mentions x at all, but every later cell that uses x still works. A reader who restarts the kernel and runs the cells top-to-bottom gets a NameError on a line that, by inspection, looks fine. Pimentel et al.'s (2019) survey of 1.16 million GitHub notebooks found that only 24% executed end-to-end without error and only 4% produced the same output as the committed version. The artefact is unreliable by default.

The response is a layer of discipline and a layer of tooling. The discipline is restart-and-run-all: a notebook earns the right to be shared only after it has been re-executed from a clean kernel and shown to produce the same outputs. The tooling layer has four parts: jupytext pairs the .ipynb with a plain .py that diffs cleanly in git; nbstripout removes outputs before commit so the merge history is reviewable; papermill parametrises a notebook for batch execution; nbconvert renders the notebook to HTML, PDF, or slides for sharing. The two modern alternatives are Quarto (Posit, 2022), which treats notebooks as one input among many, and Marimo (2023), which rebuilds the notebook from first principles so hidden state cannot exist.

Feynman test A notebook is a JSON file whose order of cells, on disk, is not the order of execution, in the kernel. The kernel remembers everything that was run; the file remembers everything that was saved. Anyone, including a future version of you, who opens the file and presses "run all" is running the cells in file order on a fresh kernel, which is rarely the order in which the author originally produced the outputs they see. If you can hold that gap in mind, you understand the entire reproducibility problem.
What's beyond the syllabus The deep tension behind notebooks is Knuth's idea of literate programming (Lecture 1), in which prose and code are interleaved deliberately, against the reality of exploratory programming, in which the cells get reordered, mutated, and abandoned as the author's understanding evolves. The notebook format does literate programming well and exploratory programming badly, but it is mostly used for the latter. Donoho (2017) describes the field this is producing as data science 2.0: a generation of analysts whose primary tool is a literate-programming environment used in an anti-literate way. The reproducibility crisis is the symptom; the cure is to admit that exploration and publication are different artefacts and tool them differently.
Step 2

Why this matters

The first reason is that notebooks are how data science actually happens. The Stack Overflow Developer Survey, the GitHub Octoverse, and the Kaggle State of ML reports all converge on the same finding: a majority of professional data scientists use notebooks as their primary working surface. Pandas dataframes, matplotlib plots, scikit-learn pipelines, and PyTorch experiments are all built and inspected in cells. Whatever the engineering objection is to notebooks, the format is not going away, and the only useful posture is to learn its failure modes and the tools that mitigate them.

The second reason is that risk modelling, regulatory work, and audit live or die on reproducibility. A credit-risk model whose calibration sits in a notebook that "ran last December" but does not run today is a model that cannot be defended. The CRR's IRB conditions on Article 174 require that the rating process be "consistent", a word the EBA's RTS interprets to mean "re-executable with the same inputs". A notebook that depends on the cells being run out of order, on a variable defined in a deleted cell, or on a kernel state from yesterday, fails that test silently. The auditor opens it, presses "restart and run all", and the model fails to fit. The remediation is not a methodology paper; it is engineering discipline.

The third reason is that the gap between notebooks and the engineering practices in the rest of this course is the principal source of bugs in data-science pipelines. The 2016 Sculley et al. paper "Hidden technical debt in machine learning systems" identified glue code and notebook-to-production translation as among the biggest contributors to ML-system fragility, and the situation has not changed since. Tests do not run on notebooks. Code review is hard on JSON. Continuous integration cannot tell whether a notebook works. The whole apparatus the previous lectures have built sits on top of .py files, not .ipynb files. Closing the gap is a measurable productivity win.

Step 3

The mental model

What a notebook actually is

A .ipynb file is JSON. The top-level structure is a dictionary with a list of cells, a kernel specification, and some metadata. Each cell has a type (code or markdown), a source string, an execution count (or null if never run), and, for code cells, a list of outputs. The outputs include text streams, error tracebacks, and rich representations (HTML for a dataframe, PNG bytes for a plot, LaTeX for a sympy expression). When you "open the notebook in Jupyter", you are opening the file in an editor that renders this JSON as cells and connects each code cell to a long-running kernel process.

{
  "cells": [
    {
      "cell_type": "markdown",
      "source": "# Calibrating PD on the consumer book"
    },
    {
      "cell_type": "code",
      "execution_count": 3,
      "source": "import pandas as pd\ndf = pd.read_parquet('book.parquet')",
      "outputs": []
    },
    {
      "cell_type": "code",
      "execution_count": 7,
      "source": "df.head()",
      "outputs": [ { "output_type": "execute_result", "data": { "text/html": "..." } } ]
    }
  ],
  "metadata": { "kernelspec": { "name": "python3" } },
  "nbformat": 4,
  "nbformat_minor": 5
}

Two consequences fall out of that file format. First, the file is a record of execution as well as source. The outputs are part of the artefact, which is why diff in git is unreadable for a notebook with changing plots: the binary-encoded PNG image is rewritten on every run. Second, the execution_count field records the order in which the cells were last run; out-of-order execution is encoded directly in the file (cell 1 has count 3, cell 2 has count 7) and is invisible in the rendered view unless you look at the small bracket in front of each cell.

The three failure modes

Almost every reproducibility incident with notebooks is one of three failure modes.

Hidden state. A name in the kernel that no longer appears in any cell. The classic origin is a cell defined a variable, the cell was deleted (or its contents replaced), but the kernel still holds the binding. Later cells use the binding, look correct, and produce output. On a fresh kernel, the same notebook fails.

Out-of-order execution. The cells were run in a different order than they appear. Imagine cell 5 was run before cell 3, perhaps because the author was experimenting. The output of cell 5 reflects an earlier state of cell 3; the rendered notebook shows cell 5's output, but a reader running top-to-bottom gets a different result. The execution_count brackets show the order, but few readers notice.

Environment drift. The notebook was run a year ago against pandas 1.3 and scikit-learn 0.24. The repository today resolves to pandas 2.2 and scikit-learn 1.4. Some API has changed, some default has shifted, and the notebook either errors or produces a subtly different result. The fix lives in Lecture 12 (project setup and dependency management); the notebook itself cannot defend against it.

The four-stage maturity ladder

Where a team sits on the notebook-reproducibility question can usually be placed on a four-rung ladder. Rung 1, anarchic: notebooks committed with stale outputs, no environment file, last-run-by-someone state. Rung 2, hygienic: outputs stripped before commit, kernel restart enforced before sharing. Rung 3, paired: every notebook has a parallel .py twin via jupytext, so git diff is readable. Rung 4, executable: notebooks run end-to-end in CI on every push, producing the same outputs as the committed version (or failing the build). Most teams sit on Rung 1; the engineering work in this lecture is the move to at least Rung 3.

Reproducibility. The property that the same inputs, in the same environment, produce the same outputs every time. A notebook is reproducible if a fresh kernel, running the cells in file order, on the pinned environment, lands on the committed outputs.
Restart-and-run-all. The standard hygiene check before sharing a notebook: kill the kernel, restart it, and execute every cell in order. If the result differs from the committed version, the notebook is not reproducible and is not ready to share.
Step 4

The detail

jupytext: pairing with a plain .py file

Jupytext (Marc Wouts, 2018) is a Jupyter plugin that pairs every .ipynb with a "twin" plain-text file: a .py script with special cell-delimiter comments, or a Markdown file with code-fence cells. Saving the notebook saves both files; opening either re-syncs the pair. The .py twin is what gets reviewed in pull requests, because it diffs as a normal Python file; the .ipynb can be excluded from git or kept with outputs stripped.

pip install jupytext

# pair an existing notebook on disk
jupytext --set-formats ipynb,py:percent analysis.ipynb

# convert in either direction at any time
jupytext --sync analysis.ipynb

The py:percent format produces a file in which each cell is delimited by a # %% comment. VS Code recognises these as runnable cells in its Python extension; PyCharm has a similar interactive cell mode. The result is that the same artefact is a notebook in Jupyter and a script in the IDE; the team picks whichever is right for the task. For credit-risk modelling work, the .py twin is the artefact that ships into production; the .ipynb is the exploration log.

# %% [markdown]
# # Calibrating PD on the consumer book

# %%
import pandas as pd
df = pd.read_parquet('book.parquet')

# %%
df.head()

nbstripout: stripping outputs before commit

nbstripout (Florian Rathgeber, 2014) is a git filter that strips the outputs field from every .ipynb on its way into a commit. The notebook on disk keeps its outputs; the version in git does not. The benefit is that the diff between two commits of a notebook reflects changes in source, not changes in PNG bytes; the cost is that a reviewer cannot see the rendered output without opening the notebook locally.

pip install nbstripout
nbstripout --install --attributes .gitattributes

The combination of jupytext (so the diff is on the .py twin) and nbstripout (so the .ipynb diff is at least small) is the standard hygiene baseline. For teams that want output preserved for review, the alternative is to commit a rendered HTML version of the notebook alongside the source, generated by nbconvert on every push.

papermill: parametrised execution

Papermill (Netflix, 2017) treats a notebook as a parametrisable function. The author marks one cell as the "parameters" cell (a tagged metadata flag); papermill replaces that cell's contents with caller-supplied values, executes the notebook from scratch, and writes a new .ipynb with the resulting outputs. This is the pattern Netflix's data platform uses to run thousands of notebooks per day in production, each parametrised by date, region, or model version.

papermill calibrate_pd.ipynb \
          output/calibrate_pd_2026Q1.ipynb \
          -p portfolio "consumer" \
          -p as_of_date "2026-03-31" \
          -p macro_scenario "central"

Papermill's promise is that a notebook can become a reproducible batch job without being rewritten as a script. In practice, the notebooks that papermill executes well are the ones that were written defensively in the first place: top-to-bottom executable, no hidden state, parameters at the top. A messy exploratory notebook is not made reproducible by adding papermill; papermill exposes the messiness.

nbconvert: rendering to HTML, PDF, slides

nbconvert (Jupyter project, 2015) is the rendering pipeline that turns a .ipynb into another format. The classic uses are HTML for sharing on a web page, PDF for inclusion in a model document, and reveal.js slides for presentation. nbconvert is the engine behind the GitHub notebook viewer and behind every "render this notebook as a webpage" feature in MkDocs Material.

jupyter nbconvert --to html      analysis.ipynb
jupyter nbconvert --to pdf       analysis.ipynb
jupyter nbconvert --to slides    analysis.ipynb --post serve

The HTML output is self-contained: the page can be opened locally or hosted on any static site. The PDF output requires a LaTeX installation (or Pandoc, as in Lecture 7), because PDF is produced via TeX intermediate. The slides output uses reveal.js; each Markdown heading becomes a slide.

Quarto: the modern alternative

Quarto (J. J. Allaire and Posit, 2022; quarto.org) is the descendant of R Markdown, generalised to Python, R, Julia, and Observable. A Quarto document is a .qmd file, which is Markdown with executable code chunks. The Quarto CLI executes the chunks (against a Jupyter kernel under the hood, in the Python case), substitutes the outputs, and renders to HTML, PDF, EPUB, Word, slides, or a website. Unlike Jupyter, the source is plain-text Markdown by design; unlike RMarkdown, the language is not tied to R.

---
title: "Calibrating PD on the consumer book"
author: "Risk modelling team"
format:
  html:
    toc: true
    theme: cosmo
jupyter: python3
---

## Loading the data

```{python}
import pandas as pd
df = pd.read_parquet('book.parquet')
df.head()
```

Quarto's appeal is that the source is the same Markdown that the rest of the documentation site uses. There is no JSON file. Diff and review work normally. The CLI is a single binary. For teams whose Jupyter use is mostly "literate documentation around a calculation", Quarto is the cleaner answer than the jupytext-plus-nbstripout combination. The cost is that interactive exploration is less smooth than in JupyterLab; Quarto is better for finished artefacts than for the discovery phase.

Marimo: rebuilding the notebook from scratch

Marimo (Akshay Agrawal, 2023; marimo.io) is the most aggressive response to the hidden-state problem. A Marimo notebook is a .py file containing decorated cell functions. The runtime tracks the dependency graph between cells: when cell A is edited, every cell that reads a name A defined is automatically re-executed; cells that no longer reference a name are released. By construction, the kernel state matches the file. Out-of-order execution and hidden state are unrepresentable.

import marimo as mo

@mo.cell
def __():
    import pandas as pd
    return pd

@mo.cell
def __(pd):
    df = pd.read_parquet('book.parquet')
    return df

@mo.cell
def __(df):
    df.head()

The trade-off Marimo makes is that the per-cell ergonomics of "set a variable, then mutate it three times" no longer work; every cell's outputs are a pure function of its inputs. For teams used to Jupyter, this feels restrictive at first and liberating afterwards. The format is also new (2023), so the ecosystem of extensions, kernels, and integrations is still shallow.

Common pitfall The biggest mistake when adopting any of these tools is to try to add them to an existing messy notebook. jupytext on a notebook with twenty out-of-order cells produces a .py that is just as confusing, only now in script form. papermill on a notebook with hidden state simply re-executes the file and produces a broken output. The order of operations is: first restart-and-run-all, fix the failures, get the notebook clean; then add the tooling. Tooling exposes mess; it does not clean it up.

Notebooks in continuous integration

The discipline of "notebooks must execute end-to-end in CI" is the move from Rung 3 to Rung 4 on the maturity ladder. The pattern is the same as for tests: a GitHub Actions job, on every push, runs jupyter nbconvert --execute on every notebook in the repo and fails the build if any cell errors. For notebooks that take longer than a CI step's tolerance, papermill produces the same effect with parametrised, shorter-running inputs.

# .github/workflows/notebooks.yml
name: Execute notebooks
on:
  pull_request:
    paths: ['notebooks/**/*.ipynb', 'notebooks/**/*.py']

jobs:
  run:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }
      - run: pip install -r requirements.txt jupyter nbconvert
      - run: |
          for f in notebooks/*.ipynb; do
            jupyter nbconvert --to notebook --execute "$f" \
                              --output "/tmp/$(basename $f)"
          done

The job does not commit the executed outputs back to the repo; its purpose is the binary check "did every cell succeed". A team that runs this on every PR has a guarantee no team without it can offer: every notebook in the repo, on the trunk, is reproducible at the moment of merge.

Worked example: turning an exploratory notebook into a reproducible artefact

Worked example: cleaning up pd_calibration.ipynb

The notebook in question is two months old. It calibrates a PD model on the consumer book. The author (you, two months ago) ran the cells in roughly the right order, then went back and tweaked a feature engineering cell, never re-ran the cells below it, and committed the file with stale outputs. The new validator wants to reproduce the result. The remediation has five steps.

Step 1 (kernel restart and run all). Open the notebook, "Kernel → Restart and Run All". Three cells fail: one because of a name from a cell that was deleted last week (hidden state); one because the data file path has moved (environment drift); one because a pandas method was deprecated in 2.2 (environment drift). Note each failure.

Step 2 (fix the hidden state). Search the notebook for the orphaned name. Either restore the cell that defined it or remove the references. In this case, a feature called balance_log was computed in a deleted cell; restoring the one-line computation as cell 4 fixes the four cells below it.

Step 3 (pin the environment). Add a requirements.txt (or pyproject.toml, Lecture 11) listing pandas, scikit-learn, matplotlib, and statsmodels at the versions the notebook actually works against. Run pip install -r requirements.txt in a clean virtualenv to confirm.

Step 4 (pair with jupytext). Run jupytext --set-formats ipynb,py:percent pd_calibration.ipynb. The new pd_calibration.py is the file that will be reviewed; the .ipynb is for exploration. Add a .gitignore entry, or use nbstripout, to keep the JSON tidy.

Step 5 (CI). Add a one-job GitHub Actions workflow that runs jupyter nbconvert --execute pd_calibration.ipynb on every PR. The PR template now includes a line "All notebooks execute cleanly from a fresh kernel", which the CI job enforces automatically. The next time someone tweaks a feature engineering cell without re-running the rest, the build fails and the author is told.

The notebook is now reproducible, reviewable, and defensible. The investment was three hours; the gain is that the validator can re-run the calibration in the audit pack without phoning the original author.

Step 5

Synthesis and what's next

The Jupyter notebook is the medium in which most modern data analysis is done and the medium in which most reproducibility incidents happen. The mismatch is intrinsic: the file format records source and outputs in a way that does not enforce execution order or kernel cleanliness, and most authors do not work top-to-bottom by habit. The remediation is half discipline (restart-and-run-all before sharing) and half tooling (jupytext for diffs, nbstripout for hygiene, papermill for batch, nbconvert for rendering). The two newer alternatives, Quarto and Marimo, attack different parts of the problem: Quarto by treating the notebook as Markdown-with-code, Marimo by rebuilding the runtime so hidden state cannot exist.

For risk modelling work specifically, the rule that wins audits is unromantic: every notebook in the repository must execute end-to-end in CI, against a pinned environment, on every pull request. A team that enforces that rule has a documentation surface that survives validation, regulatory scrutiny, and the inevitable departure of the original author. The next lecture starts Part IV by taking the broader question seriously: how the project is set up so the environment, dependencies, and Python version are themselves reproducible. Notebook reproducibility, in that frame, is one application of a discipline that applies to the whole project.
