Auto-generated documentation and codewikis

The cheapest documentation is the kind a tool generates from the code itself. This final lecture covers the long-standing toolchain (Sphinx autodoc, MkDocs mkdocstrings, the docstring conventions that feed them), the more recent README-generation tools, and the 2024 generation of LLM-driven codewikis (DeepWiki, GitHub Copilot Workspace, Mintlify, Swimm) that have changed what is feasible to produce.

Step 1

The 30-second version

Auto-generated documentation is the documentation that the build extracts from the source code, rather than the documentation the team writes by hand. The original mechanism is the docstring (PEP 257, 2001): a string literal that is the first statement in a module, class, or function, available at runtime as the __doc__ attribute. A documentation tool reads the docstrings, formats them, and produces a website. The pattern is forty years old (Knuth's WEB system in 1984 was the first major example) and it has not gone out of fashion because the cost of a good docstring is small and the benefit, a reference page that is always in sync with the code, is large.

The Python toolchain has converged on two tools. Sphinx with its autodoc extension (Lecture 7) is the older standard, designed for library documentation and still dominant in the scientific-Python world. mkdocstrings (Timothée Mazzucotelli, 2019) is the MkDocs equivalent and the right answer for projects already on MkDocs Material. Both read the same docstrings, both support the same three docstring conventions (Google, NumPy, reStructuredText), both produce a reference section with one page per module that updates automatically as the code changes.

The new layer, since around 2024, is LLM-driven codewikis: DeepWiki (Cognition, 2025; deepwiki.com), GitHub Copilot Workspace, Mintlify, Swimm, and the long tail of "point this at your repo and we will generate a wiki" tools. The premise is that a language model can read an entire codebase and produce explanation-level documentation (the Diátaxis quadrant that is hardest to write by hand) on top of the existing reference and tutorials. The output is sometimes excellent and sometimes hallucinated; the discipline is to treat the LLM output as a draft, not as the final artefact, and to keep the human-authored documentation as the source of truth on intent.

Feynman test Auto-generated documentation is a compiler. The input is the source code (with docstrings, type hints, module structure). The output is a documentation site or a section of one. The author edits the input; the build runs the compiler; the site rebuilds. The reason the pattern works is that the input is co-located with the code it describes, and a code change that breaks the documentation will be obvious in the same pull request. If the docs and the code are in two different files, drift is the default; if they are in the same file, sync is the default.
What's beyond the syllabus The deep cultural shift, from "documentation is what you write after the code" to "documentation is what the code generates", parallels the shift in testing twenty years ago. Tests used to be a separate document; now they are code in the same repository, run on every commit. Documentation is on the same trajectory: the human-written prose layer is shrinking, the auto-extracted reference layer is growing, and the LLM layer (still new in 2025) is filling the explanation gap that neither of the others reaches. The future stable equilibrium is probably the same as for tests: a small layer of hand-written conceptual prose, a large layer of auto-generated reference, and a tooling layer that catches drift between them.
Step 2

Why this matters

The first reason is the cost ratio. A reference page that lists every public function in a module, with its signature, type hints, and docstring, takes a tool about 50 milliseconds to produce. The same page hand-written takes a person about thirty minutes, drifts within a month, and is wrong within a quarter. The argument for auto-generation is not aesthetic; it is the simple recognition that a tool can do this work much better than a person and never gets bored. Every minute spent hand-writing a reference page is a minute not spent on the higher-value documentation tasks (tutorials, explanations, decision records) the tool cannot produce.

The second reason is the drift problem that documentation is famous for. The "outdated documentation" finding in the Aghajani et al. (ICSE 2019) study cited in Lecture 7 is overwhelmingly about prose documentation that was correct once and is wrong now. Auto-generated reference cannot drift, because it is regenerated on every push. The same property holds for the docstring inside the function: a function whose body changes will usually have its docstring updated in the same review, because the reviewer can see them side by side. The mechanism is the same as the one that made tests trustworthy: keep the documentation close enough to the code that updating one without the other is awkward.

The third reason, specific to risk modelling, is that audit-grade model documentation is increasingly expected to be generated, not written. The PRA's SS3/24 paragraph 4.20 explicitly mentions "automated reproduction of model documentation" as evidence of model risk management maturity. The EBA's RTS on the IRB process expect a model card that can be regenerated from the model artefact. A team whose documentation lives in Confluence is doing this by hand once a year; a team whose documentation is the rendered output of a CI pipeline is doing it on every commit. The latter is cheaper, more accurate, and easier to defend.

Step 3

The mental model

The three layers of documentation

A complete documentation site has three layers, and they need different production methods. Recognising which layer a given page belongs to is the structural decision that drives every other choice.

The point Diátaxis (Lecture 7) makes about quadrants applies here in production terms. Reference (the "what does this return?" quadrant) is the cheapest to produce because the source already exists in the code. Tutorials (the "teach me how" quadrant) can be produced by running and rendering notebooks. Explanation (the "why is it this way?" quadrant) is the layer that needs human writing, because no part of the code records the rationale; this is where the team's effort should concentrate. Hand-writing reference pages is the wrong place to spend time.

The docstring contract

A docstring is a string literal placed as the first statement in a module, class, or function. At runtime it is available as the __doc__ attribute; at build time it is what autodoc or mkdocstrings reads. The PEP 257 convention says the docstring is the contract: what the function does, what arguments it expects, what it returns, what exceptions it raises. Three formatting conventions dominate.

Google style uses indented sections with capitalised headers. It is the most readable when viewing the source file. It is the recommended style for new Python projects in 2025 and the one this course uses.

def calibrate_pd(features: pd.DataFrame, outcomes: pd.Series,
                 regularisation: float = 0.0) -> LogisticModel:
    """Fit a logistic-regression PD model.

    Given a feature matrix and a binary default indicator, fit a
    logistic model with optional L2 regularisation, and return the
    fitted parameters along with calibration diagnostics.

    Args:
        features: Feature matrix, one row per account, one column
            per predictor. All columns must be numeric.
        outcomes: Binary default indicator (1 = defaulted within
            12 months, 0 = not). Must be the same length as
            features.
        regularisation: L2 penalty strength. 0 disables regularisation.
            Typical values: 0.01 to 1.0.

    Returns:
        A `LogisticModel` containing fitted coefficients, the
        intercept, and calibration metrics (AUC, KS, Brier).

    Raises:
        ValueError: If features contains non-numeric columns or if
            features and outcomes have different lengths.
    """
    ...

NumPy style uses underlined section headers, in the convention of the SciPy ecosystem. Slightly more verbose than Google, but ubiquitous in the scientific-Python libraries and supported by every tool.

reStructuredText style uses Sphinx field markers (:param x:, :returns:). Older, denser, and less readable in the source; still common in legacy projects. For new projects there is no reason to choose it.

The convention matters less than the consistency. A project that mixes styles produces ugly rendered docs and confuses parsers; a project that picks one and enforces it in the linter (ruff has D rules for docstring conventions) produces uniform reference pages with little ongoing effort.

Type hints as documentation

The type hint (PEP 484, 2014; Lecture 2) does part of the docstring's job automatically. A signature of def calibrate_pd(features: pd.DataFrame, outcomes: pd.Series, regularisation: float = 0.0) -> LogisticModel communicates the shapes of inputs and output without prose. The auto-doc tools render the types alongside the docstring, and modern conventions skip the type names in the Args: block because they would be redundant. The combination "type hints plus prose docstring" is the modern norm; the older pattern of "type names spelled out in the docstring" is on the way out.

autodoc. The Sphinx extension (and its mkdocstrings equivalent) that walks the project's source, extracts docstrings and signatures, and emits documentation pages. Pure mechanical extraction: the tool cannot improve a bad docstring, only render it.
Codewiki. The 2024-era category of LLM-driven documentation generators (DeepWiki, Mintlify, Swimm) that read a whole codebase and produce explanation-level prose. Distinct from autodoc, which only extracts what is already there; codewikis attempt to synthesise what is implied but not stated.
Step 4

The detail

Sphinx autodoc

Sphinx (Lecture 7) is the older of the two Python documentation tools and the standard for the scientific-Python ecosystem (NumPy, SciPy, pandas, scikit-learn). Its autodoc extension does the extraction; the napoleon extension parses Google- and NumPy-style docstrings; the sphinx_autodoc_typehints extension renders type hints. The minimum configuration in conf.py is six lines:

# docs/conf.py
extensions = [
    "sphinx.ext.autodoc",
    "sphinx.ext.napoleon",          # Google and NumPy docstring styles
    "sphinx_autodoc_typehints",     # render type hints in signature
    "myst_parser",                  # use Markdown not reStructuredText
]
autodoc_typehints = "description"   # types appear in the param description
napoleon_google_docstring = True
napoleon_numpy_docstring = False

The reference pages are then generated by a small Markdown stub (using MyST) that names the module:

## credit_risk_models.pd

```{eval-rst}
.. automodule:: credit_risk_models.pd
   :members:
   :undoc-members:
   :show-inheritance:
```

That five-line block produces a full reference page for the module, with one section per public function, the signature, the type hints, the docstring formatted, and inheritance diagrams for any class hierarchy. The build is one command (sphinx-build -b html docs/ site/), and the output is a static HTML site that can be hosted anywhere.

The pattern for a multi-module project is the sphinx-apidoc command, which walks the source tree and writes the stub for each module automatically; sphinx-apidoc is usually a step in the CI workflow that runs before sphinx-build. Read the Docs (readthedocs.org) is the free hosting service for Sphinx sites; it builds on every git push and serves versioned docs (one site per release tag).

mkdocstrings for MkDocs Material

For projects already using MkDocs Material (Lecture 7's recommendation), the equivalent extension is mkdocstrings. Configuration in mkdocs.yml:

plugins:
  - search
  - mkdocstrings:
      handlers:
        python:
          options:
            docstring_style: google
            show_source: true
            show_signature_annotations: true
            separate_signature: true
            merge_init_into_class: true

And in a Markdown page, a one-line directive embeds a function or module's reference inline:

# PD calibration

The training-time interface is `calibrate_pd`.

::: credit_risk_models.pd.calibrate_pd

For a worked example, see [the tutorial](../tutorials/calibrate.md).

The advantage of mkdocstrings over Sphinx, for a team already using Markdown, is that the same page can mix human prose and auto-extracted reference seamlessly: a paragraph of explanation, then the rendered function reference, then a follow-up sentence linking to a tutorial. Sphinx can do this too, but the syntax is heavier.

README generators and badges

The README.md at the root of every repository is, in some sense, the smallest documentation site. The README-generator category of tools (readme-gen, readme-md-generator, ai-readme, the various cookiecutter templates) attempts to scaffold a good README from project metadata: the name, the description, the install instructions, badge bars for CI status and coverage, a quick-start example. The output is rarely the final README, but it is a useful skeleton.

The badge convention deserves a mention. A README badge is a small SVG image rendered by a service (shields.io, codecov.io, github.io) that displays a status: green if CI is passing, the package version, the coverage percentage, the licence. Badges are syntactic sugar but they communicate at a glance: a contributor seeing a red CI badge knows the project is broken; seeing a coverage badge under 50% knows the test suite is sparse.

The 2024 generation: LLM-driven codewikis

The new layer, since 2024, is the LLM-driven codewiki: a tool that reads an entire repository and produces explanation-level documentation, the layer that autodoc cannot reach. The category leaders, as of 2025, are DeepWiki (Cognition, the team behind Devin; deepwiki.com), GitHub Copilot Workspace, Mintlify Docs (mintlify.com), and Swimm (swimm.io). The mechanism is broadly the same: the tool ingests the codebase, indexes it with embeddings, runs an LLM over each module to summarise it, walks the dependency graph to produce architecture descriptions, and renders the output as a static site. The user can then ask questions against the indexed corpus and get LLM-generated answers grounded in the code.

Two things are worth saying about the category. First, the output is genuinely useful: a 50,000-line codebase becomes navigable in a way that no human has time to produce by hand, and the architecture overviews are often clearer than what any individual developer could write. Second, the output also hallucinates: it confidently describes functions that exist but get used differently than the description claims, attributes design decisions that were never made, and asserts behaviour from signatures that the implementation contradicts. The discipline, as with every LLM-assisted artefact, is to treat the output as a draft. Use it to seed the documentation; do not promote it to the source of truth without human review.

Common pitfall The biggest mistake teams make with LLM codewikis is publishing the unreviewed output as the team's official documentation. Within a quarter, the team's understanding of the system has been replaced by the LLM's plausible-sounding but partly-fictional summary, because the latter is easier to find. The defence is to keep the human-authored explanation pages as the source of truth, treat the LLM site as a search-engine-style aid only, and update the human pages when the LLM surfaces something useful. The LLM is a research assistant; it is not the editor.

Architecture decision records (ADRs)

One specific kind of explanation documentation deserves its own pattern: the architecture decision record (Michael Nygard, 2011; "Documenting architecture decisions"). An ADR is a short Markdown file (usually under one page) recording one architectural choice: what was decided, what alternatives were considered, what the consequences are, what triggered the decision. ADRs live in docs/adr/ in the repository, numbered sequentially (0001-use-uv-for-dependency-management.md, 0002-squash-merge-as-default.md). They are append-only: a decision that is later reversed becomes a new ADR (0017-replace-uv-with-x.md) that supersedes the older one.

# ADR 0007: use Google-style docstrings

Status: Accepted

Date: 2025-08-12

## Context

Our docstring style was inconsistent across modules. Some used
Google style, some NumPy, some reStructuredText fields. The
linter could not enforce a single convention, and rendered docs
were ugly.

## Decision

We adopt Google-style docstrings everywhere. ruff is configured
with `pydocstyle.convention = "google"` and the D rules are
enabled.

## Consequences

- Existing NumPy- and rST-style docstrings need migration. We
  budget one engineer-day for this.
- mkdocstrings is configured with `docstring_style: google`.
- New contributors have a single style to learn.

ADRs are the most under-used piece of engineering documentation. They are cheap to write (twenty minutes per decision), they capture the rationale that no other layer of documentation does, and they make the next change easier because the original reasoning is recoverable. The 2024 LLM codewikis sometimes attempt to synthesise ADRs from commit history; the results are at the "useful starting point" level, not the "final artefact" level.

Documentation in CI

The same CI workflow that runs tests (Lecture 14) should also build the documentation, on every push, and fail the build if the documentation does not build cleanly. The pattern is the --strict flag in MkDocs (mkdocs build --strict fails on any warning) or the -W flag in Sphinx (sphinx-build -W treats warnings as errors). A broken link, a missing image, a docstring with a syntax error, all become build failures with names attached.

  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen --extra docs
      - run: uv run mkdocs build --strict
      - uses: actions/upload-pages-artifact@v3
        with: { path: site/ }

  deploy-docs:
    if: github.ref == 'refs/heads/main'
    needs: docs
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    steps:
      - uses: actions/deploy-pages@v4

The pattern: the docs job runs on every PR (catching breakages before merge), and the deploy-docs job runs only on main (publishing the site). The same pattern works for Sphinx with the sphinx-build command and the Read the Docs hosting service. A team that runs this pipeline has documentation that is, by construction, always green and always rebuilt.

Worked example: documenting the credit-risk-models project

Worked example: complete documentation site for the PD/LGD/EAD project

The project from Lecture 11 is now mature. The team wants a documentation site with three layers: reference (auto-generated from docstrings), tutorials (rendered from notebooks), and explanation (hand-written, including ADRs).

Step 1 (structure). Add a docs/ folder with the Diátaxis four-quadrant layout: tutorials/, how_to/, reference/, explanation/. The reference/ folder will be largely empty; each subpage is a one-line mkdocstrings directive pointing at a module.

Step 2 (docstrings). Enforce Google-style docstrings via ruff D rules in pyproject.toml. Run uv run ruff check --select D src/ and fix the failures. Budget half an engineer-day. The pre-commit hook catches drift from then on.

Step 3 (mkdocs config). Configure mkdocs.yml with the Material theme, the mkdocstrings plugin, the search plugin, and the navigation. Add a docs group to pyproject.toml with mkdocs-material, mkdocstrings, and mkdocs-jupyter.

Step 4 (reference pages). For each module, write a one-line stub: ::: credit_risk_models.pd.calibrate. Build locally with mkdocs serve; verify every public function appears with its signature and docstring.

Step 5 (tutorials). The team's existing exploration notebooks become tutorial pages. Configure mkdocs-jupyter to render .ipynb files inline. Add a CI step that re-runs the notebooks (Lecture 10) before the docs build so the rendered output is fresh.

Step 6 (explanation and ADRs). Write three explanation pages: "why we use IRB rather than standardised", "why our LGD uses workout method, not market", "how the staging logic interacts with IFRS 9 paragraph 5.5.4". Add the first six ADRs covering the key decisions to date.

Step 7 (CI deployment). Add the docs and deploy-docs jobs to the existing CI workflow. Configure GitHub Pages as the deployment target. After the next merge to main, the site is live at org.github.io/credit-risk-models/.

Step 8 (optional: codewiki). Run DeepWiki on the repository; review the generated output; copy the bits that are accurate into the explanation pages, discard the bits that are wrong. Re-run quarterly; treat the LLM output as a draft inspector that surfaces gaps in the human-written documentation.

The total investment is roughly one engineer-week. The recurring cost is the docstring discipline (enforced by ruff and pre-commit) and the rare ADR. The asset is a documentation site that always matches the code, has a coherent structure, and survives the departure of the original author.

Step 5

Synthesis and what's next

Auto-generated documentation is the documentation that the build extracts from the code, in contrast with the documentation that a person writes by hand. The mechanism (Sphinx autodoc or MkDocs mkdocstrings) reads docstrings and type hints and produces reference pages on every build, eliminating drift in the largest layer of any documentation site. The remaining layers, explanation and tutorials, are where human effort concentrates: hand-written prose for the rationale, rendered notebooks for the worked examples, ADRs for the decisions. The 2024 LLM codewiki tools are a new option for the explanation layer; they produce useful drafts and confident hallucinations in roughly equal measure, and they belong in the workflow as research assistants, not as editors.

This is also the last lecture of the course. Looking back at the fifteen, the spine is one idea: the artefacts of software engineering exist to support the team's theory of the system, and that theory dies if it cannot be re-read. Style and idiom make the code re-readable to the next developer. Tests, debugging, and profiling let the system be re-investigated under failure. Markdown, diagrams, HTML, notebooks, and auto-generated docs let the design be re-explained. Project setup, git, code review, and CI/CD make the changes re-runnable and re-defensible. Knuth, Naur, Brooks, Beck, and Humble & Farley are the canonical voices behind those threads; the rest is the working detail. The student of this course who comes back five years later, opens a project they have not touched in two years, and finds it still runnable, still readable, still extensible, is the student who took the course seriously. That is the only test the course was ever trying to set.
