Diagrams as code: Mermaid and friends

A diagram is the smallest unit of documentation that survives translation between people. This lecture covers the family of text-source diagram languages (Mermaid, PlantUML, Graphviz, D2), the rendering pipeline that turns them into pictures, and the editorial discipline that decides which kind of diagram earns a place on the page.

Lecture 9 of 16 Reading time, 45 minutes Part III: documentation
Step 1

The 30-second version

Diagrams as code is the practice of describing a diagram in a plain-text source file and letting a renderer produce the picture. The source lives in the repository alongside the prose, is reviewed in the same pull request, and is rebuilt by CI when something changes. Contrast the older workflow, in which a diagram is drawn in Visio or PowerPoint, exported to PNG, and pasted into Confluence, where it begins to rot the moment it is uploaded.

Four tools cover roughly nine in ten cases. Mermaid (Knut Sveidqvist, 2014) is a Markdown-friendly language for flowcharts, sequence diagrams, class diagrams, state diagrams, entity-relationship diagrams, and a handful of others. It is the diagram language GitHub renders natively inside fenced code blocks. PlantUML (Arnaud Roques, 2009) is the older, UML-rigorous predecessor, more verbose but with stronger semantics for software-engineering diagrams. Graphviz, by Stephen North and Emden Gansner at AT&T Bell Labs (1991), is the low-level layout engine that sits underneath much of the family. D2 (Alexander Wang, 2022) is the newest member, with a typed-language feel and a renderer that puts more thought into final-frame layout than the others.

The structural argument for all of them is the same: text is diffable, text is reviewable, text survives the death of any specific editor. The structural argument against is also the same: an automatic layout engine never makes the diagram a hand drawing would have made, and there are diagrams (a polished architecture poster, a marketing schematic) where a human placing the boxes is the correct answer. The art is choosing the right tool for the right diagram, and accepting that the gain from diffability usually outweighs the loss of typographic control.

Feynman test A diagram language is a compiler. The input is a description of nodes and edges (or actors and messages, or states and transitions). The output is a picture. The language constrains what you can say; the renderer decides where each shape lands. If you know what the language can express, what the renderer is free to change, and what survives version control, you can hold an opinion on every "should we use Mermaid or PlantUML" debate without rehearsing the syntax.
What's beyond the syllabus The deep reason diagrams matter, beyond aesthetics, is that they compress relations that prose cannot. Edward Tufte's argument in The Visual Display of Quantitative Information (1983) is that a good diagram has high data-ink ratio: every mark on the page carries information that is hard to convey in words. A flowchart of an approval workflow communicates branching faster than a five-paragraph description; an ER diagram communicates referential structure faster than a schema dump. The diagram is not decoration. It is the most compact representation of structural understanding the team has.
Step 2

Why this matters

The first reason is that diagrams rot faster than prose. Prose can be wrong in a paragraph and still be useful; a diagram that is wrong in one box is wrong everywhere, because the reader trusts the picture as a single artefact. A Confluence page from 2019 with a PNG architecture diagram and a paragraph below it almost always has the picture out of date and the paragraph somewhere closer to the truth, because the prose was easier to edit. Diagrams as code closes that gap. When the source is one Markdown commit away from the diagram, the diagram is fixed in the same review that fixes the surrounding text.

The second reason is that diagrams in version control are reviewable in the engineering sense. A pull request that changes a flowchart shows the diff as text: an arrow added, a node renamed, a branch removed. A reviewer can spot a missing edge or an inconsistent label the way they spot a missing return statement. A PNG attached to a PR is opaque; either you replace it wholesale or you do not touch it. The same Bacchelli and Bird study cited in Lecture 5 (Microsoft 2013) found that reviewers comment on what they can read; if the artefact is binary, the artefact gets a rubber stamp.

The third reason is that the diagram-as-code workflow scales with the team. A team of five with one designer can keep Visio diagrams roughly in sync with the system. A team of fifty cannot. The discipline that the source is text, the renderer is automatic, and the build is CI is the same discipline that scaled documentation in the docs-as-code era (Lecture 7). Brooks's "Show me your flowcharts and conceal your tables, and I shall continue to be mystified. Show me your tables, and I won't usually need your flowcharts; they'll be obvious" (1975) is the classic warning against decorative diagrams. The flowcharts that earn their place are the ones that show structure the prose cannot.

Step 3

The mental model

The rendering pipeline

Every diagram-as-code tool fits the same four-stage pipeline. The author writes source in a text file (or a fenced Markdown block). A parser reads the source and builds an internal graph: nodes, edges, attributes. A layout engine decides where each node lands and how each edge routes; this is the hard problem, and most tools delegate it to one of a small number of algorithms. A renderer emits the final SVG or PNG. The author edits the first stage; the rest is automatic.

Layout: the part the human gives up

The reason a hand-drawn diagram can look better than an auto-laid one is that a human reasons about reading order, visual weight, and white space at the same time. A layout engine optimises a measurable proxy: edge crossings, total edge length, hierarchical level separation. The classic algorithm is Sugiyama-style layered layout (Sugiyama, Tagawa, Toda, 1981), implemented as dot in Graphviz and as dagre in Mermaid. It produces clean top-down or left-right flowcharts when the graph is acyclic, and acceptable results when it is not. The Eclipse Layout Kernel (ELK) is a more recent option, with better routing for large graphs and the ability to nest containers; Mermaid offers ELK as an alternative engine since version 10.

The thing the engine cannot do is intent. If two boxes are conceptually paired but unrelated in the graph, the engine will not place them next to each other. If a node is "more important" than its neighbours, the engine will not make it bigger. Diagrams as code is the right default; the exception is the diagram that needs to look exactly a certain way, and for those the answer is to draw it in Excalidraw or draw.io and accept the cost.

The pragmatic rule for which diagram to pick is the question the reader is trying to answer. If the question is "what happens next?", a flowchart or state diagram. If the question is "who talks to whom?", a sequence diagram. If the question is "what does the data look like?", an ER or class diagram. If the question is "how is the system put together?", a C4 architecture diagram. Diagrams that try to answer more than one question are usually worse at all of them.

C4 model. Simon Brown's diagrammatic framework (proposed 2011, c4model.com) for software architecture, structured as four nested levels: context (the system in its environment), container (the deployable units), component (the major pieces inside a container), and code (class-level detail, rarely drawn). The cardinal rule is that each level zooms one step deeper; you never mix scales on the same page.
Step 4

The detail

Mermaid

Mermaid is the diagram language that has won the documentation default. GitHub renders it inside Markdown fenced blocks; GitLab, Bitbucket, Notion, Obsidian, and the MkDocs Material theme do the same. The grammar is small enough that you can learn the constructs in an evening, and the renderer is a JavaScript library (mermaid-js) that ships in every major Markdown surface.

A flowchart in Mermaid begins with flowchart (or graph) and a direction (TD, LR, BT, RL). Nodes are declared with an identifier and a label in brackets; the bracket style chooses the shape. Edges are arrows of various weights. The whole construct is a fenced block with the language tag mermaid.

```mermaid
flowchart LR
    A[Loan application] --> B{Score >= cutoff?}
    B -->|Yes| C[Approve]
    B -->|No|  D[Decline]
    C --> E[(Disbursement)]
    D --> F[/Notify customer/]
```

A sequence diagram begins with sequenceDiagram. Actors are declared with participant or actor; messages are arrows between them, with the arrow style indicating whether the message is synchronous, asynchronous, or a response.

```mermaid
sequenceDiagram
    participant C as Client
    participant API as Auth API
    participant DB as Token store
    C->>API: POST /token (credentials)
    API->>DB: lookup user
    DB-->>API: user record
    API-->>C: 200 + access_token
```

A state diagram begins with stateDiagram-v2. States are declared by name; transitions use a colon-separated label.

```mermaid
stateDiagram-v2
    [*] --> Performing
    Performing --> Stage_2 : DPD > 30
    Stage_2 --> Stage_3 : DPD > 90 or default trigger
    Stage_2 --> Performing : cure
    Stage_3 --> Performing : cure
    Stage_3 --> [*] : write-off
```

An entity-relationship diagram begins with erDiagram. The crow's-foot notation is built in; cardinalities are signalled by symbols on each end of the relationship line.

```mermaid
erDiagram
    CUSTOMER ||--o{ ACCOUNT : holds
    ACCOUNT  ||--o{ TRANSACTION : records
    CUSTOMER {
        string customer_id PK
        string name
        date   date_of_birth
    }
    ACCOUNT {
        string account_id PK
        string customer_id FK
        string product
        decimal balance
    }
```

A C4 context diagram is supported via the C4Context directive (since Mermaid 9), with Person, System, System_Ext, and Rel primitives.

```mermaid
C4Context
    Person(customer, "Customer", "Holds a current account")
    System(banking, "Core banking", "Ledger, products, statements")
    System_Ext(payments, "Faster Payments", "UK retail rails")
    Rel(customer, banking, "Uses")
    Rel(banking,  payments, "Settles via")
```

Mermaid also supports class diagrams, gantt charts, mindmaps, user journeys, requirement diagrams, timeline diagrams, and a quadrant chart, all with similar fenced-block syntax. The Mermaid Live Editor (mermaid.live) is the standard authoring surface, with instant preview and PNG/SVG export. The full grammar is at mermaid.js.org.

Common pitfall Mermaid's parser is strict about reserved characters. Parentheses, square brackets, and curly braces in node labels need to be quoted: A["State (i)"], not A[State (i)]. Likewise, the pipe character in edge labels needs escaping. The error messages from the parser are unhelpful; the fix is almost always to wrap any non-trivial label in double quotes.

PlantUML

PlantUML is older and more verbose. Where Mermaid optimises for brevity, PlantUML optimises for UML compliance. A PlantUML file begins with @startuml and ends with @enduml; in between, the grammar is rich enough to express every UML 2 diagram type, plus archmate, gantt, BPMN, work-breakdown structures, salt wireframes, and a long tail of domain extensions.

@startuml
actor Customer
participant "Auth API" as API
database "Token store" as DB

Customer -> API : POST /token
API -> DB : lookup user
DB --> API : user record
API --> Customer : 200 + access_token
@enduml

PlantUML's strengths are the depth of its UML semantics (proper aggregation versus composition arrows, full UML state-machine vocabulary, formal use-case actors), its skinparam system for typography control, and its long history of integrations (Atlassian Confluence, Eclipse, IntelliJ, VS Code). Its weakness is that the renderer is a Java service: you either install Java locally, run a Docker image, or hit a hosted plantuml.com endpoint. None of those is as frictionless as Mermaid's "GitHub already renders it".

The decision rule between Mermaid and PlantUML in practice is: Mermaid for documentation that lives in a Markdown surface (GitHub, MkDocs, Notion), PlantUML where the team writes UML rigorously and a Java toolchain is acceptable.

Graphviz and DOT

Graphviz is the elder of the family. Its language, DOT, is the lowest-level of the four covered here: a graph is a list of nodes and edges with attributes, and the layout engine (dot for hierarchical, neato and fdp for spring-model, circo for circular, twopi for radial) chooses the geometry. Most higher-level tools, including PlantUML and Mermaid in some modes, sit on top of Graphviz.

digraph PD_pipeline {
    rankdir=LR;
    node [shape=box, style=rounded, fontname="Inter"];

    raw       [label="raw data"];
    features  [label="feature engineering"];
    train     [label="train / test split"];
    fit       [label="logit fit"];
    val       [label="validation"];
    monitor   [label="monitoring"];

    raw -> features -> train -> fit -> val -> monitor;
    val -> features [label="iterate", style=dashed];
}

DOT's value is that everything else delegates to it. When a Mermaid or PlantUML diagram lays out badly, the fix is sometimes to drop into DOT directly. The cost is that DOT has no domain semantics: there is no "actor", no "state", no "class". It is a low-level graph language; you build the abstractions yourself.

D2

D2 (Alexander Wang, 2022; d2lang.com) is the newest entrant and the only modern language designed from scratch for declarative diagramming. Its syntax is dense and HCL-like, the renderer is written in Go, and the layout engine (dagre, ELK, or D2's own TALA) is selectable per diagram. D2 supports nested containers, themes, and an animation feature that Mermaid lacks.

customer -> web_app: places order
web_app -> order_service: HTTP POST
order_service -> inventory: reserve stock
order_service -> payments: charge card
payments -> bank: ISO 20022

bank: {
  shape: cylinder
  style.fill: "#FBF1D4"
}

D2's selling point is layout quality and aesthetic polish: the same source produces diagrams that look closer to a hand drawing than Mermaid or DOT manage. The trade-off is ecosystem maturity. GitHub does not render D2 inline; MkDocs needs a plugin; the community is smaller. For an internal documentation site where look matters, D2 is worth the install cost. For a README on GitHub, Mermaid still wins.

The category beyond text: Excalidraw and draw.io

Not every diagram should be code. A hand-drawn architecture poster that hangs above a team's desk, a marketing schematic for a pitch deck, or a domain map drawn collaboratively in a workshop are all better served by a direct-manipulation editor. The two relevant tools are Excalidraw (Vjeux et al., 2020), with its hand-drawn aesthetic and JSON file format, and draw.io (now diagrams.net, JGraph 2005), the workhorse for technical diagrams in pretty much any team that has used Confluence.

Both Excalidraw and draw.io save to text-based formats (Excalidraw to a JSON-ish file, draw.io to an XML file) that can be checked into git. The diff is not human-readable in the same way Mermaid is, but the file is at least versionable and the source is not lost when someone deletes the Confluence page. The rule of thumb is: use Mermaid for diagrams that exist to support prose, use Excalidraw or draw.io for diagrams that exist as the artefact.

Diagrams in continuous integration

Diagrams as code earns its name when the build is automated. The pattern is the same as for prose: a CI job runs on every push, the renderer is invoked on each diagram source file, the output is checked against the previous render, and the build fails if a referenced diagram source has a syntax error. For Mermaid, the renderer is mmdc (mermaid-cli); for PlantUML, the Java jar or a Docker image; for Graphviz, the dot binary; for D2, the d2 binary.

# .github/workflows/diagrams.yml
name: Render diagrams
on:
  pull_request:
    paths: ['docs/**/*.mmd', 'docs/**/*.puml']

jobs:
  render:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm install -g @mermaid-js/mermaid-cli
      - run: |
          for f in $(find docs -name '*.mmd'); do
            mmdc -i "$f" -o "${f%.mmd}.svg" --theme neutral
          done
      - run: git diff --exit-code docs/

The final git diff --exit-code turns the job into a check: if the rendered SVGs have drifted from what is committed, the build fails and the author is prompted to commit the rendered output. This is the same pattern as auto-formatting (Lecture 2): the CI is the enforcement layer; the developer never argues with the tool.

Worked example: a credit-risk pipeline diagram

Worked example: documenting an IFRS 9 ECL pipeline in Mermaid

The task is to produce a single-page overview of the IFRS 9 ECL calculation pipeline for the model documentation pack. The reader is an internal validator who needs to understand the data flow before reading the methodology in detail. The previous version of this page used a PowerPoint slide exported to PNG; it had drifted from the code by two releases.

Step 1 (identify the artefact). The diagram should answer one question: "what are the inputs, the stages, and the outputs of the ECL calculation?". This is a flowchart, not a sequence diagram (there are no actors) and not a class diagram (we are showing flow, not types).

Step 2 (sketch the nodes and edges). The inputs are: account-level exposure data, macroeconomic scenarios, calibrated PD/LGD/EAD models, and the staging criteria. The stages are: feature build, PD term-structure projection, LGD application, EAD projection, ECL aggregation, and disclosure tables. The outputs are: Stage 1/2/3 ECL by portfolio, FLI-overlay, and the IFRS 9 disclosure file.

Step 3 (draft the Mermaid source). A left-to-right flowchart with three swimlanes (inputs, stages, outputs) implemented as subgraph blocks. Stage colouring is via class definitions at the bottom of the block.

```mermaid
flowchart LR
    subgraph Inputs
        E[Account exposures]
        M[Macro scenarios]
        P[PD model]
        L[LGD model]
        S[Staging rules]
    end
    subgraph Pipeline
        F[Feature build]
        T[PD term structure]
        A[LGD application]
        X[EAD projection]
        G[ECL aggregation]
        V[FLI overlay]
    end
    subgraph Outputs
        O1[Stage 1/2/3 ECL]
        O2[Disclosure tables]
    end
    E --> F
    P --> T
    L --> A
    M --> T
    M --> A
    S --> G
    F --> T --> A --> X --> G --> V --> O1
    V --> O2
```

Step 4 (commit and embed). The Mermaid source is saved at docs/ifrs9/figures/pipeline.md, fenced as a mermaid block. The model documentation page in MkDocs references it with an --8<-- "ifrs9/figures/pipeline.md" include. A pull request that retires the FLI overlay step is a one-line change to the source; the diagram updates on the next build.

Step 5 (review). A reviewer pulls the PR, looks at the rendered diagram in the build preview, and comments inline on the diagram source: "the LGD model also takes macroeconomic scenarios; should there be an arrow from M to L?". The author adds the arrow, commits, and the diagram is corrected in the same review that surfaced the gap. None of that conversation would have happened if the diagram had been a PNG.

Step 5

Synthesis and what's next

Diagrams as code is the same idea as docs as code, applied to the visual layer. The source is text; the source lives in the repository; the rendering is automatic; the review is the pull request. The four languages worth knowing are Mermaid, PlantUML, Graphviz, and D2. The default is Mermaid, because GitHub renders it natively and the other tools are one configuration line away in every Markdown surface. PlantUML earns its keep on teams that take UML seriously. Graphviz is the layout engine of last resort. D2 is the new option to evaluate when aesthetics matter more than ecosystem reach.

The discipline beneath the tool choice is editorial. A diagram earns its place by answering one question better than prose could. A flowchart that restates a paragraph is decoration; an ER diagram that compresses three pages of schema dump is doing work. The Tufte principle is the right test: every mark on the page should carry information.
