Project setup and dependency management

A Python project is not just a folder of scripts. It is a contract: which interpreter, which libraries at which versions, which lint rules, which entry points. This lecture covers pyproject.toml, the choice between pip, uv, poetry, and pdm, virtual environments, lockfiles, semantic versioning, and the pre-commit hooks that keep all of it consistent across a team.

Step 1

The 30-second version

Every Python project, from a one-file script to a thousand-module library, has the same three set-up questions to answer. Which interpreter? Python 3.11, 3.12, 3.13, on which operating system. Which dependencies? pandas at which version, scikit-learn at which version, with which transitive constraints. Which dev-loop tooling? formatter, linter, type checker, test runner, build back-end. Getting all three right is the difference between a project a new joiner can clone and run in ten minutes and a project that requires a Slack thread to set up.

The modern answer is a single file, pyproject.toml (PEP 518, 2016; PEP 621, 2020), that records every one of those answers in a standardised TOML format. The Python interpreter version goes there or in a sibling .python-version. The dependencies and dev-dependencies go there. The configuration for ruff, mypy, pytest, and the build back-end all goes there. The file is the contract; the tooling reads from it. A project with a well-formed pyproject.toml is one command away from a working environment: uv sync, poetry install, or pip install -e . depending on which front-end the team uses.

The four front-ends worth knowing are pip (Python's bundled installer, plus pip-tools or pip-compile for lockfiles); poetry (Sébastien Eustace, 2018), the first all-in-one project manager that put pyproject.toml on the map; pdm (Frost Ming, 2019), the PEP-pure alternative to poetry; and uv (Astral, 2024), the Rust-written replacement that is 10 to 100 times faster than the rest and has emerged in 2025 as the new default for new projects. All four read the same pyproject.toml; the choice between them is about speed, opinion, and how much they decide for you.

Feynman test A Python project's set-up is a function. The input is the recipe (pyproject.toml plus a lockfile). The output is a working environment: an interpreter at a known version, with a known set of libraries, each at a known version, installed in an isolated folder. If you can describe what each line of pyproject.toml contributes to that function, and what role the lockfile plays in making the output deterministic, you have the mental model that every dependency-management tool is implementing.
What's beyond the syllabus The deep reason dependency management is harder than it looks is that pinning is a graph problem. Project A wants pandas >= 2.0; library B wants pandas < 2.1; the resolver has to find an intersection that satisfies both, and the intersection may not exist (the "dependency hell" problem). The resolver implementing this is the same kind of SAT-solver problem that powers package managers in every language: Cargo for Rust, Bundler for Ruby, npm for JavaScript. The reason uv is so fast is partly that it borrows Cargo's algorithm and rewrites it in Rust; the reason poetry was slow for years is partly that the original resolver did not.
Step 2

Why this matters

The first reason is reproducibility. The Jupyter lecture (Lecture 10) ended with the observation that a notebook only reproduces if its environment is pinned; this lecture is where the pinning happens. A team that pins to a uv.lock or poetry.lock can guarantee that the calibration notebook from January reproduces in October, byte-for-byte. A team that relies on a hand-edited requirements.txt with pandas>=2.0 cannot. For regulatory work, where a model has to be re-runnable years after it was first deployed, the gap is not academic; it is the difference between a defensible artefact and an explanatory phone call.

The second reason is onboarding. The single most common piece of friction reported in developer-experience surveys (Stack Overflow, GitHub State of the Octoverse) is the time from git clone to "first test passes". A project whose set-up is one command (uv sync && uv run pytest) has effectively zero onboarding cost. A project whose set-up is a wiki page with seven steps, each of which fails on one of macOS, Windows, or Linux, costs a new joiner half a day on their first morning and is the kind of thing that gets remembered. The investment in a clean pyproject.toml is paid back the first time someone new joins the team.

The third reason is supply-chain hygiene. A 2024 review of Python supply-chain attacks (Sonatype, the State of the Software Supply Chain report) counted 245,000 malicious packages uploaded to public registries in the year, a 156% year-on-year rise. The defence is not abstinence but discipline: pin dependencies to specific versions, review the lockfile in code review, run an SBOM (software bill of materials) scan in CI, prefer well-maintained packages over abandoned ones. None of that works without a single source of truth for what the project depends on, which is what pyproject.toml plus a lockfile gives you.

Step 3

The mental model

The four-file contract

A well-formed Python project records its set-up in four files. pyproject.toml is the declared contract: human-edited, version-controlled, the source of truth for what the project depends on. The lockfile (poetry.lock, pdm.lock, uv.lock, or requirements.txt if produced by pip-compile) is the resolved contract: machine-generated, version-controlled, the exact graph of every package and every transitive dependency at exact versions and hashes. .python-version records the interpreter version, read by pyenv and uv. .pre-commit-config.yaml records the hook configuration. Together the four files describe everything a fresh clone needs.

The declared / resolved distinction

The single biggest conceptual leap in dependency management is the distinction between a declared dependency and a resolved dependency. The declared dependency is what the human writes: "I want pandas, version 2 or higher". It is a constraint. The resolved dependency is what the tool computes: "pandas 2.2.1, numpy 1.26.4, python-dateutil 2.9.0, pytz 2024.1, six 1.16.0, and four more transitive packages, each at a specific version with a specific SHA-256 hash". The resolved set is a solution to the constraint problem.

The lockfile records the solution. Without it, every fresh install re-runs the resolver against the live state of the package index, which can produce a different solution today than it did yesterday (because a new pandas was released, or a transitive dependency changed). Pinning the lockfile and checking it into git is the move that makes the install deterministic. The team's CI installs from the lockfile; the team's developers install from the lockfile; the production deployment installs from the lockfile. The resolver only runs again when someone deliberately bumps a dependency, at which point the lockfile is regenerated and reviewed in a pull request.

The role of the virtual environment

A virtual environment (venv, built into Python 3.3+; virtualenv, the older standalone version) is a private folder containing a copy of the Python interpreter and a private site-packages directory. Activating the venv prepends its bin directory to PATH, so python and pip refer to the private copy. The mechanism is dumber than it sounds; it is essentially a symlink farm and a PATH hack, but it solves the central problem cleanly: project A and project B can depend on incompatible versions of pandas because each lives in its own venv, with its own site-packages.

# the modern python -m venv approach
python -m venv .venv
.venv/bin/python -m pip install pandas

# uv hides this behind one command
uv venv          # creates .venv with the project's interpreter
uv pip install pandas

The convention across modern tooling is to put the venv in a folder called .venv at the project root and add it to .gitignore. The venv is local to a checkout; recreating it is one command. The dependency manager (poetry, pdm, uv) creates and populates the venv on demand, so most users rarely interact with it directly. The conda environment (Anaconda, 2012) is a heavier alternative that manages non-Python dependencies (CUDA, R, Fortran libraries) as well; the cost is a slower install and a separate package ecosystem. For modelling work in pure Python, venv is the default; for ML work with GPU or compiled-numerical dependencies, conda still has a role.

Virtual environment. A self-contained Python installation in a folder, with its own interpreter and its own site-packages. Activating it changes PATH so the project's interpreter is used in preference to the system one. The mechanism by which two projects on the same machine can depend on incompatible versions of the same library.
Lockfile. A machine-generated file that records the exact resolved version of every direct and transitive dependency, with cryptographic hashes. Reproduces the installed set deterministically on any machine. The lockfile is committed; the venv is not.

Semantic versioning and the bound choices

The version-number convention that the Python ecosystem mostly follows is semantic versioning (semver: Tom Preston-Werner, 2011): three numbers MAJOR.MINOR.PATCH. A patch bump is a backwards-compatible bug fix; a minor bump is a backwards-compatible feature addition; a major bump is a breaking change. The convention gives the dependency declarer four useful bounds to pick from:

ConstraintReads asResolves toWhen to use
pandas"any version"the newest availableThrowaway scripts only
pandas>=2.0"at least 2.0"newest >= 2.0Library publishing a minimum
pandas~=2.2"compatible with 2.2" (PEP 440)>= 2.2, < 3.0Application that trusts semver
pandas==2.2.1"exactly this"2.2.1, no otherLockfile contents (machine-written)

The right default in pyproject.toml is ~= (or its caret ^ equivalent in poetry's syntax), which trusts the upstream library to follow semver and pins the major version while allowing minor and patch updates. The lockfile then resolves to a specific version. The pattern gives you both signals: the declared constraint says "this is what we depend on conceptually", the lockfile says "this is what we have installed today".

Step 4

The detail

pyproject.toml: the full anatomy

A complete pyproject.toml for a credit-risk modelling project, with comments, looks like this:

# Build back-end. Tells pip how to build the project when someone
# runs `pip install .` or builds a wheel. Hatchling is the modern
# default; setuptools is the legacy choice.
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

# Project metadata (PEP 621). The single source of truth.
[project]
name = "credit-risk-models"
version = "0.3.1"
description = "PD, LGD, EAD models for the consumer book."
requires-python = ">=3.12"
authors = [{ name = "Risk modelling team", email = "risk@bank.example" }]
readme = "README.md"
license = { text = "Proprietary" }

dependencies = [
    "pandas~=2.2",
    "numpy~=1.26",
    "scikit-learn~=1.4",
    "statsmodels~=0.14",
    "pyarrow~=16.0",
    "pydantic~=2.6",
]

# Optional dependencies, grouped. Install with
# `pip install -e .[dev]` or `uv sync --extra dev`.
[project.optional-dependencies]
dev = [
    "pytest~=8.0",
    "pytest-cov~=4.1",
    "hypothesis~=6.99",
    "ruff~=0.4",
    "mypy~=1.10",
    "pre-commit~=3.7",
]
notebook = [
    "jupyterlab~=4.0",
    "jupytext~=1.16",
    "nbstripout~=0.7",
    "papermill~=2.5",
]

# Project entry points. The CLI command `credit-fit` calls the
# `main` function in the named module.
[project.scripts]
credit-fit = "credit_risk_models.cli:main"

# Tool-specific configuration. Each linter / type checker / test
# runner reads its own section. Keeps everything in one file.
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "N"]
ignore = ["E501"]

[tool.mypy]
strict = true
python_version = "3.12"

[tool.pytest.ini_options]
addopts = "-ra --strict-markers --cov=credit_risk_models"
testpaths = ["tests"]

The [build-system] section is required by PEP 518 and tells pip what to do when building the package. The [project] section, standardised by PEP 621, holds the metadata. The [project.optional-dependencies] table groups dependencies by purpose: the production set, the development set, the notebook set. The [tool.*] sections are namespaced for each tool that wants to read its config from the same file, eliminating the proliferation of setup.cfg, .flake8, pytest.ini, and mypy.ini that older projects had.

The four front-ends, compared

Four tools sit on top of pyproject.toml. They install dependencies, manage the venv, lock versions, and run scripts. They are interchangeable in the file format but differ in speed, ergonomics, and opinion.

pip + pip-tools is the orthodox combination. pip installs; pip-compile (from pip-tools) reads pyproject.toml and produces a pinned requirements.txt lockfile. The pair is the lowest-friction choice because pip ships with Python; you do not install anything extra. The cost is that the workflow is several commands long: create a venv, activate it, pip-compile, pip-sync, run.

poetry was the first all-in-one tool to popularise pyproject.toml. It manages the venv, resolves dependencies, locks them, builds the package, and publishes it to PyPI in one CLI. Its early adoption is the reason most older projects you encounter use it. The downsides are speed (the resolver is slow on big graphs), and poetry's slightly non-standard TOML schema ([tool.poetry] instead of [project]; the gap closed in 2024 but old projects still use the old schema).

pdm is poetry's PEP-pure alternative: same scope, but it sticks to the PEP 621 [project] schema and offers a PEP 582 mode that skips the venv entirely (a __pypackages__ folder is used in its place). pdm has a smaller community than poetry but the design is cleaner.

uv (Astral, 2024) is the new default for new projects in 2025. Written in Rust, it installs packages 10 to 100 times faster than pip or poetry, resolves the dependency graph using the Cargo-style PubGrub algorithm, manages Python interpreters as well as packages, and reads the standard pyproject.toml schema. The speed difference is qualitative, not just quantitative: a uv sync on a 50-package project completes in two seconds where poetry install takes ninety. Astral, the same company, also makes ruff (the linter and formatter used in this course), and the two are designed to work together.

ToolYearLockfileManages Python?SpeedWhen to choose
pip + pip-tools2008requirements.txtNoSlowMinimal-dependency projects; CI base images
poetry2018poetry.lockNoSlowExisting projects, or teams already on it
pdm2019pdm.lockPartialMediumPEP-purist teams
uv2024uv.lockYesVery fastNew projects in 2025+

The recommendation for new projects, as of this writing, is uv. For existing poetry or pdm projects, the migration cost is real but bounded; uv reads the same pyproject.toml, and the lockfile regeneration is one command. The pip + pip-tools combination remains the right answer for projects whose deployment target cannot install anything but pip, such as some Lambda runtimes or restricted internal package indices.

The pre-commit hook layer

A team's set-up contract is only enforced if the tools actually run. The pre-commit framework (Anthony Sottile, 2014; pre-commit.com) is the standard mechanism: a .pre-commit-config.yaml file declares hooks (ruff, mypy, nbstripout, gitleaks, and a long tail), and a single pre-commit install wires them into the local git hook directory. From then on, every commit runs the hooks, blocking the commit if any hook fails. The same hooks run again in CI as a belt-and-braces check.

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.4.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.10.0
    hooks:
      - id: mypy
        additional_dependencies: [pandas-stubs, types-requests]

  - repo: https://github.com/kynan/nbstripout
    rev: 0.7.1
    hooks:
      - id: nbstripout

  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: check-toml
      - id: check-yaml
      - id: end-of-file-fixer
      - id: trailing-whitespace

The hooks above format and lint Python code, type-check it, strip outputs from notebooks, validate TOML and YAML syntax, normalise file endings, and remove trailing whitespace. None of these checks are interesting individually; they are the boring class of bug that takes a full code review to spot and a single hook to prevent. The discipline of running them on every commit is the engineering equivalent of brushing your teeth.

Multi-Python: pyenv, asdf, uv

Different projects on the same machine often need different Python versions: project A on 3.11, project B on 3.12, project C on 3.13. The classical tool is pyenv (Yamashita, 2013): a shim layer that intercepts the python command and routes it to whichever interpreter the current directory's .python-version file names. asdf (HashiCorp-adjacent) generalises the pattern to many languages. uv, again, folds the function into itself: uv python install 3.12 downloads the interpreter; uv venv --python 3.12 uses it; the .python-version file is honoured automatically.

echo "3.12.4" > .python-version
uv python install 3.12.4
uv venv
uv sync

The convention this course recommends is: commit a .python-version file, install the interpreter through uv (or pyenv for older toolchains), and let the venv be created automatically. The interpreter version then travels with the project; no one has to be told it.

Common pitfall The most common cause of a "works on my machine" Python bug is the interpreter version, not the package versions. A library may rely on a syntax (the walrus operator, structural pattern matching, the new type-statement syntax) that was added in a particular Python version; running on an older interpreter produces a syntax error. The fix is to commit .python-version and to add requires-python = ">=3.12" to pyproject.toml, so a user with the wrong interpreter is told before they install.

Worked example: setting up a fresh credit-risk modelling project

Worked example: bootstrapping credit-risk-models/ from zero

The task is to set up a new repository for the team's PD / LGD / EAD models. The contract is: anyone in the team should be able to clone, run one command, and have a working environment.

Step 1 (skeleton). Create the directory, run git init, add a .gitignore that excludes .venv/, __pycache__/, *.pyc, and any data files.

Step 2 (Python). Decide on Python 3.12. Write 3.12.4 into .python-version. Run uv python install 3.12.4.

Step 3 (pyproject). Run uv init --package credit-risk-models. The command scaffolds a pyproject.toml, a src/credit_risk_models/__init__.py, and a stub README.md. Edit the TOML to add the production dependencies (pandas, numpy, scikit-learn, statsmodels, pyarrow, pydantic) and the dev group (pytest, ruff, mypy, pre-commit).

Step 4 (lock and install). uv sync. The command resolves the dependency graph, creates .venv/, installs every package, and writes uv.lock. Commit the lockfile.

Step 5 (pre-commit). Write the .pre-commit-config.yaml shown above. Run uv run pre-commit install. From now on, every commit runs ruff, mypy, and nbstripout before it lands.

Step 6 (CI). Add a minimal GitHub Actions workflow that runs uv sync then uv run pytest on every push. Lecture 14 covers this in depth.

Step 7 (README). Add a one-paragraph "to run, install uv (curl -LsSf https://astral.sh/uv/install.sh | sh) and run uv sync && uv run pytest". That is the entire onboarding instruction.

The project is now reproducible, lintable, type-checked, and CI-tested. A new joiner clones, runs two commands, and is productive. The whole bootstrap takes about twenty minutes.

Step 5

Synthesis and what's next

A Python project is a contract recorded in four files: pyproject.toml, the lockfile, .python-version, and .pre-commit-config.yaml. Together they describe the interpreter, the dependencies, and the dev-loop tooling. The choice of front-end (pip-tools, poetry, pdm, or uv) determines speed and ergonomics but not the file format, which is the same in every case. The pattern that wins in 2025 is uv with ruff and mypy, with pre-commit enforcing the hooks. The pattern that loses is "we have a requirements.txt and nobody knows whose Python that uses".

The deeper point is that "set-up" is not a one-off task at the start of a project; it is a continuous concern. Dependencies are bumped, the interpreter is updated, the linter adds new rules, and the lockfile is regenerated each time. Treating pyproject.toml as a living document, reviewed in pull requests like any other code, is the discipline that keeps a project habitable five years in. The next lecture turns to the version control system that makes those reviews possible: git, and the mental model that lets you use it without fear.
