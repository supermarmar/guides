Lectures / Software engineering

Continuous integration and delivery

CI/CD is the automation layer that runs on every git push. It turns "did we break anything?" from a manual question into a machine-checked answer. This lecture covers the historical argument behind continuous integration (Humble & Farley 2010), the mechanics of the modern pipeline on GitHub Actions and GitLab CI, the test-pyramid trade-offs that govern CI run time, and the deployment strategies that turn a green build into a production release.

Lecture 15 of 16 Reading time, 50 minutes Part IV: project and collaboration
Step 1

The 30-second version

Continuous integration (CI) is the practice of merging every developer's work into a shared trunk many times a day, with automated tests run on every merge. Continuous delivery (CD) extends the practice: every commit that passes CI is also automatically built into an artefact that could be deployed to production, and the deployment itself is one button press away. Continuous deployment (a stricter variant) removes even the button: every passing commit is deployed to production automatically. The terms drift in everyday use; the substance is that the path from commit to deployable artefact is automated, fast, and run on every change.

The intellectual case for the practice is in two books. Martin Fowler's "Continuous Integration" essay (martinfowler.com, 2006) is the short version. Jez Humble and David Farley's "Continuous Delivery" (Addison-Wesley, 2010) is the long version, and remains the canonical text. The empirical case is in the DORA reports (Forsgren, Humble, Kim, Accelerate, 2018, and the annual State of DevOps reports through 2024): teams that deploy more frequently have lower change-failure rates, faster recovery times, and higher developer satisfaction than teams that batch their releases. The result is consistent across every industry, including regulated ones.

The mechanics in 2025 are well-standardised. A YAML file in the repository (.github/workflows/ci.yml for GitHub Actions, .gitlab-ci.yml for GitLab CI, azure-pipelines.yml for Azure DevOps) declares one or more workflows, each made up of jobs that run on hosted or self-hosted runners. A job has steps; a step is either a shell command or a reusable action. The workflow is triggered by events: a push to a branch, the opening or update of a pull request, a tag, a manual dispatch, or a schedule. Branch protection (Lecture 13) refers to specific job names as required checks; a PR cannot merge until those checks are green.

Feynman test A CI pipeline is a sequence of programs that run on a fresh machine every time you push, against the exact contents of the commit. The output is a verdict: green or red. Green means the commit passes every check the team agrees on (lint, types, tests, security scan, license audit). Red means at least one check failed and the commit cannot ship without intervention. If you can name the checks you would put in your pipeline and describe what each one prevents, you have the working model.
What's beyond the syllabus The deep ancestor of continuous integration is the nightly build, which Microsoft popularised in the 1990s and which Joel Spolsky's "Joel Test" (2000) listed as point number one. The nightly build's promise, that a clean machine could rebuild the whole product overnight, was modest by today's standards, but it was the first generation of the discipline: the build had to work on a machine other than the developer's, and someone had to fix it when it broke. Modern CI is that discipline taken to its limit, "every commit" instead of "every night", with the build broken into a workflow of parallel jobs and the cost of a build dropped from hours to minutes.
Step 2

Why this matters

The first reason is feedback latency. The most important number in any engineering process is the time between making a mistake and finding out about it. A bug discovered in code review is cheap to fix; the same bug found in production is two orders of magnitude more expensive (Boehm 1981, "Software Engineering Economics", later revised by McConnell and others). CI compresses that distance: a test broken by a commit is reported within minutes, by the same automation that ran the tests, with a link directly to the failing build. The team's stand-up no longer needs the "is anyone blocked on the main branch?" question.

The second reason is that CI is the enforcement layer for everything the previous lectures established. Lecture 2's formatter and linter rules are local pre-commit hooks; CI runs them again because some authors forget to install the hooks. Lecture 5's tests are useful in proportion to how often they run; CI runs them on every commit. Lecture 10's notebook-execution check, Lecture 11's lockfile install, Lecture 13's required-reviewer rule, all bind to CI checks by name. Without the automation, each of these is a soft norm that drifts; with it, each is a binary gate that does not.

The third reason, specific to risk modelling, is that audit-quality reproducibility requires the build to be a script, not a memory. A model whose retraining requires "open this notebook, run cells 1 through 12, then download the snapshot, then run the calibration script" is a model whose retraining cannot be reproduced if the original author leaves. A model whose retraining is the contents of a CI workflow file, triggered on a schedule, with the artefact written to object storage, is reproducible by anyone with read access to the repository. The PRA's SS3/24 "Model risk management principles for banks" and the EBA's IRB RTS both expect this level of automation for production models; meeting the expectation costs a one-off engineering investment and an ongoing maintenance cost in the low single-digit percent of model team time.

Step 3

The mental model

The pipeline as a graph of jobs

A modern CI workflow is a directed acyclic graph of jobs, each running on its own machine. Jobs that have no dependencies run in parallel; jobs that declare a needs: dependency run after their prerequisites. The total wall-clock time of the workflow is the longest path through the graph, not the sum of every job. Designing for parallelism is therefore the principal lever on CI speed.

The cost ladder: what to run when

Not every check is worth running on every commit. The right design layers checks by cost and frequency. The pattern this course recommends is a three-tier ladder.

On pre-commit (seconds). Format, lint, the cheap unit tests. Runs locally before the commit even happens. If pre-commit blocks the commit, the developer fixes it before pushing.

On every push (minutes). The full unit-test suite, typecheck, integration tests against a local stub, the lockfile-install check, the notebook-execution check (for short notebooks). This is the CI workflow that gates the PR.

On a schedule or tag (longer). The expensive checks: model regression tests against a held-out dataset, end-to-end tests against a real (non-stubbed) service, security scans, license audits, dependency-update checks. These run nightly or on the release tag, not on every PR.

Workflow. A top-level CI configuration unit, typically one YAML file. Triggered by events (push, pull_request, schedule, manual dispatch). Contains one or more jobs.
Runner. The machine that executes a job. Hosted runners are provided by the CI service (GitHub-hosted runners are Linux, Windows, or macOS VMs spun up fresh per job); self-hosted runners are machines the team owns, useful for GPU work, large memory, or private network access.

The build artefact

The output of a successful CI run, beyond the green check, is the build artefact: the thing that the team intends to deploy. For a Python project this is typically a wheel (.whl file), a Docker image, or a versioned bundle on an S3 bucket. The artefact is built once, tested in CI, and then promoted through environments (staging, production) without being rebuilt. The principle is "build once, deploy many"; it guarantees that the production binary is the same one the tests ran against.

Step 4

The detail

A complete GitHub Actions workflow

The example below is a realistic CI workflow for a credit-risk modelling project using uv, ruff, mypy, pytest, and MkDocs. It runs on every push and pull request, with parallel jobs that fan out from a shared setup step.

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# Cancel old runs when a new commit lands on the same PR.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
        with: { version: latest }
      - run: uv sync --frozen --extra dev
      - run: uv run ruff format --check .
      - run: uv run ruff check .

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen --extra dev
      - run: uv run mypy src/

  tests:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: ['3.12', '3.13']
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen --extra dev --python ${{ matrix.python-version }}
      - run: uv run pytest --cov=credit_risk_models --cov-report=xml
      - uses: codecov/codecov-action@v4
        with: { files: coverage.xml }

  notebooks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen --extra dev --extra notebook
      - run: |
          for f in notebooks/*.ipynb; do
            uv run jupyter nbconvert --to notebook --execute "$f" \
                                     --output "/tmp/$(basename $f)"
          done

  docs:
    runs-on: ubuntu-latest
    needs: [lint]
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen --extra docs
      - run: uv run mkdocs build --strict
      - uses: actions/upload-pages-artifact@v3
        with: { path: site/ }

The features worth naming. The concurrency: block cancels old runs when a new commit arrives on the same PR, saving runner minutes. The strategy.matrix on the tests job runs the suite against multiple Python versions in parallel; the fail-fast: false setting lets all the matrix legs finish so you see which versions fail, not just the first one. The uv sync --frozen command installs from the committed lockfile exactly, with no resolver step; this is the CI-side equivalent of the reproducibility discipline in Lecture 11. The mkdocs build --strict command turns documentation warnings into errors, so a broken cross-reference in a Markdown file fails the build the same way a broken test does.

Caching: the speed multiplier

The single largest determinant of CI speed, once the workflow shape is right, is whether dependencies are cached between runs. Without caching, each job downloads and installs every dependency from scratch; with caching, the dependencies are pulled from an artefact store keyed by the lockfile hash. The setup-uv action does this automatically when the project has a uv.lock: the cache key is derived from the lockfile, the cache is restored at the start of each job, and updated at the end.

For Docker-based pipelines, the equivalent mechanism is the buildx cache: a layered image cache keyed by the Dockerfile and the build context, stored on the runner host or in a remote registry. A multi-stage Dockerfile that puts RUN uv sync as an early layer takes one minute on a cache hit and four minutes on a cache miss; getting the cache hits right is the difference between a 90-second pipeline and a five-minute one.

The test pyramid in CI

Lecture 5 introduced the test pyramid: many fast unit tests, fewer integration tests, very few end-to-end tests. CI is where the pyramid pays for itself. Unit tests run on every push because they take seconds; integration tests run on every push when they take less than a minute, on a schedule otherwise; end-to-end tests run on the merge to main or on the release tag, not on every PR. A team that runs every test on every commit either has a slow pipeline (which discourages frequent commits) or a brittle one (which discourages trust in green builds).

The empirical rule is: a CI pipeline that takes more than 10 minutes will be ignored by the team. Developers switch context after a green check, return to the PR much later, lose the cache of intent, and produce worse follow-up work. The investment in pipeline speed is therefore investment in human attention. Caching, parallelisation, and the pyramid discipline together can keep most projects' PR pipeline under five minutes.

Continuous delivery: from green build to deployable artefact

CI produces the green check; CD produces the artefact. The dividing line is a job that publishes the build to a registry or storage location: uv publish for a PyPI package, docker push for a container image, aws s3 cp for a bundle. The artefact is versioned by the git tag or by the commit SHA; the same version can then be promoted through environments without rebuilding.

  release:
    if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v')
    needs: [lint, typecheck, tests, notebooks, docs]
    runs-on: ubuntu-latest
    permissions:
      id-token: write          # for trusted publishing to PyPI
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv build
      - run: uv publish --trusted-publishing

The pattern above triggers only on tag pushes that match the v* pattern (e.g. v0.3.1). The release job depends on every other job passing first, so a tag that breaks tests does not ship. The --trusted-publishing flag is PEP 740: PyPI authenticates the publisher via the GitHub OIDC token, removing the need for stored API keys. The same shape, with different publish targets, covers Docker images, Helm charts, and S3-hosted bundles.

Deployment strategies

Once an artefact exists, getting it into production is a separate problem with its own established patterns. Four strategies cover most cases.

All-at-once replaces the running version with the new one in a single step. Simple, fast, all-or-nothing; the right answer for stateless services with quick rollbacks. Used by most internal tools.

Blue-green runs two production environments side by side (blue and green); traffic is routed to one. Deploys to the inactive environment, runs smoke tests, then flips traffic. Rollback is instant: flip back. Used where any downtime is unacceptable.

Canary sends a small fraction of traffic (1%, 5%, 25%) to the new version while the rest stays on the old. Telemetry is monitored; if error rates rise, traffic is rolled back. If not, the fraction is increased progressively. Used for high-volume services where a bad deploy would affect many users.

Feature flag deploys the new code path behind an off-by-default flag; the flag is then toggled on for an increasing percentage of users. The deploy and the release become separate events: code can ship dark and be activated later. Used where the user impact of a feature is unpredictable.

StrategyRollback speedOperational complexityWhen to choose
All-at-onceMinutes (re-deploy)LowestInternal tools, batch jobs
Blue-greenSeconds (traffic flip)Medium (2× infrastructure)Customer-facing services with downtime cost
CanarySeconds (route rollback)High (telemetry, routing)High-traffic services
Feature flagInstant (flag flip)Medium (flag service)Behavioural changes, A/B testing

The four are not mutually exclusive. A typical mature setup uses blue-green for the infrastructure layer, canary at the traffic-routing layer, and feature flags at the application layer. The artefact is the same in every case; the differentiation is in how it is rolled out.

Common pitfall The most common CI/CD mistake is putting all the rigorous checks behind a "deploy" job rather than a "PR" job. The pattern looks reasonable, deploy gates are stricter than PR gates, but it means broken code lands on main and is caught only at deploy time, by which point the original author has moved on. The correct shape is: the PR pipeline is the strict pipeline; the deploy pipeline runs the same checks plus an additional smoke-test against the live environment. Defects should never reach main.

Worked example: a model-retraining pipeline

Worked example: scheduled retraining of a PD model

The team's PD model is retrained monthly on the latest available data. The retraining used to be manual (open the notebook, change two dates, run all cells, upload the artefact); the team wants to move it to a scheduled CI pipeline so that the artefact has a verifiable build trail.

Step 1 (script the retraining). Convert the notebook to a .py file via jupytext (Lecture 10). The script takes --as-of-date as an argument; reads inputs from the data lake; outputs a fitted model plus a validation report.

Step 2 (write the workflow). A new .github/workflows/retrain.yml. Triggered by a schedule (cron: '0 2 1 * *', the second hour of the first day of each month) and by manual dispatch with the date as an input.

Step 3 (the job). Check out the repo at the latest tagged release; set up uv; install dependencies from the lockfile; download the data slice from S3 using OIDC credentials; run uv run retrain --as-of-date $TARGET; upload the fitted model and the validation report as a release artefact on a new tag model-2026-05.

Step 4 (validation gate). After the artefact is produced, an automated validation job checks that the new model passes the team's regression criteria (AUC within tolerance of the previous model, PSI on calibration features below threshold, no overrides). If the gate fails, the workflow opens an issue assigned to the model risk team. If it passes, the artefact is marked deployable.

Step 5 (audit trail). Every retraining is now a tagged release with an artefact, a build log, and a validation report, all linked back to the commit that defined the methodology. A regulator asking "show me how the March model was produced" has a clickable answer: open the workflow run, see the inputs, see the outputs, see the validation. No notebook to find, no laptop state to reconstruct.

The investment is one engineer-week. The recurring cost is zero, except when the script needs updating (which it would have anyway). The audit value is the part that pays back the investment many times.

Step 5

Synthesis and what's next

CI is the automation that runs every check the team agrees on, on every commit, with a green-or-red verdict at the end. CD extends CI by producing a deployable artefact on every passing build, with deployment one click (or zero) away. The mechanics are a YAML file declaring a graph of jobs, each running on a fresh machine; the design lever is parallelism, the speed lever is caching, and the discipline lever is layering by cost (pre-commit, every push, scheduled). The deployment side adds four strategies (all-at-once, blue-green, canary, feature flag) that decide how an artefact reaches users.

The deeper point is that CI/CD is the operational expression of every engineering practice in this course. Lecture 2's formatter, Lecture 5's tests, Lecture 10's notebook executions, Lecture 11's lockfile, Lecture 13's required reviewers, all bind to specific named CI checks. A team that has invested in those practices but not in CI is keeping a sports car in the garage; a team that has CI without those practices is running it empty. The two work together, or not at all. The next and final lecture turns to the documentation side of the same automation: documents that are auto-generated from the code itself, kept in sync by the same pipeline that runs the tests.
