Debugging and profiling

Tests prevent and detect; debugging diagnoses. This lecture covers the scientific-method discipline that separates surgical debugging from random poking, the Python tools that support it (logging, pdb, faulthandler), and the profiling step that turns "this is slow" into a numbered list of where the time and memory go.

Step 1

The 30-second version

Debugging is the activity of reducing the gap between what a program does and what it is supposed to do. The premise is that the program contains at least one defect, the symptom is observed (a wrong output, an exception, a crash, a slow run, a memory leak), and the goal is to identify the cause precisely enough to fix it. Debugging is mostly a matter of inference, not coding; the actual fix is usually one or two lines once the cause is known.

Andreas Zeller's Why Programs Fail (2nd edition, 2009) frames debugging as the scientific method applied to a misbehaving program. You observe a symptom, form a hypothesis about what could cause it, run an experiment that would distinguish that hypothesis from competitors, and refine until you reach a single explanation that survives every test. The discipline matters because the alternative, "change something and see if it goes away", produces fixes that mask the real cause and reappear elsewhere.

Profiling is the corresponding activity for performance. "The program is slow" or "the program uses too much memory" are symptoms; the profiler tells you which function, which line, which allocation is responsible. Donald Knuth's much-quoted "premature optimisation is the root of all evil" (Knuth 1974) is, in full, "We should forget about small efficiencies, say about 97 per cent of the time: premature optimisation is the root of all evil. Yet we should not pass up our opportunities in that critical 3 per cent." The profiler is what tells you which 3 per cent.

Feynman test A bug is a difference between your mental model of the program and the program itself. The model says "this function returns the discount-adjusted price"; the program says "it returns the gross price minus zero, because the discount lookup silently fails". Debugging is the process of finding which of the two is wrong (almost always the model), and updating it. The reason the discipline is hard is that the wrong half of the model is exactly the half you do not know is wrong: you cannot just inspect your own assumptions, because the wrong ones are the ones that feel obvious.
What's beyond the syllabus The deepest bugs are not in the code but in the specification: the code does exactly what its author intended, and the intention was wrong. Naur's "Programming as theory building" essay (Lecture 1) is the canonical statement of why these are the hardest bugs to find: the theory in the team's heads diverges from the world, and no inspection of the source can detect that. The remedy is conversation with the people who know the world, not better debugging tools.
Step 2

Why this matters

Two empirical observations motivate the discipline. The first is that debugging absorbs an unusually large fraction of professional time. Britton, Jeng, Carver, Cheak and Katzenellenbogen (Cambridge 2012) measured a sample of developers and found 50 to 75 per cent of time was spent on activity that could be classed as debugging or its prevention. Whatever the exact number, the order of magnitude is robust across surveys: debugging is the single largest line item in the engineering budget, larger than writing new features. Improving it by even 20 per cent is therefore more valuable than improving any other phase.

The second is that debugging is unevenly distributed across engineers. The same study, and the much longer informal record of Brooks's Mythical Man-Month, finds productivity differences between engineers of roughly an order of magnitude, with the gap most pronounced when the task is diagnosing existing problems. The gap is almost entirely a matter of method: experienced engineers use the scientific approach; inexperienced engineers change the code at random. The cost of acquiring the method is one careful session with a hard bug; the saving is permanent.

The performance argument is symmetric. A program that is 10x slower than necessary costs 10x in cloud bills, 10x in user latency, and an unbounded amount in opportunity (some features only ship at all if they fit a budget). Profiling, like debugging, is a method rather than a tool: the tool is two commands, the method is the discipline of measuring before guessing.

Step 3

The mental model

Scientific debugging (Zeller)

Zeller's framing turns debugging into a four-step loop, modelled on the scientific method:

The crucial discipline is that each turn of the loop must distinguish hypotheses. A debugger who keeps running the same failing test learns nothing on each iteration. A debugger who, on each iteration, changes exactly one variable and predicts a specific outcome learns one bit per turn; in log2(N) iterations they will have isolated the cause from N candidates.

Agans's nine rules

David Agans's Debugging (2002) is the most-cited practitioner book on the subject. The book is one rule per chapter; the rules together are an excellent checklist.

  1. Understand the system. Read the documentation; know what it is supposed to do before you ask why it is not.
  2. Make it fail. Reproduce the bug. If you cannot, you cannot debug it.
  3. Quit thinking and look. Get the actual data: logs, values, traces. Your model of the program is suspect by definition; the program itself is the ground truth.
  4. Divide and conquer. Binary search the code or the input. Bisect commits with git bisect.
  5. Change one thing at a time. Otherwise you do not know which change mattered.
  6. Keep an audit trail. Write down each hypothesis, each experiment, each result. Hard bugs take hours; you will lose your place.
  7. Check the plug. The obvious-but-stupid cause is the cause more often than your pride lets you accept.
  8. Get a fresh view. Explain the bug to a colleague (or a rubber duck). Often the explanation is the diagnosis.
  9. If you didn't fix it, it ain't fixed. Resist the temptation to believe a bug "just went away". It will return at the worst time.

Profiling: the same loop for performance

Profiling is the equivalent loop for performance bugs. Observe the symptom ("this script takes 30 minutes"), hypothesise where the time goes, measure with a profiler to confirm or refute, change one thing, measure again. Without measurement, performance work is guessing, and almost everyone guesses wrong: human intuition about where time goes in a program is famously bad. Knuth's "97 per cent" line is partly a statement about this fact.

Profilers come in two flavours. A deterministic profiler instruments every function call (cProfile, the Python default); accurate but slows the program by 10-100x. A sampling profiler interrupts the program at fixed intervals and records the stack (py-spy, scalene); approximate but adds 1-5 per cent overhead. For production-like workloads, prefer sampling; for small benchmarks, prefer deterministic.

Step 4

The detail

Reading a Python stack trace

The first artefact every debugger reads is the stack trace Python prints when an exception is unhandled. A trace has three structural pieces: the chain of frames (each line is one function call), the location within each frame (file and line number), and the exception type plus message at the bottom. Read it from the bottom up: the exception name and message are the symptom; the deepest frame is where the program actually failed; the frames above are how it got there.

Traceback (most recent call last):
  File "main.py", line 42, in <module>
    run_pipeline("input.csv")
  File "src/pipeline.py", line 15, in run_pipeline
    scores = compute_pd(df)
  File "src/pricing.py", line 87, in compute_pd
    return df["score"] / df["normaliser"]
ZeroDivisionError: float division by zero

The exception type tells you the genus of fault. KeyError means a dict lookup missed; AttributeError means an object did not have the named attribute (almost always a typo or a None where you expected an object); IndexError means an out-of-range sequence access; TypeError means an operation was applied to a value of the wrong type. Each has a small set of typical causes; learning the catalogue is one of the highest-leverage parts of becoming fluent.

For exceptions raised inside another exception ("during handling of the above exception, another exception occurred"), Python prints both with a separator. Read each chain from the bottom: the original cause is the most informative, even when the surface message is about the handler.

Three levels of "let me see what is happening"

From least to most powerful:

print debugging is the unfashionable workhorse. Add a print(x), run, look, remove. It works on every platform, in every IDE, and in the most hostile environments (production over SSH at 3 a.m.). The two refinements worth the effort: print the variable name with the value, and print to stderr so the output is not interleaved with the program's normal output:

import sys

x = 17
print(f"DEBUG: x = {x!r}", file=sys.stderr)

Python 3.8 added a special debug syntax that does both: print(f"{x=}") prints x=17. Use it.

logging is print debugging with structure. The standard logging module gives you levels (DEBUG, INFO, WARNING, ERROR, CRITICAL), per-module loggers, and configurable output formatting. The advantage over print is that the logging calls stay in the code; in production you set the level to INFO and the DEBUG calls do nothing; in an outage you set the level to DEBUG and the full trace is available.

import logging

logger = logging.getLogger(__name__)

def calibrate(scores, odr):
    logger.debug("calibrating scores=%d odr=%.4f", len(scores), odr)
    result = ...
    logger.info("calibration converged in %d iterations", result.iters)
    return result

Use %-style placeholders, not f-strings, in log messages: the logging machinery defers string formatting until it knows the log will actually be emitted, saving the cost on filtered-out messages. Configure the logger once, at program start, with logging.basicConfig; never print in library code.

the debugger is the most powerful tool. Python ships with pdb; the more user-friendly ipdb wraps it with the IPython REPL. The single-most-useful command is the one-liner that breaks at the current source line:

breakpoint()       # pauses here; runs the configured debugger (pdb by default)

Inside the debugger, the eight commands that cover 90 per cent of use:

CommandWhat it does
l (list)Show source around the current line.
p <expr>Print an expression.
pp <expr>Pretty-print (for dicts, lists).
n (next)Step to the next line, skipping into calls.

Modern IDEs (PyCharm, VS Code) wrap pdb in a graphical interface. The commands are the same; the GUI just makes the current state visible. For headless or remote use, the raw REPL is faster.

Post-mortem debugging

When a test or script fails with an unhandled exception, you can launch the debugger at the exact point of failure rather than re-running with a breakpoint. The --pdb flag does this for pytest:

pytest --pdb            # drop into pdb on the first failure
python -m pdb script.py # debug a crash, replaying it
import pdb; pdb.pm()    # post-mortem of the last unhandled exception

This is the single largest debugging time-saver most engineers do not know about. Instead of inserting breakpoint() calls and re-running, you let the failure happen and then inspect the corpse.

Common bug genera

A short taxonomy worth recognising. Naming the genus often suggests the fix.

git bisect: binary search through history

When a bug was introduced by some commit between "yesterday it worked" and "today it doesn't", git bisect binary-searches the history. Mark a known-bad commit, mark a known-good one, and git checks out the midpoint. You test, mark good or bad; it picks the next midpoint; in log2(N) steps you arrive at the offending commit. For N = 1024 commits, that is 10 tests.

git bisect start
git bisect bad           # current HEAD is broken
git bisect good v1.2     # a known-good earlier version
# git checks out the midpoint; run the test
git bisect good          # if the midpoint works
# ... or
git bisect bad           # if it does not
# repeat until git reports "first bad commit"
git bisect reset         # return to where you started

This is profoundly cheap once you have a reproducer and a test command. For a deterministic check (a unit test that fails), pass --bisect-run and a script and walk away.

Profiling: where does the time go?

The Python standard library ships cProfile, a deterministic profiler:

python -m cProfile -o profile.out -s cumulative script.py

# Or, in code:
import cProfile, pstats
profiler = cProfile.Profile()
profiler.enable()
run_pipeline("input.csv")
profiler.disable()
pstats.Stats(profiler).sort_stats("cumulative").print_stats(20)

The output is one row per function: ncalls (how many times it was called), tottime (total time spent in the function, excluding sub-calls), cumtime (total time including sub-calls), percall (average per call), and the function name. Sort by cumtime to see the time spent at the top of the call tree; sort by tottime to see the leaf functions doing the actual work.

For interpretation, two principles. First, the Pareto principle almost always applies: 80 to 95 per cent of the time is in 5 to 20 per cent of the functions. The slowest function is rarely subtle; usually one row at the top dwarfs the rest. Second, the cost of optimisation is the engineering attention you spend; if a function takes 1 per cent of the time, optimising it to zero saves 1 per cent. Spend your attention on the rows at the top, not at the bottom.

For long-running or production workloads, py-spy is a sampling profiler that attaches to a running process without modifying the code:

pip install py-spy
py-spy record -o profile.svg --pid <PID>       # produces a flamegraph
py-spy top --pid <PID>                          # live top-like view

The output is a flamegraph (Gregg 2011, originally for DTrace): the x-axis is the cumulative time fraction across samples; the y-axis is the call stack at the moment of each sample. Wide flames are functions where the program spent its time. Reading flamegraphs is its own skill but the pattern is intuitive: the widest bars at the bottom name the hot paths.

Memory profiling

Time profilers do not tell you where memory goes. Two tools fill the gap.

tracemalloc is in the standard library and tracks Python-level allocations:

import tracemalloc

tracemalloc.start()
run_pipeline("input.csv")
snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics("lineno")[:10]:
    print(stat)

scalene (Berger et al. 2020) is a third-party profiler that handles time, CPU, and memory together, including line-level resolution and a separate breakdown of Python vs native code. It is the closest thing to a one-stop tool.

The most common Python memory bug is the silent accumulation: a long-running loop appends to a list that is never cleared, or builds an ever-larger pandas DataFrame, or caches everything it sees. The signature in tracemalloc output is a single line of code with steadily-growing allocations. The fix is usually a generator (Lecture 3) or an explicit eviction policy.

Big-O: the other reason your program is slow

A profiler tells you which function is slow on the inputs you ran. The complexity of an algorithm tells you how the time grows as the input grows. A function that is fast on 10 items and slow on 10,000 has an algorithmic problem the profiler will name but not explain. The complexity hierarchy worth committing to memory:

Big-OName10x input → timeTypical operation
O(1)constant×1Dict lookup; appending to a list.
O(log n)logarithmic~×1.1Binary search; balanced-tree lookup.
O(n)linear×10Single pass over a list.
O(n log n)linearithmic~×13Sorting; FFT.
O(n²)quadratic×100Nested loop over a list; string concatenation in a loop.
O(2ⁿ)exponential×∞Brute-force subset enumeration.

The most common algorithmic bug is the inadvertent O(n²): a loop that does an in check on a list (each check is O(n)) instead of a set (O(1)). For small n, the loop is fast; for production-sized n, it dominates. The fix is one character: change [] to set() at the point of construction.

Worked example: a slow pipeline, diagnosed in five steps

Symptom: a calibration pipeline that ran in 2 minutes last quarter now takes 18 minutes on the same hardware.

Step 1 (observe). Reproduce: run with the production input on a clean machine. 18 minutes confirmed. Look at the log: no errors, no warnings.

Step 2 (hypothesise). Three candidates: (a) the input is 9x bigger; (b) a recent commit introduced an O(n²); (c) the database fixture is slower.

Step 3 (experiment). git bisect between last quarter's tag and HEAD with a 1-minute test workload. Twelve bisections later: one commit increases runtime fourfold, and it touched load_calibration_history.

Step 4 (verify). Profile that function with cProfile. tottime for one helper, find_segment_history, is 96 per cent of the whole. ncalls is roughly N². The helper does for h in history: if h.segment in segments_of_interest: ..., with segments_of_interest declared as a list.

Step 5 (fix). Change segments_of_interest from a list to a set. Re-run: 90 seconds. The other two hypotheses are discarded by the experiment.

The total wall-clock time is roughly 30 minutes (the bisection runs and the profile dominate). The fix is one character. Without the discipline, the same diagnosis from "the pipeline is slow" via "let me try a few things" is a day's work.

Step 5

Synthesis and what's next

Debugging is the application of the scientific method to a misbehaving program. Observe the symptom precisely; hypothesise causes that the evidence would let you distinguish; predict what an experiment would show under each hypothesis; run the experiment with one variable changed; repeat. Use logging in preference to print, the debugger in preference to logging, git bisect when the bug is recent, and post-mortem inspection in preference to re-running with breakpoints. Recognise the common genera (off-by-one, None, aliasing, mutable default, type, race, encoding, floating-point, specification); the diagnosis usually follows from the name.

Profiling is the same loop for performance. Measure first; the human intuition for where time goes is famously bad. Use cProfile for benchmarks, py-spy for production, scalene for combined time-and-memory. Read the output for the Pareto rows at the top. Combine the profiler's diagnosis with the Big-O table to tell the difference between "this function is slow" and "this function is asymptotically wrong".
