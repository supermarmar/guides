Markdown and the documentation toolchain

Documentation is the medium through which the team's theory of a system is communicated and preserved. This lecture covers the small, learnable language (Markdown), its standardised dialect (CommonMark), the structure that turns prose into a navigable site (Diátaxis), and the tools that compile it all (MkDocs, Sphinx, Pandoc).

Lecture 8 of 16 Reading time, 45 minutes Part III: documentation
Step 1

The 30-second version

Markdown is a plain-text syntax for marking up prose, invented by John Gruber and Aaron Swartz in 2004. The premise is that the source should be readable as-is, before any tool renders it. A heading is a line with a hash in front of it; an emphasised word is wrapped in asterisks; a list is a column of lines starting with dashes. The format succeeded because the source survives copy-paste into an email and back, and because any text editor on any operating system can edit it.

The original Gruber spec was famously ambiguous. The same source could render differently on two engines, because edge cases were under-specified. CommonMark (Jeff Atwood and John MacFarlane, 2014) is the corrective: a 90-page specification with a reference parser, against which any other implementation can be tested. Modern Markdown is almost always CommonMark with extensions: GitHub Flavoured Markdown (GFM) for code-hosting platforms, MyST for the Sphinx scientific-Python ecosystem, and the bespoke extensions that MkDocs adds for navigation and call-outs. Writing Markdown without knowing which dialect you are in is the documentation equivalent of writing Python without knowing which version.

Markdown is the input. The output is a documentation site, and the toolchain that produces it is the second half of this lecture. The three relevant tools are MkDocs (simple, Python, theme-led), Sphinx (older, more powerful, the standard for Python library docs), and Pandoc (a universal converter that treats Markdown as one input among many). The structural question, "what goes on which page?", is answered by Daniele Procida's Diátaxis framework: four quadrants (tutorials, how-to guides, reference, explanation), each with a different reader and purpose. Most bad documentation is one quadrant pretending to be another.

Feynman test A documentation site is a book with a search box. Markdown is the syntax in which each chapter is written; CommonMark is the agreed grammar of that syntax; MkDocs or Sphinx is the printer that binds the chapters; Diátaxis is the editorial decision about which chapter goes where. If you can name those four layers and the role of each, you can debate any documentation question with someone, without either of you talking past the other.
What's beyond the syllabus The deep reason documentation exists is not "to record what the code does", which a reader can in principle reconstruct, but to record why it does it. Naur's "Programming as theory building" essay (Lecture 1) is the canonical statement: the team's theory of the world is the asset, the code is the artefact, and when the people leave, the theory leaves with them unless it has been written down somewhere. Documentation is the institutional memory layer. Markdown is just the medium in which it happens to be written.
Step 2

Why this matters

The first reason is brutally practical: the team's wiki is the search engine for the team's brain. Aghajani et al. (ICSE 2019, "Software documentation issues unveiled") catalogued 4,000 documentation-related issues across 91 open-source projects and found that "incomplete or outdated" was the single most common complaint, followed by "incorrect" and "missing". The cost is paid in the form of questions asked twice, mistakes repeated, onboarding stalled, and decisions revisited because the rationale was lost. A documentation system that is cheap to write and cheap to host is not optional infrastructure.

The second reason is that Markdown specifically has eaten the world. GitHub, GitLab, Bitbucket, Reddit, Discord, Notion, Obsidian, and Slack all use a Markdown dialect for their input. The 2019 GitHub Octoverse report counted Markdown as the most-edited non-code file type across every public repository. Learning the syntax is therefore not a doc-engineering specialism; it is a baseline skill, like knowing how to format an email. The investment is one hour; the return is permanent.

The third reason is that Markdown enables docs-as-code: documentation that lives in the same repository as the code, in version control, reviewed by pull request, built by CI, and deployed alongside the artefact. The contrast is the old workflow, in which a doc team maintained a Confluence or Word document at one remove from the source. The docs-as-code workflow is the one industry surveys (the GitLab DevSecOps Report, the Stack Overflow Developer Survey) now treat as the default: documentation drifts less when it is one folder away from the code it describes, and a reviewer who notices that the docstring is wrong can fix it in the same PR.

Step 3

The mental model

Markdown in four shapes

Almost every Markdown construct fits in one of four shapes. Inline markup decorates words within a paragraph: emphasis, strong emphasis, code, links, images. Block markup creates structural units: headings, paragraphs, blockquotes, lists, horizontal rules. Code markup turns a block into a literal monospace display, optionally with a language hint for syntax highlighting. Tabular markup, an extension over the original Gruber spec, lets a grid of cells be authored in a pipe-and-dash pseudo-grid. Almost everything else is a flavour-specific extension on one of these four.

Markdown. A plain-text markup syntax, invented by John Gruber and Aaron Swartz (2004), in which structural elements are signalled by ASCII punctuation. Designed so the source is human-readable, the output is HTML.
CommonMark. A strongly-specified subset of Markdown (Atwood and MacFarlane, 2014) with a reference parser. Resolves the ambiguities of the Gruber spec. Adopted as the base for GFM, MyST, and the MkDocs and Sphinx Markdown back-ends.
GitHub Flavoured Markdown (GFM). CommonMark plus extensions for tables, fenced code blocks with language hints, task lists, strikethrough, automatic URL linking, and a few others. The de facto dialect across code-hosting platforms.

The Diátaxis framework

Daniele Procida's Diátaxis framework (proposed 2017, formalised at diataxis.fr) is the structural answer to "what kind of page am I writing?". It divides documentation into four quadrants, organised by two axes: the reader is either studying (acquiring skills) or working (using existing skills); and the page is either practical (action-oriented) or theoretical (cognition-oriented).

The diagnostic power of Diátaxis is that bad pages are usually identifiable as cross-contamination. A tutorial that lists every option of every function is a reference pretending to be a tutorial; a reader trying to learn cannot find the path through it. A reference page that explains why the API was designed a certain way is an explanation buried inside a reference; the reader looking up a flag has to wade through history. The framework's prescription is the same in every case: split the page along the quadrant line and let each side serve its reader.

Tools as compilers

Markdown by itself is a syntax, not a website. To get from a folder of .md files to a navigable, searchable site you need a static site generator: a program that reads the Markdown, applies a theme, builds a navigation tree, runs a search index, and emits HTML. In the Python ecosystem the two relevant choices are MkDocs (simpler, Markdown-only, theme-led) and Sphinx (older, originally reStructuredText, now with a strong Markdown front-end via MyST). Both produce a site; the choice between them is mostly a question of how much extension you need.

Pandoc, by John MacFarlane (who also wrote the CommonMark reference parser), is a separate beast. It is not a site generator; it is a many-to-many document converter. Given Markdown on stdin, it can emit HTML, PDF (via LaTeX), DOCX, EPUB, RTF, or any of about 30 other formats. The relationship between Pandoc and a site generator is the relationship between a printing press and a publishing house: one converts, one structures.

Step 4

The detail

Markdown syntax, by construct

The full CommonMark grammar runs to about 600 rules in the reference parser. The working subset, the one a writer needs to fluency, is about 15 constructs.

Headings. One to six hash signs at the start of a line, followed by a space and the heading text. The number of hashes is the level: one hash for an H1, six for an H6. Trailing hashes are allowed but optional. House style across this course is sentence-case headings, an H1 per file, and no skipped levels.

# File title (H1, one per file)
## Section heading (H2)
### Subsection (H3)

Emphasis. A single asterisk (or underscore) around a span gives italic emphasis; a double asterisk gives bold; a triple combines both. Style guides differ on whether to use asterisks or underscores; the root rule in this course is to use bold to define a term on first appearance only, and italic for genuine emphasis of meaning, not for general decoration.

*italic* and **bold** and ***both***

Inline code. Backticks around a span render the contents in a monospace font, with no further Markdown interpretation. Used for variable names, file paths, command-line snippets, and any literal token from the codebase. The empirical rule is that anything an editor would syntax-highlight inside a code block belongs in backticks when it appears inside prose.

Run `pytest -k test_pricing` to filter tests by name.

Fenced code blocks. Three backticks on a line by themselves open a code block; an optional language identifier on the same line tells the renderer how to syntax-highlight it. Three more backticks close the block. The same can be done with three tildes; the choice is conventional.

```python
def pd_to_logit(p: float) -> float:
    return math.log(p / (1 - p))
```

Links. Square brackets around the visible text, parentheses around the target. Both relative paths and absolute URLs work. Optional title text, shown on hover, goes in quotes inside the parentheses.

[CommonMark spec](https://spec.commonmark.org/0.31.2/ "the current spec")
[Lecture 1](01-what_is_software_engineering.html)

Images. Identical syntax to links, prefixed with an exclamation mark. The alt-text in the square brackets is what screen readers will announce, and it is what is shown if the image fails to load. Avoid decorative images with no alt-text; if the image carries no information, that is itself a sign it should be removed.

![ROC curve for the application scorecard](figs/roc.png)

Lists. Unordered lists use a hyphen, asterisk, or plus at the start of each line; ordered lists use a number followed by a full stop. The actual numbers are not enforced; 1. three times renders as 1, 2, 3. Nest with four spaces (or one tab) of indentation. The general drafting rule is that prose beats bullets except when items are genuinely enumerable.

- credit risk
- market risk
- operational risk

1. observe the symptom
2. hypothesise a cause
3. experiment

Blockquotes. A greater-than sign at the start of a line marks a quotation. Useful for direct quotes, primary-source extracts, and call-outs in styles that do not support fancier admonitions. In MkDocs Material a blockquote becomes a stylised aside.

> Premature optimisation is the root of all evil. (Knuth, 1974)

Tables. Pipes separate cells, a header-separator row of dashes (optionally with colons for alignment) sits below the header. Tables are not in the original Gruber spec; they are a GFM extension supported by every modern parser.

| Metric  | Definition       | Unit |
|---------|------------------|------|
| PD      | Probability of default | %    |
| LGD     | Loss given default     | %    |
| EAD     | Exposure at default    | £    |

Math. Inline maths is single-dollar-delimited, display maths is double-dollar-delimited, both rendered by KaTeX or MathJax in the browser. Maths is not in CommonMark; it is an extension provided by MkDocs (via pymdownx.arithmatex) or by Sphinx (via the math directive). The lectures in this course use KaTeX.

The Basel A-IRB capital charge $K$ is given by

$$K = LGD \cdot \left[ \Phi\!\left(\frac{\Phi^{-1}(PD) + \sqrt{R}\,\Phi^{-1}(0.999)}{\sqrt{1-R}}\right) - PD\right]$$

Task lists. A GFM extension. A list item starting with - [ ] renders as an unchecked checkbox; - [x] renders checked. Useful for in-document checklists.

- [x] write the lecture
- [ ] proofread the lecture
- [ ] publish the lecture

Horizontal rules, strikethrough, and footnotes round out the working set. Three dashes on a line by themselves render as a horizontal rule. Double-tilde around a span renders as strikethrough (GFM). Footnotes use [^1] in-text and a corresponding [^1]: definition at the bottom of the file; they are a Pandoc and MkDocs extension, not core CommonMark.

Common pitfall The most common Markdown bug is forgetting a blank line. CommonMark requires a blank line above and below block elements (headings, lists, code fences, blockquotes); without it, a heading that follows a paragraph without a blank line is rendered as part of the paragraph. The diagnostic, when a heading "disappears" or a list runs into the prose above, is almost always a missing blank line.

Tools: MkDocs, Sphinx, Pandoc

MkDocs (Tom Christie, 2014) is the simpler of the two site generators. It reads a folder of Markdown files, a YAML configuration file (mkdocs.yml), and emits a static site. The Material theme by Martin Donath has become the de facto standard; it gives an instant-search box, dark mode, code-block copy buttons, and an admonition system out of the box.

# mkdocs.yml
site_name: Risk modelling guide
theme:
  name: material
  features:
    - navigation.tabs
    - content.code.copy
nav:
  - Home: index.md
  - Credit risk:
      - PD models: credit/pd.md
      - LGD models: credit/lgd.md
markdown_extensions:
  - pymdownx.arithmatex:
      generic: true
  - admonition
  - footnotes
  - tables

Sphinx (Georg Brandl, 2008) was built for the Python language documentation itself and is still the standard for library docs in the scientific-Python ecosystem (NumPy, SciPy, pandas, scikit-learn). Its original input language is reStructuredText, which has stronger semantics for cross-referencing than Markdown. The MyST extension lets you write in Markdown while preserving the cross-reference power. Sphinx wins where you need autogenerated API documentation from docstrings (an apparatus called autodoc; Lecture 14 covers it in depth).

Pandoc (John MacFarlane, 2006) is the universal converter. The classic invocation produces a PDF from a Markdown file via LaTeX:

pandoc lecture.md -o lecture.pdf --pdf-engine=xelatex
pandoc lecture.md -o lecture.docx
pandoc lecture.md -o lecture.html --standalone --mathjax

Pandoc's value proposition is that the input format and the output format are independent. Once a piece of prose is in Markdown, it can become any of about 30 formats with a one-line change. This is what makes Markdown a durable choice: if the toolchain dies, the source is still readable, and Pandoc will convert it to whatever survives.

Admonitions and call-outs

Plain CommonMark has no syntax for "this is a warning" or "this is a note". The MkDocs Material theme adds an admonition syntax that has become a de facto standard; Sphinx has its own directive form; the MyST flavour bridges the two. The shape of the syntax is a fenced block prefixed with three exclamation marks (in MkDocs) or three colons (in MyST), followed by the admonition type:

!!! warning "Use a set, not a list"
    For an `in` check inside a loop, a list is O(n) per lookup; a set is O(1).

!!! note "PEP reference"
    The relevant standard is PEP 8 §4 (whitespace in expressions).

The recognised admonition types across MkDocs Material are note, abstract, info, tip, success, question, warning, failure, danger, bug, example, and quote. The taxonomy is large enough that the temptation is to use too many; the discipline, mirrored in the four call-out classes used in these lectures, is to choose two or three and apply them consistently.

The CommonMark spec and dialect drift

Until 2014, the canonical Markdown reference was Gruber's original 2004 page, which left dozens of edge cases unspecified. Different engines (Markdown.pl, MultiMarkdown, Pandoc, Maruku, Discount, Showdown) resolved the ambiguities differently, and source that rendered one way on Stack Overflow could render differently on GitHub. The CommonMark project (Atwood, MacFarlane, Brand) responded with a 90-page specification, a reference parser written in C, and a test suite of about 650 examples. Any compliant parser must produce the prescribed HTML for every example.

CommonMark is the base. Three extension layers sit on top: GFM adds tables, task lists, strikethrough, and autolinks; MyST adds the Sphinx directive system (cross-references, footnotes, citations, math, embedded code execution); PHP Markdown Extra (older, still in use by some engines) adds footnotes and definition lists. When a piece of Markdown does not render the way you expect, the diagnosis is almost always "wrong dialect": the source uses a GFM extension on a CommonMark-only renderer, or a MyST directive on a vanilla MkDocs install.

Worked example: structuring a credit-risk model document

Worked example: applying Diátaxis to a real handbook

Suppose you inherit a single 80-page Word document titled "PD model methodology". A reader asks where to find out how to recalibrate the model on new data; another asks why the model uses logit rather than probit. A third needs to look up the exact CRR article the model claims compliance with. Currently all three of them must read the whole document. Applying Diátaxis is a structural fix.

Step 1 (classify each section). Skim the document and label every section with one of T (tutorial), H (how-to), R (reference), or E (explanation). The methodology overview becomes E; the recalibration steps become H; the table of parameter values becomes R; the worked example for a new joiner becomes T.

Step 2 (split into files). Move each section into its own Markdown file, named for the quadrant. The folder structure becomes docs/credit/pd/{tutorials,how_to,reference,explanation}/. A reader now navigates directly to the quadrant they need.

Step 3 (de-duplicate and link). Sections that drifted will have repeated content. Pick the canonical home for each idea, link the others to it. The model's compliance claim lives in reference/regulatory_mapping.md; the recalibration how-to that mentions compliance simply links to it.

Step 4 (compile). Add an mkdocs.yml with a four-tab navigation matching the quadrants, point Read the Docs at the repository, push, and the site builds. The reader asking "how do I recalibrate" is now one tab and one link away.

The same 80 pages of content, structured this way, becomes ten times more useful for the same word count. The investment is one week of editorial work, with no new writing.

Step 5

Synthesis and what's next

Markdown is a small language with a large reach. The 15 constructs you need to fluency can be learned in an hour; the dialect (CommonMark, GFM, MyST, Material) needs to be confirmed before any non-trivial document is written, because the differences are real. The tooling layer is a separate question: MkDocs for an internal site, Sphinx where Python API docs need to be auto-generated, Pandoc for any one-off conversion. Diátaxis is the editorial framework that sits above all of it; the four quadrants of tutorials, how-to guides, reference, and explanation are the structural answer to most "where does this page go?" arguments.

The deeper point is that documentation is the artefact in which the team's theory of the system is recorded. Naur's argument (Lecture 1) is that the code is only the visible half of the system; the invisible half is the shared understanding of why the code is shaped the way it is. Markdown is the most durable form in which that understanding is recorded: it survives the death of any tool, because the source is still readable. Treat docs-as-code accordingly: in the repository, in version control, reviewed by pull request, built by CI.
