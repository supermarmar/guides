Testing: unit, integration, property-based

A test is an automated assertion that the code behaves as you expect. The test suite is the only definition of "correct" that survives the original author. This lecture covers the three test levels, the pytest framework, the Arrange-Act-Assert pattern, Hypothesis for property-based testing, test doubles, the coverage trap, and Kent Beck's red-green-refactor cycle.

Step 1

The 30-second version

A test is a small program that exercises another program with known inputs and asserts that the outputs are correct. When the assertion fails, the test fails; when every assertion passes, you have evidence (not proof) that the program works for the cases the tests cover. A test suite is a collection of tests run automatically, on every change, by a continuous-integration server.

Tests are usually classified by their scope. A unit test exercises a single function or class in isolation, with all its collaborators replaced by simpler stand-ins. An integration test exercises several real components together: a function plus the database it writes to, or a service plus the HTTP API it calls. An end-to-end test drives the whole system from the outside, the way a user would. The three levels trade speed and isolation against realism: a unit test runs in milliseconds and tells you the function is correct in isolation; an end-to-end test runs in minutes and tells you the system works.

Python's standard test framework is pytest, with Hypothesis for property-based testing and coverage.py for measuring how much of the code is exercised. The setup cost for a new project is minutes; the working idiom (functions named test_* containing assert statements) is small enough to recite. Three commands carry most of the practice: pytest to run, pytest -k name to filter, pytest --lf to re-run only the last failures.

Feynman test A test is a frozen example of how the code should behave. When you write assert square(3) == 9, you have recorded, in code, that "the meaning of square includes the case of three going to nine". Once that example is in the suite, no future change to square can break that case without the test failing first and someone having to look at it. The test is a one-way ratchet on the behaviour: behaviour can grow, but it cannot quietly regress. The discipline of writing tests is the discipline of writing down enough examples that the ratchet covers the behaviour you care about.
What's beyond the syllabus Tests are not proofs. A passing test suite is evidence that no example you wrote down behaves wrongly; it says nothing about cases you did not write down. The discipline of formal verification (Coq, Isabelle, Dafny, TLA+) produces proof rather than evidence and is used in compilers, distributed protocols, and safety-critical avionics. For everyday application code, the cost is too high; the test suite is the engineering substitute. Hillel Wayne's "Practical TLA+" (2018) is the accessible entry point if the proof side ever becomes relevant.
Step 2

Why this matters

Tests pay back along the cost-of-defects curve introduced in Lecture 1. A regression that the test suite catches in CI, two minutes after the offending commit, costs the author a few minutes to investigate. The same regression caught by a user, in production, two days later, costs the team an outage, a post-mortem, a hotfix, and the trust of whichever customer was affected. The order-of-magnitude differences in Boehm's curve are mostly a statement about the cost of paged engineers and rolled-back releases.

The deeper case is the one Forsgren, Humble and Kim make in Accelerate (2018). Across a decade of DORA survey data, the practices most strongly correlated with high delivery performance are (1) version control of everything, (2) automated tests, (3) trunk-based development, and (4) continuous integration. Teams with strong automated testing deploy more often, recover faster, and have lower change-failure rates than teams without. The result contradicts the older intuition that tests slow you down. The mechanism is that tested code can be changed without fear, and code that can be changed without fear is shipped faster.

Kent Beck's Test-Driven Development by Example (2003) makes the same point at the individual level. Writing a test before the code (1) forces you to specify what "done" means, (2) keeps each change small enough to fit in working memory, and (3) gives you immediate feedback when something breaks. Beck's claim is not that TDD produces more correct code, although the empirical evidence (Erdogmus et al. 2005; Fucci et al. 2017) modestly supports it; the claim is that TDD produces a steadier, less anxious development rhythm. Tests are scaffolding for the writer as well as for the reader.

Step 3

The mental model

Three abstractions organise everything in the lecture. The first is the test pyramid; the second is the AAA pattern; the third is the distinction between example-based and property-based testing.

The pyramid (Cohn)

Mike Cohn's Succeeding with Agile (2009) introduced the test pyramid as a visual heuristic for how to spend the testing budget. Many, fast, isolated unit tests at the base; fewer integration tests in the middle; very few end-to-end tests at the top. The pyramid is a guide to proportion, not a rule; the underlying principle is that tests at higher levels are more expensive to write, slower to run, and more brittle, so their value has to be higher to justify them.

Arrange, Act, Assert

Every test, regardless of level, fits one shape. Arrange: set up the input data and any context the code under test needs. Act: call the code under test. Assert: check the output against the expected value. The pattern is sometimes called "Given/When/Then" (Cucumber, BDD). A test that does not have these three sections visible is usually doing too much.

def test_square_of_three_is_nine():
    # Arrange
    x = 3

    # Act
    result = square(x)

    # Assert
    assert result == 9

The discipline pays off when tests fail. A failing test with a clear Arrange section tells you immediately what data it ran with; a failing test with a one-line assert tells you what it expected. The opposite, a 30-line test that mixes setup, calls, and assertions, is essentially debugged anew on every failure.

Example-based vs property-based

An example-based test pins one specific input to one specific output: assert square(3) == 9. A property-based test asserts a relationship that should hold for all inputs in some space: "for every non-negative x, square(x) is non-negative". The framework (Hypothesis, in Python; QuickCheck in Haskell, originally) generates random inputs, runs the assertion, and on failure shrinks the failing input towards a minimal counterexample.

from hypothesis import given, strategies as st

@given(st.floats(min_value=0, allow_nan=False))
def test_square_is_non_negative(x):
    assert square(x) >= 0

Property-based tests find edge cases that human authors do not think to write (zero, negative zero, NaN, the largest representable float, the empty list). The cost is that the property itself must be worth stating: most production code has more examples than properties, so property tests complement rather than replace example tests.

Step 4

The detail

pytest in 80 per cent

pytest is the standard Python test framework. A pytest test is a function whose name begins with test_, in a file whose name begins with test_, in any directory the runner discovers. The body uses bare assert statements; pytest rewrites them at import time to give detailed failure messages.

# tests/test_pricing.py
from pricing import compute_pd

def test_compute_pd_returns_a_probability():
    pd = compute_pd(score=0.5, segment="retail")
    assert 0 <= pd <= 1

def test_compute_pd_is_monotonic_in_score():
    low  = compute_pd(score=0.2, segment="retail")
    high = compute_pd(score=0.8, segment="retail")
    assert high > low

Run with pytest; useful flags:

pytest                          # run everything
pytest tests/test_pricing.py    # run one file
pytest -k "monotonic"           # filter by name (substring)
pytest -m "not slow"            # filter by marker
pytest --lf                     # run only the last-failed tests
pytest -x                       # stop on first failure
pytest -v                       # verbose: one line per test
pytest -s                       # do not capture stdout

Parametrize for table-driven tests

When the same test logic should run on many inputs, use @pytest.mark.parametrize rather than copying the function:

import pytest

@pytest.mark.parametrize("x, expected", [
    (0, 0),
    (1, 1),
    (3, 9),
    (-2, 4),
    (10, 100),
])
def test_square(x, expected):
    assert square(x) == expected

This is a single test function executed five times, with five rows in the output. The pattern is the natural fit for table-driven specifications: a list of (input, expected) pairs, each row a self-contained example.

Fixtures: setup and teardown without inheritance

A fixture is a function that produces a value for tests to consume. Pytest's fixture model uses dependency injection: any test that names a fixture as a parameter gets the fixture's value passed in. Fixtures replace the older xUnit-style setUp and tearDown methods.

import pytest
from pricing import PricingModel

@pytest.fixture
def model():
    m = PricingModel.load("config/default.yaml")
    yield m              # value handed to the test
    m.close()            # teardown after the test

def test_model_calibrates_on_default_segment(model):
    result = model.calibrate(segment="retail")
    assert result.converged

Fixtures have a scope, which controls when they are re-created. The default is function (a fresh instance per test). For expensive setup (a database connection, a loaded model), use module or session scope to share across tests. Beware shared state: a session-scoped fixture mutated by one test will leak into the next.

@pytest.fixture(scope="session")
def db():
    conn = sqlite3.connect(":memory:")
    conn.executescript(SCHEMA_SQL)
    yield conn
    conn.close()

Test doubles (Meszaros)

When the code under test depends on something inconvenient (a database, an API, a clock, a random-number generator, an LLM), unit tests replace it with a test double. Gerard Meszaros's xUnit Test Patterns (2007) gives the canonical taxonomy. Four are worth distinguishing.

DoubleWhat it isWhen to use
DummyAn object passed but never used.Filling a required argument.
StubReturns canned values to questions.The code under test reads from a dependency; you control the reads.
SpyStub plus recording of calls made to it.You want to assert "the dependency was called with X".
MockSpy with pre-programmed expectations; fails the test if the expectations are not met.Verifying interaction patterns. Use sparingly.
FakeA working alternative implementation, simpler than the production one.An in-memory database for tests that would otherwise hit Postgres.

The Python standard library's unittest.mock module provides Mock, MagicMock, and patch; the third-party pytest-mock integrates the same machinery as a fixture (mocker). The general advice (Khorikov, Unit Testing, 2020) is to prefer real objects, then fakes, then stubs, then spies, then mocks, in that order. Mocking is brittle: a test that asserts "the database's save method was called with this exact argument" breaks the moment you refactor to call save_all instead, even if the behaviour is unchanged.

Property-based testing with Hypothesis

Hypothesis (MacIver, ongoing since 2013) brings the QuickCheck idea (Claessen and Hughes 2000) to Python. You describe the input space using strategies; Hypothesis generates examples, runs your assertion, and shrinks any counterexample to a minimal form.

from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_reverse_is_involution(xs):
    assert list(reversed(list(reversed(xs)))) == xs

@given(st.integers(min_value=0), st.integers(min_value=0))
def test_addition_is_commutative(a, b):
    assert a + b == b + a

@given(st.text())
def test_json_round_trip(s):
    import json
    assert json.loads(json.dumps(s)) == s

The trick is finding the property worth asserting. The four idiomatic shapes:

  1. Round-trip: encode-then-decode is the identity. parse(format(x)) == x.
  2. Invariant: a relationship that holds for all inputs. "sorted output has the same length as the input".
  3. Idempotence: applying twice equals applying once. normalise(normalise(x)) == normalise(x).
  4. Oracle: a slow but obviously-correct implementation. "the fast sort agrees with bubble sort on all inputs".

When Hypothesis finds a counterexample, the report tells you the exact input and the steps it took to shrink it (often from a 50-item list to a 2-item one). Saving the failing case to a regression file means the example becomes part of the suite forever.

Coverage and its limits

Coverage is the fraction of source lines (or branches) the test suite executes when run. coverage.py measures it; pytest --cov integrates with pytest. A line that is never executed by any test is one whose behaviour your suite says nothing about.

Two cautions. First, line coverage is a weak measure; branch coverage is tighter (does every conditional take both paths?), and even branch coverage misses untested combinations. Second, coverage is subject to Goodhart's law: when 80 per cent coverage becomes the team target, people write tests that touch lines without asserting anything, and coverage rises without improving the suite. Coverage is a diagnostic for the absence of tests, not a measure of the presence of good ones. Treat it as a smoke alarm, not a thermostat.

100 per cent coverage is not the goal A test suite at 100 per cent line coverage can still miss every interesting edge case if every test asserts only that the function does not raise. Conversely, a suite at 70 per cent coverage that catches every regression for two years is excellent. Use coverage to identify untested regions and decide, deliberately, whether they need tests. Trivial getters and setters, pass-through methods, dataclasses, and the bodies of __repr__ usually do not.

The TDD cycle (Beck)

Beck's Test-Driven Development by Example (2003) prescribes a three-step loop:

  1. Red. Write a failing test for the smallest piece of behaviour you want next. Run it; confirm it fails.
  2. Green. Write the simplest code that makes the test pass. Resist the urge to generalise.
  3. Refactor. With the test passing, improve the structure of the code without changing its behaviour. Run the test after every change; it must stay green.

The loop has two non-obvious benefits beyond the obvious one (you get a test). First, the "red" step is a forcing function for specification: you cannot write a failing test for behaviour you cannot describe. Second, the "refactor" step is safe because the test is the harness; you can rearrange the code aggressively, knowing that the test will tell you when you have broken it.

TDD is a personal discipline, not a team mandate. Many practitioners adopt it for greenfield code and skip it for exploratory work. The lectures that follow assume only that tests exist, not that you wrote them first.

Test smells

A smell is a surface feature that suggests a deeper problem. Khorikov's Unit Testing (2020) catalogues the worst test smells, of which six are common enough to name.

SmellSymptomUnderlying problem
Brittle testBreaks on internal refactors that do not change behaviour.Over-mocking; testing internals instead of contracts.
Flaky testPasses sometimes, fails sometimes, on the same code.Time, randomness, shared state, network. Fix the cause; do not retry.
Slow testTakes seconds or more.Hitting a real database or network. Move to integration tier.
Test interdependenceTest B passes only when A runs first.Shared state via fixture scope or module variables.
Assertion rouletteTest has ten asserts; failure does not say which behaviour broke.One test is doing too many things. Split.
Mystery guestTest relies on an external file or fixture not visible in the test body.Move inputs inline, or name the fixture explicitly.
Worked example: testing a PD calibrator with three styles

The unit under test is calibrate(scores, observed_default_rate), which fits a logistic recalibration so the predicted default rate matches the observed rate on the calibration sample.

Example-based unit test, AAA pattern:

def test_calibrate_matches_observed_rate(): scores = pd.Series([0.1, 0.3, 0.5, 0.7, 0.9]) odr = 0.30 cal = calibrate(scores, odr) assert abs(cal.predicted_rate - odr) < 1e-6

Parametrised version covering several segments:

@pytest.mark.parametrize("odr", [0.05, 0.10, 0.30, 0.50]) def test_calibrate_matches_each_rate(odr): scores = pd.Series([0.1, 0.3, 0.5, 0.7, 0.9]) cal = calibrate(scores, odr) assert abs(cal.predicted_rate - odr) < 1e-6

Property-based version asserting monotonicity:

@given( scores=st.lists(st.floats(min_value=0, max_value=1), min_size=10, max_size=100), odr=st.floats(min_value=0.01, max_value=0.5), ) def test_calibrate_is_monotonic_in_score(scores, odr): cal = calibrate(pd.Series(scores), odr) sorted_scores = sorted(scores) sorted_outputs = [cal.predict(s) for s in sorted_scores] assert sorted_outputs == sorted(sorted_outputs)

The three styles tell complementary stories. The example tests state one fact each, in plain code. The parametrised test states that the calibration works at several rates without repeating itself. The property test states the deeper fact that calibration preserves the score ordering, a thing the example tests do not assert and which is the property a reviewer would most want to know is preserved across refactors.

Step 5

Synthesis and what's next

Tests are the standing record of what "correct" means for your code, written in code. The discipline is: many small example tests at the unit level, a deliberate smaller set of integration tests at the seams, a very small set of end-to-end tests for the critical paths. Use pytest, parametrize for tables, fixtures for setup, and Hypothesis for properties. Prefer real objects over fakes, fakes over stubs, stubs over spies, spies over mocks. Treat coverage as a smoke alarm, not a target.

The economic argument is two-fold and converges. Tests shift defects left on Boehm's curve, so each defect costs less to fix; tests also enable the trunk-based, continuous-delivery flow that the DORA programme finds is associated with higher delivery performance. The deeper effect is on the writer: tested code can be changed without fear, and code that can be changed without fear is the only kind that ships fast for years.
