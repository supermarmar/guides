Orchestration

A kitchen at service is not a sequence of recipes. It is a set of dishes that must exist, in a state, by a time, drawing on ingredients that arrive when suppliers feel like delivering them, with a plan for the evening the fish is late. An orchestrator is that plan, written down and executable, and the interesting question is whether it thinks in tasks or in dishes.

Step 1

The 30-second version

An orchestrator decides what runs, in what order, on what trigger, with what concurrency, and what happens when a step fails. The dependency structure is a directed acyclic graph, and the orchestrator's job is to execute it, observe it, retry it, and let a human intervene.

Two philosophies compete, and the difference is more than presentational. Task-centric orchestration, exemplified by Apache Airflow, describes work: run this extract, then run that transformation, then send that email. Asset-centric orchestration, exemplified by Dagster, describes outcomes: this table should exist, be fresh within four hours, and be derived from those two tables. The task view asks "what should happen?"; the asset view asks "what should be true?", and derives the tasks from it.

Whichever you pick, four properties separate a pipeline that survives from one that generates a weekly incident. Every step is idempotent, so a retry is safe. Every run is parameterised by a partition, usually a date, so a rerun for March is a rerun for March. Retries have backoff and a limit, and failure alerts a named owner. And concurrency is capped, so a backfill does not overwhelm the source system you share with the bank's customers.

Feynman test Two ways to run a kitchen. The first is a list: at six, start the stock; at seven, prepare the garnish; at half past, plate the fish. It works until the fish is late, at which point the list is useless because it describes actions rather than the state of the kitchen, and someone must reason from scratch about what can still proceed. The second is a set of dishes, each with its ingredients and a time by which it must be ready. When the fish is late, the answer is visible: everything not downstream of the fish continues, the fish dish is stale, and the head chef is told which service is at risk. Both are plans. Only the second one answers the question you actually have at seven o'clock.
The orchestrator is not where logic lives A recurring failure is a pipeline whose business logic has leaked into the orchestration layer: transformations written inside task definitions, values passed between tasks through the orchestrator's own message mechanism, conditional business rules encoded as branching in the graph. It runs, and it is untestable, unreadable, and locked to the tool. Keep the orchestrator thin: it triggers, sequences, retries, and reports. The logic belongs in SQL models, in tested Python modules, in the transformation layer of Lecture 15, where it can be run and tested without the orchestrator being present at all.
Step 2

Why this matters

Partial failure is the normal case, and the recovery question is what costs you. A twelve-step monthly pipeline fails at step seven. Which steps must rerun? With idempotent, partitioned steps the answer is "seven onwards, for that partition", and it is a button. Without them the answer requires reasoning about what each step already wrote, whether rerunning step eight will double count, and whether step five's output is still valid, which is an hour of careful thought at three in the morning by someone who did not write it.

Time-based scheduling is a guess about data arrival. A job scheduled for two in the morning because the extract "usually lands by one" fails whenever the extract is late, and worse, sometimes succeeds on stale data. Data-aware triggering, a sensor waiting for the manifest file or an asset declaring that it depends on another asset's materialisation, replaces the guess with a fact. The distinction is the single largest source of avoidable overnight failures in banking pipelines, where the upstream extract is produced by a batch you do not control.

Backfills are where an orchestrator earns its cost. Reprocessing twenty-four months means twenty-four runs of the same graph with different parameters, with limited concurrency, individual failure tracking, and the ability to resume. That is a feature of the orchestrator or it is a bespoke script somebody writes under pressure. Since Lecture 10 established that backfills are routine rather than exceptional, the capability is not optional.

Step 4

The detail

Airflow, and its four classic traps

Airflow's model is a Python file defining a DAG of tasks, each an operator instance, executed by a scheduler dispatching to workers. It is mature, ubiquitous, and has a large operator ecosystem, which is why most banks that orchestrate anything orchestrate it with Airflow.

from airflow.decorators import dag, task
from airflow.sensors.filesystem import FileSensor
import pendulum

@dag(
    schedule="0 2 1 * *",                      # 02:00 on the first of each month
    start_date=pendulum.datetime(2021, 6, 1, tz="Europe/London"),
    catchup=False,                             # do NOT silently backfill on deploy
    max_active_runs=1,
    default_args={"retries": 3, "retry_exponential_backoff": True,
                  "retry_delay": pendulum.duration(minutes=5),
                  "execution_timeout": pendulum.duration(hours=2)},
    tags=["risk", "monthly"],
)
def monthly_risk_pipeline():

    wait_for_manifest = FileSensor(
        task_id="wait_for_manifest",
        filepath="/landing/loans/{{ data_interval_start | ds }}/_MANIFEST",
        poke_interval=300, timeout=6 * 3600, mode="reschedule",   # frees the worker slot
    )

    @task
    def load_bronze(reporting_date: str) -> None:
        ...     # thin wrapper: calls a tested module, passes the date explicitly

    @task
    def validate(reporting_date: str) -> None:
        ...     # the Lecture 16 suite; raises to fail the task

    @task
    def build_models(reporting_date: str) -> None:
        ...     # invokes dbt for the partition

    date = "{{ data_interval_start | ds }}"
    wait_for_manifest >> load_bronze(date) >> validate(date) >> build_models(date)

monthly_risk_pipeline()

Four traps account for most Airflow incidents. Top-level code: anything at module level runs every time the scheduler parses the file, which is constantly, so a database query or a large import there will cripple the scheduler. Passing data through XCom: the inter-task message mechanism is for small values such as identifiers and paths, and pushing a dataframe through it is an anti-pattern that fills the metadata database. Catchup: with catchup=True and a historical start date, deploying a DAG launches a run for every missed interval at once, which has taken down more than one source system. And timezones and the data interval: the parameter you want is almost always the data interval rather than the wall-clock execution time, and confusing them shifts every partition by one period.

    return dg.AssetCheckResult(passed=duplicates == 0,

Three things follow from describing assets rather than tasks. The unit of observability is the table, so the interface answers "is fact_account_month for March fresh, and did its checks pass?" rather than "did job 4,412 exit zero". Partitions are first-class, so a backfill is selecting a range of partitions in the interface rather than a special script. And asset checks attach the Lecture 16 validations to the asset itself, with a blocking flag that prevents downstream materialisation, which is the publish gate expressed structurally rather than as a task that someone might reorder.

The pragmatic view: an existing Airflow installation is not a problem to be migrated away from, and most of this lecture's value is available in either tool provided you supply the four properties yourself. What Dagster does is make those properties the path of least resistance rather than a discipline you must impose.

Failure handling that works at three in the morning

Retries with exponential backoff for transient failures, and a hard limit so a genuinely broken step stops rather than retrying for six hours. An execution timeout on every task, because a hung task holds resources and never alerts. Alerts routed to a named owner per pipeline, not to a shared inbox, with the alert containing the partition, the failing step, the error, and a link to the run. And a runbook per pipeline: what this does, who owns it, what the common failures are, what is safe to rerun, and who to call upstream. The runbook is what makes the pipeline supportable by someone other than its author, which is the actual test of whether it is production code.

One more control belongs here. Cap concurrency per external system, using Airflow pools or Dagster concurrency limits. A backfill of twenty-four months that runs twenty-four extracts in parallel against a live core banking database is an outage you caused, and it is entirely preventable with one configuration value.

Orchestrate the checks, not just the work A pattern worth adopting: make validation a node in the graph with the same status as any other, positioned so that nothing downstream runs when it fails. This sounds obvious and is frequently not done, because validation is bolted on as a notification rather than a dependency. When the check is a blocking node, "the data is bad" and "the pipeline stopped" become the same event, which is exactly what you want: consumers keep yesterday's good data instead of receiving today's bad data, and somebody is told. When the check merely emails, consumers get the bad data and the email arrives after they have used it.
Worked example: the monthly risk pipeline, and then a twenty-four-month backfill

The pipeline, in dependency order, with the choices that matter at each step.

1. Wait, do not guess. A sensor waits for the manifest file for the reporting month, in reschedule mode so it releases its worker between checks, with a six-hour timeout. On timeout it alerts the data owner with the expected path. Note what this replaces: a schedule at 02:00 that assumed the extract landed at 01:00 and failed silently on the three nights a year it did not.

2. Land bronze, idempotently. The task calls a tested module with the reporting date passed explicitly, writing the raw arrival to the partition. Rerunning replaces that partition, per Lecture 06. The task itself is a dozen lines: the orchestrator holds no logic.

3. Validate, blocking. The Lecture 16 suite runs as its own node. Gate 1 and gate 2 failures raise, which fails the task, which stops the graph. Quarantine counts are recorded as metadata on the run so they are visible in the interface rather than buried in a log.

4. Build the models. One node invoking the transformation layer for the partition, or better, the transformation models exposed as individual assets so that a failure in one mart does not obscure the success of the others. Reconciliation, gate 3, runs after the build and before anything is marked published.

5. Publish and notify. The publish step is the atomic commit of Lecture 14. Notification goes to consumers on success with the partition and the headline reconciliation figures, which turns the pipeline into something people trust because they can see it working, rather than something they only hear about when it breaks.

Now the backfill. A definition change requires reprocessing twenty-four months. The mechanics, given the four properties:

# Dagster: select the asset and the partition range, in the UI or the CLI
dagster asset backfill --select fact_account_month+ \
    --partition-range 2024-04-01...2026-03-01

# Airflow: clear the interval and let the scheduler re-run it
airflow tasks clear monthly_risk_pipeline \
    --start-date 2024-04-01 --end-date 2026-03-01 --yes

The four things that make it safe. Concurrency capped at three partitions at a time, so the source database sees a load comparable to a normal night rather than twenty-four times it. Each partition idempotent, so a partial backfill can simply be re-run for the failed partitions without reasoning about what was already written. Each partition reconciled independently, so a break in one month is visible and localised rather than averaged away. And the whole operation logged as an approved change with a reason, because reprocessing twenty-four months of reported figures is a change to published numbers and belongs in the change record alongside the code that motivated it.

What goes wrong without them. Without capped concurrency the source degrades and someone from operations calls. Without idempotency the retried partitions double count and the exposure figures are wrong in a way that looks like growth. Without per-partition reconciliation a single bad month hides inside a twenty-four-month average. Without the change record the auditor finds that historical figures moved with no documented reason, which is the finding you least want. Each of these is a five-minute design decision made months earlier.

Step 5

Synthesis and what's next

An orchestrator triggers, sequences, retries, and reports, and should contain no business logic. Prefer data-aware triggering to clock-based guessing, since the upstream extract is not yours to schedule. Make validation a blocking node so that bad data stops the pipeline rather than emailing about it afterwards. And supply the four properties regardless of tool: idempotent steps, explicit partition parameters, bounded retries with owned alerts, and capped concurrency per external system. Asset-centric tools make these the default; task-centric tools let you have them if you insist. Both are far better than the cron job and the hope.
