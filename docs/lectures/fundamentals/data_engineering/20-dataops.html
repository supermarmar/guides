Lectures / Data engineering

DataOps and delivery

Software engineering learned how to ship changes safely and repeatedly, and data work spent two decades not adopting any of it. DataOps is the adoption, plus the one genuine complication: software is code and can be recreated anywhere, while a data platform is code plus state, and the state is confidential, enormous, and impossible to copy into a development environment.

Step 1

The 30-second version

DataOps applies the delivery practices of software engineering to data platforms: everything in version control, automated tests on every change, continuous integration that builds and verifies before merge, environment promotion rather than editing production, infrastructure defined as code, and monitoring wired in from the start rather than added after the first incident.

Almost all of it transfers unchanged from the software engineering track, which this lecture will not repeat. Three things are genuinely different and are what this lecture is about. Environments cannot be identical, because you cannot copy the production data, so the discipline is about what you substitute and how you keep the substitute representative. Deployments change state as well as behaviour, so a release may need to rebuild tables, and rolling back a bad release means rolling back data, which is where Lecture 14's time travel earns its keep. And cost is a first-class engineering property, because a query is a purchase and an inefficient pipeline shows up on an invoice rather than merely feeling slow.

Feynman test A workshop where each craftsman keeps their own jigs and works from memory produces good pieces and cannot produce the same piece twice, and when one craftsman leaves their pieces become unmaintainable. A factory writes the process down, tests the first article against a specification, changes the line through a controlled procedure, and can tell you exactly which batch a defect came from. Neither is more skilled. The factory is repeatable, and repeatability is what lets a bank rely on the output. The complication is that this particular factory's raw material cannot leave the building, so the test line has to run on a substitute.
The maturity trap Every item in this lecture is worth doing, and doing them in the wrong order wastes months. The order that works: version control first, because nothing else is possible without it; then automated tests on the transformation logic, because they are what make change safe; then continuous integration to run those tests before merge; then environment promotion; then infrastructure as code; then cost engineering. A team that builds sophisticated infrastructure automation before it has tests has automated the deployment of unverified logic, which is faster delivery of the same defects.
Step 2

Why this matters

Deployment is the riskiest moment in a platform's life, and in data work it is usually the least controlled. The characteristic incident is a change made directly in production because that is where the data is: a column added by hand, a query edited in a console, a job's schedule adjusted and forgotten. Each is unreviewed, unrecorded, and irreproducible, and collectively they mean the deployed state of the platform is not described by any repository. When a supervisor asks what changed and when, the answer must come from a version history or it does not exist.

Reproducibility is a regulatory requirement, not an engineering aesthetic. Model risk standards expect a model, including its data preparation, to be reproducible by an independent party. That requires the code in version control, the environment pinned, the parameters explicit, and the input data version identifiable, which is the intersection of this lecture with Lectures 14 and 15. A pipeline that runs correctly but cannot be re-run to produce an identical result is a validation finding.

Cost surprises are an engineering failure with a finance signature. A missing partition filter turns a daily query into a full-history scan; a poorly clustered table multiplies data scanned by twenty; small files multiply overhead; an idle cluster left running costs the same as a busy one. None of these show up as errors, and all of them show up on the monthly invoice, usually attributed to nobody. Treating cost as a monitored metric with owners is what stops a platform's cost growing faster than its usefulness.

Step 4

The detail

What lives in the repository

risk-platform/
├── ingestion/            # extract and load code, parameterised by partition
├── transform/            # dbt project: models, tests, snapshots, macros
├── contracts/            # one YAML per published dataset (Lecture 18)
├── quality/              # pandera schemas and validation suites (Lecture 16)
├── orchestration/        # DAG or asset definitions: thin, no business logic
├── infra/                # Terraform: storage, catalogue, compute, IAM, secrets refs
├── tests/                # unit tests mirroring the source layout
├── .github/workflows/    # CI pipeline definitions
├── .pre-commit-config.yaml
└── pyproject.toml        # pinned dependencies, lint and type configuration

Two properties matter more than the exact layout. Everything needed to recreate the platform is here, so a new environment is a Terraform apply and a deployment rather than an archaeology exercise. And nothing here is a secret: credentials are referenced by name and resolved at runtime from the secret manager of Lecture 19, with a pre-commit hook and a CI scan to catch the accident.

Pinned environments, because reproducibility depends on them

# pinned, resolved, committed: the same versions everywhere, including in three years
[project]
requires-python = "==3.12.*"
dependencies = [
  "dbt-core==1.9.2",
  "duckdb==1.1.3",
  "pandera[pandas]==0.22.1",
  "pyspark==3.5.4",
]

Unpinned dependencies are the most common reason a pipeline that ran in March cannot be re-run in September: a library changed a default, a date parser became stricter, an aggregation changed its null handling. Pin exact versions, commit the lock file, and rebuild the container image deliberately rather than implicitly. Containerising the runtime with Docker takes this further by pinning the interpreter and the system libraries too, which is what makes "reproduce this model build" a defensible claim rather than an optimistic one.

Deployment strategies when the deliverable is a table

Three patterns, in increasing safety.

In-place rebuild. The new code runs and overwrites the table. Simple, and the table is briefly wrong or absent if the run fails partway, unless the table format's atomic commit protects you, which is one more reason for Lecture 14.

Blue-green tables. Build the new version alongside the old under a different name, verify it, then atomically swap a view or a catalogue pointer so consumers move in one step. Rollback is swapping the pointer back. This is the right pattern for a table feeding a regulatory submission, because the verification happens before anyone can read the new version.

Time-travel rollback. With a table format, a bad deployment can be reverted by restoring the table to its prior version, which is faster than rebuilding and works even when the cause of the badness is not yet understood. It is not a substitute for the previous pattern, because it operates after consumers may already have read the bad data, but it is the fastest available remedy and it should be a documented, practised procedure rather than something improvised during an incident.

Whichever pattern, the deployment of a definition change needs the decision from Lecture 15: does history rebuild under the new definition, or does the change apply only prospectively? Both are legitimate, the choice has reporting consequences, and it must be recorded in the change record rather than emerging from whichever command someone happened to run.

Infrastructure as code, briefly

Storage buckets, catalogue objects, compute resources, service identities, access grants, and secret references all belong in Terraform or an equivalent. The argument is the same as for the rest of the repository: a change to a permission is then a reviewed commit rather than a console click, environments are consistent by construction, and the current state of the platform is described by a file somebody can read. For access grants specifically this closes the loop with Lecture 19: the quarterly entitlement review becomes a review of a file with a change history, not an export from a console that nobody can compare with last quarter's.

The last lever is the one that makes the others happen. Tag every job and query with a team and a pipeline, report cost by owner monthly, and the conversations follow: the team that discovers its nightly job costs more than the rest of the platform combined will fix it without being asked. Cost attribution is a monitoring problem, and it belongs alongside the monitors of Lecture 18 rather than in a finance spreadsheet.

The four-eyes principle, applied to data In a bank, changes to production risk figures generally require a second person's approval, and the natural implementation is the pull request: no direct commits to the main branch, no direct changes in production, every merge reviewed and recorded, and deployment automated from the main branch so that what is deployed is what was reviewed. This is not extra process bolted on for compliance; it is the ordinary practice from the code review lecture, which happens also to satisfy a control requirement. When an auditor asks how you prevent unreviewed changes to regulatory calculations, the branch protection rule is the answer, and it is a better answer than a policy document.
Worked example: the delivery pipeline for the risk platform, and a cost review

Bring the whole course together on one change: adding a forbearance flag to the default definition, the same change as in Lecture 15, and following it from a developer's laptop to a published regulatory figure.

1. Local. The engineer works in their own schema against a tokenised subset of one month. The transformation runs in seconds on DuckDB, unit tests cover the new edge cases with synthetic rows, and the pandera schema is updated if the output shape changed. Nothing here touches real personal data, and nothing here needs a cluster.

2. Pre-commit. Formatting, SQL linting, secret scanning, and type checks run before the commit is created. These take two seconds and prevent the class of review comment that wastes a reviewer's attention on whitespace instead of logic.

3. Continuous integration on the pull request. The changed models and their dependants build into an ephemeral schema against real inputs, read-only, under production access controls. Data tests run on the output: grain unique, keys resolve, ranges hold. The contract test confirms the published dataset still satisfies its schema and documented semantics. The impact job posts to the pull request: 214 accounts newly in default, exposure of £31.2 million, March default rate moving from 1.42 to 1.51 per cent, no change to row counts.

4. Review. Two reviewers, one engineer and one credit risk modeller. The diff is one file plus tests. The impact figures are in the pull request. The reviewer's job is to judge whether the definition is right, which is the only question a machine cannot answer, and everything mechanical has already been verified. This is the four-eyes control and the code review practice being the same act.

5. Merge and deploy. Merge to main triggers deployment. The definition change requires history to rebuild, which is a conscious decision recorded in the change record, so the deployment runs a full refresh of the affected models across all partitions, with concurrency capped, each partition reconciled, and the previous table versions retained. Blue-green for the table feeding the regulatory submission: build alongside, verify the reconciliation, swap the pointer.

6. Verify and communicate. Monitors confirm freshness and that the distributional shift matches the predicted impact rather than exceeding it, which is the check that the deployment did what the analysis said it would. Consumers named in the contract are notified with the new version number and the restated figures. The lineage graph and the commit history now record what changed, when, why, and who approved it, which is the audit trail the whole exercise exists to produce.

Then the cost review, three months later. Cost attribution reports show the platform's spend has grown forty per cent while volumes grew five. Three findings, each traceable to a lecture in this course. First, the payments aggregation rebuilds ten years nightly to add one day, because it was written as a full refresh: making it incremental removes most of the growth. Second, a dashboard query filters on a derived month column rather than the partition column, so it scans the full history every refresh, and moving the filter onto the partition column fixes it. Third, the streaming sink writes a file every thirty seconds and compaction was never scheduled, so a table of modest size consists of four hundred thousand files and every query pays per-file overhead. None of the three was an error, none raised an alert, and all three were visible the moment somebody was shown the invoice broken down by pipeline.

The closing observation. Notice that this single change exercised nearly every lecture in the course: the file formats and pruning of Part I, the SQL and modelling of Part II, the ingestion and restatement window of Part III, the engine, table format, and transformation layer of Part IV, and every undercurrent in Part V. That is the argument for treating the lifecycle as one subject rather than a collection of tools. The tools will all be replaced. The lifecycle, and the question of whether anyone should believe the number at the end of it, will not.

Step 5

Synthesis and what's next

DataOps is the software engineering discipline applied to data, with three genuine differences: environments cannot share data so the substitutes must be chosen deliberately, deployments change state as well as behaviour so rollback means rolling back tables, and cost is an engineering property that only gets managed once it is attributed. Build the practices in order, version control before tests before continuous integration before infrastructure automation, and let the pull request be both the engineering practice and the four-eyes control. The measure of the whole apparatus is a single question: can an independent party reproduce this number, and can you show what changed since the last time it was produced?

Closing the course Twenty lectures, and one claim running through them. Data engineering is the supply chain that delivers usable data to models and people, and the difference between a pipeline that runs and a platform anyone should rely on is entirely in the undercurrents: definitions with one home, quality checked at the boundary, lineage derived from code, history that can be reproduced, and access that can be proven. For a credit risk modeller specifically, the leverage is unusually clear. The data engineering stage of an A-IRB or IFRS 9 model build is this course applied to one portfolio, and the findings that sink model approvals are almost never about the model form. They are about whether the arrears count meant what you thought, whether the observation window was censored correctly, whether the March figure can be reproduced, and whether anyone can say where the number came from. Those are the questions this course was built to answer.
