Extraction from awkward sources

A PDF of a valuation report contains a table in the sense that a human eye assembles one from ink positioned on a page. The file itself contains no rows, no columns, and no cells: only glyphs with coordinates. Everything difficult about extracting from documents follows from that single fact, and everything responsible about it follows from never trusting the result until it has been checked.

Lecture 11 of 20 Reading time, 45 minutes Part III: ingestion
Step 1

The 30-second version

Not every source is a table you can query. Three families of awkward source recur, and each has its own discipline. HTTP APIs return data in pages, under rate limits, behind authentication, with no transactional view of the whole. Semi-structured files arrive as JSON, XML, or spreadsheets whose structure is a suggestion. Documents, overwhelmingly PDFs in banking, contain information a human can read and a machine must reconstruct.

Two principles cover all three. First, keep the raw response. The JSON body, the original spreadsheet, the PDF itself, stored with a checksum and a retrieval timestamp, is your evidence when the extracted figure is questioned, and re-extraction from a stored original is cheap while re-fetching from a source that has moved on is often impossible. Second, extraction is a measurement, so it needs a control. A number lifted from a document is an estimate of what the document says, and the estimate must be checked against something independent: a stated total, a count, a cross-foot, a second extraction method.

Feynman test Photocopy a financial statement and hand it to a machine. The machine sees a grid of dark and light patches. It does not see that the second column is 2025 and the third is 2024, that the indented line belongs under the heading above it, or that the number in brackets is negative. A human reader supplies all of that from context. Every table extraction library is an attempt to reconstruct that context from geometry, and the reason you check the totals afterwards is that the reconstruction is a guess, however good.
When to stop and ask for a feed Extraction is engineering effort spent because a source will not give you data properly. Before investing in a PDF parser, ask whether the underlying data exists in a database somebody could expose, whether the producer can send a CSV alongside the report, or whether the report is generated from a system you already have access to. In a bank the answer is often yes, and a week of negotiation beats a permanent parser whose failure mode is a wrong number in a report. Build the parser when the source is genuinely external and immovable, such as a regulator's published text or a counterparty's statement.
Step 2

Why this matters

A great deal of authoritative banking information exists only as documents. Regulatory texts and supervisory statements, credit agreements and term sheets, property valuation reports, rating agency opinions, audited financial statements of corporate borrowers, and trustee reports on securitisations. Most of this is re-keyed by hand today, which is slow, unauditable, and about as error-prone as you would expect from manual transcription of numbers. Automating it with provenance and controls is strictly better than automating nothing, and both are better than a spreadsheet with no record of where the figures came from.

API extraction fails in ways that batch database extraction does not. There is no transaction, so a paginated read of a changing collection can miss or duplicate records as the underlying data shifts beneath you. There are rate limits, so a naive loop gets throttled or banned. There is no schema declaration, so a field can change type between calls. Each of these needs a specific countermeasure, and none of them is obvious to somebody whose instincts come from SQL.

Silent extraction errors are the worst kind of data defect. A parser that misaligns a column produces a number that is real, plausible, and wrong. A parser that drops a row produces a total that is short by one line item. Neither raises an exception. This is why the discipline in this lecture is weighted towards validation rather than towards parsing cleverness: the parsing is the easy half.

Step 3

The mental model

What a PDF actually contains

Two kinds of PDF exist and the difference decides everything. A digital PDF, produced by software, contains a text layer: the characters are present with coordinates, and extraction is geometry. A scanned PDF is an image of a page, containing no text at all, and requires optical character recognition to produce a text layer first, with an error profile that includes confusing 8 for 3 and losing decimal points. Test which you have before designing anything: extract text from a page and see whether anything comes back.

The API problems, and their standard answers

ProblemSymptomStandard answer
PaginationOnly the first hundred records arriveFollow the cursor or link header until exhausted; never assume a fixed page count
Drift during pagingRecords missed or duplicated across pages as the source changesPrefer cursor or keyset pagination over offset; sort by an immutable key; deduplicate on arrival
Rate limitsHTTP 429, or silent throttlingRespect Retry-After; exponential backoff with jitter; a client-side rate limiter below the published ceiling
Transient failureTimeouts, 502s, connection resetsRetry idempotent reads; for writes, send an idempotency key so a retry cannot duplicate
Schema driftA field becomes a string, or disappearsValidate the response against a schema on arrival; store the raw body regardless
AuthenticationTokens expire mid-runRefresh on 401 and retry once; never hard-code a credential, per Lecture 19
Step 4

The detail

A defensible API client

import time, random, hashlib, json
from pathlib import Path
import requests

def fetch_all(url: str, params: dict, token: str, raw_dir: Path) -> list[dict]:
    """Page through an API, persisting every raw response before parsing."""
    session = requests.Session()
    session.headers.update({"Authorization": f"Bearer {token}"})
    records: list[dict] = []
    cursor: str | None = None
    page = 0

    while True:
        query = {**params, **({"cursor": cursor} if cursor else {})}
        body = _get_with_retries(session, url, query)

        # persist the raw response first: it is the evidence
        payload = json.dumps(body, sort_keys=True).encode()
        digest = hashlib.sha256(payload).hexdigest()[:16]
        (raw_dir / f"page_{page:05d}_{digest}.json").write_bytes(payload)

        records.extend(body["data"])
        cursor = body.get("next_cursor")
        page += 1
        if not cursor:
            return records


def _get_with_retries(session, url, params, attempts: int = 5) -> dict:
    for attempt in range(attempts):
        response = session.get(url, params=params, timeout=30)

        if response.status_code == 429:
            wait = float(response.headers.get("Retry-After", 2 ** attempt))
            time.sleep(wait + random.uniform(0, 1))     # jitter avoids thundering herd
            continue
        if response.status_code >= 500:
            time.sleep(2 ** attempt + random.uniform(0, 1))
            continue

        response.raise_for_status()
        return response.json()

    raise RuntimeError(f"exhausted {attempts} attempts for {url}")

Three details carry the weight. The raw body is written to disk before anything is parsed, so a parsing bug is fixable without refetching and a disputed figure can be traced to bytes. The retry loop distinguishes rate limiting, which has a stated wait, from server errors, which need backoff, and adds jitter so that many clients do not retry in lockstep. And pagination follows the server's cursor rather than incrementing an offset, which is what protects against records shifting between pages while you read.

Extracting from PDFs with pdfplumber

import pdfplumber
import pandas as pd

with pdfplumber.open("basel_framework.pdf") as pdf:
    page = pdf.pages[316]

    # is there a text layer at all? if this is empty, the page is a scan
    text = page.extract_text()

    # tables: returns a list of tables, each a list of row lists
    tables = page.extract_tables()

    # and the geometry, when the defaults get it wrong
    words = page.extract_words()          # each with x0, x1, top, bottom
    lines = page.lines                    # ruled lines, useful as column hints

frame = pd.DataFrame(tables[0][1:], columns=tables[0][0])

When the default detection fails, the lever is table_settings. The two strategies are "lines", which uses ruled lines to find cell boundaries and is accurate on bordered tables, and "text", which infers columns from the alignment of words and is the only option for tables laid out with whitespace. Supplying explicit column positions, taken from the word coordinates of a known-good page, converts a fragile guess into a deterministic parse.

settings = {
    "vertical_strategy": "explicit",
    "explicit_vertical_lines": [72, 286, 352, 420],   # from page geometry
    "horizontal_strategy": "text",
    "snap_tolerance": 3,
}
tables = page.extract_tables(settings)

# crop to a region when a page holds several tables or unwanted furniture
region = page.crop((72, 540, 420, 640))    # (x0, top, x1, bottom) in points
tables = region.extract_tables(settings)

The cleaning layer that is always needed

Extracted cells are strings shaped by typography, and every one of these transformations is required in practice: strip thousands separators; convert parenthesised numbers to negatives; treat dashes, blanks, and "n/a" as explicit nulls rather than zeros; join header rows that span two lines; drop repeated headers where a table continues across pages; and detect footnote markers glued to values. Write these as one tested function shared by every extractor, because they recur in every document and getting them slightly different per parser is how two reports disagree.

def to_amount(cell: str | None) -> float | None:
    """Convert a rendered table cell to a number, or None if genuinely absent."""
    if cell is None:
        return None
    value = cell.strip().replace(",", "").replace(" ", "")
    if value in {"", "-", "–", "—", "n/a", "N/A", "nil"}:
        return None
    negative = value.startswith("(") and value.endswith(")")
    value = value.strip("()")
    value = value.rstrip("*†‡")          # footnote markers
    number = float(value)
    return -number if negative else number
Provenance is part of the record Every row extracted from a document should carry where it came from: the source file name, its checksum, the page number, the table index on that page, the extraction timestamp, and the version of the extraction code. This costs six columns and it converts an unauditable number into a traceable one. When a figure is challenged eighteen months later, the question "which page of which version of which document, parsed by which code?" has an answer, and re-running that exact extraction is possible. Without provenance, a document-derived number is an assertion; with it, it is evidence.
Worked example: extracting a capital table from a regulatory PDF, with controls

The task: pull an exposure-class table from a published regulatory document into a typed frame, reliably enough that a downstream calculation can use it. The document is digital, not scanned, and roughly a thousand pages.

1. Establish what kind of document this is. Extract text from the target page. If it returns content, there is a text layer and geometry will work. If it returns nothing, stop and plan for optical character recognition, with a much stronger validation regime because the error profile changes from misalignment to misread digits.

2. Locate the table by content, not by page number. Page indices shift between document versions, so hard-coding page 318 guarantees a wrong answer at the next revision. Search for the caption or the distinctive header text across pages, and record which page matched.

target_pages = [i for i, p in enumerate(pdf.pages)
                if (p.extract_text() or "").find("Exposure class") >= 0]

3. Extract, then immediately assert the shape. Check the column count against expectation, check that the header row contains the expected labels, and check the row count is within a plausible band. A parse that yields three columns where four were expected must fail loudly at this point rather than producing a frame that is silently misaligned.

4. Coerce types through the shared cleaner, and count what it rejected. Every cell that should be numeric and is not becomes a null, and the number of such cells is a quality metric. Zero is expected; a handful means a footnote marker or a new dash character; many means the column mapping is wrong.

5. Reconcile against the document's own arithmetic. This is the control that makes the whole exercise defensible. The table has a stated total row; sum the extracted components and compare. Foot the columns and cross-foot the rows where both exist. If a published total and your sum of parts differ, the extraction is wrong, or the document has a footnote you have not read, and either way it is not usable yet.

components = frame.loc[frame.exposure_class != "Total", "amount_2025"].sum()
stated     = frame.loc[frame.exposure_class == "Total", "amount_2025"].iloc[0]
assert abs(components - stated) < 1.0, f"cross-foot failed: {components} vs {stated}"

6. Attach provenance and store both artefacts. The output frame carries file name, checksum, page, table index, extraction timestamp, and code version. The original PDF is retained in raw storage under its checksum. Both go to the bronze layer, and only the reconciled frame is promoted to silver.

7. Make the next version cheap. Store the resolved page number and column positions as configuration keyed by document version, so a re-run against the same version is deterministic while a new version triggers rediscovery and a fresh cross-foot. When the cross-foot fails on a new version, a human looks once, updates the configuration, and the pipeline resumes; that is a supportable operating model, unlike a parser that silently adapts.

The general shape. Notice that steps 3 to 5 are all validation and only step 4 touches the data. That ratio is correct for document extraction. The parse is a hypothesis about what the page says, and the controls are the test of the hypothesis. Where no independent control exists, no stated total, no cross-foot, no expected count, the extraction should be treated as indicative and never fed into a calculation that matters, because there is no way to know it is right.

Step 5

Synthesis and what's next

Awkward sources are handled by the same two rules regardless of family: keep the raw artefact with a checksum, and treat every extracted value as a measurement requiring an independent control. For APIs that means cursor pagination, backoff with jitter, idempotency keys, and schema validation on arrival. For PDFs it means knowing whether a text layer exists, locating tables by content rather than page number, pinning geometry where the defaults are fragile, sharing one tested cell cleaner, and reconciling to the document's own totals before the numbers are allowed anywhere. Where no control exists, the figure is indicative, and saying so is part of the job.
