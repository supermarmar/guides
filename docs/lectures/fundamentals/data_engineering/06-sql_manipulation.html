SQL III: manipulation

A ledger is never erased. When a bookkeeper discovers an error, they do not rub out the entry; they post a correcting entry and leave both visible, so the history of what was believed remains inspectable alongside what is now believed. Double-entry bookkeeping worked this out in the fifteenth century, and it is still the right instinct for a data platform.

Lecture 6 of 20 Reading time, 50 minutes Part II: SQL and data modelling
Step 1

The 30-second version

Data manipulation language changes contents: INSERT adds rows, UPDATE edits them, DELETE removes them, and MERGE does whichever of the three each incoming row requires. Wrapped around all of them are transactions, which make a group of statements behave as a single all-or-nothing unit.

The transactional world uses all four statements freely, because a till must edit the balance it holds. The analytical world, which is where this course lives, uses them differently and much more sparingly. An analytical table is written by one pipeline in bulk, must be reproducible, and usually must retain history for audit. That pushes the design towards append and overwrite rather than row-level editing: append new snapshots, overwrite a whole partition when it needs rebuilding, and never edit a row in place if the previous value has any evidential value.

The property that ties this together is idempotency: running the same load twice produces the same table as running it once. A pipeline without it accumulates duplicates on every retry, and retries are not exceptional, they are how a scheduler responds to a network blip at three in the morning.

Feynman test A bookkeeper finds that last March's rent was posted twice. They do not reach for an eraser. They post a reversing entry dated today, referencing the original, and both lines stay in the book forever. Anyone can now answer two different questions: what do we believe the March rent was, and what did we believe it was in March? A data platform that runs UPDATE to fix last March can answer only the first, and it is the second question that a supervisor asks.
The two statements that end careers DELETE FROM table; with the WHERE clause forgotten empties the table. UPDATE table SET x = y; with the WHERE clause forgotten sets every row. Both are valid SQL, both execute instantly, and both are irreversible outside a transaction. The habit that prevents it: write the statement as a SELECT first, inspect the row count, then convert it to the mutation, and run mutations inside an explicit transaction so that a wrong count can be rolled back rather than explained.
Step 2

Why this matters

Non-idempotent loads corrupt slowly, which is the worst way to corrupt. A load that appends without first clearing what it is replacing does not fail on the second run; it succeeds and doubles a month. The row count looks large but plausible, the default rate is unchanged because both copies carry the same flags, and the total exposure is exactly twice what it should be. That defect can survive several reporting cycles, and the discovery usually comes from an external reconciliation, which is the most expensive place to find it.

Row-level editing destroys the evidence a regulated model needs. BCBS 239 expects a bank to explain a risk number and to reproduce it. An UPDATE that corrects an arrears count leaves no record that the previous value existed, so the question from Lecture 03, why did last month's number change, becomes unanswerable. This is why analytical platforms in banks trend towards immutability: append corrections with a system date, never overwrite the past.

On columnar storage, updates are not cheap. A transactional database updates a row in place. A columnar file cannot: the value is buried inside a compressed column chunk, so changing one row means rewriting the file that holds it, and changing one row in each of a thousand files means rewriting a thousand files. Lecture 14 covers the two strategies table formats use to make this tolerable, but the design lesson is available now: batch your changes, address whole partitions, and prefer rebuilding a slice to editing rows within it.

Step 3

The mental model

Transactions, and what can go wrong without them

BEGIN TRANSACTION;

  DELETE FROM account_snapshots
  WHERE  reporting_date = DATE '2026-03-31';

  INSERT INTO account_snapshots
  SELECT * FROM staging_march_snapshot;

COMMIT;   -- or ROLLBACK; to abandon both statements

The two statements above are a single logical operation: replace March. Without the transaction, a failure between them leaves the table with March missing, which is a worse state than either the old data or the new. With it, a reader either sees the old March or the new one, and a crash leaves the old one intact. This is atomicity and isolation from Lecture 03 doing exactly the job they were designed for.

Isolation is not binary; engines offer levels, and the level determines which anomalies are possible.

AnomalyWhat you observePrevented by
Dirty readYou see another transaction's uncommitted change, which may then be rolled backRead committed and above
Non-repeatable readThe same row read twice in one transaction gives different valuesRepeatable read and above
Phantom readThe same filter read twice returns a different set of rows, because someone insertedSerialisable, or snapshot isolation
Lost updateTwo transactions read, compute, and write; one result silently overwrites the otherExplicit locking, or a conflict-detecting engine

Most modern engines implement multi-version concurrency control, keeping several versions of each row so that readers see a consistent snapshot as at the moment their statement or transaction began, without blocking writers. This is why a long analytical query on such an engine does not stop the writes, and it is the mechanism behind the snapshot reads that Lecture 03 said analytical platforms need. For a data pipeline the practical guidance is short: wrap each logical publish in one transaction, keep transactions short, and do not hold one open while a human thinks.

Four write patterns, and when each is right

Step 4

The detail

Inserting

-- positional: fragile, breaks silently when a column is added
INSERT INTO customers
VALUES ('C0001', 'Nadoy', DATE '1985-03-14', 'retail', 'samir@example.com', CURRENT_TIMESTAMP);

-- named: always do this instead
INSERT INTO customers (customer_id, surname, date_of_birth, segment, email)
VALUES ('C0001', 'Nadoy', DATE '1985-03-14', 'retail', 'samir@example.com');

-- from a query, which is how pipelines actually load
INSERT INTO account_snapshots (account_id, reporting_date, balance, arrears_months)
SELECT account_id, DATE '2026-03-31', balance, arrears_months
FROM   staging_march
WHERE  account_id IS NOT NULL;

-- DuckDB conveniences: straight from a dataframe or a file
INSERT INTO reporting BY NAME SELECT * FROM my_dataframe;
INSERT INTO reporting BY NAME SELECT * FROM 'extracts/loans_2026_03.parquet';

Always name your columns. A positional insert is a bet that nobody will ever add a column to the table, and when that bet loses the failure is a silent column shift rather than an error, which puts the arrears count into the balance field. DuckDB's BY NAME clause matches source columns to target columns by name rather than position and is worth using for exactly this reason.

Deleting, and its faster cousin

DELETE FROM account_snapshots
WHERE  reporting_date = DATE '2026-03-31';   -- never omit the WHERE

-- remove everything, fast, keeping the table definition
TRUNCATE TABLE staging_march;

DELETE is row-by-row and logged, so it can be rolled back and is slow over large volumes. TRUNCATE discards everything at once and is dramatically faster, at the cost of finer control and, in some engines, of transactional rollback. Use truncate for staging tables you rebuild every run and delete for a targeted removal inside a transaction.

In a regulated platform, prefer neither. A soft delete marks a row as no longer current instead of removing it, typically with a valid_to timestamp or an is_current flag, so the row remains available for audit and for reproducing an earlier report. Queries then read a view filtered to current rows, which keeps the complexity in one place. This is the same mechanism as the slowly changing dimension in Lecture 08, arriving here as an operational habit.

Updating, including the trap

UPDATE customers
SET    segment = 'sme'
WHERE  customer_id = 'C0001';

-- conditional on another table
UPDATE accounts
SET    interest_rate = interest_rate + 0.0025
WHERE  account_id IN (SELECT account_id FROM rate_review WHERE outcome = 'increase');

Now the trap, which is worth its own paragraph because it is both common and silent. Consider setting a discount from another table with a correlated subquery:

-- WRONG: sets discount to NULL for every customer with no promotion
UPDATE customers
SET    discount = (SELECT discount FROM promotions p WHERE p.customer_id = customers.customer_id);

-- RIGHT: restrict the rows being updated to those with a match
UPDATE customers
SET    discount = (SELECT discount FROM promotions p WHERE p.customer_id = customers.customer_id)
WHERE  customer_id IN (SELECT customer_id FROM promotions);

Without the outer WHERE, the statement updates every row in the table, and for rows with no matching promotion the subquery returns null, so their existing discount is wiped. The statement reports success and the damage is invisible until someone notices that discounts disappeared. The general rule: an UPDATE driven by a subquery needs the outer WHERE to restrict the update to rows the subquery can actually serve.

Merge: the upsert

-- ANSI form, supported by most warehouses and Spark
MERGE INTO customers AS target
USING staging_customers AS source
   ON target.customer_id = source.customer_id
WHEN MATCHED AND (target.segment    IS DISTINCT FROM source.segment
               OR target.email      IS DISTINCT FROM source.email)
  THEN UPDATE SET segment = source.segment,
                  email   = source.email,
                  updated_at = CURRENT_TIMESTAMP
WHEN NOT MATCHED
  THEN INSERT (customer_id, surname, date_of_birth, segment, email)
       VALUES (source.customer_id, source.surname, source.date_of_birth,
               source.segment, source.email);

-- PostgreSQL and DuckDB also offer the shorter conflict form
INSERT INTO customers (customer_id, surname, segment, email)
SELECT customer_id, surname, segment, email FROM staging_customers
ON CONFLICT (customer_id)
DO UPDATE SET segment = EXCLUDED.segment,
              email   = EXCLUDED.email;

Three details make the difference between a merge that works and one that quietly misbehaves. The match condition must be a genuine key, because if the source contains two rows for one key the merge is ambiguous and most engines raise an error, which is the good outcome; deduplicate the source first with the ROW_NUMBER idiom from Lecture 05. The IS DISTINCT FROM comparison treats nulls as comparable, so a change from null to a value is detected, which != would miss. And updating a timestamp on matched rows only when something actually changed keeps the change history meaningful rather than recording a touch on every run.

The idempotent load, written out

BEGIN TRANSACTION;

  -- 1. clear exactly the slice this run owns
  DELETE FROM account_snapshots
  WHERE  reporting_date = DATE '2026-03-31';

  -- 2. write it, deduplicated, from the staged arrival
  INSERT INTO account_snapshots
      (account_id, reporting_date, customer_id, product, balance,
       arrears_months, default_date, source_system, loaded_at)
  SELECT account_id,
         DATE '2026-03-31',
         customer_id,
         product,
         balance,
         arrears_months,
         default_date,
         'core_banking',
         CURRENT_TIMESTAMP
  FROM   staging_march
  QUALIFY ROW_NUMBER() OVER (PARTITION BY account_id
                             ORDER BY extract_timestamp DESC) = 1;

  -- 3. assert before committing
  -- (row count within tolerance of last month, no nulls in key columns)

COMMIT;

This is the pattern to internalise, and it is the one Lectures 10 and 17 will assume. The delete and the insert address the same slice, defined by the same predicate, inside one transaction. Run it once or five times and the table is identical. The third step, asserting before committing rather than after, is what turns a bad load into a rollback instead of an incident, and it is the operational half of Lecture 16.

The parameter that must not be implicit Notice that the reporting date appears three times as a literal. In a real pipeline it is a parameter, and the single most common cause of a corrupted load is a parameter that defaults to "today" when the job is rerun for a past date. Make the date an explicit required argument with no default, so that a rerun for March is a rerun for March rather than a rerun that overwrites March's slice with today's data. This is the same argument as the one against hard-coded paths in notebook promotion, and it costs one line to get right.
Worked example: a late-arriving payments correction, done three ways

The situation, which recurs monthly in every bank. On 12 May, the collections system sends corrected payment records for March: 214 accounts were recorded as having missed a payment they in fact made. The March arrears counts, the March default flags, and therefore the March default rate are all wrong. Consider three responses.

Response one: update the rows. An UPDATE sets arrears_months = 0 and default_date = NULL for the 214 accounts in the March snapshot. The March default rate now reads correctly at 1.42 per cent. The cost is that the platform can no longer produce the number it reported in April, which was 1.51 per cent, so the variance question is unanswerable and the April regulatory submission cannot be reconciled to the platform that produced it. In a bank this is not a shortcut, it is a control failure.

Response two: rebuild the partition, keeping the old version. Rerun the March load from the corrected source with the idempotent pattern above, which deletes and rewrites March. Before doing so, the previous version of the partition is retained: either because the table format keeps prior versions, per Lecture 14, or because the load archives the slice it is about to replace. The corrected March is now current, the reported March is still retrievable, and the difference is a query. This is the standard answer.

Response three: append a corrected version with bitemporal keys. The snapshot table carries both a reporting_date (business date, March) and a version_valid_from (system date, 12 May). The corrected rows are appended rather than replacing anything, and a view selects the latest version per account per reporting date. Every consumer sees corrected data by default, any consumer can ask for the data as it stood on any past date, and nothing is ever deleted. The cost is a more complex model and a mandatory view layer, so that no analyst accidentally queries the base table and double counts the two versions.

Which to choose. Response two is the right default: it is simple, it satisfies reproducibility, and modern table formats give it to you almost for free. Response three earns its complexity on tables where corrections are frequent and the audit requirement is explicit, which in practice means the datasets feeding regulatory capital and IFRS 9 numbers. Response one is never right on a table anybody has reported from.

The control that catches this class of problem. Whichever response you choose, the load should record how many rows changed and how the aggregate moved, and alert when either exceeds a tolerance. A correction touching 214 accounts and moving the default rate by nine basis points is worth a human reading a line in a log. A correction touching 214,000 accounts is worth stopping the pipeline. Lecture 18 makes that instinct into monitors.

Step 5

Synthesis and what's next

Manipulation in an analytical platform is not the same activity as manipulation in a transactional one. Insert with named columns, delete only within a transaction and only to define what an insert may replace, treat in-place updates as a last resort because they destroy the evidence a regulated model needs, and use merge where reference data genuinely changes in place. Wrap each logical publish in a transaction, assert before committing, and make the partition parameter explicit. The test of all of it is the rerun: if running the load twice does not produce the same table as running it once, the pipeline is not finished.
