Open table formats and the lakehouse

A directory of Parquet files is a pile of paper. A table is a pile of paper plus a register saying which sheets are currently part of the table, added when, by whom, and superseding what. The files were never the hard part. The register is the invention, and it is the whole of what a table format adds.

Lecture 14 of 20 Reading time, 50 minutes Part IV: transformation at scale
Step 1

The 30-second version

An open table format is a metadata layer over ordinary Parquet files in ordinary object storage that makes them behave like a database table. The three implementations are Delta Lake, Apache Iceberg, and Apache Hudi. They differ in detail and agree on the essentials.

What the register buys, and no directory of files can offer. Atomic commits: a reader sees the table before a write or after it, never halfway, which is the guarantee Lecture 06 needed for a safe publish. Time travel: because superseded files are retained and the register records versions, the table as it stood at any past commit is queryable. Schema evolution: columns can be added, renamed, or retyped with rules, tracked in metadata rather than by rewriting history. Partition evolution (in Iceberg): the partitioning scheme can change without rewriting existing data. And efficient row-level change: updates and deletes become tractable through file-level rewrites or delete markers rather than reprocessing everything.

The consequence is the lakehouse: warehouse guarantees on lake storage, with several engines able to read and write the same single copy of the data. That last property is the strategic argument, and it is about optionality rather than speed.

Feynman test A clerk keeps records in a filing room. Anyone walking in and reading whatever is on the shelves gets whatever state the room happens to be in, including a half-finished refiling. Now add a bound register at the door: entry 4,412 says the table currently consists of these ninety sheets. The clerk refiles freely, then writes one new entry when finished, and every reader consults the register first. Readers now always see a coherent table, the old entries let you reconstruct last Tuesday's, and nothing about the sheets themselves changed. That register is the transaction log.
Why this was the missing piece Lecture 03 described the lake's failures as governance failures rather than technical ones: no transactions, no schema enforcement, and a tendency to become a swamp. Notice that all three are solved by metadata rather than by new storage. That is why the lakehouse could arrive as a layer rather than a migration: the Parquet files stay exactly as they were, and a log next to them supplies what the warehouse used to provide by owning the disks. It is one of the cleaner examples in this field of a hard problem yielding to better bookkeeping.
Step 2

Why this matters

Reproducing a past report stops being a project. The worked example in Lecture 03 asked why the March default rate changed between April and June, and the best answer required immutable snapshots and careful archiving. With time travel, the query is a clause: read the table as at the version the April report used. That turns a forensic exercise into a diff, and in a regulated environment where "explain the movement" is a monthly conversation, it is the single most valuable feature in this lecture.

Concurrent readers and writers stop corrupting each other. Without a table format, a monthly load that deletes and rewrites a partition is dangerous precisely while it runs: a consumer querying at that moment sees a partial table, and there is no mechanism to prevent it. With atomic commits, the consumer sees the previous version until the new one is complete. This is what makes the idempotent overwrite pattern of Lecture 06 safe in production rather than merely correct in principle.

Schema and partition changes stop being rewrites. A source adds a field; a partitioning choice made three years ago turns out wrong. Without metadata-managed evolution, the first requires backfilling every historical file and the second requires rewriting the entire table. With it, the first is a metadata operation and the second, in Iceberg, applies to new data while old data remains readable under the old scheme. Both changes are common enough that the difference compounds.

Step 3

The mental model

The mechanics, in one pass

A write produces new Parquet files, then appends one entry to the log naming the files added and removed. The append must be atomic, and the mechanisms differ: Delta Lake writes numbered JSON entries and relies on the storage layer's conditional put or a coordinating service, while Iceberg writes a new metadata file and atomically swaps a pointer held in a catalogue. Both give optimistic concurrency: two writers proceed in parallel, and the second to commit either succeeds because they touched different files or fails and retries because they conflicted. Snapshot isolation for readers follows for free, since a reader resolves the file list once and then reads only those files.

Because the log lists files with their statistics, the engine prunes at the metadata level before touching storage: file skipping using per-file minimum and maximum values, which is Lecture 02's row group statistics promoted to table scope. This is why a well-clustered lakehouse table can answer a selective query by opening a handful of files out of a hundred thousand without any directory listing at all, and why Iceberg scales to table sizes where listing object storage would itself be the bottleneck.

Step 4

The detail

The operations you will actually use

-- create a table in the format, not just a directory of files
CREATE TABLE risk.fact_account_month (
    account_id      VARCHAR,
    reporting_date  DATE,
    balance         DECIMAL(18,2),
    arrears_months  INTEGER
) USING DELTA                          -- or USING ICEBERG
PARTITIONED BY (reporting_date);

-- the idempotent publish from Lecture 06, now atomic and concurrent-safe
INSERT OVERWRITE risk.fact_account_month
SELECT * FROM staging WHERE reporting_date = DATE '2026-03-31';

-- row-level change, which a plain Parquet directory cannot express
MERGE INTO risk.fact_account_month AS t
USING corrections AS s
   ON t.account_id = s.account_id AND t.reporting_date = s.reporting_date
WHEN MATCHED THEN UPDATE SET arrears_months = s.arrears_months
WHEN NOT MATCHED THEN INSERT *;

-- time travel: by version, or by timestamp
SELECT * FROM risk.fact_account_month VERSION AS OF 2;
SELECT * FROM risk.fact_account_month TIMESTAMP AS OF '2026-05-01 00:00:00';

-- what happened to this table, and who did it
DESCRIBE HISTORY risk.fact_account_month;

-- maintenance: compact small files, then reclaim superseded ones
OPTIMIZE risk.fact_account_month WHERE reporting_date >= '2026-01-01';
VACUUM  risk.fact_account_month RETAIN 720 HOURS;

Two of these deserve emphasis. DESCRIBE HISTORY is an audit trail the platform maintains for you: operation, timestamp, user, and the predicates involved, which is a large fraction of what a lineage question asks for and costs nothing to keep. And VACUUM is the one destructive operation in the list: it deletes files that are no longer part of any retained version, and setting its retention shorter than your time travel requirement silently destroys your ability to reproduce past reports. Choose the retention from the reproducibility policy, not from a storage cost target.

Compaction, clustering, and why they are not optional

Frequent small writes produce many small files, and Lecture 02's small files problem applies with force because the metadata itself grows too. Compaction rewrites many small files into fewer large ones, and it is routine maintenance rather than an intervention: schedule it. Clustering is the ordering decision from Lecture 02 made a first-class operation: writing or rewriting the data sorted by the columns you filter on makes file skipping effective, since statistics only prune when values are physically grouped. Delta offers Z-ordering and, more recently, liquid clustering; Iceberg has sort orders. The practical guidance is unchanged from Lecture 04's closing note: on columnar analytical storage the sort order you write is worth more than any index you create.

The honest summary is that the three have converged substantially, that Delta and Iceberg are the two you will meet, and that interoperability layers now let one physical dataset be read as more than one format. The decision matters less than it did in 2021, and it matters far less than deciding to use one at all. The genuine differentiator for a long-lived risk platform is Iceberg's partition evolution, because a partitioning choice made today will be wrong in five years and the alternative is rewriting a decade of history.

The catalogue is not optional either A table format needs something to record where tables live and who may read them: Unity Catalog, AWS Glue, a Hive Metastore, Iceberg's REST catalogue, or Polaris. Without it you have files with a log and no way for a second engine to find them, and no place to hang permissions. Treat the catalogue as part of the architecture from the start, because retrofitting one across an estate that grew by convention is considerably harder than choosing one on day one. This is also where Lecture 19's access control attaches.
Worked example: making the March restatement reproducible, end to end

Return to the case from Lectures 03 and 06. March was published with a default rate of 1.42 per cent. On 12 May, corrected payments arrive and March is rebuilt, giving 1.51 per cent. An auditor asks three questions: what did we report, what do we now believe, and precisely which accounts moved. Show what the table format contributes.

1. The publish itself, made safe. The March rebuild is an INSERT OVERWRITE restricted to the March partition, executed as one commit. Consumers querying during the rebuild see the pre-restatement version throughout and then the new one; nobody ever sees a partial March. Without the format, this window is a real exposure and the usual mitigation is scheduling the load when nobody is looking, which is not a control.

2. Identify the version the April report read. DESCRIBE HISTORY lists commits with timestamps and operations. The April report ran on 3 May, so the relevant version is the latest commit at or before that instant, which the history makes explicit rather than inferential.

3. Answer all three questions with one query.

WITH reported AS (
    SELECT account_id, arrears_months, balance
    FROM   risk.fact_account_month TIMESTAMP AS OF '2026-05-03 00:00:00'
    WHERE  reporting_date = DATE '2026-03-31'
),
restated AS (
    SELECT account_id, arrears_months, balance
    FROM   risk.fact_account_month           -- current
    WHERE  reporting_date = DATE '2026-03-31'
)
SELECT COALESCE(r.account_id, s.account_id)              AS account_id,
       r.arrears_months                                   AS arrears_as_reported,
       s.arrears_months                                   AS arrears_as_restated,
       s.balance                                          AS balance,
       CASE WHEN r.account_id IS NULL THEN 'added'
            WHEN s.account_id IS NULL THEN 'removed'
            ELSE 'changed' END                            AS movement
FROM      reported  r
FULL JOIN restated s USING (account_id)
WHERE r.arrears_months IS DISTINCT FROM s.arrears_months
   OR r.account_id IS NULL
   OR s.account_id IS NULL;

The result is the 214 accounts, each with its before and after position and whether it entered, left, or changed. The movement in the default rate is now attributable account by account, which is what "explain the variance" actually means and what a spreadsheet reconciliation spends a week approximating.

4. Protect the ability to do this. The whole exercise depends on version at 3 May still existing, which depends on VACUUM retention. If the reproducibility policy is "any reported figure must be reproducible for seven years", then either the retention must be seven years, which is expensive in storage, or, more practically, each published figure's version identifier is recorded in a small reporting register and the underlying partition is additionally archived at publication. Decide this deliberately: the failure mode is discovering in year three that a routine maintenance job has been quietly destroying the evidence.

5. What this replaces. Compare with the pre-lakehouse answer: archive a copy of every published partition, maintain a naming convention, hope nobody deleted anything, and write bespoke comparison scripts. The table format turns that discipline into a property of the storage layer, and it converts a BCBS 239 lineage requirement from a documentation exercise into a query. That is the strongest practical argument for adopting one in a bank, and it is worth more than the performance improvements that usually lead the sales pitch.

Step 5

Synthesis and what's next

A table format is a transaction log over Parquet files, and it supplies atomic commits, snapshot isolation, time travel, schema and partition evolution, and workable row-level change. The files remain open and the storage remains cheap, so several engines can share one copy, which is the lakehouse. Copy on write suits batch publishes read many times; merge on read suits frequent small updates and makes compaction mandatory. Compaction and clustering are routine maintenance, not tuning. And VACUUM retention is a reproducibility policy wearing the costume of a storage setting, which in a regulated environment makes it one of the more consequential configuration values in the platform.
