Analytics engineering with dbt

For thirty years, transformation logic lived where software engineering could not reach it: inside graphical ETL tools, stored procedures, and spreadsheets, with no version control, no tests, no review, and no way to tell what depended on what. Analytics engineering is the project of hauling that logic back into a repository. The tooling is incidental; the relocation is the point.

Lecture 15 of 20 Reading time, 50 minutes Part IV: transformation at scale
Step 1

The 30-second version

dbt (data build tool) manages the T of ELT. You write each transformation as a SELECT statement in a file; dbt wraps it in the right CREATE TABLE or CREATE VIEW, works out the dependency order from the references between files, executes them in that order in your warehouse, and runs tests against the results.

The mechanism that makes it work is one function. Instead of naming a table, a model refers to another model with {{ ref('other_model') }}. From those references dbt builds a dependency graph, which gives it four things at once: execution order without a hand-maintained schedule, environment portability because the reference resolves to whichever schema you are building into, lineage documentation for free, and the ability to build only what changed and what depends on it.

What you get beyond scheduling is the software engineering apparatus applied to SQL: version control and code review on every definition, tests that assert uniqueness, non-nullity, accepted values, and referential integrity, generated documentation including the lineage graph, and reusable logic through macros. It runs against a warehouse or engine that does the compute, so it is a layer over Lectures 09, 13, and 14 rather than a competitor to them.

Feynman test Two teams maintain the same calculation. The first keeps it in a graphical tool where the logic is boxes and arrows saved in a proprietary file: you cannot diff two versions, you cannot see who changed the definition of default last March, and finding what breaks if you change a column means opening every box. The second keeps it as a folder of SQL files in git: every change is a reviewed commit, the dependency graph is derived from the code, and the question "what breaks if I change this?" is answered by the tool. Same calculation, same warehouse. One of them can be audited.
Why this matters more in a bank than elsewhere Model risk and BCBS 239 both demand that you can say what a number is, where it came from, and who changed its definition when. A transformation layer in version control answers all three by construction: the definition is a file, the lineage is a graph derived from the code, and the change history is the git log with a reviewer's name attached. Compare the alternative, which is a data dictionary maintained by hand and hoped to be current. This is the cheapest lineage story available, and it is a by-product of a practice you would want anyway.
Step 2

Why this matters

Definitions stop being duplicated. Lecture 04 argued that the regulatory default definition should live in one place. dbt makes that practical: one model computes it, every downstream model references that model, and changing it changes everything at once. The alternative, which is the current state of many risk functions, is the same definition implemented in the PD extract, the LGD extract, the IFRS 9 staging job, and two dashboards, drifting apart quietly until a validation exercise finds the difference.

The dependency graph answers the questions that cost the most time. What does this model depend on, upstream to the raw source? What breaks if I change this column? Which models must rebuild after this source lands late? Each of these is a graph traversal that dbt performs and a hand-maintained pipeline cannot answer at all. In a platform of a few hundred models, that is the difference between a change taking an afternoon and taking a fortnight of cautious archaeology.

Tests convert assumptions into failures. Lecture 04 put as much as possible into constraints, and noted that analytical engines enforce less than transactional ones. dbt tests fill the gap in the right place: uniqueness of the grain, non-nullity of keys, accepted values of categoricals, and referential integrity between models, all declared alongside the model and run on every build. A model whose grain is asserted unique cannot silently start double counting, which is the most common way an analytical table goes wrong.

Step 3

The mental model

The three-layer convention

StagingOne model per source table, materialised as a view. It renames columns to your conventions, casts types, and does nothing else. No joins, no business logic, no filtering beyond obvious junk. This layer exists so that a source's naming and quirks are isolated in exactly one place per table.
IntermediateShared business logic that several marts need: the default flag, the payment history aggregated to month, the customer-to-account resolution. Usually not exposed to consumers. This is where the definitions live, and the layer whose existence prevents duplication.
MartsThe tables consumers read, modelled dimensionally per Lecture 08 and materialised as tables for performance. Named for the business meaning rather than the source, and documented as products with owners.
Step 4

The detail

A model is a select statement

-- models/staging/stg_account_snapshots.sql
{{ config(materialized = 'view') }}

SELECT
    account_id::VARCHAR                     AS account_id,
    reporting_date::DATE                    AS reporting_date,
    customer_id::VARCHAR                    AS customer_id,
    product_code::VARCHAR                   AS product_code,
    balance::DECIMAL(18,2)                  AS balance,
    arrears_months::INTEGER                 AS arrears_months,
    COALESCE(unlikely_to_pay, FALSE)        AS unlikely_to_pay,
    loaded_at::TIMESTAMP                    AS loaded_at
FROM {{ source('core_banking', 'account_snapshots') }}
QUALIFY ROW_NUMBER() OVER (PARTITION BY account_id, reporting_date
                           ORDER BY loaded_at DESC) = 1
-- models/intermediate/int_default_flag.sql
-- The single implementation of the regulatory default definition.
-- Changing this file changes every downstream consumer, by design.
{{ config(materialized = 'table') }}

SELECT
    account_id,
    reporting_date,
    arrears_months,
    unlikely_to_pay,
    (arrears_months >= {{ var('default_arrears_threshold') }} OR unlikely_to_pay) AS in_default
FROM {{ ref('stg_account_snapshots') }}

Note the pieces. source() names a raw table declared in a YAML file, which lets dbt track freshness and lineage back past its own graph. ref() names another model. var() pulls a value from project configuration, so the arrears threshold is a documented parameter rather than a magic number buried in SQL. And the config block chooses the materialisation, which is a performance decision independent of the logic.

Materialisations

MaterialisationWhat it buildsUse for
viewA view; recomputed on every queryStaging models and anything cheap and rarely queried
tableDropped and rebuilt in full each runMarts and intermediate models where a full rebuild is affordable
incrementalBuilt once, then only new or changed rows merged inLarge fact tables where a full rebuild does not fit the window
ephemeralNothing; inlined as a common table expression in dependantsSmall intermediate steps that need no independent existence
snapshotA type 2 history table, maintained automaticallySlowly changing dimensions over a source that keeps only current state

The snapshot materialisation deserves particular attention from this audience, because it solves the problem Lecture 07 flagged and Lecture 08 formalised. Point it at a source table that holds only current values, declare the key and either a timestamp or the columns to watch, and dbt maintains validity intervals for you, appending a new version whenever it observes a change. That is a type 2 dimension built by configuration rather than by hand-written merge logic, and it is the correct answer to "the source overwrites the customer segment and we need to know what it was at origination".

-- snapshots/customer_segment_snapshot.sql
{% snapshot customer_segment_snapshot %}
{{ config(
     target_schema = 'snapshots',
     unique_key    = 'customer_id',
     strategy      = 'check',
     check_cols    = ['segment', 'risk_grade', 'region']
) }}
SELECT customer_id, segment, risk_grade, region FROM {{ source('core_banking', 'customers') }}
{% endsnapshot %}

Incremental models, and the same idempotency argument

-- models/marts/fact_account_month.sql
{{ config(
     materialized = 'incremental',
     unique_key   = ['account_id', 'reporting_date'],
     incremental_strategy = 'merge',
     partition_by = 'reporting_date'
) }}

SELECT s.account_id,
       s.reporting_date,
       s.customer_id,
       s.balance,
       s.arrears_months,
       d.in_default,
       COALESCE(p.payment_count, 0) AS payment_count
FROM        {{ ref('stg_account_snapshots') }} s
INNER JOIN  {{ ref('int_default_flag') }}      d USING (account_id, reporting_date)
LEFT JOIN   {{ ref('int_payments_monthly') }}  p USING (account_id, reporting_date)

{% if is_incremental() %}
  -- on an incremental run, rebuild a trailing window rather than only the newest month,
  -- so late-arriving corrections from Lecture 10 are absorbed
  WHERE s.reporting_date >= (SELECT DATEADD('month', -3, MAX(reporting_date)) FROM {{ this }})
{% endif %}

The trailing three-month window is the restatement policy of Lecture 10 expressed in the transformation layer, and the merge on the declared key is the idempotency of Lecture 06. Together they mean a rerun changes nothing and a late correction is picked up automatically. Note the discipline this requires: the incremental filter must be on a column that reflects when the business event belongs, and the unique key must genuinely be the grain, or the merge either misses rows or duplicates them.

Tests

# models/marts/schema.yml
version: 2
models:
  - name: fact_account_month
    description: |
      Periodic snapshot fact at the account-month grain. One row per account per calendar
      month end for every account open at any point in the month. Balance is semi-additive:
      do not sum across reporting dates.
    tests:
      - dbt_utils.unique_combination_of_columns:
          combination_of_columns: [account_id, reporting_date]
    columns:
      - name: account_id
        tests: [not_null]
      - name: reporting_date
        tests: [not_null]
      - name: customer_id
        tests:
          - not_null
          - relationships:
              to: ref('dim_customer')
              field: customer_id
      - name: arrears_months
        tests:
          - not_null
          - dbt_utils.accepted_range: {min_value: 0, max_value: 120}
      - name: in_default
        tests: [not_null]

Four kinds of test cover most needs. Generic tests are the built-in four: unique, not_null, accepted_values, and relationships, the last being referential integrity enforced in a layer where the engine may not enforce it. Package tests from dbt_utils and similar add composite uniqueness, ranges, expression checks, and mutual exclusivity. Singular tests are arbitrary SQL files that must return zero rows, which is the escape hatch for anything else, including the cross-table reconciliations that a constraint cannot express. And unit tests supply fixed inputs to a model and assert the output, which is the right tool for the tricky logic: the default flag with forbearance interaction, the window that handles a missing month.

Note the description block above. It states the grain in one sentence and warns about the semi-additive measure, and because it is generated into the documentation site, it is where a consumer will actually see it. Documentation adjacent to the code, published automatically, is the only kind that stays true.

Running it

dbt build                                  # run models, then their tests, in dependency order
dbt build --select int_default_flag+       # that model and everything downstream of it
dbt build --select +fact_account_month     # that model and everything it depends on
dbt build --select state:modified+         # what changed on this branch, plus dependants
dbt test --select tag:critical             # a subset, for a quick gate
dbt docs generate && dbt docs serve        # the lineage graph and column documentation
dbt source freshness                       # has the raw data actually arrived?

The state:modified+ selector is what makes continuous integration practical: a pull request builds and tests only the models it changed and their dependants, against a temporary schema, so a reviewer sees evidence rather than assurances. That is the CI/CD lecture applied to data, and it is the point at which the transformation layer genuinely joins the software engineering discipline.

What dbt is not, and its failure mode dbt does not extract or load; it transforms what has already landed, so Lectures 10 to 12 remain necessary. It is not an orchestrator either: it resolves the order within its own graph, but something must decide to run it, retry it, and coordinate it with ingestion, which is Lecture 17. And its characteristic failure mode is a sprawl of hundreds of thinly-reasoned models with duplicated logic in the intermediate layer, no tests beyond not_null, and a lineage graph nobody can read. The tool enforces order of execution, not clarity of thought. The three-layer convention, real tests, and code review are what keep a project comprehensible; without them dbt reproduces the old mess in a format that merely diffs better.
Worked example: changing the default definition, and knowing what it touched

The situation: the regulator's definition of unlikely-to-pay is being widened to include a forbearance concession granted in the last twelve months. Today the definition exists in int_default_flag and nowhere else. Walk the change through.

1. Establish the blast radius before writing anything. dbt ls --select int_default_flag+ lists every downstream node: the risk mart, the PD observation dataset, the IFRS 9 staging input, two aggregate models, and four exposures registered against BI dashboards. That list is the impact assessment, produced in a second, and in a pre-dbt estate it is a week of grep and interviews with an answer nobody fully trusts.

2. Make the change in one file, on a branch. The forbearance condition is added to int_default_flag, with the lookback window as a project variable rather than a literal. Because every consumer references this model, no other model changes.

3. Add the tests that encode the new rule. A unit test with fixed rows: an account with two months of arrears and a recent concession is in default; the same account with a concession fourteen months old is not; an account with three months of arrears is in default regardless. These are the edge cases a reviewer would otherwise have to reason about in their head, and they will still be checked in three years when somebody else edits the file.

4. Quantify the effect before merging. Build the branch into a temporary schema and compare the new default population against production for the last twenty-four months: how many accounts newly qualify, what exposure they carry, and how the monthly default rate series moves. This is the number the credit risk committee will ask for, and the pull request is the natural place to put it. Note that this comparison is only possible because both versions can be built side by side, which is what environment-portable references buy.

5. Review, merge, and rebuild deliberately. The review sees a small diff to one file, the new unit tests, and the quantified impact. On merge, continuous integration has already built and tested the affected subgraph. The production rebuild is dbt build --select int_default_flag+ --full-refresh, because a definition change must reprocess history rather than apply only to new months, and that distinction is a decision the operator must make consciously; an incremental run would leave the history under the old definition and the recent months under the new one, which is the worst of both.

6. What the auditor now gets. The definition is a file with a git history naming every change, its author, its reviewer, and its date. The lineage graph shows every consumer. The tests document the intended edge cases. The impact analysis is in the pull request. Compare with the pre-dbt answer to "when did the default definition change and what did it affect?", which is usually a search through email. This is the case for analytics engineering in a regulated environment, and it has very little to do with any feature of the tool beyond ref().

Step 5

Synthesis and what's next

Analytics engineering relocates transformation logic into a repository, where version control, review, tests, and generated documentation apply to it. dbt does this with one idea, references between models, from which execution order, environment portability, lineage, impact analysis, and selective builds all follow. Organise models in three layers so that source quirks are isolated, shared definitions have exactly one home, and marts are products. Test the grain, the keys, the ranges, and the edge cases. And remember what the tool does not do: it does not extract, load, orchestrate, or think for you. Part IV closes here; Part V is the undercurrents that decide whether any of it is trusted.
