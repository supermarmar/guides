DuckDB: the in-process analytical engine

A server database is a restaurant kitchen: you write an order, a waiter carries it away, something happens out of sight, and a plate comes back. DuckDB is a kitchen in your own house. There is no waiter, no queue, and no van bringing ingredients from a depot, because the ingredients are already on your counter. Removing the journey turns out to be worth more than most of the cleverness it replaced.

Lecture 9 of 20 Reading time, 45 minutes Part II: SQL and data modelling
Step 1

The 30-second version

DuckDB is an in-process analytical database. In-process means it runs inside your Python session as a library rather than as a separate server you connect to, exactly as SQLite does for transactional work, which is why it is often described as SQLite for analytics. It came out of CWI Amsterdam and is free and open source.

Three properties make it the right default for analytical work below the scale where a cluster is genuinely needed. It is columnar and vectorised, so it processes batches of values through tight loops and delivers the scan performance of a warehouse. It reads files directly, so a Parquet dataset, a CSV, a JSON file, a pandas or Polars dataframe, or an Arrow table can be queried in place with no load step. And it speaks full SQL, including window functions, common table expressions, and the QUALIFY clause from Lecture 05, so everything in Part II runs unchanged.

What it is not is a transactional multi-user database. One process writes at a time, there is no network protocol for a hundred concurrent clients, and it is not where a bank's ledger belongs. It is where an analyst's queries, a modeller's dataset construction, and a pipeline's local development all belong.

Feynman test Two cooks make the same omelette. The first phones a depot, waits for a van, signs for the eggs, cooks, then packs the result into another van to send back. The second takes the eggs off the counter. If the recipe is complicated enough, the depot's industrial equipment eventually wins. For an omelette, the second cook has finished before the first van arrives. Most analytical questions are omelettes, and for years we sent them all to the depot because that was the only kitchen anyone had built.
Why "it does not fit in memory" stopped being the argument Two things changed after 2015. Machines grew: a laptop with 32 or 64 GB of RAM is now ordinary, and a single cloud instance can have a terabyte. And engines got much better at not reading what they do not need, so a 200 GB Parquet dataset queried for three columns of one month's partition may only touch a few hundred megabytes. The consequence is that the dataset size that genuinely requires distribution moved up by more than an order of magnitude, and a large share of the Spark clusters running today are solving a problem their data no longer has. DuckDB also spills to disk when a query exceeds memory, so exceeding RAM slows a query rather than failing it.
Step 2

Why this matters

The journey is often the whole cost. Running a query against a remote warehouse from a notebook costs a network round trip, serialisation of the result into some wire format, deserialisation into a dataframe, and often a queue wait behind other users. For a query returning ten million rows, that overhead can exceed the computation. In-process execution removes all of it, and Arrow integration removes the serialisation too, so handing a result to pandas or Polars is close to free rather than a copy.

It removes the excuse not to use SQL. The historical reason analysts did dataframe gymnastics instead of writing SQL was that SQL required a database, and a database required someone to provision it, grant access, and load data into it. DuckDB requires pip install duckdb. The set-based operations of Lecture 05, which are declarative, parallelised by the engine, and far easier to review than a chain of dataframe mutations, become available with no infrastructure conversation.

It makes pipeline development local and cheap. A transformation developed against a local DuckDB instance over sample Parquet files can be tested in seconds, in a unit test, with no cluster and no cloud credentials. Because the SQL is largely portable, the same logic can then run in the production warehouse or in Spark. That is a much shorter feedback loop than the alternative, and a shorter feedback loop is the main determinant of how carefully anybody tests anything.

Where DuckDB is the wrong choice Concurrent writes from several processes: one writer at a time is a hard constraint, and a shared file on a network drive is not a substitute for a server. High-frequency single-row transactions: that is OLTP and belongs in PostgreSQL or the core system. Datasets whose working set genuinely exceeds one machine even after pruning, or joins between two very large tables that need distributed shuffling: that is Lecture 13. And anything requiring a governed multi-tenant permission model, which is a catalogue and warehouse concern from Lecture 19. Reach for it as the default, not as the answer to everything.

The pandas comparison deserves a nuance the table cannot carry. This is not a competition, because they share memory. The idiomatic modern pattern is to use DuckDB for the relational heavy lifting, joins across several tables, aggregations over many rows, window functions, and pandas or Polars for the row-wise and modelling work that follows, passing data between them at no cost because both speak Arrow. Choosing between them is usually the wrong question; the right one is which tool each step belongs in.

Step 4

The detail

Connecting

import duckdb

# in-memory: everything vanishes at the end of the session
con = duckdb.connect(":memory:")

# persistent: a single file holding tables, views, and metadata
con = duckdb.connect("risk.db")

# and when finished
con.close()

The choice is not about size, since both spill to disk as needed. It is about whether you want the tables to survive. Use in-memory for ad hoc analysis over files that are themselves the source of truth, and a file when you are building a small warehouse whose tables are the artefact.

Querying files with no load step

-- a single Parquet file
SELECT * FROM 'extracts/loans_2026_03.parquet' LIMIT 5;

-- a glob across many files
SELECT COUNT(*) FROM 'extracts/loans_*.parquet';

-- a Hive-partitioned dataset: the partition column becomes a real column,
-- and a filter on it prunes whole directories before reading anything
SELECT reporting_date, COUNT(*) AS accounts
FROM   read_parquet('lake/loans/**/*.parquet', hive_partitioning = true)
WHERE  reporting_date >= DATE '2025-01-31'
GROUP BY reporting_date
ORDER BY reporting_date;

-- CSV, with the schema declared rather than guessed
SELECT * FROM read_csv('extracts/loans.csv',
                       header = true,
                       delim  = ',',
                       columns = {'account_id': 'VARCHAR',
                                  'reporting_date': 'DATE',
                                  'balance': 'DECIMAL(18,2)',
                                  'arrears_months': 'INTEGER'});

-- newline-delimited JSON
SELECT * FROM read_json_auto('events/applications_2026_03.jsonl');

Declaring the CSV schema explicitly rather than relying on inference is the direct application of Lecture 02's defect table. Inference is convenient for exploration and a liability in a pipeline, because the inferred type depends on the sample the reader happened to see, so a column that is integer this month becomes text next month when one value arrives with a stray space.

Replacement scans: querying dataframes by name

import pandas as pd, duckdb

loans = pd.read_parquet("extracts/loans_2026_03.parquet")
segments = pd.read_csv("reference/segments.csv")

# the dataframe names are visible to SQL directly, with no registration
result = duckdb.sql("""
    SELECT s.segment,
           COUNT(*)                                   AS accounts,
           SUM(l.balance)                             AS exposure,
           SUM(CASE WHEN l.arrears_months >= 3 THEN l.balance ELSE 0 END) AS defaulted_exposure
    FROM   loans l
    JOIN   segments s USING (customer_id)
    GROUP BY s.segment
    ORDER BY exposure DESC
""").df()

This is the feature that changes daily habits. Any pandas, Polars, or Arrow object in scope can be referenced as if it were a table, and the result comes back as whichever of the three you ask for. A join between two dataframes, which in pandas requires attention to index alignment, suffixes, and merge semantics, becomes the SQL you already know, and it runs in parallel.

Creating tables, and exporting

-- create a table from a query, the usual way to materialise a step
CREATE OR REPLACE TABLE fact_account_month AS
SELECT * FROM read_parquet('lake/silver/loans/**/*.parquet', hive_partitioning = true);

-- write results back out, partitioned, in one statement
COPY (SELECT * FROM fact_account_month)
TO 'lake/gold/fact_account_month'
(FORMAT PARQUET, PARTITION_BY (reporting_date), COMPRESSION ZSTD, OVERWRITE_OR_IGNORE);

-- or a single file for a colleague
COPY (SELECT * FROM v_defaulted_accounts) TO 'out/defaults.csv' (HEADER, DELIMITER ',');

The COPY ... PARTITION_BY form is worth noting: it writes a Hive-partitioned Parquet dataset with the layout Lecture 02 recommended, in one statement, which makes the round trip from files to files complete without any other tooling.

Extensions, and reaching other systems

INSTALL httpfs;  LOAD httpfs;      -- read S3, Azure, GCS, and plain HTTPS
SELECT * FROM 's3://bucket/lake/loans/reporting_date=2026-03-31/*.parquet';

INSTALL postgres; LOAD postgres;    -- query a live PostgreSQL database
ATTACH 'host=... dbname=core user=...' AS core (TYPE POSTGRES, READ_ONLY);
SELECT * FROM core.public.accounts LIMIT 10;

INSTALL sqlite; LOAD sqlite;        -- and SQLite files
INSTALL iceberg; LOAD iceberg;      -- and Iceberg tables (Lecture 14)

The PostgreSQL attachment is more useful than it first appears: it lets one query join a table in the analytical store to a small reference table still living in an operational database, without an export step. Note the READ_ONLY flag, which is the right default when pointing anything at a system you do not own, and remember Lecture 03's warning about scanning a production transactional database at all.

Settings worth knowing

SET threads TO 8;                 -- defaults to the core count
SET memory_limit = '24GB';        -- above this, the engine spills to disk
SET temp_directory = '/fast/ssd/tmp';   -- where it spills; put it on fast storage
SET preserve_insertion_order = false;   -- allows more parallelism on large writes

PRAGMA database_size;             -- how big the file has become
EXPLAIN ANALYZE SELECT ...;       -- the plan and the actual timings

The pairing of memory_limit and temp_directory is what makes larger-than-memory work behave predictably: the engine will use up to the limit and then spill hash tables and sort runs to the temporary directory, so a query that exceeds RAM becomes slower rather than failing, provided the temporary directory has space and is not a slow network mount.

Worked example: a default rate time series over sixty monthly snapshots, without loading anything

The setup: lake/silver/loans/ holds sixty Hive-partitioned monthly snapshots of a mortgage book, roughly two million accounts each, 140 columns. The task: produce a monthly default rate series, by product, with a twelve-month moving average, and hand the result to matplotlib. No cluster, no warehouse, no load step.

import duckdb

con = duckdb.connect(":memory:")
con.execute("SET memory_limit = '24GB'")

series = con.sql("""
    WITH book AS (
        SELECT reporting_date,
               product,
               balance,
               arrears_months,
               unlikely_to_pay
        FROM   read_parquet('lake/silver/loans/**/*.parquet',
                            hive_partitioning = true)
        WHERE  reporting_date >= DATE '2021-06-30'
    ),
    monthly AS (
        SELECT reporting_date,
               product,
               COUNT(*)                                            AS accounts,
               SUM(balance)                                         AS exposure,
               COUNT_IF(arrears_months >= 3 OR unlikely_to_pay)     AS defaults,
               SUM(CASE WHEN arrears_months >= 3 OR unlikely_to_pay
                        THEN balance ELSE 0 END)                    AS defaulted_exposure
        FROM   book
        GROUP BY reporting_date, product
    )
    SELECT reporting_date,
           product,
           accounts,
           defaults,
           -- sum numerator and denominator, then divide once: never average rates
           defaults::DOUBLE / accounts                       AS default_rate,
           defaulted_exposure / NULLIF(exposure, 0)          AS default_rate_by_value,
           AVG(defaults::DOUBLE / accounts) OVER (
               PARTITION BY product ORDER BY reporting_date
               ROWS BETWEEN 11 PRECEDING AND CURRENT ROW)    AS rate_ma_12m
    FROM   monthly
    ORDER BY product, reporting_date
""").df()

What the engine did, and did not do. The WHERE on the partition column eliminated the partitions before 2021 without opening them. Of the 140 columns, five were read, because Parquet stores columns separately and the footer says where each one is. The five columns of sixty partitions were scanned in parallel across cores, aggregated to a few hundred rows, and the window function ran on that small result. The data never left the process, and the final .df() handed the few hundred rows to pandas through Arrow with no serialisation. Nothing was loaded, copied, or staged.

Two correctness points embedded in the query. The default rate is computed by summing defaults and accounts separately and dividing once, not by averaging monthly rates, per the non-additivity discussion in Lecture 08. Both a count-based and a value-weighted rate are produced, because they answer different questions and diverge when defaults concentrate in large exposures, which is exactly when someone will ask.

How to know whether it was fast for the right reason. Run it under EXPLAIN ANALYZE. Confirm that the reported number of files or row groups read is far smaller than the total, which proves pruning happened, and that the time is dominated by the scan rather than by a spill to the temporary directory. If a spill dominates, the fix is usually the memory_limit and temp_directory settings above, not a cluster.

When this stops working. Two signals. If the same query needs a join between two multi-billion-row tables rather than an aggregation, the shuffle may exceed what one machine can do comfortably. If several people need to run heavy queries against the same store concurrently, you want a served engine with a scheduler rather than everyone's laptop reading object storage. Until one of those is true, this is the whole architecture, and Lecture 13 explains what changes when it is not.

Step 5

Synthesis and what's next

DuckDB removes two costs rather than optimising them: the journey between your process and a database server, and the load step before files can be queried. What remains is a columnar, vectorised, parallel SQL engine that reads Parquet, CSV, JSON, and dataframes in place and shares memory with the rest of the Python stack. It is the right default for analytical work on a single machine, the right tool for developing and testing transformations that will later run at scale, and the wrong tool for concurrent writers, transactional workloads, and genuinely distributed joins. Part II closes here: you can now declare a schema, query it, write to it safely, design it, and run all of it locally.
