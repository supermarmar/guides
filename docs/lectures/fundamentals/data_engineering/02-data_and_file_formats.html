Data and file storage

Two libraries hold the same customer records. In the first, each customer has a folder containing everything about them. In the second, all the surnames are in one ledger, all the balances in another, all the arrears counts in a third. Ask for one customer's complete file and the first library wins easily. Ask for the mean balance across two million customers and the second library wins by two orders of magnitude. That single choice, row against column, explains most of what follows.

Step 1

The 30-second version

Data is a collection of facts, usually about entities an organisation cares about: customers, accounts, loans, payments. Each entity has attributes. How rigidly those attributes are fixed in advance gives the three-way classification every data platform starts from: structured data conforms to a schema declared before the data arrives, semi-structured data carries its own structure but permits variation between instances, and unstructured data has no schema the machine can read at all.

That classification determines the file format, and the file format determines what the platform can do cheaply. Three choices matter, and they are independent of each other. First, is the file human-readable text or binary? Text is universally interoperable and expensive; binary is compact, typed, and needs a library. Second, is it laid out by row or by column? Rows suit writing one record and reading it whole; columns suit scanning one attribute across millions of records. Third, does the file carry its own schema? A CSV does not, so every reader guesses; a Parquet or Avro file does, so every reader agrees.

The practical summary for analytical work is short. Land data as it arrives, keep it, and convert it to Parquet for anything you will read more than once. Use CSV only at boundaries you do not control, and treat every CSV as untyped text until proven otherwise. Reserve JSON for genuinely variable structure, and flatten it as early as you can defend doing so.

Feynman test Two libraries hold the same records. Library R gives each customer a folder holding everything about them: name, address, balance, arrears. Library C keeps ledgers instead: one ledger of every surname, one of every balance, one of every arrears count, each in the same customer order. Ask for everything about customer 4,182 and library R hands you one folder while library C makes you walk to twelve ledgers. Ask for the average balance of two million customers and library C hands you one thin ledger while library R makes you open two million folders and ignore almost everything in each. Transactional systems are library R. Analytical systems are library C. Nobody is being clever; they are answering different questions.
Why a format choice is an architecture choice It is tempting to treat file format as a detail to be settled late. It is not, because the format decides which operations are cheap, and which operations are cheap decides which questions people actually ask. A team whose history lives in gzipped CSV will not run an ad hoc query across five years of it, because the query takes an hour; so they will not ask the question; so nobody will know the answer. Convert the same data to partitioned Parquet and the query takes seconds, and the question gets asked weekly. Format choices propagate into what an organisation knows about itself.
Step 2

Why this matters

Three consequences follow from getting this wrong, and each is routine rather than exotic.

Untyped text loses information silently. A CSV has no types. Every field is a string until some reader decides otherwise, and readers decide differently. An account number of 0012345 becomes the integer 12,345 and the leading zeros are gone. A date written 03/04/2024 is the third of April in London and the fourth of March in New York, and neither reader will tell you which it chose. A blank field is an empty string to one reader, a null to another, and the string "NaN" to a third. A field containing a comma inside quotes is fine until a source system stops quoting. None of these produce an error. All of them produce a plausible wrong answer, which is exactly the failure mode Lecture 01 called the expensive one.

Row layout makes analytical scans cost what they need not cost. A credit risk dataset with 120 columns, queried for the mean of one of them, reads all 120 columns from a row-oriented file because rows are the unit of storage. Columnar layout reads one. The saving is roughly the ratio of columns you want to columns you have, multiplied again by compression, because a column of values of one type compresses far better than a row of mixed types. On a wide table the combined factor is commonly between ten and a hundred.

Small files destroy distributed performance. Every file carries fixed overhead: a listing entry, an open, a footer read, a task scheduled. A directory of fifty thousand two-kilobyte JSON files takes longer to read than a single one-gigabyte Parquet file containing the same data, sometimes by orders of magnitude, because the work is per file rather than per byte. This is the small files problem, and it is the most common performance complaint about data lakes. Lecture 14 covers compaction, which is the cure.

The one that catches banks Financial amounts must not be stored as binary floating point. A 64-bit float cannot represent 0.1 exactly, so sums of many amounts drift, and a reconciliation to the general ledger fails by a few pence for reasons nobody can locate. Use a fixed-precision decimal type, which Parquet, Avro, and every serious database support, and specify the precision and scale deliberately. If the source hands you amounts inside a CSV, the conversion to decimal is your first transformation, not an afterthought.
Step 3

The mental model

The three degrees of structure

Structured dataAdheres to a fixed schema declared before the data arrives, so every instance has the same fields with the same types. Usually tabular: rows are instances, columns are attributes. A loan book extract with account number, balance, rate, and arrears count is structured. The schema is a contract, and violating it is an error rather than a variation.
Semi-structured dataCarries its own structure, but permits variation between instances. One customer has two email addresses, another has none, a third has a field nobody has seen before. JSON is the canonical format. The structure is self-describing rather than pre-declared, which buys flexibility at the source and costs work at every consumer.
Unstructured dataNo machine-readable schema at all: scanned facility letters, valuation reports, call recordings, photographs of collateral. The bytes are stored as a binary large object and the meaning is extracted by a model or a human. In banking this is a large and mostly untapped share of the estate, and Lecture 11 covers pulling tables out of it.

The boundaries are softer than the definitions suggest. A JSON file whose every instance happens to have identical fields is structured data in a semi-structured format, and should be flattened. A PDF containing a well-formed table is unstructured to the file system and structured to a human, which is exactly why extraction is worth automating. The classification is a statement about guarantees, not about appearance: structured means somebody promised the shape, and that promise is enforceable.

Row layout against column layout

A file is a one-dimensional sequence of bytes and a table is two-dimensional, so the table must be unrolled in some order. Two orders are useful. Row-oriented storage writes all fields of record one, then all fields of record two. Column-oriented storage writes all values of field one, then all values of field two.

Self-describing files, and why schema-carrying matters

A CSV is a sequence of characters. Nothing in it states that column three is a decimal with two places, that column seven is nullable, or that dates are ISO-8601. Every reader must be told, or must guess, and the guesses differ. A self-describing format embeds the schema in the file itself: Parquet writes it into the footer, Avro into the header. Any reader, in any language, then agrees on types, nullability, and column names without a side agreement.

This is the single most underrated property in the list. It converts a class of silent errors into an impossibility. You cannot accidentally read the account number as an integer from a Parquet file that declares it a string, and you cannot lose the distinction between null and empty. When Lecture 16 talks about schema enforcement, self-describing formats are what make enforcement cheap rather than aspirational.

Step 4

The detail

Delimited text: CSV and its relatives

Data is often stored as plain text with a field delimiter and a row terminator. Comma-separated values is the most common, with tab-separated, pipe-delimited, and fixed-width variants all in regular use, the last still arriving from mainframes.

account_id,origination_date,balance,rate,arrears_months
A001,2019-04-03,142000.00,0.0429,0
A002,2021-11-17,88500.50,0.0515,2
A003,2015-01-29,315000.00,0.0312,0

The format's one virtue is that everything reads it, including a human with a text editor, which is why it will never die. Its defects are worth listing explicitly, because each one has bitten a production pipeline.

Ambiguous dates03/04/2024 parsed as March or April depending on localeRequire ISO-8601 in the contract; parse with an explicit format string
Null ambiguityEmpty, NULL, NA, N/A, -, and NaN all appear in one fileSpecify the null sentinel list explicitly; reconcile counts after load
Delimiter collisionAn address containing a comma splits into two fields when quoting is droppedPrefer a delimiter absent from the data, validate the field count per row
EncodingNames with accents arrive as mojibake, or the file starts with a byte-order markInsist on UTF-8 in the contract; handle the BOM explicitly
No compression or splittingA 40 GB gzipped CSV cannot be read in parallel because gzip is not splittableConvert on arrival; if you must compress text, use a splittable codec

JSON, and the cost of flexibility

JSON expresses hierarchy: objects in braces, arrays in brackets, attributes as name-value pairs. It is the default for application events and web APIs, and it handles the case that defeats a table, which is an attribute that repeats an unpredictable number of times.

{
  "customer_id": "C8814",
  "name": {"first": "Samir", "last": "Nadoy"},
  "addresses": [
    {"type": "residential", "postcode": "SW1A 1AA", "since": "2019-04-01"}
  ],
  "contacts": [
    {"type": "email", "value": "samir@example.com"},
    {"type": "mobile", "value": "+44 7700 900123"}
  ]
}

For pipelines, the important variant is newline-delimited JSON (also called JSON Lines), one complete document per line. A single JSON array spanning a whole file cannot be split across workers or read incrementally without parsing the entire structure; newline-delimited JSON can be split at any line break, which makes it usable at scale. If you are offered a choice, take the newline-delimited form.

The engineering question with JSON is when to flatten. Nested structure is expressive and expensive: every consumer must understand the nesting, every query must traverse it, and any two consumers may traverse it differently. The usual discipline is to land the JSON as it arrived, then flatten to a typed table as the first transformation, promoting the fields you actually use to columns and keeping the original document alongside for the ones you do not. Arrays become separate tables with a foreign key, which is the normalisation of Lecture 07 arriving early.

Binary large objects

All files are ultimately binary. In text formats the bytes map to printable characters through an encoding such as UTF-8; in other formats they do not, and an application must interpret them. Images, video, audio, and application-specific documents are stored this way, and the term of art is BLOB, a binary large object. The engineering pattern is almost always the same: keep the object itself in cheap object storage, keep a row in a table holding its identifier, location, size, checksum, and whatever metadata you can extract, and never put the bytes in the database. Lecture 11 covers extracting structure from the most common banking case, the PDF.

The optimised analytical formats

Three binary formats dominate. They differ on the row-or-column axis, which drives everything else.

FormatLayoutStrengthUse it when
ParquetColumnar (hybrid: row groups of column chunks)Analytical scans, compression, predicate and projection pushdown; the de facto standard, and the substrate of every lakehouse table formatAlmost always, for anything you will read more than once
AvroRow-orientedCompact per-record writes and first-class schema evolution, with the schema in the header; strong in streaming and event pipelinesWriting many individual records, or moving events through Kafka
ORCColumnarComparable to Parquet, with lightweight indexes and strong compression; historically tied to the Hive ecosystemYou are in a Hive or legacy Hadoop estate that already uses it

Parquet is worth understanding one level deeper, because its structure explains its performance. A Parquet file is divided into row groups, each holding a horizontal slice of the rows. Within a row group, each column is stored as a separate column chunk, itself divided into pages. The file ends with a footer holding the schema and, for every column chunk, statistics: minimum, maximum, and null count.

Those statistics deliver the two savings that matter. Projection pushdown means a query for three columns of a hundred reads only three column chunks, because the footer says where each one is. Predicate pushdown means a query filtered to origination_date >= 2023-01-01 reads the footer, sees that a row group's maximum origination date is 2019, and skips the entire row group without decompressing a byte. Add dictionary encoding for low-cardinality columns and run-length encoding for sorted ones, and a Parquet copy of a wide table is routinely five to twenty times smaller than the CSV and scans faster by more than that ratio.

Sort order is a free index Predicate pushdown works on the row group statistics, so it works well when the filter column is correlated with the physical order of the file and hardly at all when it is not. Writing a Parquet dataset sorted by the column you filter on most, usually a date, can turn a full scan into a handful of row group reads. This is the cheapest performance work available in a data platform: no index to maintain, no engine to tune, just deciding the write order deliberately. Lecture 14 formalises it as clustering.

Compression, and Arrow

Compression inside Parquet is chosen per column chunk. Snappy is the traditional default, fast to compress and decompress and not especially small. Zstandard has largely displaced it for storage, compressing appreciably better at similar decompression speed, which matters when the file lives in object storage and the network is the bottleneck. Gzip compresses well and decompresses slowly, and its lack of splittability makes it a poor choice for whole text files even when it is fine inside Parquet. The rule of thumb: zstd for data you keep, snappy for intermediate data you will delete tomorrow.

One more name belongs here. Apache Arrow is not a file format but an in-memory columnar standard, and it is why the modern stack interoperates cheaply. Historically, moving a table from one tool to another meant serialising it to some format and parsing it back, and the conversion often cost more than the computation. Arrow defines one memory layout that pandas, Polars, DuckDB, Spark, and others can all read in place, so handing a table between them approaches free. Parquet is how a table rests; Arrow is how it travels.

Partitioning and file size

A large dataset is stored as many files in a directory tree, and the tree is part of the design. Hive-style partitioning encodes column values in directory names, so a reader can eliminate whole directories before opening anything.

loans/
  reporting_date=2026-05-31/
    part-0000.parquet
    part-0001.parquet
  reporting_date=2026-06-30/
    part-0000.parquet

A query for June reads one directory. The choice of partition column follows the dominant filter, which for a bank's risk data is almost always the reporting date. Two failure modes bracket the good choice. Partition on something high-cardinality, such as account number, and you get millions of tiny files and the small files problem. Partition on nothing and every query scans everything. Aim for partitions holding files in the region of a hundred megabytes to a gigabyte each, and accept that the ideal depends on the engine.

Worked example: choosing the storage for a monthly IFRS 9 modelling dataset

The requirement: sixty monthly snapshots of a retail mortgage book, roughly two million accounts per snapshot, 140 columns, of which a typical query touches eight. Consumers are the ECL model build, the SICR analysis, and an ad hoc query workload from the risk team. Work through the choices in order.

Format. Columnar, because every consumer scans few columns over many rows. Parquet rather than ORC, because the surrounding tooling (DuckDB locally, Spark at scale, pandas and Polars in the analysts' notebooks) treats Parquet as native. Indicative arithmetic for a table of this shape: as CSV, on the order of tens of gigabytes per snapshot's raw text; as Parquet with zstd, a small single-digit fraction of that, with an eight-column query reading a small fraction again of the Parquet.

Types. Amounts as decimal with explicit precision and scale, never float. Dates as date, not string. The account identifier as string, because leading zeros and alphanumeric prefixes both occur and no arithmetic is ever done on it. Categorical fields such as product code and arrears bucket as dictionary-encoded strings, which cost almost nothing and stay readable.

Partitioning. By reporting_date, one partition per month-end, which gives sixty partitions of a manageable size and matches the dominant filter in every consumer. Not by product, which would multiply the file count for a filter nobody applies first. Within a partition, write sorted by account identifier so that point lookups and joins benefit from row group elimination.

Raw retention. Keep the source extract exactly as it arrived, compressed, in a separate raw location, with its checksum and arrival timestamp. It will be needed the first time someone asks whether a discrepancy was introduced by the source or by the pipeline, and that question always arrives eventually.

What this buys. The ECL model build reads sixty partitions of eight columns instead of sixty full snapshots of text. The SICR analysis, which needs a two-year lookback per account, reads twenty-four partitions and nothing else. The ad hoc query workload becomes fast enough that people run queries instead of requesting extracts, which is the real return on the work.

Step 5

Synthesis and what's next

Three independent axes describe any data file: how structured it is, whether it is laid out by row or by column, and whether it carries its own schema. Structured tabular data with a columnar layout and an embedded schema, which is to say Parquet, is the right default for analytical work, and the reasons are projection and predicate pushdown, type safety, and compression that only becomes available once each run of bytes holds one type. Text formats survive at boundaries you do not control, and every one of them should be treated as untrusted until a schema check has passed.
