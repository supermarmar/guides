SQL I: definition

A constraint is a test that runs on every write, forever, without anyone remembering to run it. Most of what a team calls data quality tooling is an attempt to recover, after the fact and at great expense, guarantees that six lines of DDL would have enforced for free at the moment of writing. This lecture is about those six lines: types, keys, constraints, views, and indexes.

Step 1

The 30-second version

SQL, Structured Query Language, manages data held in relational databases through declarative statements. Declarative means you state the result you want, not the procedure for obtaining it: SELECT the accounts in arrears, rather than open the file, loop over the rows, and test each one. The engine chooses the procedure, which is why the same statement can run unchanged as the data grows from a thousand rows to a billion.

SQL statements group into four sub-languages. Data definition language (DDL) declares the structure: CREATE, ALTER, DROP. Data manipulation language (DML) changes the contents: INSERT, UPDATE, DELETE. Data query language (DQL) asks questions: SELECT. Data control language (DCL) governs permissions: GRANT, REVOKE. This lecture is DDL. Lecture 05 is DQL, Lecture 06 is DML, and DCL appears in Lecture 19 alongside the rest of access control.

DDL is the least glamorous of the four and the one with the largest effect on how much time you later spend firefighting. Every type declaration prevents a class of coercion error, every constraint is a permanent assertion about what the data may contain, and every foreign key makes a whole category of orphaned record impossible rather than merely unlikely.

Feynman test Think of a form at a bank counter. A badly designed form has a blank box labelled "date" and accepts anything a customer writes there, so somebody downstream has to work out whether 03/04 was March or April, and sometimes guesses wrong. A well designed form has three boxes, DD, MM, YYYY, and rejects a thirteenth month at the counter. DDL is the second form. The constraint is not paperwork; it is the reason nobody downstream has to guess.
One standard, several dialects SQL is an ANSI standard, so the core is portable, and every engine extends it. Microsoft SQL Server speaks T-SQL and dominates large enterprise estates. PostgreSQL is the open-source reference implementation, unusually complete and standards-faithful. SQLite fits an entire database in one file with no server. DuckDB is the analytical counterpart to SQLite, in-process and columnar, and is the engine used in this course's examples because it needs no installation beyond a Python import. The examples below are written in a portable style; where a dialect differs materially, the difference is flagged.
Step 2

Why this matters

A constraint is the cheapest data quality control that exists. Lecture 16 will build validation suites that check data after it lands, and those suites are necessary. But a check that runs after the fact discovers a problem; a constraint prevents one. The declaration arrears_months INTEGER NOT NULL CHECK (arrears_months BETWEEN 0 AND 120) means no process, no matter how carelessly written, will ever put a null or a negative arrears count in that column. That guarantee costs one line, is enforced by the engine on every write forever, and needs no scheduling, no monitoring, and no maintenance.

The schema is documentation that cannot go stale. Prose describing a table drifts from reality within months. A DDL definition is the reality: if the document says the account identifier is unique and the table declares it unique, that is not a claim but a fact enforced by the system. This is why reviewing the DDL is the fastest way to understand an unfamiliar database, and why a schema kept in version control is a more reliable data dictionary than any wiki page.

Types stop silent coercion. Lecture 02 catalogued the damage untyped text does. DDL is where the types are asserted: the account number is text so leading zeros survive, the balance is a fixed-precision decimal so sums reconcile, the reporting date is a date so no locale can reinterpret it. Each of these turns a silent wrong answer into a loud failure at load time, which is the whole strategy.

Where constraints are not free Constraints and indexes cost write performance, because every insert must be checked and every index updated. On a transactional system with heavy write rates this is a real trade-off requiring measurement. On analytical tables written once per month by a pipeline, it is close to irrelevant, and the argument against constraints is nearly always misapplied transactional folklore. Note the opposite caution for analytical engines: some, DuckDB included, support declaring keys but do not enforce foreign keys the way PostgreSQL does, and several warehouses accept constraint syntax while treating it as documentation. Check what your engine actually enforces rather than assuming, because an unenforced constraint is worse than none: it invites trust it has not earned.
Step 3

The mental model

Three kinds of promise

Everything in DDL is one of three promises, and it helps to know which you are making.

A typeA promise about the domain of values a column may hold: integer, decimal with two places, date, boolean, text. Violating it is a load failure. Types also determine storage size and the operations available, so a date column can be compared to another date and a text column cannot be summed.
A constraintA promise about which values within the type are admissible, and how rows relate to each other: not null, unique, a check expression, a primary key, a foreign key. Violating it rejects the write. This is where business rules become enforceable.
An indexNot a promise about content at all, but a promise about performance: a separate data structure that lets the engine find matching rows without reading every one. Indexes never change what a query returns, only how long it takes. The exception is a unique index, which also constrains.

Keys and referential integrity

A primary key is the column, or set of columns, that uniquely identifies a row. It is equivalent to declaring unique and not null together, with two differences: a table may have only one primary key, and other tables reference it. When no single column identifies a row, a composite primary key of several columns does the job. This case is the norm in risk data: a monthly loan snapshot is keyed on account identifier and reporting date, because the same account appears sixty times.

A foreign key in a child table references the primary key of a parent, and the engine then guarantees referential integrity: no arrears record may exist for an account that is not in the accounts table. The behaviour when a parent row is deleted must be chosen explicitly. ON DELETE RESTRICT refuses the deletion while children exist, which is the safe default. ON DELETE CASCADE deletes the children too, which is convenient and occasionally catastrophic. In a bank, prefer restrict, and prefer never deleting anything at all.

Step 4

The detail

Creating a table

CREATE TABLE names a table, names each column, gives each column a type, and attaches constraints. The examples use DuckDB, which needs no server: duckdb.connect(':memory:') for a database that vanishes at the end of the session, or duckdb.connect('risk.db') for one that persists in a file.

CREATE OR REPLACE TABLE customers (
    customer_id     VARCHAR      PRIMARY KEY,
    surname         VARCHAR      NOT NULL,
    date_of_birth   DATE         NOT NULL,
    segment         VARCHAR      NOT NULL DEFAULT 'retail',
    email           VARCHAR      UNIQUE,
    created_at      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (date_of_birth < CURRENT_DATE),
    CHECK (segment IN ('retail', 'sme', 'corporate'))
);

Read every line as an assertion. The customer identifier is text, not an integer, because identifiers with leading zeros or alphabetic prefixes are common and no arithmetic is ever performed on one. Surname and date of birth must be present. Segment defaults to retail and is restricted to three values, which is a poor man's enumerated type and considerably better than nothing. Email is unique but nullable, because not every customer has one, and note that most engines permit multiple nulls in a unique column since nulls are not equal to each other. The final two checks encode facts about the world: nobody is born in the future, and there is no fourth segment.

A CHECK may reference several columns of the same row, so any logic you could write in a WHERE clause against one row can be enforced. What it cannot do is span rows or tables: "the sum of exposures must equal the portfolio total" is not a check constraint, it is a reconciliation test, and it belongs in Lecture 16.

Altering, dropping, replacing

-- add a column; existing rows get NULL unless a default is supplied
ALTER TABLE accounts ADD COLUMN forbearance_flag BOOLEAN DEFAULT FALSE;

-- remove one
ALTER TABLE accounts DROP COLUMN legacy_reference;

-- tighten a column after backfilling it
ALTER TABLE accounts ALTER COLUMN forbearance_flag SET NOT NULL;

-- remove the whole table definition and its contents
DROP TABLE IF EXISTS staging_accounts;

Three distinctions catch people out. DROP TABLE removes the definition and the data; TRUNCATE removes the data and keeps the definition, and is far faster than an unqualified DELETE because it does not log each row. CREATE OR REPLACE TABLE is convenient in a pipeline that rebuilds a table from scratch and destructive if you believed the table held history. And adding a NOT NULL column to a populated table fails unless a default is supplied, so the usual sequence is add nullable, backfill, then tighten, exactly as in the third statement above.

Views: a query with a name

CREATE OR REPLACE VIEW v_defaulted_accounts AS
SELECT account_id,
       reporting_date,
       balance,
       arrears_months
FROM   account_snapshots
WHERE  arrears_months >= 3
   OR  unlikely_to_pay_flag;

A view stores a query, not a result: every reference re-executes it against current data. Views are the right tool for giving a definition one home. If the regulatory default definition lives in a view, then the PD dataset, the LGD dataset, and the IFRS 9 staging engine all read the same definition, and changing it changes all three at once. That is a governance win, not merely a convenience.

A materialised view stores the result and must be refreshed, trading freshness for speed. Support varies by engine, and in a modern stack the same job is usually done by a scheduled table build in dbt, covered in Lecture 15, which has the advantage of being version controlled and testable.

Indexes

An index is a separate structure that lets the engine locate rows without scanning the table. The default is a B-tree, a balanced tree that halves the search space at each level, so finding a value among a million rows takes on the order of log2(1,000,000), roughly twenty comparisons, instead of a million. That is the entire argument for indexes, and it is a strong one for selective lookups.

-- single column
CREATE INDEX accounts_customer_id_idx ON accounts(customer_id);

-- multi-column: column order matters, this suits filters on
-- (reporting_date) or (reporting_date, product), not (product) alone
CREATE INDEX snap_date_product_idx ON account_snapshots(reporting_date, product);

-- partial: index only the subset that is queried
CREATE INDEX snap_defaulted_idx ON account_snapshots(account_id)
WHERE arrears_months >= 3;

-- expression-based: make a case-insensitive lookup indexable
CREATE UNIQUE INDEX customers_email_lower_idx ON customers(LOWER(email));

Column order in a multi-column index matters because the structure is sorted by the first column, then within that by the second. An index on (reporting_date, product) serves a filter on reporting date alone, and does not serve a filter on product alone. The convention <table>_<columns>_idx is worth following; primary key indexes conventionally end _pkey and are created automatically, as are indexes backing unique constraints.

The distinction between clustered and non-clustered is worth the paragraph. A clustered index determines the physical order of the rows in the table, so it is like a dictionary where the entries themselves are alphabetical: once you find the position, the data is there. There can be only one, because a table can only be in one physical order. A non-clustered index is like a book's index: sorted keys plus a pointer to where the row actually lives, requiring a second lookup to fetch the rest of the row. Terminology and behaviour differ between engines, and in PostgreSQL the CLUSTER command is a one-off reordering rather than a maintained property.

When an index helps, and when it is a liability

Four rules of thumb, in decreasing order of how often they are forgotten.

Needles, not haystacks. The more of the table a query returns, the less an index helps. Finding one row in a million is ideal; finding nine hundred thousand is worse than a sequential scan, and a good planner will ignore the index and scan anyway, leaving you with the maintenance cost and none of the benefit.

Reads benefit, writes pay. Every insert, update, and delete must maintain every index on the table. A stable table read constantly is an excellent candidate; a table under heavy write load with six indexes is a performance problem. When bulk loading a large volume into an indexed table, dropping the indexes, loading, and recreating them is often faster than maintaining them row by row.

AND is friendly, OR is not. Conjunctions narrow the result and compose well with a multi-column index. Disjunctions across different columns usually cannot use one index, and may require a scan or a union of index scans.

Cardinality matters. Indexing a boolean flag with an even split rarely helps, because either value matches half the table. Indexing it as a partial index over the rare value can help a great deal, which is why the defaulted-accounts index above is written that way.

Analytical engines mostly do not want your indexes Everything above is transactional-database advice. Columnar analytical engines take a different route: instead of a B-tree, they keep per-block minimum and maximum statistics, exactly the Parquet row group footer from Lecture 02, and skip blocks that cannot match. These are variously called zone maps or block statistics, they cost nothing to maintain because they are computed at write time, and they work well when the data is physically ordered by the filter column. So the analytical equivalent of index design is not creating indexes: it is deciding the sort order in which you write the data. DuckDB, Snowflake, and BigQuery all follow this model, and adding conventional indexes to an analytical table is usually the wrong instinct.

Reading the plan

Whether an index is being used is not a matter of opinion. Prefix a query with EXPLAIN to see the plan the engine chose, or EXPLAIN ANALYZE to execute it and see actual timings and row counts alongside the estimates.

EXPLAIN ANALYZE
SELECT account_id, balance
FROM   account_snapshots
WHERE  reporting_date = DATE '2026-03-31'
  AND  arrears_months >= 3;

Three things to look for. The access method: a sequential scan reads every row, an index scan does not, and seeing the former where you expected the latter means the index is missing, unusable, or judged unhelpful. The row counts: a large divergence between estimated and actual rows means the statistics are stale and the planner is choosing badly for that reason, so refresh them. And where the time actually goes, which in analytical queries is nearly always a join or an aggregation rather than the scan you were worrying about. Optimise from the plan, never from intuition.

Worked example: DDL for a monthly arrears snapshot, with the business rules made enforceable

The requirement: a monthly snapshot of a mortgage book supporting PD modelling and IFRS 9 staging. Write the DDL so that as many known facts as possible are enforced by the engine rather than trusted.

CREATE OR REPLACE TABLE account_snapshots (
    account_id           VARCHAR        NOT NULL,
    reporting_date       DATE           NOT NULL,
    customer_id          VARCHAR        NOT NULL,
    product              VARCHAR        NOT NULL,
    currency             VARCHAR(3)     NOT NULL,
    balance              DECIMAL(18, 2) NOT NULL,
    limit_amount         DECIMAL(18, 2),
    interest_rate        DECIMAL(9, 6)  NOT NULL,
    origination_date     DATE           NOT NULL,
    maturity_date        DATE           NOT NULL,
    arrears_months       INTEGER        NOT NULL,
    unlikely_to_pay      BOOLEAN        NOT NULL DEFAULT FALSE,
    forbearance_flag     BOOLEAN        NOT NULL DEFAULT FALSE,
    default_date         DATE,
    source_system        VARCHAR        NOT NULL,
    loaded_at            TIMESTAMP      NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (account_id, reporting_date),
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id),

    CHECK (arrears_months BETWEEN 0 AND 120),
    CHECK (interest_rate BETWEEN 0 AND 1),
    CHECK (currency = UPPER(currency)),
    CHECK (maturity_date > origination_date),
    CHECK (origination_date <= reporting_date),
    CHECK (reporting_date = LAST_DAY(reporting_date)),
    CHECK (default_date IS NULL OR default_date >= origination_date),
    CHECK ((arrears_months >= 3 OR unlikely_to_pay) = (default_date IS NOT NULL))
);

What each group of checks buys. The arrears bound catches a source system that starts sending days rather than months, which presents as arrears counts in the hundreds and would otherwise flow silently into a PD model as extreme values. The rate bound catches the perennial percentage-against-decimal confusion, where 4.29 arrives instead of 0.0429. The currency check catches casing drift. The date checks catch a whole family of extract errors: maturity before origination, accounts originated after the reporting date, and a reporting date that is not a month end, which is how a mid-month reprocessing run announces itself.

The last check is the important one. It asserts that the default flag and the default date agree: an account is in default exactly when it has ninety days of arrears or is judged unlikely to pay, and exactly then does it carry a default date. This is the regulatory default definition, written once, enforced on every row, and impossible for a downstream consumer to contradict. Without it, the PD team and the LGD team can and eventually will disagree about which accounts defaulted, and the disagreement will surface in validation rather than at load time.

What is deliberately not here. The primary key permits one row per account per month and nothing more, so a duplicated load fails rather than double counting. There is no ON DELETE CASCADE, because nothing in a risk history should be deletable as a side effect. And there is no index, because this is an analytical table that will be written monthly and scanned by date; the equivalent tuning is to write it partitioned and sorted by reporting_date, per Lecture 02.

The caveat. Verify what your engine enforces. Some analytical engines accept this DDL and enforce only some of it, in which case the unenforced assertions must be duplicated as tests in Lecture 16. That is a reason to write the tests, not a reason to omit the DDL.

Step 5

Synthesis and what's next

DDL is where meaning becomes enforceable. Types constrain the domain, constraints constrain the admissible values and the relationships between rows, and indexes change performance without changing answers. In a bank the highest-value use of DDL is encoding definitions that several teams must share, the default definition above being the canonical case, because a definition held in a constraint or a view cannot be quietly reinterpreted downstream. The analytical caveat runs through all of it: verify what your engine enforces, and remember that on columnar engines the sort order you write is worth more than any index you create.
