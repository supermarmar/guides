SQL II: querying

A query is a request to a librarian. You say it in one order and the librarian executes it in another: fetch the shelf, discard what does not qualify, sort into piles, discard whole piles, then compute the answer, then order it, then hand over the first ten. Almost every confusing SQL error dissolves once you know the order the librarian works in.

Lecture 5 of 20 Reading time, 60 minutes Part II: SQL and data modelling
Step 1

The 30-second version

Data query language is one statement, SELECT, surrounded by clauses that filter, group, combine, and order. It reads in one sequence and evaluates in another, and the gap between the two is the source of most beginner confusion and a fair amount of expert confusion too.

The written order is SELECT, FROM, JOIN, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. The logical evaluation order is FROM and JOIN first, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY, then LIMIT. Two consequences follow immediately and explain questions people ask for years. A column alias defined in SELECT cannot be used in WHERE, because WHERE ran first. And filtering on an aggregate needs HAVING rather than WHERE, because the aggregate does not exist until after grouping.

Beyond that skeleton, three capabilities carry most of the analytical weight: joins combine tables and are where quiet duplication enters; common table expressions make a long query readable by naming its steps; and window functions compute across related rows without collapsing them, which replaces whole categories of procedural loop.

Feynman test You hand a librarian a request: "the average balance by product for mortgages originated this year, only products with more than fifty accounts, best first, top ten". The librarian cannot start with the average. They go to the loan shelf (FROM), pull out the mortgages originated this year and put the rest back (WHERE), sort the remainder into piles by product (GROUP BY), push aside every pile with fifty or fewer (HAVING), compute one average per surviving pile (SELECT), arrange the averages (ORDER BY), and hand you ten (LIMIT). You spoke the sentence backwards. The librarian works forwards.
Why this matters more than it sounds The logical order is also the performance story. Anything you can push into WHERE shrinks the data before grouping and joining, which is the single largest lever in most queries. Filtering after the fact, in HAVING or in a wrapping query, means the engine did work it could have avoided. The optimiser will often rewrite your query to push filters down for you, and it can only do so when the filter is expressible against the raw rows. Writing the filter where it belongs is both clearer and faster.
Step 2

Why this matters

Joins duplicate silently. A join between a loan table and a collateral table where one loan has three charges registered against it returns three rows for that loan. Sum the balance and the exposure is overstated by two whole mortgages. Nothing errors, no null appears, and the total is merely wrong. This fan-out is the most common serious defect in analytical SQL, and the discipline that prevents it is knowing the cardinality of every join before you write it: one to one, one to many, or many to many, with the last always deserving suspicion.

Nulls do not behave like values. SQL uses three-valued logic: a comparison against null yields unknown, not false, and WHERE keeps only rows where the condition is true. So WHERE arrears_months != 0 silently drops every account whose arrears count is null, and WHERE x NOT IN (subquery) returns nothing at all if the subquery yields a single null. Both defects present as a row count that looks plausible.

Window functions turn loops into one statement. An arrears streak, a prior-month comparison, a twelve-month forward outcome, a rank within a segment, a deduplication keeping the latest record: each of these is a loop in procedural code and a single window expression in SQL. The practical effect for a risk analyst is that the construction of an observation dataset, which was once several hundred lines of scripted iteration, becomes a query that the engine parallelises. This is the highest-return material in the lecture.

The mental model

The joins, and the cardinality question

Before writing any join, answer one question: how many rows of the right table can match one row of the left? If the answer is "one", the row count cannot change. If it is "several", the left table's rows multiply and any subsequent sum is inflated unless you intended the multiplication. If it is "several on both sides", stop and reconsider, because a many-to-many join is almost always a missing intermediate table or a missing filter. Checking the row count before and after a join is a five-second habit that catches most of these.

Three-valued logic

Every comparison in SQL returns true, false, or unknown, and null comparisons return unknown. WHERE admits only true.

NULL = NULL        -- unknown, not true
NULL != 5          -- unknown, so the row is dropped
NULL IS NULL       -- true; this is the only way to test for null
5 IN (1, 2, NULL)  -- unknown, behaves as not matched
5 NOT IN (1, NULL) -- unknown, so NOT IN with any null returns nothing

COUNT(*)           -- counts rows
COUNT(column)      -- counts non-null values, which is often the real question
SUM(column)        -- ignores nulls; SUM of all nulls is NULL, not zero
AVG(column)        -- divides by the non-null count, not the row count

The AVG line deserves emphasis in a risk context. The mean of a column where forty per cent of values are null is the mean of the sixty per cent that are populated, which is rarely what a report intends when it says "average loan to value". Use COALESCE to make the treatment explicit, or count the nulls and state the population. Never let the engine's default choice stand in for a decision about missing data.

Step 4

The detail

Selecting, shaping, and conditional logic

SELECT DISTINCT product                          -- deduplicate the result
FROM   account_snapshots;

SELECT account_id           AS account,           -- aliases rename output
       balance / 100000     AS balance_hundred_k,
       CAST(arrears_months AS DOUBLE) AS arrears_num,
       arrears_months::VARCHAR        AS arrears_text,   -- shorthand cast
       surname || ', ' || forename    AS full_name       -- concatenation
FROM   account_snapshots;

SELECT account_id,
       CASE WHEN arrears_months = 0            THEN 'performing'
            WHEN arrears_months BETWEEN 1 AND 2 THEN 'early arrears'
            WHEN arrears_months >= 3            THEN 'defaulted'
            ELSE 'unknown'
       END AS credit_state
FROM   account_snapshots;

CASE is SQL's if-then, and it is worth writing carefully. Conditions are evaluated in order and the first match wins, so overlapping conditions are resolved by position rather than by specificity. Always supply an ELSE: without one, unmatched rows get null, and a null credit state propagates into a group by as its own silent category.

Dates, which is where most bugs live

SELECT reporting_date,
       DATE_TRUNC('month', reporting_date)                    AS month_start,
       DATE_TRUNC('quarter', reporting_date)                  AS quarter_start,
       EXTRACT(YEAR FROM reporting_date)                      AS year,
       DATE_PART('month', reporting_date)                     AS month_number,
       reporting_date - INTERVAL '12 months'                  AS one_year_earlier,
       LAST_DAY(reporting_date)                               AS month_end,
       DATE_DIFF('month', origination_date, reporting_date)   AS months_on_book
FROM   account_snapshots;

Two habits prevent most date defects. Write literals as unambiguous ISO strings with an explicit type, DATE '2026-03-31', never '31/03/2026'. And never compare a timestamp to a date with equality: WHERE ts = DATE '2026-03-31' matches only the instant at midnight, so use a half-open range, ts >= DATE '2026-03-31' AND ts < DATE '2026-04-01'. Half-open ranges also compose correctly when you chain months, with no risk of double counting a boundary.

Filtering

SELECT * FROM account_snapshots
WHERE  product IN ('mortgage', 'buy_to_let')      -- set membership
  AND  balance BETWEEN 50000 AND 500000            -- inclusive both ends
  AND  surname LIKE 'A%'                           -- % is any number of chars
  AND  sort_code LIKE '20-__-__'                   -- _ is exactly one char
  AND  default_date IS NULL                        -- the only null test
  AND  NOT (forbearance_flag AND arrears_months = 0);

LIKE is case-sensitive in some engines and not in others; ILIKE where available is the explicit case-insensitive form. Pattern matching beyond this belongs in a regular expression function, and the software engineering track covers the syntax.

Aggregating and filtering groups

SELECT product,
       COUNT(*)                                     AS accounts,
       COUNT(default_date)                          AS defaulted_accounts,
       SUM(balance)                                 AS total_exposure,
       AVG(arrears_months)                          AS mean_arrears,
       MEDIAN(balance)                              AS median_balance,
       SUM(CASE WHEN arrears_months >= 3 THEN balance ELSE 0 END) AS defaulted_exposure
FROM   account_snapshots
WHERE  reporting_date = DATE '2026-03-31'
GROUP BY product
HAVING COUNT(*) > 50
ORDER BY total_exposure DESC;

The conditional sum on the penultimate line is worth memorising. Putting a CASE inside an aggregate computes a subtotal for a subset without a second query or a second pass, and stacking several of them produces a small cross-tabulation in one statement. This is the SQL equivalent of the pivot in the data analysis track.

Combining tables: joins, unions, anti-joins

-- enrich a spine without losing rows
SELECT s.account_id, s.balance, c.segment, col.valuation
FROM       account_snapshots s
LEFT JOIN  customers  c   ON c.customer_id = s.customer_id
LEFT JOIN  collateral col ON col.account_id = s.account_id;

-- stack results: UNION deduplicates, UNION ALL does not and is faster
SELECT account_id FROM mortgages
UNION ALL
SELECT account_id FROM personal_loans;

-- anti-join: accounts with no collateral at all
SELECT s.account_id
FROM   account_snapshots s
WHERE  NOT EXISTS (SELECT 1 FROM collateral col
                   WHERE col.account_id = s.account_id);

Note the collateral join in the first query. If an account can have several charges, this query fans out and SUM(s.balance) over its result is wrong. The fix is to aggregate collateral to one row per account first, in a common table expression, and join that. Aggregate before joining whenever the right side is one-to-many; it is both correct and usually faster.

Prefer NOT EXISTS to NOT IN for anti-joins. It is immune to the null trap described earlier, and it can stop as soon as it finds one matching row rather than materialising the whole subquery result.

Common table expressions

WITH latest_collateral AS (
    SELECT account_id,
           SUM(valuation) AS total_valuation,
           COUNT(*)       AS charge_count
    FROM   collateral
    WHERE  valuation_date <= DATE '2026-03-31'
    GROUP BY account_id
),
book AS (
    SELECT *
    FROM   account_snapshots
    WHERE  reporting_date = DATE '2026-03-31'
)
SELECT b.product,
       COUNT(*)                                   AS accounts,
       SUM(b.balance)                             AS exposure,
       SUM(b.balance) / NULLIF(SUM(lc.total_valuation), 0) AS ltv
FROM   book b
LEFT JOIN latest_collateral lc USING (account_id)
GROUP BY b.product;

A common table expression, introduced by WITH, names a query so the rest of the statement can refer to it. Its value is readability: a long analytical query becomes a sequence of named steps that a reviewer can check one at a time, which matters enormously when the query encodes a regulatory definition somebody will audit. Note NULLIF in the final expression, which turns a zero denominator into a null rather than an error, and is the standard defence in any ratio.

Recursive common table expressions, written WITH RECURSIVE, walk a hierarchy: an ownership structure, a group of connected counterparties, a chain of refinanced accounts. They are the right tool when the depth of the traversal is not known in advance, and they are the SQL answer to the graph problem raised in Lecture 03.

Window functions

An aggregate collapses rows. A window function computes across a set of related rows and keeps every row, which is why it can add context to a record rather than replacing the record with a summary. The syntax is any function followed by OVER, and the OVER clause has three parts: PARTITION BY divides the rows into groups, ORDER BY sequences them within a group, and the frame specifies which rows around the current one participate.

SELECT account_id,
       reporting_date,
       balance,

       -- running total within an account, ordered in time
       SUM(balance) OVER (PARTITION BY account_id ORDER BY reporting_date)
           AS cumulative_balance,

       -- the previous and next month's arrears for the same account
       LAG(arrears_months)  OVER (PARTITION BY account_id ORDER BY reporting_date)
           AS arrears_prior_month,
       LEAD(arrears_months) OVER (PARTITION BY account_id ORDER BY reporting_date)
           AS arrears_next_month,

       -- twelve-month trailing mean, an explicit row frame
       AVG(balance) OVER (PARTITION BY account_id ORDER BY reporting_date
                          ROWS BETWEEN 11 PRECEDING AND CURRENT ROW)
           AS mean_balance_12m,

       -- first and last value across the whole partition
       FIRST_VALUE(balance) OVER (PARTITION BY account_id ORDER BY reporting_date
                                  ROWS BETWEEN UNBOUNDED PRECEDING
                                           AND UNBOUNDED FOLLOWING) AS opening_balance,

       -- ranking within a reporting date
       ROW_NUMBER() OVER (PARTITION BY reporting_date ORDER BY balance DESC) AS row_num,
       RANK()       OVER (PARTITION BY reporting_date ORDER BY balance DESC) AS rank_with_ties,
       DENSE_RANK() OVER (PARTITION BY reporting_date ORDER BY balance DESC) AS dense_rank,
       NTILE(10)    OVER (PARTITION BY reporting_date ORDER BY balance DESC) AS balance_decile
FROM   account_snapshots;

Four points that cause real defects.

The default frame is not what most people assume. When you supply ORDER BY inside OVER and no frame, the frame runs from the start of the partition to the current row, which is what makes the running total work. When you supply no ORDER BY at all, the frame is the whole partition, so the function behaves like an aggregate broadcast across every row. This is why LAST_VALUE without an explicit frame returns the current row rather than the last one, which surprises everybody exactly once.

ROWS and RANGE differ. ROWS counts physical rows; RANGE counts by value of the ordering column, so ties are included together. For monthly data with one row per account per month they coincide; for data with duplicate ordering values they do not, and ROWS is usually what you meant.

Ranking functions differ on ties. ROW_NUMBER is arbitrary but unique, RANK gives ties the same rank and leaves gaps, DENSE_RANK gives ties the same rank without gaps. For deduplication you want ROW_NUMBER with a deterministic tiebreaker in the ORDER BY, otherwise two runs of the same pipeline can keep different rows, and a non-reproducible pipeline is a validation finding.

Windows are computed after grouping and before ordering. You therefore cannot filter on a window result in WHERE or HAVING. Wrap the query, or use QUALIFY where the engine supports it, which DuckDB and Snowflake both do.

-- keep only the latest record per account: the deduplication idiom
SELECT *
FROM   account_snapshots
QUALIFY ROW_NUMBER() OVER (PARTITION BY account_id
                           ORDER BY reporting_date DESC, loaded_at DESC) = 1;
Introspecting the database The information_schema views are part of the SQL standard and let you query the database's own structure: information_schema.tables for what exists, .columns for types, nullability, and defaults, .key_column_usage for which columns participate in keys. This is how you check that the DDL you believe is in place actually is, and it is the mechanism behind automated schema documentation and schema drift detection. A pipeline that asserts its expected schema by querying information_schema before it runs catches a source change on the first day rather than the first quarter end.
Worked example: constructing a twelve-month PD observation dataset in one query

The requirement, familiar to anyone who has built a PD model: for each account and each monthly observation date, record the state of the account at that date and whether it defaulted within the following twelve months. Traditionally this is a script with nested loops. It is one query.

WITH monthly AS (
    -- one row per account per month end, deduplicated deterministically
    SELECT account_id,
           reporting_date,
           balance,
           arrears_months,
           default_date,
           product,
           DATE_DIFF('month', origination_date, reporting_date) AS months_on_book
    FROM   account_snapshots
    QUALIFY ROW_NUMBER() OVER (PARTITION BY account_id, reporting_date
                               ORDER BY loaded_at DESC) = 1
),
flagged AS (
    SELECT *,
           -- was the account already in default at the observation date?
           (arrears_months >= 3 OR default_date IS NOT NULL) AS in_default_now,

           -- arrears one and twelve months ago, for the behavioural features
           LAG(arrears_months, 1)  OVER w AS arrears_lag_1,
           LAG(arrears_months, 12) OVER w AS arrears_lag_12,

           -- the worst arrears position reached in the next 12 months
           MAX(arrears_months) OVER (PARTITION BY account_id
                                     ORDER BY reporting_date
                                     ROWS BETWEEN 1 FOLLOWING AND 12 FOLLOWING)
               AS max_arrears_next_12m,

           -- how many future months we actually observe, for censoring
           COUNT(*) OVER (PARTITION BY account_id
                          ORDER BY reporting_date
                          ROWS BETWEEN 1 FOLLOWING AND 12 FOLLOWING)
               AS months_observed_ahead
    FROM   monthly
    WINDOW w AS (PARTITION BY account_id ORDER BY reporting_date)
)
SELECT account_id,
       reporting_date                       AS observation_date,
       product,
       months_on_book,
       balance,
       arrears_months,
       arrears_lag_1,
       arrears_lag_12,
       CASE WHEN max_arrears_next_12m >= 3 THEN 1 ELSE 0 END AS default_flag_12m,
       months_observed_ahead
FROM   flagged
WHERE  NOT in_default_now                    -- performing at observation
  AND  months_observed_ahead = 12            -- full outcome window observed
ORDER BY account_id, observation_date;

What each piece is doing, and why it is the correct construction. The first expression deduplicates to one row per account-month with a deterministic tiebreaker, so two runs produce identical datasets. The LAG terms build behavioural features from the account's own past, which is legitimate because that information was available at the observation date. The forward MAX over the frame one to twelve months ahead is the outcome, and it deliberately excludes the current row, because a default at the observation date is a filter, not an outcome.

The two filters are the part that separates a correct dataset from a subtly wrong one. Excluding accounts already in default at observation is required by the definition of a PD: it is a probability of transitioning into default, conditional on being performing. Requiring twelve observed future months handles right-censoring: the final twelve months of your history cannot yet have a twelve-month outcome, and including them with a zero flag would understate the default rate by counting unresolved cases as good. Both mistakes are common, and both produce a model that validates well in development and underpredicts in production.

What the query does not do. It does not resolve the definition of default beyond arrears months, so unlikely-to-pay and forbearance treatment must be folded into the in_default_now and outcome expressions using the shared definition from Lecture 04, ideally by reading a view rather than restating the logic here. It also assumes a complete monthly spine per account; if months can be missing, cross join the account list against a calendar of month ends first, because LAG(arrears_months, 12) counts rows rather than months and silently reaches the wrong month when a row is absent. That distinction between row offset and time offset is the single most dangerous assumption in window-function code.

Step 5

Synthesis and what's next

Querying is one statement with a written order and a different logical order, and knowing the second explains the errors the first produces. Joins are the main source of quiet arithmetic damage, and the defence is knowing the cardinality before you write and checking the row count after. Nulls follow three-valued logic, which drops rows you did not intend to drop and breaks NOT IN outright. Common table expressions turn a long query into reviewable steps, which is what makes a regulatory definition auditable. Window functions are the highest-leverage feature in the language for risk work, because observation datasets, behavioural features, deduplication, and ranking are all one expression each.

Recall
  1. State the logical evaluation order of a SELECT and use it to explain why a SELECT alias works in ORDER BY but not in WHERE.
  2. You join loans to collateral and the total exposure rises by eighteen per cent. Explain what happened and give two fixes.
  3. Why does WHERE arrears_months != 0 drop accounts you probably wanted, and why does NOT IN with a nullable subquery return nothing?
  4. Distinguish COUNT(*), COUNT(column), and AVG(column) in the presence of nulls, and say which one a report on average loan to value should use.
  5. Give the default window frame when ORDER BY is present inside OVER, and when it is absent. Which behaviour surprises people about LAST_VALUE?
  6. Distinguish ROW_NUMBER, RANK, and DENSE_RANK, and say which you would use for deduplication and why the ORDER BY must be deterministic.
  7. In the PD observation query, why are accounts already in default excluded, and why is a full twelve-month forward window required? What does each mistake do to the estimated default rate?
  8. Why is LAG(x, 12) dangerous on a table with missing months, and what is the fix?
