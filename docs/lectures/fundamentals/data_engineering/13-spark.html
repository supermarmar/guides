Distributed processing with Spark

Ten million ballots and one counter takes forever, so you hire a hundred counters and give each a pile. Then someone asks for the result by constituency, and the hundred piles must be re-sorted and physically carried across the hall to the right counter. The counting was never the expensive part. The carrying is, and it has a name: the shuffle.

Lecture 13 of 20 Reading time, 55 minutes Part IV: transformation at scale
Step 1

The 30-second version

Apache Spark is a distributed engine for computing over data that does not fit, or does not fit comfortably, on one machine. A driver process plans the work and a set of executor processes on other machines do it, each on its own slice of the data. The unit of that slicing is a partition, and the number of partitions is the amount of parallelism available.

Two properties shape everything you write. Spark is lazy: transformations such as filter, select, and join build a plan and compute nothing, and only an action such as writing, counting, or collecting triggers execution. That laziness is what lets the optimiser rearrange your work, push filters down to the file reader, and fuse steps together. And transformations divide into narrow ones, where each output partition depends on one input partition and no data moves, and wide ones, where output partitions draw from many input partitions, which forces a shuffle: writing intermediate data to disk and moving it across the network.

Almost all Spark performance work is shuffle work. Group by, join, distinct, and window functions with a partition clause are the wide operations, and the craft consists of avoiding them, shrinking them, or fixing the cases where one partition is far larger than the rest.

Feynman test A hundred counters, each with a pile of ballots. "How many ballots in total?" is easy: each counter counts their own pile and you add up a hundred numbers. That is a narrow operation followed by a tiny combine. "How many for each constituency?" is different: ballots for one constituency are scattered across all hundred piles, so either everyone shouts partial tallies (which works, because addition is associative) or the ballots must be re-sorted and carried. Joining two different stacks of paper by voter name is the hard case: nothing can be matched until the two stacks are re-piled so that the same names are in the same hands. That re-piling is the shuffle, and it is why joins cost what they cost.
First, check that you need it Spark carries real overhead: a cluster to run and pay for, a JVM to configure, serialisation between Python and the executors, and a minimum job latency measured in seconds. Below roughly the scale of a few hundred gigabytes, and especially where the query prunes well, the single-node engine of Lecture 09 is usually faster in wall-clock terms and always faster to iterate on. Reach for Spark when the data genuinely does not fit after pruning, when a join between two very large tables needs distributed shuffling, or when you are already in a platform such as Databricks where it is the native execution engine. "We might grow into it" is not a reason.
Step 2

Why this matters

The three Vs still describe when distribution becomes necessary. Volume: more data than one machine's disk or memory can handle. Velocity: arrival faster than one machine can absorb. Variety: enough different shapes that a single schema and engine will not serve. In banking, volume arrives with transaction-level histories, card authorisations, and market data; portfolio-level monthly snapshots usually do not reach it. Being honest about which of the three you actually have is the difference between a cluster that earns its cost and one that exists because a diagram said so.

Skew turns a hundred machines into one. A job is only finished when its slowest task is finished. If you group payments by counterparty and one counterparty holds forty per cent of the rows, that partition's task runs alone for most of the job's duration while ninety-nine executors idle. Skew is endemic in financial data, because concentration is a real property of portfolios rather than an accident of loading, so it must be designed for rather than discovered.

Understanding the plan is the whole skill. Spark will run almost anything you write, and the difference between a query that takes four minutes and the same query taking four hours is usually one broadcast hint, one repartition, or one filter moved earlier. Since the engine tells you exactly what it did, in the query plan and the web interface, performance work here is diagnosis rather than guesswork, and a practitioner who reads plans will consistently outperform one who tunes configuration flags.

Step 3

The mental model

The layers, and why the DataFrame API won

Spark's original abstraction was the resilient distributed dataset: an immutable, partitioned collection with a recorded lineage of the operations that produced it, so a lost partition can be recomputed rather than replicated. Lineage is why the R in the name is resilient, and it remains the recovery mechanism underneath everything.

The problem with the low-level interface is that the engine cannot see inside your functions. A map containing arbitrary Python is opaque, so nothing can be optimised, reordered, or pushed down. DataFrames replaced it with a declarative interface over named, typed columns, which the Catalyst optimiser can analyse: it reorders filters, prunes columns, chooses join strategies, and generates efficient code. The practical rule is therefore unambiguous: express work in DataFrame operations or Spark SQL, and drop to the lower level only for the rare case they cannot express. The two are the same engine, so mixing SQL and DataFrame calls in one pipeline costs nothing.

Step 4

The detail

Session, reading, and the two equivalent interfaces

from pyspark.sql import SparkSession, functions as F

spark = (SparkSession.builder
         .appName("risk_monthly")
         .config("spark.sql.shuffle.partitions", 200)     # tune to data size, not left at default
         .config("spark.sql.adaptive.enabled", True)      # on by default in recent versions
         .getOrCreate())

snapshots = (spark.read
             .parquet("s3://lake/silver/loans/")          # partition columns are discovered
             .filter(F.col("reporting_date") >= "2025-01-31"))

# the same aggregation, two ways, one engine
by_product = (snapshots
              .groupBy("product")
              .agg(F.count("*").alias("accounts"),
                   F.sum("balance").alias("exposure"),
                   F.sum(F.when(F.col("arrears_months") >= 3, F.col("balance"))
                          .otherwise(0)).alias("defaulted_exposure")))

snapshots.createOrReplaceTempView("snapshots")
by_product_sql = spark.sql("""
    SELECT product,
           COUNT(*)  AS accounts,
           SUM(balance) AS exposure,
           SUM(CASE WHEN arrears_months >= 3 THEN balance ELSE 0 END) AS defaulted_exposure
    FROM   snapshots
    GROUP BY product
""")

Nothing has executed yet. Both objects are plans. An action, write, count, show, toPandas, triggers the whole chain, and the optimiser sees the filter, the projection, and the aggregation together, so it reads only the needed partitions and columns from Parquet, exactly as Lecture 02 described.

Joins: the one decision that matters most

# SHUFFLE HASH / SORT MERGE JOIN: both sides shuffled by key. Unavoidable when both are large.
result = payments.join(accounts, on="account_id", how="left")

# BROADCAST JOIN: ship the small side to every executor; no shuffle of the large side at all.
result = payments.join(F.broadcast(product_reference), on="product_code", how="left")

If one side of a join is small enough to fit in each executor's memory, a few tens of megabytes to a couple of hundred, broadcasting it eliminates the shuffle of the large side entirely. In banking this covers a large share of real joins, because reference data (products, currencies, branches, risk grades, mappings) is small and the fact tables are large. Spark broadcasts automatically when it can see that a side is small, which requires accurate statistics; the explicit hint is worth adding when it cannot, for instance when the small side is itself the result of an earlier computation whose size the planner has to guess.

The other join hazard is the fan-out of Lecture 05, at scale: joining to a table with duplicate keys multiplies rows across a distributed dataset, which turns a modest job into an enormous one and produces a wrong total. Deduplicate the right side first, and check the row count before and after; both are cheap compared with the alternative.

Partitions, repartitioning, and caching

Partition count is the parallelism. Too few and cores sit idle and individual tasks may spill or fail; too many and the scheduler overhead and tiny output files dominate, which is the small files problem from Lecture 02 arriving from the write side. A useful starting point is partitions sized in the low hundreds of megabytes each, with the shuffle partition count set accordingly rather than left at whatever the default happens to be.

df.repartition(400, "account_id")   # full shuffle, gives even distribution and co-locates by key
df.coalesce(20)                     # no shuffle, only merges existing partitions; use before writing
df.write.partitionBy("reporting_date").parquet(path)   # physical layout for downstream pruning

reused = expensive_transformation.cache()   # or .persist(StorageLevel...)
reused.count()                              # materialise it once
# ... several actions that read `reused` ...
reused.unpersist()

repartition shuffles and can increase or decrease the count evenly; coalesce only decreases and avoids the shuffle by merging neighbours, which makes it the right choice immediately before writing to avoid thousands of small files. Caching pays only when a dataset is genuinely read more than once by separate actions: because Spark is lazy, an uncached DataFrame referenced by three actions is computed three times, which is the most common source of surprise in Spark performance.

Skew, and what to do about it

Adaptive query execution, on by default in current versions, detects skewed shuffle partitions at runtime and splits them, which handles many cases without intervention. When it does not, three manual techniques apply. Salting adds a random suffix to the hot key so that it spreads across several partitions, aggregates partially, and combines in a second pass. Splitting processes the heavy keys as a separate job with a different strategy, often a broadcast, and unions the results. And pre-aggregation reduces the volume before the wide operation, which is the cheapest fix when it applies: if you are joining payments to accounts only to sum by account, aggregate the payments by account first, then join the much smaller result.

Python functions, and why they are slow

A row-at-a-time Python user-defined function forces every row to cross from the JVM to a Python process and back, serialised in both directions, and is invisible to the optimiser. Costs of an order of magnitude are normal. Three preferences, in order. Use built-in Spark functions, which are compiled and optimised, and they cover far more than people expect, including date arithmetic, regular expressions, JSON parsing, and window functions. Where you must write Python, use a pandas user-defined function, which passes Arrow batches rather than individual rows and recovers most of the loss. Only as a last resort use a plain Python function, and then measure it.

Reading the web interface Four numbers answer most performance questions. Task duration distribution within a stage: a long tail means skew. Shuffle read and write bytes: the size of the carrying, and the thing to reduce. Spill to disk and to memory: an indication that partitions are too large for the memory available, so increase the partition count rather than the cluster. And input size against the total dataset: if a query over sixty partitions reads all sixty when it should read three, pruning is not happening and the cause is usually a filter the optimiser cannot push down, such as one wrapped in a Python function or applied to a computed column.
Worked example: monthly exposure and default rates, joined to payments, at a scale that justifies a cluster

The data: sixty monthly snapshots of two million accounts (silver, Parquet, partitioned by reporting date), a payments table of 400 million rows, and a small product reference table of about two hundred rows. The task: monthly exposure and default rate by product, plus each account's payment count in the month. The payments table is what pushes this past a single machine.

from pyspark.sql import functions as F

snapshots = spark.read.parquet("s3://lake/silver/loans/") \
                 .filter(F.col("reporting_date") >= "2021-06-30") \
                 .select("account_id", "reporting_date", "product_code",
                         "balance", "arrears_months", "unlikely_to_pay")

# 1. pre-aggregate the large side BEFORE joining: 400m rows become ~120m
payments_monthly = (spark.read.parquet("s3://lake/silver/payments/")
                    .filter(F.col("value_date") >= "2021-06-01")
                    .withColumn("reporting_date", F.last_day("value_date"))
                    .groupBy("account_id", "reporting_date")
                    .agg(F.count("*").alias("payment_count"),
                         F.sum("amount").alias("payment_amount")))

# 2. broadcast the tiny reference table: no shuffle of the big side
enriched = (snapshots
            .join(F.broadcast(product_reference), on="product_code", how="left")
            .join(payments_monthly, on=["account_id", "reporting_date"], how="left"))

# 3. aggregate, computing the rate from summed numerator and denominator
monthly = (enriched
           .groupBy("reporting_date", "product_family")
           .agg(F.count("*").alias("accounts"),
                F.sum("balance").alias("exposure"),
                F.sum(F.when((F.col("arrears_months") >= 3) | F.col("unlikely_to_pay"), 1)
                       .otherwise(0)).alias("defaults"),
                F.sum(F.coalesce(F.col("payment_count"), F.lit(0))).alias("payments"))
           .withColumn("default_rate", F.col("defaults") / F.col("accounts")))

monthly.coalesce(1).write.mode("overwrite").parquet("s3://lake/gold/monthly_by_product/")

Why it is written in this order. Step one is the single largest saving: aggregating payments to the account-month grain before the join reduces the shuffled volume by roughly a factor of three and, more importantly, removes the fan-out risk entirely, since the aggregated side has exactly one row per key. Step two removes the second shuffle by broadcasting two hundred rows instead of redistributing tens of millions. Step three computes the rate from summed components rather than averaging rates, per Lecture 08. The final coalesce(1) is appropriate only because the output is a few thousand rows; applying it to a large output would serialise the write through one task.

What to verify in the interface. Confirm two shuffles at most, one for the payments aggregation and one for the final grouping, and none for the reference join. Confirm the snapshot read touched only the partitions from June 2021 onward. Check the task duration distribution in the payments aggregation: if a handful of tasks take many times the median, some accounts have pathologically many payments, and the fix is salting that key rather than enlarging the cluster.

The question to ask before running any of it. Would DuckDB do this? The snapshots alone, five columns of sixty partitions, are comfortably single-node. The payments table at 400 million rows is borderline: aggregated to account-month it is not, and a single large machine reading Parquet with pruning may well finish faster than a cluster starts. The honest answer is to measure both once, on a month of data, and let the numbers decide, because the wrong answer here costs either an unnecessary cluster or an unnecessary rewrite. What tips it towards Spark in practice is not the snapshot query but the payments pre-aggregation over the full history, and if that is run once and stored, the rest of the pipeline may not need a cluster at all.

Step 5

Synthesis and what's next

Spark distributes work across executors by partitioning data, builds a lazy plan that the Catalyst optimiser rearranges, and pays its costs at shuffle boundaries created by wide operations. Performance work is therefore shuffle work: pre-aggregate before joining, broadcast small sides, size partitions deliberately, cache only what is genuinely reused, and treat skew as an expected property of financial data rather than an anomaly. Use DataFrames and SQL rather than the low-level interface so the optimiser can see what you mean, and avoid row-wise Python. Before any of it, confirm the data justifies a cluster, because below a few hundred gigabytes the single-node engine of Lecture 09 usually wins.
