Lectures / Data analysis

DataFrames and the pandas core

Before you aggregate, model, or visualise anything, you load a rectangle into memory and characterise it. This lecture teaches the dataframe as a typed table, the four verbs you apply to it (load, inspect, select, transform), and the half-dozen pandas patterns that account for most of the analytical work a credit risk team does in a week. Master this layer and Polars, Spark, and SQL all feel like dialects of the same language.

Lecture 1 of 5 Reading time, 55 minutes Part I: the dataframe layer
Step 1

The 30-second version

A dataframe is a typed rectangle in memory: rows are observations, columns are variables, and every column carries a single dtype that determines which operations are legal on it. Pandas is the canonical Python library for working with this object. Almost every analytical task reduces to four verbs applied to that rectangle: load it from somewhere (CSV, Parquet, a SQL database), inspect it (shape, dtypes, head, describe), select the part you want (a column, a slice of rows, a filtered subset), and transform it (add columns, replace values, recast types). Everything else in the pandas API is a refinement of one of those four verbs.

The discipline this lecture trains is typing the rectangle correctly the first time. A column read as a string when it should be a date, a float read with thousand-separator commas as text, an integer code read as float because of a single missing value: each of these is a one-line mistake that propagates silently through every downstream analysis. Half the bugs in a junior analyst's notebook live in the first cell.

Feynman test Think of a dataframe as a spreadsheet with one extra rule: every column must hold values of the same kind. A salary column holds numbers, a country column holds strings, a default-date column holds dates. The rule lets pandas precompute how to add, group, sort, and join entire columns at once without checking each cell. Break the rule (mix strings and numbers in one column) and pandas falls back to a generic "object" dtype, which is slow, opaque, and the most common cause of "my pipeline was fast last week".
Where this sits in the data analysis world This lecture lives at the load and shape stage of the data analysis pipeline. Lecture 02 takes the same rectangle and folds it (groupby, pivot, join). Lecture 03 swaps pandas for Polars, the same vocabulary running on a faster engine. Lectures 04 and 05 leave shape behind and ask what the data says (exploratory analysis, visualisation). Without the layer this lecture teaches, none of the next four are reproducible.
Step 2

Why this matters

Three reasons to take the dataframe layer seriously despite its apparent simplicity. First, every model development document opens with df = pd.read_csv(...). The choice of dtype at load time determines what df.describe() reports, whether a join later in the pipeline matches the keys you expected, and whether a date filter does what you wrote or silently sorts strings lexicographically. A loan_id column read as integer and then joined to a customer table where loan_id was read as string returns an empty merge, and a junior analyst spends a morning before finding it.

Second, memory and speed are functions of dtype. A 32,000-row loan dataset costs roughly 3 MB if every column is the right dtype and 30 MB if everything is read as the generic object type. The factor of ten matters less on toy data and more on the 30-million-row portfolio extract that a real credit risk model is built on. Bad dtypes are the difference between an analysis that runs in a notebook and one that does not.

Third, pandas is the lingua franca of analytical Python. Scikit-learn, statsmodels, seaborn, ydata-profiling, even Polars itself all accept and return objects that look like pandas dataframes. The verbs in this lecture are the API surface that the rest of the data science stack assumes you have already mastered. Polars (Lecture 03) and SQL (the data engineering track) both reuse this vocabulary; learn it here once.

Step 3

The mental model

Hold the following picture in your head. A dataframe is a rectangle of n rows and p columns. The rows are observations (loans, customers, transactions, days, snapshots). The columns are variables, each with a name (a string label), a dtype (the kind of value it holds), and a possibly-missing value at each row. Two further structures sit alongside the rectangle: an index (the row labels, an integer range by default), and the columns object (an analogous list of column labels). Every pandas operation is parameterised on one or both of those axes.

The dtype taxonomy is short. Integer (int8 through int64, plus the nullable Int64 with a capital I) for counts and IDs. Float (float32, float64) for measured continuous quantities. Boolean (bool) for flags. Datetime (datetime64[ns]) for timestamps. Category for repeated string labels with a small fixed vocabulary (loan grade, employment status). Object for arbitrary Python objects, almost always strings, and the fallback that pandas uses when it cannot infer anything more specific. Memory follows directly: an int8 column is eight times smaller than an int64 column, a categorical column is one byte per row plus a dictionary, an object column is a pointer per row plus the strings themselves. Speed follows for the same reason: the narrower the dtype, the more values per cache line, the faster the operation.

Step 4

The detail

NumPy underneath: arrays before dataframes

Pandas is built on NumPy. A pandas Series is, conceptually, a NumPy array with a label per element (the index) and a name. A DataFrame is a dictionary of Series sharing one index. Three NumPy ideas leak through pandas and are worth knowing directly.

First, vectorisation. NumPy operations apply elementwise to arrays without a Python-level loop, and run in compiled C. The performance gap between a vectorised operation and an explicit Python loop is typically two orders of magnitude. The first principle of analytical Python is: write the operation on the whole column, not on each row.

Second, broadcasting. When two arrays have compatible shapes, NumPy applies an operation pair-wise without you having to reshape them manually. df["loan_amount"] * 1.05 multiplies every value by the scalar; df["loan_amount"] - df["loan_amount"].mean() subtracts the scalar mean from every value; df[["a", "b"]] - df[["a", "b"]].mean() subtracts a per-column mean from each column. The rules are mechanical and worth reading once in the NumPy documentation; in practice, "scalar broadcasts everywhere" covers 80 per cent of cases.

Third, missing values. NumPy floats represent missingness with NaN (not-a-number), the IEEE 754 sentinel. Pandas extends this to other dtypes via the nullable extensions (Int64, boolean, string), which use a separate bitmask to mark missing entries and preserve the underlying dtype. The classic pandas trap is that any column with a single missing integer becomes a float column if you use the legacy int64 dtype; the cure is to use the nullable Int64 explicitly.

Loading data: read_csv done properly

The single most important pandas function is pd.read_csv. Used naively it accepts a path and returns a dataframe; used properly it parameterises five things you should specify, not let pandas guess.

Loading a credit risk CSV with dtypes specified

import pandas as pd df = pd.read_csv( "data/credit_risk_dataset.csv", dtype={ "person_age": "Int16", "person_income": "Int64", "person_emp_length": "float32", "person_home_ownership": "category", "loan_intent": "category", "loan_grade": "category", "loan_amnt": "Int32", "loan_int_rate": "float32", "loan_status": "Int8", "loan_percent_income": "float32", "cb_person_default_on_file": "category", "cb_person_cred_hist_length": "Int8", }, parse_dates=["issue_date"], date_format="%Y-%m-%d", na_values=["", "NA", "null", "n/a"], thousands=",", )

Five parameters earn their keep on every real-world load. dtype fixes column types up front and cuts memory by a factor of four to ten on a typical credit dataset. parse_dates converts date columns at read time rather than as a follow-up call; date_format tells pandas the exact pattern (much faster than letting it infer). na_values declares what counts as missing in this file beyond the defaults (NA, NaN, an empty cell). thousands handles the comma-separated numbers that come out of Excel.

The same function family covers other file formats. pd.read_parquet for columnar files (which already carry dtype information and need none of the parameters above), pd.read_sql for database extracts via SQLAlchemy, pd.read_excel for spreadsheets, pd.read_json for nested records. Parquet is the default for any dataset that lives longer than a week; CSV is for interchange with non-Python consumers and is otherwise lossy (no dtypes, no compression, no schema).

Common error Letting pandas infer dtypes on a large file ("just call read_csv with the path"). On a 30-million-row loan extract this is the difference between a 4 GB and a 28 GB dataframe and the difference between an analysis that fits in RAM and one that swaps. Even on small files, inferred dtypes lose information: a customer ID like "000123" becomes an integer 123, a date column becomes object, a category column becomes object and consumes ten times the memory.

Inspection: the five calls you make on every new dataframe

The first five lines of every analysis are the same. They confirm that the load did what you intended.

The standard inspection block

df.shape # (32_581, 12): rows, columns df.dtypes # column → dtype mapping df.head(10) # first ten rows; .tail() for last ten df.info() # dtypes + non-null counts + memory usage df.describe(include="all") # summary stats per column

shape tells you the rectangle dimensions; deviate from the expected number of rows and the load went wrong. dtypes confirms every column landed at the type you specified. head and tail show the first and last few rows for a visual sanity check (look for misaligned columns, header rows that became data, trailing summary rows). info combines dtype, non-null count (the inverse of missingness), and memory footprint in one display. describe gives count, mean, std, min, max, and quartiles for numeric columns; with include="all" it also gives count, unique, top, and freq for categorical columns.

The output of these five calls should match your prior expectations. The number of rows should match the source system's record count. Every non-null count in info should equal the row count except for columns you expect to be missing (an employment length field is typically 1-3 per cent missing). Every dtype should be the one you specified. Every numerical column's describe output should pass a sanity check: ages between 18 and 100, loan amounts positive and below the policy maximum, interest rates between 0 and 100. A single failed check here is cheaper to chase down than the same failure surfacing as a strange aggregation three steps later.

Selection: columns, rows, and the loc/iloc distinction

Three idioms cover almost all column and row selection. Square brackets on a column name return that column as a Series; with a list of names, they return a DataFrame restricted to those columns:

Column selection

df["loan_amnt"] # Series of loan amounts df[["loan_amnt", "loan_grade"]] # DataFrame with two columns df.loan_amnt # attribute access; same as df["loan_amnt"]

The attribute form works only when the column name is a valid Python identifier and is not a method on the dataframe. Square brackets work always. Prefer the bracket form in production code; reserve the attribute form for interactive exploration.

For rows, the two operators to know are .loc and .iloc. .loc selects by label; .iloc selects by integer position. They look similar and behave differently in three ways: the input type, whether the right-hand endpoint is inclusive, and the result type when you pass a scalar.

.loc vs .iloc

df.loc[0] # row with index label 0 (a Series) df.loc[0:5] # rows with labels 0 through 5 INCLUSIVE df.loc[0:5, ["loan_amnt"]] # rows 0-5, only the loan_amnt column df.loc[df["default"] == 1] # rows where default is True (boolean mask) df.iloc[0] # row at integer position 0 df.iloc[0:5] # rows at positions 0-4 EXCLUSIVE of 5 df.iloc[0:5, [3, 4]] # rows 0-4, columns at positions 3 and 4 df.iloc[-1] # last row

The inclusive-vs-exclusive endpoint is the trap. df.loc[0:5] returns six rows; df.iloc[0:5] returns five. The same difference applies to columns when you pass a slice. A working memory aid: .loc is for labels (which need not be integers, and an inclusive endpoint makes sense), .iloc is for positions (which are always integers, and Python slice semantics are exclusive).

What's beyond the syllabus The .at and .iat accessors are the scalar versions of .loc and .iloc and are roughly an order of magnitude faster for single-cell access. Most analytical code never needs them; if you find yourself writing a loop that pulls one cell at a time, the loop is usually the bug. Use .at/.iat in two cases: stress-testing a pipeline with row-by-row debug prints, or interfacing with code (a callback, a custom aggregator) that genuinely needs scalar access.

Filtering: boolean masks, query, and the convenience methods

Filtering rows is the operation you do most often. Three idioms cover almost everything: boolean masks, the .query method, and a handful of named convenience methods (.isin, .between, the string accessor).

A boolean mask is a Series of True/False the same length as the dataframe; passing it to .loc or inside square brackets returns the rows where the mask is true. Masks compose with & (and), | (or), and ~ (not), each operand wrapped in parentheses because of Python's operator precedence.

Boolean-mask filtering

defaulted = df.loc[df["loan_status"] == 1] high_grade_recent = df.loc[ (df["loan_grade"].isin(["A", "B"])) & (df["issue_date"] >= "2022-01-01") & (df["loan_amnt"].between(5_000, 50_000)) ] non_homeowners = df.loc[df["person_home_ownership"] != "OWN"] not_missing_employment = df.loc[df["person_emp_length"].notna()]

.isin tests membership in a list and replaces a chain of == comparisons joined with |. .between tests a closed numeric interval and replaces two-sided inequalities. .notna tests for non-missingness; the inverse .isna tests for missingness.

The .query method takes a string expression and is often clearer for multi-condition filters:

Query-based filtering

high_grade_recent = df.query( "loan_grade in ['A', 'B'] " "and issue_date >= '2022-01-01' " "and 5_000 <= loan_amnt <= 50_000" )

The advantages: no parentheses, no repeated dataframe name, chained comparisons (5_000 <= x <= 50_000) work as in mathematical notation. The cost: a string expression that linters cannot check until runtime, and a small parsing overhead. Prefer .query for three or more conditions; prefer boolean masks for one or two conditions or where you need to build the mask programmatically.

For string columns, the .str accessor exposes the regular Python string methods plus regex patterns:

String filtering

df.loc[df["loan_intent"].str.startswith("MED")] df.loc[df["person_home_ownership"].str.lower() == "rent"] df.loc[df["loan_intent"].str.contains(r"PERSONAL|MEDICAL", regex=True)] df.loc[df["loan_intent"].str.match(r"^[A-Z]{4,}$")] # only uppercase, 4+ chars

Every .str method propagates missing values as missing (it does not raise). For categorical columns the same operations work via .str but should usually be done by comparing against the categories list directly, which is faster.

Adding and transforming columns

Four patterns cover essentially all column construction. Each starts from one or more existing columns and produces a new one.

The direct assignment pattern is the simplest: arithmetic on Series broadcasts, and you assign the result to a new column name:

Direct assignment

df["interest_payment"] = df["loan_amnt"] * df["loan_int_rate"] / 100 df["log_income"] = np.log1p(df["person_income"]) df["loan_to_income"] = df["loan_amnt"] / df["person_income"] df["loan_age_days"] = (pd.Timestamp.today() - df["issue_date"]).dt.days

The .dt accessor on a datetime Series exposes date components (.dt.year, .dt.month, .dt.day_name(), .dt.days on a timedelta). It is the datetime equivalent of .str for strings.

The .assign method is the same idea but immutable and chainable. It does not modify df in place; it returns a new dataframe with the additional columns:

Chained assignment

enriched = ( df .assign( interest_payment=lambda d: d["loan_amnt"] * d["loan_int_rate"] / 100, log_income=lambda d: np.log1p(d["person_income"]), loan_to_income=lambda d: d["loan_amnt"] / d["person_income"], ) .query("loan_to_income < 1") )

The lambda form lets a new column reference a column produced earlier in the same chain. The chained style scales much better than a sequence of in-place assignments: there is one variable name (enriched), one pipeline you can read top-to-bottom, and no question about which line ran in which order.

For conditional logic, use np.where for a single condition and np.select for multiple:

Conditional columns

import numpy as np # binary condition df["large_loan"] = np.where(df["loan_amnt"] > 25_000, 1, 0) # multi-way condition conditions = [ df["loan_amnt"] < 5_000, df["loan_amnt"] < 15_000, df["loan_amnt"] < 30_000, ] choices = ["small", "medium", "large"] df["loan_size_bucket"] = np.select(conditions, choices, default="jumbo")

np.select evaluates the conditions in order and picks the first matching choice; rows matching none get the default. It replaces a tower of nested np.where calls or an if/elif chain inside an apply.

For everything else, .apply with a lambda or a named function applies row-wise or column-wise logic. It is the most general tool and the slowest:

Apply: the escape hatch

# row-wise apply: f is called once per row, receives a Series df["risk_score"] = df.apply( lambda row: row["loan_amnt"] * 0.001 + (10 if row["loan_grade"] == "G" else 0), axis=1, ) # column-wise apply: f is called once per column, receives a Series df.select_dtypes("number").apply(lambda s: (s - s.mean()) / s.std())

The same row-wise example written with vectorised arithmetic and np.where runs roughly fifty times faster on a million-row dataframe:

df["risk_score"] = ( df["loan_amnt"] * 0.001 + np.where(df["loan_grade"] == "G", 10, 0) )

When apply is the wrong tool Reach for apply only when no vectorised expression exists, the loop is genuinely irreducible (a recursive feature, a third-party non-vectorised function), or the dataset is small enough that the speed difference is invisible. Most uses of apply in junior code can be rewritten as vectorised arithmetic, np.where/np.select, or a string accessor; doing so is the single largest performance win available to a pandas pipeline.

Renaming, resetting, and a note on the index

Two housekeeping operations close out the core. Renaming columns uses a dictionary mapping; you can rename only the columns you want and leave the rest untouched:

Renaming

df = df.rename(columns={ "loan_amnt": "loan_amount", "person_emp_length": "employment_years", "cb_person_default_on_file": "prior_default_flag", })

For a bulk rewrite (snake_case for everything, lowercasing, stripping whitespace), apply a function via the columns attribute:

df.columns = df.columns.str.lower().str.replace(" ", "_")

The index is the row-label structure. Three operations cover it: set_index promotes a column to be the index, reset_index moves the index back to a column and reverts to the default integer range, and sort_index sorts rows by their index. The default integer index is rarely useful; setting a meaningful index (loan_id, issue_date) before joins and time-series operations is the cleanest pattern.

Index management

df = df.set_index("loan_id") # loan_id becomes the row label df.loc["L0007"] # look up a loan by ID df = df.reset_index() # loan_id becomes a column again df = df.set_index("issue_date").sort_index() # date-indexed and ordered

A datetime index unlocks the time-series methods (.resample, .rolling, partial-string slicing like df.loc["2022":"2023"]), covered in Lecture 02.

Step 5

Worked example: from raw file to typed dataframe

The credit risk dataset referenced throughout this lecture is a publicly available file of 32,581 loan applications with 12 columns (demographics, loan terms, performance flag, prior-default flag). A complete first-pass treatment of the file fits in three blocks: load it correctly, confirm the shape, and derive the first few analytical columns.

Block 1, load with explicit dtypes

import pandas as pd import numpy as np df = pd.read_csv( "data/credit_risk_dataset.csv", dtype={ "person_age": "Int16", "person_income": "Int64", "person_emp_length": "float32", "person_home_ownership": "category", "loan_intent": "category", "loan_grade": "category", "loan_amnt": "Int32", "loan_int_rate": "float32", "loan_status": "Int8", "loan_percent_income": "float32", "cb_person_default_on_file": "category", "cb_person_cred_hist_length": "Int8", }, na_values=["", "NA", "null"], )

The cost of being explicit here is a dozen lines; the benefit is a dataframe ten times smaller than the default load, with every column at a type that supports the right operations (a category for loan_grade preserves the rating order if you want it, an Int8 for loan_status takes one byte not eight).

Block 2, inspect and sanity-check

print(df.shape) # (32581, 12) print(df.dtypes) print(df.info(memory_usage="deep")) df.describe(include="all").T

The memory_usage="deep" argument follows pointers into object columns so the reported footprint is accurate. The transposed describe (one column per statistic, one row per variable) is much easier to scan than the default orientation. Read down the count column: any value below 32,581 means missing entries in that column. The person_emp_length column has roughly 900 missing entries, and the loan_int_rate column has roughly 3,000; both will need a treatment decision in the EDA lecture.

Block 3, derive analytical columns and filter

analysis = ( df .assign( loan_to_income=lambda d: d["loan_amnt"] / d["person_income"], annual_interest=lambda d: d["loan_amnt"] * d["loan_int_rate"] / 100, is_homeowner=lambda d: d["person_home_ownership"].isin(["OWN", "MORTGAGE"]), amount_bucket=lambda d: pd.cut( d["loan_amnt"], bins=[0, 5_000, 15_000, 30_000, np.inf], labels=["small", "medium", "large", "jumbo"], ), ) .query("person_age >= 18 and person_age <= 100") # drop obvious data errors .query("loan_to_income < 1") # drop loans > income ) print(analysis.shape) # (~31_500, 16) print(analysis.head())

Three derived features (loan-to-income, annual interest, homeowner flag), one binned column (pd.cut for fixed-edge bins; use pd.qcut for equal-count bins), and two filters that drop obvious data errors. The pipeline reads top-to-bottom, every transformation is in one expression, and the input df is unchanged. This is the shape every analytical pipeline in pandas should take.

What you have now: a typed, sanity-checked, lightly-feature-engineered dataframe of about 31,500 loans ready for the aggregation work of Lecture 02 and the EDA of Lecture 04. The single most important property of the result is reproducibility: if a colleague reruns the three blocks against the same source file, they get the same dataframe down to the byte. Bad dtype handling at the load stage destroys this property silently.

Step 6

Common pitfalls and how to avoid them

SettingWithCopyWarning

The warning every pandas user sees first and understands last. It triggers when you assign to a slice that pandas cannot determine is a view or a copy; the assignment may or may not propagate to the original dataframe, and the answer depends on internal implementation details you should not depend on. The cure is to avoid chained indexing entirely. Replace df[df["x"] > 0]["y"] = 1 (two indexing operations, ambiguous) with df.loc[df["x"] > 0, "y"] = 1 (one operation via .loc, unambiguous). The warning is one of pandas's better diagnostic messages; read the URL it prints and use .loc for any combined row-and-column assignment.

Integer columns silently becoming floats

The classical NumPy integer dtype has no missing-value sentinel; a single NaN forces the entire column to float64. The fix is to use pandas's nullable integer dtype, written with a capital I (Int64, Int32, Int16, Int8). It carries a separate bitmask for missing entries and preserves the integer type. Specify it at read_csv time and the column survives missing values untouched.

Comparing strings to numbers and getting silent surprises

A column read as object (typically string) compared to a numeric literal returns False for every row, with no error. The filter quietly returns an empty dataframe. The fix is to look at the dtypes output before writing the filter and convert with pd.to_numeric(col, errors="coerce") if the column should be numeric. The errors="coerce" arg turns un-parseable values into NaN rather than raising; this is what you want for diagnostic conversion of a dirty CSV, and not what you want in a production pipeline (where the NaNs become silent missing data).

Forgetting that boolean operators are bitwise on Series

Python's and and or are short-circuit operators on scalars; they raise a ValueError on Series ("The truth value of a Series is ambiguous"). Pandas uses & and | for elementwise logic on Series, and both operands must be wrapped in parentheses because & has higher precedence than <, >, and ==. The two related errors are forgetting the parentheses (which produces an unrelated, confusing exception about ambiguity) and using and/or by reflex from base Python.

Chained inplace operations

Many pandas methods accept an inplace=True argument that mutates the dataframe and returns None. The argument is seductively named and almost always the wrong choice: it does not save memory in modern pandas, it breaks method chaining (the return value is None, not a dataframe), and it makes diffs harder to read. The pandas core team has signalled that inplace is on the path to deprecation. Default to the non-inplace form (df = df.dropna()) for every method.

A subtler trap df["new_column"] = some_series aligns some_series to df's index before assignment. If the two indexes are different (one is the default integer range, the other was produced by a groupby that re-indexed), most rows in the new column will be missing and you may not notice. The cure is to either reset both indexes to a known common state before assignment, or to assign with .values (which strips the index) when you are confident the order matches. The latter is usually a bug waiting to happen; prefer the former.
Step 7

Synthesis and what's next

You now have the dataframe layer. A dataframe is a typed rectangle: rows are observations, columns carry dtypes, and dtype choice is the single largest determinant of correctness, memory, and speed. The four verbs cover almost all analytical work: load with explicit dtypes and date parsing; inspect with shape, dtypes, info, head, and describe; select with column names plus .loc/.iloc; transform with direct arithmetic, .assign chains, np.where/np.select, and (sparingly) .apply. The five pitfalls (chained indexing, integer-to-float demotion, string-numeric comparisons, bitwise operators, inplace) are the silent ways the layer goes wrong.

Three things are missing from this lecture and are taken up in the next. The folding operations — aggregating a column to one number, pivoting long to wide, and joining two tables — are Lecture 02. The same vocabulary on a faster engine (Polars) is Lecture 03. The discipline of looking at the data (missing-value diagnosis, outlier review, distributional checks) is Lecture 04. Visualisation is Lecture 05. The dataframe-as-typed-rectangle picture from this lecture is the prerequisite for all four.
