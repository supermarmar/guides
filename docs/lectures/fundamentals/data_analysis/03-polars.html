Polars and the modern dataframe stack

Polars is what pandas would be if it were designed today. It runs the same analytical vocabulary (load, select, filter, group, join) on an Arrow-backed engine that is faster, parallel by default, and lazy when you want it to be. The eighty per cent that looks like pandas you already know; the twenty per cent that differs (filter instead of boolean masks, with_columns instead of assignment, expressions instead of lambdas) is exactly where pandas habits become liabilities. This lecture is the translation guide and the case for when to switch.

Lecture 3 of 5 Reading time, 45 minutes Part I: the dataframe layer
Step 1

The 30-second version

Polars is a dataframe library, written in Rust, with a Python interface. Compared to pandas it has three differences that matter analytically. First, it stores data in Apache Arrow columnar format, which is faster to compute on and shares zero-copy with the rest of the modern data stack (DuckDB, parquet, Spark connectors). Second, it executes operations in parallel by default, using every core on your machine. Third, it has a lazy mode: you write a chain of operations against a plan, the planner optimises the plan (predicate pushdown, projection pushdown, common-subexpression elimination), and the work runs only when you ask for the result. On a typical 30-million-row credit-risk extract, Polars is five to twenty times faster than pandas and uses a fraction of the memory.

The discipline this lecture trains is thinking in expressions, not lambdas. Polars wants you to describe what should happen to a column (pl.col("loan_amnt") * 1.05) and let the engine schedule the work. Lambdas and Python-level row loops force the engine to fall back to single-threaded interpretation, and the order-of-magnitude advantage evaporates. Most of what looks like a Polars-specific quirk is actually the engine telling you to express the work in its terms.

Feynman test Pandas treats each operation as something to execute immediately on a dataframe in memory. Polars treats each operation as a request you append to a plan; the engine reorders and parallelises the plan before running anything. The advantage is the same one a query planner gives a database: it can skip work that does not contribute to the final answer.
Where this sits This lecture is the bridge between the pandas vocabulary of Lectures 01-02 and the larger-than-memory tools (DuckDB, Spark) covered in the data engineering track. Polars is the right step up when pandas hits its single-machine ceiling (typically 107-108 rows depending on the operations) and the right peer for DuckDB when SQL is not the natural expression. It is not a replacement for pandas in every project; the synthesis section below covers when each is preferred.
Step 2

Why this matters

Pandas was designed in 2008 against the constraints of the time: a single core, NumPy as the only fast numerical backend, Python's reference counting as the memory model. The library is brilliant and irreplaceable, but the design assumptions show. Operations are eager (every line of a chain materialises a full dataframe in memory). Strings, missing values, and dates are awkwardly shoe-horned onto a NumPy substrate that was not designed for them. Parallelism is bolted on rather than built in. None of this is a flaw in pandas; it is a constraint of when pandas was built.

Arrow, Rust, and the broader modern dataframe stack (Polars, DuckDB, Dask, Spark with Arrow interop) are the consequence of fifteen years of hardware change. Cores multiplied; SIMD instructions expanded; SSD bandwidth grew faster than CPU. The libraries that scale today share three properties: columnar storage (one dtype per column, contiguous in memory, suited to vectorised CPU operations), query planning (an intermediate representation the engine can optimise before running), and zero-copy interop (Arrow as a shared memory format so data does not need to be serialised between tools). Polars is the most pandas-shaped instance of this stack.

For credit risk work the practical effect is twofold. First, analyses that were borderline-infeasible in pandas become routine in Polars: the full 50-million-row IFRS 9 staging dataset, the 200-million-row counterparty exposure aggregate, the EAD profile of every loan over its remaining life. Second, the same analyses that already worked in pandas become faster enough that the iteration loop changes character: a five-second pandas chain that took ten minutes after the first dozen iterations runs in a second in Polars and supports a faster, more exploratory style of work.

Step 3

The mental model

Two pictures. The first is the memory layout: pandas stores data row-by-row in places it has historically been awkward (a block manager that often produces row-wise objects internally), while Polars stores data column-by-column in Arrow buffers that are contiguous in memory and tagged with a dtype. The columnar layout is what makes vectorised CPU operations efficient: a sum over a column reads one contiguous buffer and produces one result with no pointer chasing.

The second picture is eager vs lazy execution. In pandas every line of a chain runs immediately and produces a full intermediate dataframe in memory. In Polars you can switch to a lazy frame (pl.scan_csv, or .lazy() on an existing eager frame) and the chain builds an unexecuted query plan. When you call .collect(), the planner reorders and prunes the plan before running it.

Step 4

The detail

Construction and inspection

Polars uses the same four verbs as pandas, with different spellings. pl.read_csv and pl.read_parquet are the eager readers. pl.scan_csv and pl.scan_parquet are the lazy equivalents, which return a LazyFrame and defer reading until .collect(). The dtype argument works as in pandas, with Polars's own dtype names (pl.Int64, pl.Float32, pl.Categorical, pl.Datetime).

Loading and inspecting

import polars as pl df = pl.read_csv( "data/credit_risk_dataset.csv", schema_overrides={ "person_age": pl.Int16, "loan_grade": pl.Categorical, "loan_status": pl.Int8, }, try_parse_dates=True, ) df.shape # (32_581, 12) df.schema # column name → dtype mapping df.head(10) df.glimpse() # one row per column, like dplyr's glimpse() df.describe() # summary stats

schema_overrides is the equivalent of pandas's dtype=; try_parse_dates=True tells Polars to infer date columns from string patterns. glimpse is the most useful inspection method and has no pandas equivalent: one row per column, showing the dtype, a few example values, and the count of non-nulls.

Selection and filtering: the expression API

Selection in Polars is done through .select and .filter, each of which takes expressions built with pl.col("name"). The expression is the central abstraction: it describes what to do to a column, the engine schedules the work, and the same expression appears verbatim in .select, .with_columns, .filter, and inside .group_by(...).agg(...).

Filter and select

# filter rows where the loan amount is above 25k and the grade is A or B high_grade_large = df.filter( (pl.col("loan_amnt") > 25_000) & (pl.col("loan_grade").is_in(["A", "B"])) ) # select specific columns; rename in the same call small_view = df.select( pl.col("loan_amnt"), pl.col("loan_grade").alias("grade"), pl.col("loan_status").cast(pl.Boolean).alias("default_flag"), )

The expression pl.col("loan_amnt") > 25_000 is a boolean Series, the same as in pandas. The expression pl.col("loan_grade").is_in([...]) is the equivalent of pandas's .isin. The expression pl.col("x").alias("y") renames in flight, without a separate .rename call. Expressions can be nested arbitrarily and chained with &, |, ~, exactly as pandas.

The key syntactic difference from pandas is that Polars does not use boolean indexing with square brackets. Where pandas writes df[df["x"] > 0], Polars writes df.filter(pl.col("x") > 0). The pandas form is more compact; the Polars form is more explicit, and it composes with .select, .with_columns, and the lazy planner without special-casing.

Adding columns: with_columns and when/then/otherwise

Polars adds and modifies columns with .with_columns, which takes one or more expressions and returns a new dataframe. Direct attribute assignment (df["new"] = ...) is not supported; the immutable, expression-based API is the only path.

Adding columns with expressions

enriched = df.with_columns( interest_payment=(pl.col("loan_amnt") * pl.col("loan_int_rate") / 100), log_income=pl.col("person_income").log1p(), loan_to_income=(pl.col("loan_amnt") / pl.col("person_income")), large_loan=(pl.col("loan_amnt") > 25_000), )

Every keyword becomes a new column. Within an expression, mathematical operators are overloaded as in pandas, but the method chain on a single column (.log1p(), .floor(), .cast()) is the natural way to apply functions. The pandas equivalent of pl.col("x").log1p() is np.log1p(df["x"]); the Polars version is shorter, has no NumPy dependency, and runs inside the query planner.

For conditional logic Polars uses pl.when(...).then(...).otherwise(...), which replaces both np.where and np.select:

Conditional columns: when/then/otherwise

# single condition df = df.with_columns( large_loan=pl.when(pl.col("loan_amnt") > 25_000).then(1).otherwise(0), ) # multi-way condition: chain when().then() ... .when().then() ... .otherwise(...) df = df.with_columns( loan_size_bucket=( pl.when(pl.col("loan_amnt") < 5_000).then(pl.lit("small")) .when(pl.col("loan_amnt") < 15_000).then(pl.lit("medium")) .when(pl.col("loan_amnt") < 30_000).then(pl.lit("large")) .otherwise(pl.lit("jumbo")) ), )

The chain reads as a series of if/elif/else branches. The literal-value wrapper pl.lit is occasionally needed when Polars cannot infer that a Python value is meant as a column-wise constant; in most cases it can be omitted.

The apply trap, again Polars has .map_elements (formerly .apply), which calls a Python function once per row. Like pandas's .apply, it is one to two orders of magnitude slower than an expression and forces Polars to drop to single-threaded interpretation. The whole point of Polars is to avoid this fallback. Every reach for map_elements is a reason to ask whether the operation can be re-expressed with pl.when/then/otherwise, a built-in method on pl.col, or a join. The right answer is usually yes.

Groupby and aggregations

Polars uses .group_by (with the underscore; the legacy .groupby is deprecated) and an .agg method that takes expressions. The output is one row per group, and the columns are whatever the expressions produced.

Aggregation by grade

by_grade = ( df.group_by("loan_grade") .agg( pl.len().alias("n_loans"), pl.col("loan_amnt").sum().alias("total_exposure"), pl.col("loan_amnt").mean().alias("mean_amount"), pl.col("loan_status").mean().alias("default_rate"), ((pl.col("loan_status") * pl.col("loan_amnt")).sum() / pl.col("loan_amnt").sum()).alias("ead_weighted_dr"), ) .sort("default_rate", descending=True) )

The expression API shines here. The exposure-weighted default rate (a common credit-risk metric) is one expression with no lambdas, no joins, no helper functions. The pandas equivalent requires either a lambda inside .agg or a separate transform-and-merge, both slower and uglier.

For row-level group statistics (the pandas .transform pattern), Polars uses .over:

Window-style aggregations with .over

df = df.with_columns( grade_mean_amount=pl.col("loan_amnt").mean().over("loan_grade"), loan_amnt_zscore=( (pl.col("loan_amnt") - pl.col("loan_amnt").mean().over("loan_grade")) / pl.col("loan_amnt").std().over("loan_grade") ), )

The same expression with .over("loan_grade") appended computes the aggregate per group and broadcasts it back to row level, in one step. This is the cleanest way to compute "the group mean for this row's group" in any dataframe library.

Joins and concat

Polars joins use .join with on and how, exactly as pandas. The join types are the same ("inner", "left", "outer", plus "semi" and "anti" as additions). The validate argument is named validate and takes the same cardinality strings.

Joining and concatenating

enriched = loans.join( customers, on="customer_id", how="left", validate="m:1", ) all_loans = pl.concat([ pl.read_parquet(f"data/loans_{m}.parquet") for m in ["2024-01", "2024-02", "2024-03"] ])

The "semi" join keeps rows from the left table whose key appears in the right; the "anti" join keeps rows whose key does not. Both are common in credit risk pipelines (find loans that have or do not have a corresponding default event) and require a clunkier idiom in pandas (an indicator merge plus a filter).

Lazy frames: the query planner

The lazy API is what makes Polars qualitatively different from a faster pandas. Replace pl.read_csv with pl.scan_csv and every subsequent operation builds a query plan rather than materialising data. The plan executes only when you call .collect(); before that the planner is free to rearrange operations.

The same pipeline, lazy

plan = ( pl.scan_csv("data/credit_risk_dataset.csv") .filter(pl.col("loan_status") == 1) .group_by("loan_grade") .agg(pl.col("loan_amnt").sum().alias("total_defaulted_exposure")) ) print(plan.explain()) # show the optimised query plan result = plan.collect() # actually run it

What the planner does here, automatically: predicate pushdown means the filter on loan_status is pushed inside the CSV reader, so the reader skips rows that would later be filtered out, never materialising them. Projection pushdown means only the columns referenced downstream (loan_status, loan_grade, loan_amnt) are read from the file. On a wide CSV with many columns this alone is often a 5-10x speedup. Common subexpression elimination means an expression computed once and used multiple times is materialised once.

For very large datasets that do not fit in memory, collect(streaming=True) runs the plan in batches and never holds the full data in memory at once. This is the bridge to genuinely larger-than-memory work, the territory that traditionally required Spark or Dask. Streaming has limitations (not every operation has a streaming implementation) but covers most aggregation and join workflows.

Step 5

When not to use Polars

The case for Polars is strong but not universal. Four situations where pandas remains the better choice.

First, small data and exploratory work where pandas is already fast enough. On a 50,000-row dataset the speed difference is invisible and the cost of learning a second API is real. If your workflow lives entirely in notebooks on small extracts, pandas is the default and the right one.

Second, tight integration with the scikit-learn / statsmodels ecosystem. Both libraries accept pandas dataframes natively and return predictions as pandas Series. Polars dataframes need to be converted via .to_pandas() or .to_numpy() at the boundary, and the round trip costs both time and the loss of Arrow's type information. For ML pipelines where the dataframe layer is mostly a feeder to scikit-learn, pandas is the more ergonomic choice.

Third, team familiarity. Polars is a recent enough library that a typical credit-risk team has more pandas experience than Polars experience. Rewriting a pipeline from pandas to Polars for a 3x speedup is rarely worth the team-onboarding cost; building a new pipeline in Polars from the start is. The right rollout pattern is to use Polars on new, performance-sensitive work and to leave existing pandas pipelines alone unless they are causing actual problems.

Fourth, workloads that genuinely exceed Polars's design. Polars is designed for single-machine work. For multi-terabyte datasets that need a cluster, Spark or Dask remain the right answers. For SQL-shaped analytical work on local files, DuckDB is often a better choice than Polars (and the two interoperate via Arrow with zero copies). The honest answer is that the modern dataframe stack has three or four members, and Polars is the right member of the stack for medium-to-large in-memory analytical work that does not need a cluster.

A pragmatic rollout The two highest-leverage places to introduce Polars in a credit-risk team are (a) data engineering pipelines that load multi-million-row extracts and feed downstream pandas analyses (use Polars to load, filter, and aggregate; convert to pandas at the boundary for the slow analytical step), and (b) monitoring jobs that run on a schedule and aggregate the full portfolio every day (where the 5-10x speedup compounds across daily runs). Both let you adopt Polars one job at a time without rewriting the rest of the codebase.
Step 6

Worked example: the Lecture 02 pipeline in Polars

The portfolio analytics pipeline from Lecture 02 (load, enrich, aggregate, pivot, roll forward) translated to Polars. The shape of the work is identical; the spellings change.

The same four-step pipeline in Polars

import polars as pl # Step 1: load with explicit dtypes (lazy) loans = pl.scan_csv( "data/credit_risk_dataset.csv", schema_overrides={"loan_grade": pl.Categorical, "loan_status": pl.Int8}, ) customers = pl.scan_csv( "data/customers.csv", schema_overrides={"region": pl.Categorical}, ) # Step 2: enrich loans with customer attributes enriched = loans.join(customers, on="customer_id", how="left", validate="m:1") # Step 3: aggregate to the grade level by_grade = ( enriched .group_by("loan_grade") .agg( pl.len().alias("n_loans"), pl.col("loan_amnt").sum().alias("total_exposure"), pl.col("loan_amnt").mean().alias("mean_amount"), pl.col("loan_status").mean().alias("default_rate"), ) .with_columns( vs_portfolio=( pl.col("default_rate") - pl.col("default_rate").mean() ), ) .sort("default_rate", descending=True) ) # Step 4: pivot grade x intent by_grade_intent = ( enriched .collect() .pivot(values="loan_status", index="loan_grade", on="loan_intent", aggregate_function="mean") ) # Step 5: monthly rolling default rate monthly_dr = ( enriched .sort("issue_date") .group_by_dynamic("issue_date", every="1mo") .agg(pl.col("loan_status").mean().alias("monthly_dr")) .with_columns( rolling_12m=pl.col("monthly_dr").rolling_mean(window_size=12, min_periods=6) ) .collect() )

Three observations. First, the structure is identical to the pandas version: load, join, aggregate, pivot, time-series. Second, the lazy mode means the planner can push the validation, the join, and the aggregation into a single optimised pass over the data; on a 30-million-row extract this is the difference between thirty seconds and three. Third, the group_by_dynamic with every="1mo" replaces the pandas resample("ME") idiom; rolling_mean on a Series replaces the chained .rolling(12).mean().

The runtime difference on a real dataset is the point of this lecture. The pandas version of this pipeline on the 32,000-row credit-risk dataset runs in roughly 200 ms. The Polars version runs in roughly 25 ms. Scale the dataset up by a factor of 1,000 (a real bank's loan book) and pandas takes minutes while Polars takes seconds. At the dataset sizes where credit-risk monitoring lives, the difference is the difference between an interactive iteration loop and a coffee break.

Step 7

Synthesis and what's next

Polars is the same analytical vocabulary as pandas, expressed through expressions and executed by a query planner on a columnar Arrow backend. The eighty per cent that looks like pandas (filter, group_by, join, with_columns) translates with a name change and a syntactic adjustment. The twenty per cent that differs (the expression API, the lazy planner, .over instead of .transform, group_by_dynamic instead of resample) is where Polars's design pays off. The honest case for Polars: medium-to-large in-memory analytical work, performance-sensitive pipelines, and any job where the iteration loop is being slowed down by pandas. The honest case against: small data, scikit-learn-heavy ML pipelines, and existing pandas codebases without a performance problem.
