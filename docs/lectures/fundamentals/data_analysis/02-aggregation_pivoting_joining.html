Aggregation, pivoting and joining

Once you can load and select, the next move is folding the rectangle: many rows into one summary (groupby), tall into wide (pivot), or stitching two tables together (merge). These three verbs account for the bulk of analytical pandas work in production: every portfolio dashboard, every regulatory submission, every monitoring report is a groupby followed by a merge. The lecture closes with the time-series operations a date-indexed dataframe unlocks.

Lecture 2 of 5 Reading time, 55 minutes Part I: the dataframe layer
Step 1

The 30-second version

Three verbs fold a dataframe. Groupby takes one rectangle and a key column, splits the rectangle into one piece per key value, applies an aggregation to each piece, and returns one row per group. Pivot takes the same rectangle and rearranges it from long format (one row per observation) to wide format (one column per category). Merge takes two rectangles sharing a key and produces a third rectangle with rows from one or both, depending on the join type. Almost every analytical question above the row level is a sequence of these three operations.

The discipline this lecture trains is knowing the cardinality of every join before you run it. A merge between two tables where each side has unique keys returns the join you expect. A merge where one side has duplicate keys multiplies rows; one where both sides have duplicates produces a Cartesian explosion. The bug is silent and only visible if you check the row count of the result. Half the wrong numbers in a junior analyst's portfolio deck come from an unchecked join cardinality.

Feynman test A groupby is a SQL GROUP BY. A pivot is an Excel pivot table. A merge is a SQL JOIN. Pandas just gives you all three in one syntax, with the rectangle as a first-class object you can pass around. If you can already write the SQL, you can write the pandas; the only thing to learn is the spelling.
Where this sits Lecture 01 covered the load-and-shape verbs (load, inspect, select, transform). This lecture covers the fold-and-combine verbs. Together they cover roughly 80 per cent of every analytical pipeline. Lecture 03 reproduces both in Polars. Lectures 04 and 05 leave shape alone and start asking what the data says.
Step 2

Why this matters

Every regulatory submission a bank makes is a groupby followed by a merge. The COREP capital templates report exposure-weighted risk parameters by asset class; that is a groupby on asset class with an exposure-weighted mean of PD, LGD, and EAD. The IFRS 9 staging dashboard reports loan counts and balances by stage and segment; that is a groupby on (stage, segment) with a sum and a count, presented as a pivot. The model monitoring pack compares this month's portfolio against last month's; that is a merge on segment of two groupby outputs. None of the substantive risk-modelling decisions in those documents work without the folding layer underneath, and silent errors in the folding layer corrupt every number a regulator sees.

The second reason is that most data lives in two or more tables and needs to be joined to answer any interesting question. A typical credit data warehouse has a customer table (one row per customer), a loan table (one row per loan, many per customer), a payment table (one row per payment, many per loan), and a default events table (one row per default event). Every analytical question crosses two or more of those tables. Getting the join wrong, on either the key or the cardinality, returns a number with no obvious sign that it is wrong.

The third reason is that the same operations, applied to the time axis, unlock a different question class: drift, trend, and seasonality. The .resample, .rolling, and .shift methods convert a date-indexed dataframe into the monthly default rate, the twelve-month rolling average loss, and the month-on-month change in originations. These are the building blocks of every credit risk monitoring report.

Step 3

The mental model

Three pictures, one per verb. Groupby is a split-apply-combine pattern: one input table becomes several mini-tables (one per key value), an aggregation is applied to each, and the per-group results are stacked into one output table. Pivot is a reshape: one column's values become column headers in the output, and another column's values become the cell contents, aggregated by a chosen function when several rows fall into the same cell. Merge is a join: two tables aligned on a shared key produce a third table whose columns are the union and whose rows depend on the join type (inner, left, right, outer).

Step 4

The detail

Groupby: split-apply-combine

The .groupby method takes a key (a column name, a list of column names, or a function of the index) and returns a GroupBy object. The object is lazy: nothing happens until you apply an aggregation. The three families of aggregation are reductions (one number per group: mean, sum, count, std, min, max, nunique, first, last), transformations (one value per row, broadcasted from the group: transform("mean") returns the group mean repeated for every row in the group), and filtrations (some groups kept and the rest dropped: filter(lambda g: len(g) > 100)).

Single-key groupby with one aggregation

by_grade = df.groupby("loan_grade", observed=True)["loan_status"].mean() # loan_grade # A 0.10 # B 0.16 # C 0.21 # D 0.29 # E 0.42 # F 0.55 # G 0.79 # Name: loan_status, dtype: float64

The observed=True argument suppresses categorical levels that are not present in the data; without it, an unused grade level appears in the output with NaN values. For categorical groupby keys this is almost always what you want; the argument default will flip to True in a future pandas version, and explicit is better than implicit.

Most real aggregations want more than one statistic per group. The .agg method takes a dict mapping column to aggregation, or a list of (output_name, source_column, aggregation) tuples for named aggregations:

Named aggregations: the modern idiom

portfolio = df.groupby("loan_grade", observed=True).agg( n_loans=("loan_amnt", "count"), total_exposure=("loan_amnt", "sum"), mean_amount=("loan_amnt", "mean"), default_rate=("loan_status", "mean"), pd_weighted=("loan_status", lambda s: (s * df.loc[s.index, "loan_amnt"]).sum() / df.loc[s.index, "loan_amnt"].sum()), )

Each keyword argument names a new column; the tuple (source_col, agg) specifies which column to aggregate and how. Mixing built-in strings ("mean", "sum") and lambdas in the same call is allowed and idiomatic. The output is a dataframe with one row per group and one column per named aggregation.

For multi-key groupby, pass a list of column names. The output has a MultiIndex (one level per key) on the rows:

Multi-key groupby

by_grade_intent = ( df.groupby(["loan_grade", "loan_intent"], observed=True) .agg(n=("loan_amnt", "count"), default_rate=("loan_status", "mean")) .sort_values("default_rate", ascending=False) )

If you want the keys as columns rather than as a MultiIndex, append .reset_index(). If you want a wide layout (one column per loan_intent) instead, use .unstack("loan_intent") on the result, which is equivalent to a pivot.

The .transform family returns one value per input row rather than one per group. It is the natural way to compute "the group mean for this row's group" without an explicit merge back:

Transform: broadcast group statistics to row level

# annotate every loan with its grade's mean amount df["grade_mean_amount"] = ( df.groupby("loan_grade", observed=True)["loan_amnt"] .transform("mean") ) # standardise loan_amnt within each grade df["loan_amnt_zscore"] = ( df.groupby("loan_grade", observed=True)["loan_amnt"] .transform(lambda s: (s - s.mean()) / s.std()) )

The output Series is the same length as the input dataframe, indexed identically, so the assignment is safe. This is the right tool whenever a per-row analysis needs a group-level statistic as an input. The same effect can be achieved with a groupby + merge but is uglier and slower.

agg vs apply vs transform Three groupby methods, three different output shapes. .agg returns one row per group. .transform returns one row per input row, with group statistics broadcasted. .apply is the escape hatch: it accepts any function from group to anything (a scalar, a Series, a DataFrame) and returns whatever shape pandas can stitch together. .apply is the most flexible and the slowest; reach for it only when the operation does not fit .agg or .transform.

Pivot tables: long to wide

The pivot_table function takes a long-format dataframe (one row per observation, with category columns identifying what kind of observation each row is) and produces a wide-format dataframe (one column per category value). It is the pandas equivalent of an Excel pivot table.

The standard pivot

pivot = df.pivot_table( values="loan_amnt", # the cells index="loan_grade", # the rows columns="loan_intent", # the columns aggfunc="mean", # how to combine multiple rows per cell fill_value=0, # what to put in empty cells margins=True, # add totals row and column margins_name="all", observed=True, )

The arguments are mechanical. values is the column to aggregate. index and columns are the two grouping keys whose unique values become the row and column labels of the output. aggfunc is how to combine multiple input rows that fall into the same output cell; "mean" is the default, common alternatives are "sum", "count", "median", or a list (["mean", "std"]) for multiple statistics per cell. margins=True adds a "total" row and column, useful for reporting.

Pivot tables and multi-key groupby are different views of the same operation: df.pivot_table(values="x", index="a", columns="b", aggfunc="mean") produces the same numbers as df.groupby(["a", "b"])["x"].mean().unstack("b"). The pivot form is more readable when the output is meant for human consumption (a report, a dashboard). The groupby form is more flexible when the output feeds another computation. Use the pivot form for one-shot reports; use groupby for pipelines.

Two related operations complete the reshape family. melt is the inverse of pivot: it converts wide to long. stack and unstack move levels between the row MultiIndex and the column MultiIndex without changing the underlying values. In practice you reach for pivot_table for the forward direction and melt for the inverse; stack and unstack are the surgical alternatives when you already have a MultiIndex.

Merge: joining two tables on a key

The pd.merge function (also available as a method, df1.merge(df2, ...)) joins two dataframes on a shared key. Three arguments do the work: on (the key, a column name or a list), how (the join type: "inner", "left", "right", "outer"), and validate (a cardinality assertion that catches the silent bugs).

A standard left join

joined = pd.merge( loans, # left table customers, # right table on="customer_id", # the shared key column how="left", # keep all rows from loans validate="m:1", # many loans per customer; exactly one customer per loan indicator=True, # add a column showing where each row came from )

The validate argument is the most important and the most underused. It tells pandas the expected cardinality ("1:1", "1:m", "m:1", "m:m") and raises if the data violates it. A m:1 validation catches the case where the customer table has duplicate IDs (which would multiply loan rows); a 1:m validation catches the case where the loan table has duplicate IDs (which would duplicate customer attributes). Every production merge should declare its cardinality.

The four join types map directly to SQL. Inner keeps only rows where the key matches in both tables. Left keeps all rows from the left table, filling missing right-side columns with NaN where the key did not match. Right is the mirror. Outer keeps all rows from both tables, filling both sides with NaN where one is missing.

Three smaller arguments to know. left_on and right_on are used when the key columns have different names in the two tables. suffixes controls how name collisions in non-key columns are resolved (the default ("_x", "_y") is rarely what you want; specify them as ("_loan", "_customer") for readability). indicator=True adds a _merge column showing whether each row came from "left_only", "right_only", or "both"; this is the fastest diagnostic when a join returns the wrong row count.

The cardinality bug A merge between a 10,000-row loan table and a 10,000-row customer table can return 10,000 rows or 30,000,000 rows depending on whether the customer key is unique. The bug never raises; it just multiplies rows. The protection is to call validate="m:1" on every merge with a master table on the left, and to check the row count of the result. The protection costs one line and prevents the single most common silent corruption in pandas pipelines.

Concat: stacking dataframes

The pd.concat function stacks two or more dataframes along an axis. With axis=0 (the default), it stacks rows: the dataframes are concatenated vertically and the column unions become the result columns. With axis=1, it stacks columns: the dataframes are aligned by index and joined side-by-side. The two cases serve different purposes.

Concatenating monthly extracts

monthly_frames = [ pd.read_parquet(f"data/loans_{m}.parquet") for m in ["2024-01", "2024-02", "2024-03"] ] all_loans = pd.concat(monthly_frames, ignore_index=True)

ignore_index=True resets the row index in the result; without it, the result has duplicate index values from each input file. Use keys= if you want a MultiIndex that records which input each row came from (the natural choice for snapshot data where the snapshot date is itself a label).

The columns of the inputs do not need to match: concat takes the union of column names by default and fills missing columns with NaN. To require exact column match, pass join="inner". The case where the columns differ is usually a bug (a schema change between months); the indicator approach for merges has no direct analogue for concat, so check the column lists before stacking.

Time-series operations: resample, rolling, shift

A dataframe with a datetime index unlocks three operations that have no clean equivalent on a default integer index. resample is groupby on the time axis: it groups rows by a date frequency (month, week, business day) and applies an aggregation. rolling is a windowed reduction: for each row, it aggregates the previous n rows. shift moves the values up or down by k rows, the natural building block for "previous period" comparisons.

Monthly default rate and twelve-month rolling default rate

# promote issue_date to the index and sort ts = df.set_index("issue_date").sort_index() # monthly: rebase to month-end frequency, mean of loan_status monthly_default_rate = ( ts["loan_status"] .resample("ME") # ME = month-end; "QE", "YE" for quarter/year .mean() ) # twelve-month rolling: mean of the prior twelve monthly values rolling_12m = monthly_default_rate.rolling(window=12, min_periods=6).mean() # month-on-month change mom = monthly_default_rate.diff() # absolute change mom_pct = monthly_default_rate.pct_change() # relative change # year-on-year using shift yoy = monthly_default_rate - monthly_default_rate.shift(12)

The pandas frequency strings ("D", "W", "ME", "QE", "YE", "B" for business day) parameterise the time bucket. The min_periods argument to rolling avoids returning NaN for the first few rows when fewer than window observations are available; set it to roughly half the window length for reporting. The shift operator is also the natural way to compute lag features for a model: ts["loan_status"].shift(1) is "the default flag in the previous row", which becomes the lag-1 default rate after a groupby.

Resample, rolling, and shift together cover most credit risk monitoring needs. The twelve-month rolling default rate is the basis of every monitoring chart. The month-on-month change in originations is the basis of every volume-tracking dashboard. The shift operator is how lag features enter every regression model that uses time-series data.

What's beyond the syllabus Two refinements deserve names. .rolling with window="365D" (a string offset rather than an integer count) gives a calendar-time window rather than a row-count window: the right tool when observations are unevenly spaced. .ewm (exponentially-weighted moving) gives a smooth that weights recent observations more than older ones, with a single tuning parameter (alpha or halflife); the right tool when the recent past matters more than the distant past. Both are direct generalisations of .rolling and read identically.
Step 5

Worked example: a portfolio analytics pipeline

A typical analytical question for a credit risk team: "for each loan grade, report the count, total exposure, default rate, and a comparison against the portfolio benchmark." Building this in pandas is a four-step pipeline using every operation in this lecture.

Step 1: load the loan table and a customer reference table

loans = pd.read_csv("data/credit_risk_dataset.csv", dtype={...}) customers = pd.read_csv("data/customers.csv", dtype={"customer_id": "Int64", "region": "category"})

Use the explicit-dtype pattern from Lecture 01. The customer table has one row per customer; the loan table has many loans per customer. We will need a many-to-one merge.

Step 2: enrich loans with customer attributes

enriched = pd.merge( loans, customers, on="customer_id", how="left", validate="m:1", indicator=True, ) assert (enriched["_merge"] == "both").all(), "some loans have no matching customer" enriched = enriched.drop(columns="_merge")

The validate="m:1" catches the case where the customer table has duplicate IDs. The assertion on _merge catches the case where some loans belong to customers not in the reference table; either keep them with explicit handling or fail loudly.

Step 3: aggregate to the grade level

by_grade = enriched.groupby("loan_grade", observed=True).agg( n_loans=("loan_amnt", "count"), total_exposure=("loan_amnt", "sum"), mean_amount=("loan_amnt", "mean"), default_rate=("loan_status", "mean"), ) # portfolio-level benchmark portfolio_dr = enriched["loan_status"].mean() by_grade["vs_portfolio"] = by_grade["default_rate"] - portfolio_dr

Four aggregations in one named-agg call. The benchmark is a scalar (the portfolio-wide default rate) broadcasted into a new column. The vs_portfolio column is the difference between each grade's default rate and the portfolio mean: positive for grades that are worse than average, negative for grades that are better.

Step 4: pivot to a reporting layout

by_grade_intent = enriched.pivot_table( values="loan_status", index="loan_grade", columns="loan_intent", aggfunc="mean", margins=True, margins_name="all_intents", observed=True, )

The pivot turns the two-dimensional groupby (grade × intent) into a wide table suitable for a report: one row per loan grade, one column per loan intent, default rate in each cell, with totals along the bottom and the right. This is the table you put in a slide.

What you have at the end: a portfolio summary by grade with a benchmark comparison (by_grade), and a default-rate heat map by grade and intent (by_grade_intent). The whole pipeline is twenty lines of pandas. The same questions in SQL would take roughly the same number of lines; the advantage of pandas is that the intermediate dataframes are inspectable, the chain is reproducible, and the result feeds directly into matplotlib for visualisation in Lecture 05.

Step 5 (bonus): twelve-month rolling default rate

ts = ( enriched.set_index("issue_date").sort_index() ["loan_status"] .resample("ME").mean() .rolling(12, min_periods=6).mean() )

A four-line pipeline: index by date, sort, resample to monthly mean, then twelve-month rolling. The output is a date-indexed Series suitable for a line plot. This is the basis of every credit risk monitoring chart.

Step 6

Common pitfalls and how to avoid them

The Cartesian merge

A merge where both sides have duplicate keys returns the Cartesian product of the matching rows. Two tables of ten thousand rows each with even modest duplication can produce a result of millions of rows. The fix is validate= on every merge. If validate="m:1" raises, the right-side key is not unique; either deduplicate it (with customers.drop_duplicates("customer_id")) or investigate why duplicates exist.

Mismatched key dtypes

A merge between a table where customer_id is Int64 and one where it is object (string) returns zero matched rows, silently. Pandas does not coerce key dtypes; the comparison 123 == "123" is False. The fix is to harmonise key dtypes before merging, ideally at load time via the dtype argument to read_csv.

Aggregating a categorical with the wrong function

Computing the mean of a categorical column (a string column with a small vocabulary read as category) raises a TypeError; computing the mean of an ordinal-coded column read as integer returns a number that has no physical meaning. Use "mode" (via lambda s: s.mode().iloc[0]) for categoricals, and check that the dtype of the column you are aggregating actually supports the aggregation.

Forgetting reset_index after groupby

The result of groupby(...).agg(...) has the group keys as the index, not as columns. Plotting libraries and downstream merges usually want the keys as columns. The fix is to call .reset_index() immediately after the aggregation, or to pass as_index=False to groupby, which produces the same result in one step.

Resample without a sorted index

.resample requires the index to be sorted; if it is not, the result is silently wrong (some buckets get the wrong observations). Call .sort_index() before any .resample or .rolling chain. Better, sort once at the top of the pipeline and assert the sort order, so subsequent operations can rely on it.

Default sort behaviour changing the row order

groupby sorts the keys in the output by default. If you have a categorical with an explicit ordering (loan grade A-G), the alphabetic sort happens to coincide; if you have a non-monotone ordering (regions in a custom order), the result is sorted alphabetically and not in the order you wanted. Pass sort=False to preserve insertion order, or set the categorical to be ordered (pd.Categorical(values, ordered=True)) and use sort=True with the categorical sort.

Step 7

Synthesis and what's next

You now have the folding layer. Groupby splits a rectangle by a key, applies an aggregation per group, and combines the results; .agg with named aggregations is the modern idiom, .transform is the way to broadcast group statistics back to row level. Pivot reshapes long-to-wide, with pivot_table as the most powerful version. Merge joins two rectangles on a key; validate= and indicator=True are the defences against silent cardinality bugs. Concat stacks rectangles along an axis. Resample, rolling, and shift are the time-axis versions of groupby and the basis of every credit risk monitoring report.
