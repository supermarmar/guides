MCP: the integration layer, and code execution over it

The Model Context Protocol turns "the agent can edit files" into "the agent can reach anything you have". That is a large increase in capability and a proportional increase in three costs that are easy to miss: context, blast radius, and the amount of untrusted content flowing into a system that cannot reliably tell data from instruction.

Lecture 15 of 22 Reading time, 50 minutes Part IV: the wider stack
Step 1

The 30-second version

MCP is an open standard for connecting agents to external tools and data. A server exposes tools, and once connected the agent can call them as it calls any built-in tool. The documented trigger for adding one is a good one: connect a server when you find yourself copying data into chat from another system. Once connected, the agent reads and acts on that system directly rather than working from what you paste.

Servers arrive over four transports, HTTP, SSE, stdio, and WebSocket, and are configured at three scopes with different sharing properties. Local scope is the default and is private to you in one project. Project scope lives in a .mcp.json at the repository root and is shared through version control, which is how a team standardises its integrations. User scope applies across all your projects. Project-scoped servers from a cloned repository sit at pending approval until you trust the workspace, which is the right default given what a server can do.

The cost that catches people is context. Every connected server's tool schemas occupy the window on every turn, whether or not a tool is ever called, which is the point Lecture 2 made and which becomes concrete here. The engineering answer is now well developed: defer tool loading so schemas are fetched on demand rather than presented upfront, and where a task chains many calls or returns large intermediate results, have the agent write code that calls the tools rather than calling them one at a time through its own context.

Feynman test A connected server is a standing cost and a standing risk, both paid whether or not you use it. Before adding one, ask what it saves you and how often. A server you use daily earns both. A server connected because it might be handy is renting space in every window and widening the surface through which hostile content can arrive, in exchange for a capability you have not needed yet.
What's beyond the syllabus MCP is a bet that integration should be a protocol rather than a product, and the historical rhyme is exact: LSP did this for editors and language tooling, turning an M by N problem into an M plus N one. Before LSP, every editor implemented support for every language; after it, every editor spoke one protocol and every language shipped one server. The same arithmetic applies here, and it explains why the ecosystem grew as fast as it did. It also inherits LSP's weakness: a protocol standardises the wire format and not the quality, so the ceiling on what an integration can do is still set by whoever wrote the server.
Step 2

Why this matters

The first reason is that most real work is not confined to a repository. The ticket is in a tracker, the design is in a design tool, the data is in a warehouse, the decision is in a document. An agent that can only see source code is an agent you spend your time briefing, and the briefing is the part you were trying to avoid. MCP is what closes that gap, and it is the difference between a coding assistant and something that can carry a task end to end.

The second reason is that it is where the security model stops being theoretical. A file-editing agent can damage your working copy, which git protects you from. An agent with a mail server, an issue tracker, and a cloud storage connector can send things, publish things, and read things that belong to other people, and none of those are recoverable by git checkout. Lecture 20 handles this properly, but the exposure begins here, at the moment a server is added.

The third reason is that it is the largest silent consumer of context most people have. Instruction files get audited because they are visible and someone wrote them. Tool schemas are invisible, arrive by the dozen when a connector is enabled, and are never reviewed. A machine with twenty connectors is carrying a substantial permanent load that nobody chose, and the symptom, a session that feels duller than it should, gets attributed to the model.

The scope decision is the same one Lecture 5 made about instruction files, and the same mistake is available. A connector put at user scope because it was convenient once is now loaded in every project on the machine forever. Default to local, promote to project when the team genuinely shares the dependency, and reserve user scope for the two or three you truly use everywhere.

The context arithmetic

Code execution over MCP

The second efficiency idea is more interesting and less known. In the ordinary pattern, each tool call is a round trip: the agent calls, the full result lands in its context, it reasons, it calls again. Three chained lookups mean three round trips and three sets of intermediate data, most of which is never needed again.

The alternative is to have the agent write a short program that calls the tools, run it in a sandbox, and return only the program's output. Intermediate results are processed by ordinary control flow, loops, filters, joins, and never enter the model's context at all. Anthropic's framing of the benefit is precise: load tools on demand, filter data before it reaches the model, and execute complex logic in a single step. The token cost then scales with the size of the final answer rather than with the size of everything the task had to look at.

The decision rule follows the read-to-conclusion criterion from Lecture 10 again. Where a task calls many tools and discards most of what comes back, write code. Where it calls one tool and needs the whole result, call it directly.

Tool schema cost. The per-turn context occupied by the definitions of connected tools, independent of use. The reason connector count, not connector activity, is what to audit.
Deferred tool loading. Presenting tool names without their full schemas and fetching a schema only when a tool is about to be used. Turns a standing charge into a per-task one.
Step 4

The detail

Permissions and naming

MCP tools follow the pattern mcp__<server>__<tool>, which is what you write in permission rules and hook matchers. That naming is what makes server-level policy possible: mcp__github__.* matches everything from one server, so a deny rule or a PreToolUse hook can govern an entire integration in one line. Where an organisation has set a connector's tools to require asking, that setting survives even permissive modes, and tools marked as requiring user interaction always prompt rather than being auto-approved on the author's behalf.

The general policy worth adopting is asymmetric, because the risk is. Read tools from a connector can usually be allowlisted; write and send tools should not be, and the confirmation you get before an outbound action is the last checkpoint before something leaves your control. Lecture 18 develops this where it matters most.

Every MCP result is untrusted content

This is the point most worth carrying out of this lecture. A tool result is data, and data can contain text shaped like instructions. An issue description, a page body, a file comment, a web page: any of these can carry a sentence addressed to the agent, and the agent has no reliable way to distinguish a genuine instruction from one that arrived inside a result.

The architectural response is to assume detection will fail and constrain the consequences instead. That means read-heavy connectors are much safer than write-capable ones, that the combination of a connector reading untrusted content and another connector able to send things is the dangerous configuration rather than either alone, and that outbound actions want a human in the path regardless of how confident the session feels. Lecture 20 makes this the whole subject.

Practical hygiene

Four habits, none of them expensive. Audit by count. If a connector has not been used in your last ten sessions, disconnect it; it can be added back in one command. Prefer project scope for team dependencies so the integration is reviewable in a pull request rather than configured differently on every machine. Prefer a CLI where one exists. The documented advice is that command-line tools are the most context-efficient way to reach an external service, and a well-known CLI such as gh costs no schema at all because the agent already knows how to drive it. Treat large tool outputs as a smell, since a tool returning thousands of lines is one that should be filtered before its result reaches the window.

Common pitfall Enabling every available connector during setup, on the reasonable-sounding theory that unused ones are harmless. They are not harmless in either currency. Each contributes schemas to every turn, and each expands the set of systems a successful prompt injection could reach. The configuration to aim for is the smallest set that covers what you actually do, extended deliberately when a real need appears, rather than the largest set that might one day be convenient.

Worked example: eighteen servers, and what they are contributing

Worked example: the connector list attached to this session

This session has eighteen MCP servers connected. Three are authenticated and carry real capability: Notion with around nineteen tools, a Microsoft 365 connector with roughly forty covering Outlook, SharePoint, and Teams, and a CRM connector with fifteen. A browser-automation server adds a further two dozen. Together those account for nearly every tool that could actually do something.

The other fourteen are stubs. Asana, Atlassian, Box, Canva, DocuSign, Figma, Fireflies, Gmail, HubSpot, Intercom, Linear, Mermaid Chart, Miro, and monday.com are each present with exactly two tools: authenticate and complete_authentication. None is signed in. Their entire current capability is to begin an OAuth flow. They are twenty-eight tool definitions that cannot read, write, or fetch anything at all.

What that would cost without mitigation. Under upfront loading, all eighteen servers' schemas would sit in every window on every turn of every session, and the fourteen unauthenticated ones would contribute a permanent charge for a capability that is definitionally zero until someone signs in. That is the pure form of the pitfall above: the cost is real, the benefit is not yet, and nothing in the interface surfaces the trade.

What actually happened. The session ran with deferred loading: tool names were listed, schemas were not, and each schema was fetched only when a tool was about to be used. Over roughly fifteen lectures this session has fetched five, the two scheduling tools, the task tools, web search and fetch, and the browser set. Thirteen of the eighteen servers have contributed nothing beyond their names, which is exactly the intended outcome and a good demonstration that the mechanism works.

What deferring does not fix. It addresses the context cost and leaves the security surface untouched. Fourteen dormant OAuth stubs are fourteen integrations one consent screen away from being live, and a live Gmail connector next to a live document connector is precisely the read-untrusted-then-send-outbound pairing that Lecture 20 is about. The honest recommendation is the boring one: disconnect the ones you are not using. Deferred loading made the cost invisible, and an invisible cost is one nobody ever gets round to removing.

Step 5

Synthesis and what's next

MCP connects the agent to systems outside the repository, over four transports and at three scopes with different sharing properties. Connect a server when you are copying data into chat from somewhere else; default to local scope and promote deliberately. Watch the context arithmetic, because schemas are charged per turn regardless of use, and prefer deferred loading and code execution over MCP where a task calls many tools or discards most of what returns. Govern by the mcp__server__tool naming, allowlist reads and never writes, prefer a CLI where one exists, and treat every result as untrusted content rather than as data you can act on.

That is the protocol layer. The next three lectures are about what sits on the other end of it, and they are ordered by how much the agent has to go through to reach them. The most agent-native substrate turns out to need no protocol at all, because it is already plain files on disk, and it is the one this repository has been sitting in since before the course began.
