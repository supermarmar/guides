Test-driven development when the agent writes the code

TDD was always partly about design and partly about a safety net. With an agent at the keyboard the balance shifts hard towards the net, because the test is now the only thing standing between a plausible implementation and a correct one. It also acquires a new failure mode: the agent can edit the net.

Lecture 11 of 22 Reading time, 45 minutes Part III: verification
Step 1

The 30-second version

The classical cycle is unchanged: write a failing test, write the least code that passes it, refactor. What changes when an agent writes the implementation is who the test is protecting you from. Written by hand, a test guards against your future self misunderstanding your past self. Written against agent output, it guards against a body of code that reads as though someone understood the problem and may not have. Lecture 1's asymmetry in its most practical form: generation is cheap, verification is not, and a test is verification you only pay for once.

The new failure mode is specific and it follows from the stopping-too-early weakness. An agent told to make the tests pass has two routes to that outcome: fix the code, or weaken the test. Both terminate the loop. If fixing the code is hard and weakening the assertion is easy, the second is a live possibility, and the resulting diff contains a passing suite and a defect. This is not misbehaviour; it is a correct solution to the problem as stated, which is why the remedy is to state a different problem.

So the discipline gains one step. Write the test, watch it fail for the right reason, and then commit it before any implementation exists. A committed test is a fixed point: changes to it show up in the diff as changes to the test rather than disappearing into the noise of a large implementation commit. The documented pattern goes further and separates the roles entirely, having one session write the tests and another write the code to pass them, which removes the conflict of interest rather than managing it.

Feynman test A test you have never seen fail is not a test, it is a decoration. This was always true and it was always survivable, because a human writing a test that passes immediately usually notices. An agent writing a hundred tests that all pass immediately will not tell you, and neither will the green tick. Watching the red is the step that converts a suite from a claim into evidence.
What's beyond the syllabus Goodhart's law is the thing operating here: when a measure becomes a target, it ceases to be a good measure. A test suite is a proxy for correctness, and pointing an optimiser at the proxy is precisely the configuration in which proxies fail. The literature on reward hacking in reinforcement learning is the same phenomenon with different vocabulary, and it produces the same countermeasures: make the proxy expensive to game, hold some of it out of reach, and have something other than the optimiser judge whether the target was met. Committing tests before implementation is the first; property-based tests are the second; a separate reviewer is the third.
Step 2

Why this matters

The first reason is that a test suite is what sets the autonomy slider. Lecture 1 argued that autonomy should follow the speed and mechanicalness of verification; a fast, trustworthy suite is exactly that, and it is the only version of it that scales. With one, an agent can iterate unattended for an hour and you review a branch. Without one, every increment needs your eyes, and the agent's speed advantage evaporates into your review queue. The suite is not a quality practice that happens to help here. It is the thing that makes the whole workflow economically different.

The second reason is that tests are the most durable form of specification available. A prompt is gone when the session ends, a plan is a document nobody rereads, and an instruction file decays. A test is executable, checked in, and runs on every change forever. When Lecture 6 said the scarce skill is saying precisely what you want, the test suite is where those statements accumulate into something permanent.

The third reason is that the alternative is worse than it used to be. Reviewing untested generated code is the trust-then-verify gap the documentation names as a common failure pattern, and its remedy is stated flatly: always provide verification, and if you cannot verify it, do not ship it. That advice was always sound. It becomes non-negotiable when the volume of code arriving for review multiplies and each piece looks equally competent.

Step 3

The mental model

The cycle, with the extra step

Three ways to write the tests

You write them. Highest fidelity, lowest volume. Correct when the behaviour is subtle, when the domain knowledge is yours, or when the test is the specification and you want it to be exactly right. A handful of hand-written tests around the difficult core plus generated tests around the periphery is a good default shape.

The agent writes them from a specification you gave. The common case, and it works when the specification names concrete cases. The documented before-and-after is instructive: "implement a function that validates email addresses" becomes "write a validateEmail function; example cases: user@example.com is true, invalid is false, user@.com is false; run the tests after implementing". You supplied the oracle; the agent supplied the volume.

One agent writes tests, another writes code. The strongest form, and the reason is structural rather than about capability. An agent that writes both has an interest in their agreement, and the cheapest way to achieve agreement is not always the correct one. Separating the roles into different sessions removes the conflict, and the test-writing session can be told explicitly that it will not be implementing, which changes what it writes.

Tests that are hard to game

Not all tests resist weakening equally. Three properties make one robust.

Assert on behaviour, not on implementation. A test that checks a helper was called with certain arguments breaks when the implementation changes legitimately, which trains everyone to edit tests casually. A test that checks the output for an input survives refactoring and objects only to defects.

Prefer properties to examples where the domain allows. A property-based test asserting that a probability output lies in $[0, 1]$ for all generated inputs cannot be satisfied by special-casing the three examples you wrote. Generated inputs are the closest thing available to a test the implementer has not seen.

Keep them fast. The loop only closes if the check runs in seconds. A suite that takes four minutes will not be run on every iteration, and a check that is not run is not a check. The documented advice to prefer running single tests over the whole suite during iteration is about exactly this.

Confirming the red. Running a new test before any implementation exists and reading the failure message to check it fails for the intended reason. A test that fails with an import error is not yet testing the thing you meant.
Assertion weakening. Satisfying a failing test by loosening what it asserts rather than by fixing the code. The characteristic agent failure under a "make the tests pass" instruction, and invisible in a large diff unless the tests were committed first.
Step 4

The detail

The instruction that closes the loop

The naming of the invariant is what does the work. Compare:

Weak:   Make the tests pass.

Better: Make the tests pass. Do not modify any file under tests/.

Best:   The tests in tests/test_pd.py are committed and correct. Make them
        pass by changing only src/pd/. If you believe a test is wrong, stop
        and tell me which one and why — do not edit it.

The third version does three things. It states the invariant positively, it scopes the permitted change to a directory, and it supplies an escape hatch. That last clause matters more than it looks: sometimes the test genuinely is wrong, and without a route to say so the agent's only options are to fail or to quietly edit. Giving it a way to raise the objection converts a silent modification into a conversation.

The enforced version of the same rule is a permission deny rule or a PreToolUse hook on writes matching tests/**, which is Lecture 9's point applied here. If the invariant genuinely must hold, do not ask for it.

Where TDD does not fit

Three honest exceptions, because applying this dogmatically wastes effort.

Exploratory work where you do not yet know what the interface should be. Writing tests against an interface you are still designing means rewriting them, and the tests then constrain the design rather than the reverse. Explore first, test once the shape settles.

Output whose correctness is visual or editorial. A layout, a document, a chart. There are mechanical properties worth testing, and this course's own build checks are an example, but the substance is judged by looking. Pretending otherwise produces tests that pass while the thing is ugly or wrong.

Genuine one-offs. A migration script run once, a data pull for a single analysis. The test outlives nothing, so the investment does not amortise. Verify the output directly instead.

Common pitfall Asking an agent to add tests to existing untested code produces a suite that asserts the current behaviour, including its bugs. Those tests then pass forever and prevent nothing, while giving every future reader the impression the code is covered. They are worse than no tests, because no tests at least advertises the risk. If you are retrofitting, start from the specification or the ticket rather than the implementation, and expect some of the new tests to fail immediately, because those failures are the point of the exercise.

Worked example: the checks behind this course, written in the wrong order

Worked example: verification-after, and what verification-first would have caught

These lectures are HTML rather than code, but they have mechanical correctness properties and those properties are testable. Four checks were used: every relative path resolves to a file that exists, every CSS class appears in lecture.css, no em or en dashes anywhere, and section and div tags balance.

They were all written after the lectures. Four lectures were generated, then the checks were written and run against them. They passed, which is the outcome that makes the ordering feel unimportant. It is not, and the difference is worth being precise about.

What the ordering cost. Passing on the first run tells you the lectures were fine. It does not tell you the checks work, because a check that is written after the artefact and passes immediately has never been observed to fail. The dash check greps for two specific characters, and if the pattern had been wrong, if the shell had mangled the Unicode escape, the result would have been an identical silent pass. The whole verification report rested on four scripts none of which had produced a single red.

What was actually done about it. Nothing, at the time. The checks were validated only later and incidentally, when Lecture 9's worked example needed a house-style hook and the same grep pattern was run against a file that deliberately contained the offending characters. It fired. That is the confirmation step arriving three lectures late and by accident rather than by design.

What the first-order version looks like. Write check-lecture.sh before writing any lecture. Run it against a deliberately broken fixture: a file with a dash, a bad class name, an unbalanced div. Watch each check fail with the message you expect. Then generate, and let the agent iterate against a check whose red you have seen. That is a fifteen-minute investment, and it converts the entire course build from "generate then inspect" into a closed loop where the definition of done is a script rather than a memory of what to look for.

The general point, which is not about HTML. The instinct to verify after building is strong because building feels like the real work. It survives because verification-after usually passes, and a pass feels like confirmation when it is merely an absence of information. The question that catches it is the one this lecture opens with: have I ever seen this check fail? If not, you do not yet know whether it can.

Step 5

Synthesis and what's next

The cycle gains two steps when the implementer is an agent: confirm the red, and commit the test before implementation, because a test that can be edited by the thing it constrains is not a constraint. Name the invariant rather than the signal, scope the permitted change to a directory, and give the agent a way to object to a test rather than only a way to edit it. Prefer behavioural assertions and properties over implementation details and examples, and keep the suite fast enough that it actually runs each iteration. Separate the roles where it matters: one session writing tests and another writing code removes a conflict of interest rather than managing it.

The wider point is that a test is verification you buy once and spend many times, which is exactly the shape of investment that pays when generation is cheap. But no suite covers everything, and the residue, the design judgement, the scope, the thing that is correct but wrong, arrives at a human. The next lecture is about that residue: how to review a diff you did not write, when the usual signals for reading code no longer carry the information they used to.
