CLAUDE.md: the project constitution and the drift problem

An instruction file is the only artefact that speaks on every turn of every session, which makes it both the highest-leverage thing you can write and the easiest thing to ruin. The failure is not that people write bad rules. It is that they keep adding good ones until nothing is salient any more.

Lecture 5 of 22 Reading time, 50 minutes Part II: steering the agent
Step 1

The 30-second version

CLAUDE.md is a markdown file the harness loads at the start of every session and re-sends on every turn. It exists to hold the facts an agent cannot infer from the code: the build command that is not in the README, the convention that differs from the language default, the decision the team made in March and never wrote down. It is delivered as a message after the system prompt rather than as part of it, which places it firmly on the advisory side of the line drawn in Lecture 3: the model reads it, weighs it, and usually complies. There is no enforcement.

Files load from four scopes, from broadest to most specific: an organisation's managed policy file, your user file at ~/.claude/CLAUDE.md, the project's own CLAUDE.md, and a gitignored CLAUDE.local.md for personal notes. They are concatenated rather than overridden, which is the single most consequential fact about the system and the one people get wrong. Adding a project file does not replace your user file. It appends to it. Every scope you use is paid for on every turn, forever.

Which gives the discipline its shape. The documented target is under 200 lines per file, and the documented failure mode is stated plainly: bloated files cause Claude to ignore your actual instructions, because the important rules get lost in the noise. The test the documentation offers for each line is the right one and almost nobody applies it: would removing this cause a mistake? If not, cut it. An instruction file is not documentation, and treating it as documentation is how it dies.

Feynman test Every line in an instruction file is rent, paid on every turn of every session in scope, in exchange for preventing a mistake. A line that prevents a mistake once a week is cheap. A line that describes something the agent could read from the code in one grep is a pure loss, twice over: you pay the tokens, and you dilute the lines that matter. The file is not a place to be thorough. It is a place to be selective.
What's beyond the syllabus Notice what kind of object this is. It is a configuration file whose semantics are "please", enforced by nothing, interpreted probabilistically, and degrading in effect as it grows. Software engineering has no other artefact quite like it, and the closest analogues are organisational rather than technical: a company handbook, a coding standard, a constitution. They fail the same way, for the same reason. Everyone can add a clause, nobody is responsible for removal, and past a certain length the document stops being read and starts being cited selectively. The engineering response and the organisational response turn out to be identical: give it an owner, review it, and delete more than you add.
Step 2

Why this matters

The first reason is that this is where unstated context goes to become stated. Lecture 1 named it as one of the four structural weaknesses: the agent knows what is in its window and nothing else, so every fact that lives only in your head is a fact it will contradict. Writing it down is the entire remedy, and the file is where it goes. A team that has never written one is re-explaining its conventions in every session, paying for it in tokens and in the corrections that follow.

The second reason is that the file compounds in both directions. Written well, it gets better with age: each entry is a mistake that will not happen again, and the value accrues to everyone who clones the repository. Written badly, it decays with age in a way that is almost invisible, because the symptom of a bloated file is not an error message. It is the agent quietly ignoring the rule you care about while obeying eleven you had forgotten writing. You will diagnose that as the model being unreliable, and you will be wrong.

The third reason is scope hygiene, which is subtle and expensive to get wrong. Because scopes concatenate, a personal preference written into a user-level file applies to every project on the machine, including the ones where it makes no sense. A convention that belongs to one language ends up loaded during sessions in another. Nobody notices, because there is no error, just a slow accumulation of irrelevant instruction that crowds out the relevant kind. The worked example at the end of this lecture is exactly this failure, measured.

Step 3

The mental model

Four scopes, concatenated

ScopeLocationApplies toShared via
Managed policySystem location, deployed by ITEveryone on the machineMDM or group policy; cannot be excluded
User~/.claude/CLAUDE.mdYou, in every projectNothing; it is yours
Project./CLAUDE.md or ./.claude/CLAUDE.mdEveryone who clonesgit
Local./CLAUDE.local.mdYou, in this repositoryNothing; gitignore it

Beyond the four scopes, the harness walks up the directory tree from where you started, loading every CLAUDE.md it passes, in order from the filesystem root down. Files in subdirectories behave differently and better: they load on demand, when the agent actually reads a file in that directory. That asymmetry is the lever. Instruction placed above you is always paid for; instruction placed below you is paid for only when it becomes relevant, which is the just-in-time principle from Lecture 2 appearing in the instruction layer.

What belongs, and what does not

The documented include-and-exclude table is the sharpest guidance available on this, and it is worth reproducing in substance because the boundary it draws is not obvious.

IncludeExclude
Commands the agent could not guessAnything derivable by reading the code
Style rules that differ from the language defaultStandard conventions the model already knows
The test runner and how to invoke itDetailed API documentation; link instead
Repository etiquette: branch naming, PR conventionsInformation that changes frequently
Architectural decisions specific to this projectLong explanations and tutorials
Environment quirks and required variablesFile-by-file descriptions of the codebase
Non-obvious gotchasSelf-evident advice like "write clean code"

The unifying principle across the exclude column is that each item is either discoverable or inert. Discoverable content, the directory layout, the dependency list, what a function does, can be retrieved with one tool call at the moment it matters, so paying for it on every turn is a bad trade. Inert content, "write clean code", "follow best practices", changes no decision the model would otherwise make and so buys nothing at all. The include column is the complement: things that are neither discoverable nor inert, which is a narrower set than most people's instinct suggests.

Instruction rent. The per-turn token cost of a line in an always-loaded file, multiplied by every turn of every session in that file's scope. The relevant question is never whether a line is true, but whether it earns its rent.
Path-scoped rule. A file in .claude/rules/ carrying a paths: frontmatter field with glob patterns. It loads only when the agent touches a matching file, converting a permanent cost into a conditional one. Rules without a paths: field load unconditionally, like a CLAUDE.md.
Import. The @path/to/file syntax, which splices another file in at launch, up to four hops deep. It organises content across files. It does not reduce context, because imported files are loaded at launch exactly as if pasted in.

The three mechanisms, and the choice between them

Three places can hold a piece of guidance, and choosing between them is the main design decision in this lecture.

A CLAUDE.md entry is always loaded and always advisory. Use it for facts that apply to every session in scope. A path-scoped rule is conditionally loaded and advisory. Use it when the guidance is real but only applies to part of the codebase, which is most style and testing guidance in any multi-language repository. A skill is loaded on demand, when invoked or judged relevant. Use it when the guidance is a procedure rather than a fact, and Lecture 8 develops this properly. Behind all three sits the fourth option: if the requirement must hold every time without exception, none of these is right, and it belongs in a hook, which Lecture 9 covers.

The decision rule is a sequence of three questions. Does this apply everywhere, always? Then CLAUDE.md. Does it apply only to certain files? Then a path-scoped rule. Is it a procedure you invoke rather than a fact you hold? Then a skill. And cutting across all of them: must it hold without exception? Then a hook, because everything above is a request.

Step 4

The detail

Writing lines that actually land

Three properties separate an instruction that changes behaviour from one that decorates the file.

Specificity to the point of verifiability. "Use two-space indentation" beats "format code properly" because you can check compliance without judgement. The test is whether a disagreement about whether the rule was followed could be settled by looking. If it could not, the rule will not be followed consistently, because there is nothing consistent to follow.

Freedom from contradiction. When two rules conflict, the documented behaviour is that the model may pick one arbitrarily, and arbitrary means you cannot predict which. Contradictions arrive by accumulation rather than by authorship: a user-level rule and a project-level rule, written months apart by different people for different reasons, that happen to disagree. This is the specific failure that periodic review exists to catch, and it is invisible until you go looking.

Brevity that preserves salience. Emphasis markers such as "IMPORTANT" or "YOU MUST" do improve adherence, and they are worth using, but they are a currency that inflates. A file where six rules shout is a file where shouting has stopped meaning anything. Reserve emphasis for the two or three rules whose violation actually costs you something.

# Weak: unverifiable, inert, and derivable
- Write good tests
- Follow best practices for error handling
- The src/ directory contains the source code

# Strong: specific, non-obvious, and each prevents a real mistake
- Run `pytest -m "not slow"` before pushing; the full suite needs a live DB
- LGD models must never be fitted on the recovery-window subset; use `lgd_full`
- Migrations are hand-written, never autogenerated (alembic revision --autogenerate
  produces the wrong index order against our composite PKs)

Diagnosing a file that is not working

Two symptoms have specific, documented causes, and knowing them saves an afternoon.

If the agent keeps doing something you have a rule against, the file is probably too long and the rule is getting lost. The instinct is to strengthen the rule; the correct move is to shorten the file. Adding capitals to a rule buried in line 180 of a 250-line file does very little, because the problem is position and density rather than phrasing.

If the agent asks you something the file already answers, the phrasing is ambiguous rather than the file being too long. Reread the rule as a stranger would and look for the reading you did not intend.

Before either diagnosis, confirm the file is actually loaded. Running /context lists the memory files that made it into the session, and a file in the wrong location produces exactly the symptoms above while being entirely absent. Check that first; it is the cheapest hypothesis to eliminate.

Common pitfall Splitting a long CLAUDE.md into several files with @path imports feels like a fix and is not one. Imported files are expanded and loaded at launch exactly as if their contents were pasted in, so the token cost is identical and the salience problem is untouched. You have improved how the content looks to a human editor and changed nothing about what the model sees. The mechanism that genuinely reduces context is the paths: frontmatter on a rules file, because it makes loading conditional. If your motivation is organisation, import; if your motivation is context, scope.

Worked example: the instruction stack loaded in this session

Worked example: 566 lines of always-on instruction, measured

This session runs from guides/docs/lectures/. Counting every file above that directory that loads unconditionally: the user file ~/.claude/CLAUDE.md at 109 lines; four rules files at 51, 35, 57, and 32 lines; the repository root guides/CLAUDE.md at 205 lines; and guides/docs/CLAUDE.md at 77. Total 566 lines, re-sent on every turn of every session started at or below this directory.

What is genuinely good here. The content is specific and mostly verifiable. "Never American spelling", "no em or en dashes as punctuation", "stage files by name, not git add -A" are all rules you can check compliance against by looking, and each encodes a real preference the model would otherwise get wrong. The repository file's F107 coverage map earns its rent, for the reasons Lecture 2 set out. Someone has clearly been adding to this file every time a mistake happened, which is exactly the recommended habit.

Where the rent is not being earned. None of the four rules files carries a paths: frontmatter field, so all four load unconditionally in every project on the machine. That means this session, which has written nothing but HTML, has been carrying 32 lines on pytest markers and conftest.py layout, and 35 lines on Google-style docstrings and Python type annotations, on every single turn. They are good rules. They are simply not rules about anything happening here. Adding paths: ["**/*.py", "**/*.ts"] to those two files removes 67 lines from every non-code session and loses nothing, because they reappear the moment a Python file is touched.

The size problem. The documented target is under 200 lines per file. guides/CLAUDE.md is 205 on its own, and much of the overage is the folder tree: a forty-line ASCII diagram of a directory structure that the agent can list in one tool call and that goes stale the moment anyone adds a folder. That is the textbook case from the exclude column, discoverable and volatile at once. Cutting the tree to the half-dozen paths that are genuinely non-obvious would bring the file under target and make it more accurate rather than less.

The duplication. Anti-sycophancy exists twice: as a 51-line always-loaded rule and as an on-demand skill. The split is deliberate and the rule file says so, pointing at the skill for worked examples. But the division is in the wrong place. The behaviour it wants, argue before agreeing, is only load-bearing when the user shares a decision or a piece of work, which is precisely the condition the skill's description already matches on. Two or three lines in the rule with the substance in the skill would cost forty fewer lines per turn at no loss.

The general principle. Instruction files do not decay by containing wrong things. They decay by containing right things in a scope wider than the thing applies to. The audit is mechanical and takes ten minutes: for each block, ask which sessions it is true for, and if the answer is narrower than the file's scope, move it down or add a paths: field. Nobody schedules this, which is why almost every mature instruction stack is carrying a third more than it needs.

Step 5

Synthesis and what's next

CLAUDE.md holds what the agent cannot infer, on every turn, advisorily. Four scopes concatenate rather than override, ancestor files load in full while subdirectory files load on demand, and the practical target is under 200 lines per file. Include what is neither discoverable nor inert; exclude the rest. When guidance applies to only part of a codebase, a path-scoped rule converts permanent rent into conditional rent, which is the one mechanism that genuinely reduces context, since imports do not. And when a file stops working, the cause is usually length rather than phrasing, so the fix is deletion rather than emphasis.

The wider point is that this file is a shared artefact with no owner by default, which is the condition under which documents rot. Treating it like code, reviewing it, pruning it, testing whether a change actually shifted behaviour, is the whole of the discipline. The next lecture moves from the standing instruction to the individual request: what makes one prompt produce the change you wanted and another produce a plausible diff you have to read line by line to evaluate.
