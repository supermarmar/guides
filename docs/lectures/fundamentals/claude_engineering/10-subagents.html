Subagents, fan-out, and git worktrees

A subagent is not a way to go faster. It is a way to spend a hundred thousand tokens of reading somewhere other than your own context window and get two hundred words back. Once you hold that, the question of when to delegate answers itself, and so does the question of when not to.

Lecture 10 of 22 Reading time, 50 minutes Part II: steering the agent
Step 1

The 30-second version

A subagent runs in its own context window with its own set of allowed tools, does a bounded piece of work, and returns a condensed result to the parent. Anthropic's figure for that result is a thousand to two thousand tokens. Everything it read to produce those tokens, forty files, a directory tree, a stack of search results, stays in its window and dies with it. That asymmetry is the entire value proposition, and the documentation says so directly: since context is your fundamental constraint, subagents are among the most powerful tools available.

Which gives a single selection criterion. Delegate work with a high read-to-conclusion ratio: tasks that consume a lot of material and produce a short answer. "Find where token refresh is handled and whether we already have OAuth utilities" is a perfect subagent task, because the answer is a paragraph and the search is not. "Write the patch" is usually not, because the output is the point and it has to come back in full anyway.

The second use is independence rather than economy. A reviewer running in a fresh context sees only the diff and the criteria, not the reasoning that produced the change, so it evaluates the result on its own terms. That is a genuinely different property from asking the same session to check its own work, and it is why the writer-reviewer split is worth the round trip even when context is not tight.

Feynman test Before delegating, estimate two numbers: how much the task will read, and how long the answer is. If the first is much larger than the second, delegate; you are buying the difference. If they are similar, do it yourself; you are paying a briefing, a spawn, and a summary for nothing. The mistake is thinking about parallelism first, because parallelism is a side effect and context is the product.
What's beyond the syllabus Every subagent boundary is a lossy compression step, and lossy compression is not free. The parent receives what the child judged worth reporting, which means the child's judgement about relevance is now load-bearing and unauditable: you cannot see what it decided to omit. This is the same failure surface as any organisational hierarchy, where information degrades at each reporting boundary and the degradation is invisible from above. The engineering consequence is that the tasks safest to delegate are the ones where the summary can be checked against reality cheaply, and the ones most dangerous to delegate are those where the child's omissions would be indistinguishable from an absence of findings.
Step 2

Why this matters

The first reason is that unscoped investigation is the documented way to destroy a session. Asking an agent to "look into" something without bounds has it read hundreds of files, all of which land in your window, and the session is impaired for everything that follows. The named remedy is to scope the investigation narrowly or push it into a subagent so the exploration does not consume the main context. That single move is the difference between a session that stays sharp through a long task and one that goes vague around the halfway mark.

The second reason is that fresh context is a quality mechanism, not just an economy one. A model reviewing code it has just written is biased towards it, having already reasoned its way to why each choice was correct. A reviewer that never saw that reasoning has no such commitment. Getting a second opinion from the same window is close to worthless for the same reason that asking someone to proofread their own writing is.

The third reason is that delegation has a real cost that is easy to ignore because it is not billed as latency. Every subagent needs briefing, spawns with none of the parent's accumulated understanding, re-derives context the parent already had, and returns a summary that discards what it did not think mattered. On a small task those costs exceed the saving comfortably. Knowing where the crossover sits is most of the skill.

Step 3

The mental model

The economics of a delegation

Defining one

Custom subagents live in .claude/agents/ as markdown files with frontmatter naming the agent, describing when it applies, and restricting its tools and model.

---
name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior security engineer. Review code for:
- Injection vulnerabilities (SQL, XSS, command injection)
- Authentication and authorisation flaws
- Secrets or credentials in code
- Insecure data handling

Provide specific line references and suggested fixes.

The tools line is doing more than it appears. Restricting a reviewer to read-only tools means it cannot fix what it finds, which sounds like a limitation and is actually the point: a reviewer that edits is no longer a reviewer, and its findings can no longer be assessed independently of its changes. Tool restriction is how you keep the roles separate.

What a subagent does and does not inherit

A subagent starts with its own context. It does not inherit the parent conversation's accumulated understanding, nor the main conversation's automatic memory. The exception is a fork, which does inherit the parent conversation and system prompt, and which is what the context: fork skill setting from Lecture 8 produces. The practical consequence is that a briefing has to be self-contained: everything the subagent needs must be in the prompt, because it cannot see the forty turns that led here.

Under auto mode, subagent work is checked at three points: the delegated task description is evaluated before the subagent starts, each of its actions goes through the same classifier as the parent, and its full action history is reviewed when it finishes, with a warning prepended to its results if the return check flags anything. Notably, a permissionMode in a subagent's own frontmatter is ignored while this is in force, which closes the obvious escalation route.

Read-to-conclusion ratio. How much a task must read relative to how much it must report. High ratios are the delegation criterion; low ratios mean the briefing costs more than the summary saves.
Worktree isolation. Running an agent in its own git worktree so parallel agents editing files do not collide. Costs setup time and disk, so it is warranted only when the parallelism is genuinely mutating, not merely concurrent.
Step 4

The detail

Four patterns that pay

Scoped investigation. The default case. "Use subagents to investigate how authentication handles token refresh, and whether we have existing OAuth utilities I should reuse." High ratio, bounded, and the answer is checkable against the code afterwards.

Writer and reviewer. One session or agent implements, a second reviews the diff in a fresh context against stated criteria. The documentation is careful about the failure mode here, and the caution is worth repeating: a reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering. Tell the reviewer to flag only what affects correctness or the stated requirements, and treat the rest as optional.

Adversarial verification. Sharper than review. Give several verifiers the same claim and ask each to refute it, defaulting to refuted when uncertain, then keep the claim only if it survives a majority. Diversity of angle beats redundancy: three verifiers with distinct lenses, correctness, security, does-it-reproduce, catch failure modes that three identical ones cannot.

Fan-out over a work list. For migrations and sweeps, generate the list of targets first, then loop a non-interactive invocation over it with scoped permissions. The documented advice is to refine the prompt against the first two or three items before running the full set, which is the difference between a migration and two thousand identically wrong edits.

for file in $(cat files.txt); do
  claude -p "Migrate $file from React to Vue. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

Worktrees, and when they are worth it

Parallel agents editing the same checkout collide. A git worktree gives each its own directory on its own branch, which removes the collision entirely. The cost is real, a few hundred milliseconds of setup plus disk per agent, so the rule is narrow: use worktrees when agents mutate files in parallel, and not otherwise. Read-only fan-out, which is most fan-out, needs no isolation at all. This is the point at which delegation stops being a context technique and becomes a workspace-management one, and the git lecture in the software engineering track covers the underlying mechanism.

When delegation loses

Three situations where the inline version wins, and all three are common.

The briefing approaches the task. If explaining what you want takes as long as doing it, you have not saved anything, and you have added a summarisation step where information can be lost.

The work is exploratory and iterative. Delegation assumes a bounded question. Work where each finding changes the next question does not survive the round trip, because the subagent returns after one pass and the second question needs the context it just discarded.

The nuance is the deliverable. Anything where the details of what was read matter, and not just the conclusion, is a bad fit, because you receive the conclusion. A subagent that reports "no security issues found" has told you either that there are none or that it did not look properly, and those are indistinguishable from where you are sitting.

Common pitfall Delegating a task and then re-deriving its findings yourself is the most expensive pattern available, and it is a common instinct when the summary feels thin. You have paid the subagent's tokens, the briefing, and the summary, and are now paying the full inline cost as well. If you do not trust a delegation, the fix is upstream: brief it better, or do not delegate that task. Committing to the delegation is part of the decision to make it.

Worked example: the instruction conflict in this session

Worked example: two rules about subagents, in direct contradiction

This session ran under two instructions that cannot both be followed. The machine's global CLAUDE.md mandates delegation: "Every Agent tool call must set model: \"haiku\" by default," and "Three or more file reads should be batched into an Explore subagent with model: \"haiku\"." The session-level instructions state the opposite: "Do not call the AgentTool unless the user requested it." Plan mode's own workflow guidance adds a third voice, instructing that exploration be done with Explore subagents.

How it resolved, and why that is worth noticing. The narrower, later instruction won: no subagents were used, and the exploration was done by reading files directly in the main context. That is defensible as a precedence rule, and it is also exactly the failure Lecture 5 described. Two instruction sources, written at different times for different reasons, disagreed; the model picked one; nothing surfaced the conflict; and the global rule that someone deliberately wrote has been silently inert in every session on this machine that carries the session-level instruction.

What the contradiction cost. Building this course involved reading well over three files: the design specification, a sample lecture, a course landing page, the root index, the stylesheet, the bootstrap script, four instruction files, two skill definitions, and two settings files. Under the global rule that is squarely an Explore subagent task with a high read-to-conclusion ratio, and delegating it would have kept most of that material out of this window. It was instead read inline, and all of it is still resident.

Whether the global rule was right anyway. Partly. The read-to-conclusion ratio for the structural exploration was genuinely high and delegation would have paid. But a subagent returning "the lecture format uses these classes and this section structure" would have given a summary, and what the writing actually needed was the exact markup of a reference lecture, verbatim, to copy conventions from. That is the third losing case above: the nuance was the deliverable, and a summary would have produced plausible-looking markup with invented class names. The right answer was mixed, delegate the survey and read the one reference file directly, which neither instruction expresses.

The general lesson, which is about instructions rather than subagents. A blanket rule of the form "always delegate when N files" encodes a proxy for the read-to-conclusion ratio, and proxies fail at the edges. The rule that survives contact is the criterion itself: delegate when the reading is large and the conclusion is small, read directly when the material itself is what you need. Write the criterion into the instruction file rather than the threshold, and check periodically whether the rule you wrote is one any session is actually still following.

Step 5

Synthesis and what's next

A subagent buys context headroom, not speed and not tokens: it reads in its own window and returns a short report. Delegate on the read-to-conclusion ratio, and use a cheap model at low effort when doing so, because the work is volume reading. Fresh context is independently valuable for review, since a reviewer that never saw the reasoning evaluates the result rather than the argument. Restrict tools to keep roles separate. Reach for worktrees only when parallel agents actually mutate files. And know the three losing cases: when the briefing rivals the task, when the work is iterative, and when the nuance rather than the conclusion is what you need.

That closes Part II. Between them, instruction files, prompts, plans, skills, hooks, and subagents are the whole steering layer: what the agent is told, what it is asked, what it may do, and where it does it. Every one of them is upstream of the moment that actually decides whether any of this was worth doing, which is when the work comes back and somebody has to determine whether it is correct. Part III is about that moment, and it opens with the technique that makes it cheapest: writing the test before the code, when the code is not being written by you.
