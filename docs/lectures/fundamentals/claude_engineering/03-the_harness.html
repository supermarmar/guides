Anatomy of a harness: tools, permissions, sessions

The model chooses; the harness decides what choosing means. It defines the action space, gates every action against a permission model, assembles the context, and owns the session. Almost every complaint that begins "the model did X" turns out on inspection to be a statement about one of those four responsibilities.

Lecture 3 of 22 Reading time, 55 minutes Part I: foundations
Step 1

The 30-second version

A harness is the program that turns a model into an agent. It has four jobs. It assembles the context: system prompt, instruction files, tool schemas, history. It defines the action space: which tools exist, what arguments they take, and what they return. It gates every action: the permission model that decides whether a proposed tool call runs, prompts, or is refused. And it owns the session: persistence, resumption, checkpoints, compaction, and clearing. Claude Code is one such harness; the model inside it is the same model available through the API, and almost none of what follows is a property of the weights.

The permission model is the piece worth studying hardest, because it is the only genuine control surface you have. Everything you write in an instruction file is advisory: the model reads it, weighs it against everything else in the window, and usually complies. A permission rule is enforced: the harness checks it before the tool runs, and no amount of persuasion in the conversation changes the outcome. That distinction, advisory versus enforced, recurs throughout the course, and choosing the wrong side of it is the most common design mistake in agent configuration.

One caveat before the detail. This is the most version-sensitive lecture in the course. Mode names, flag spellings, and default behaviours change between releases, and the specifics below reflect the documentation at the time of writing. The structure is stable and worth learning; the spellings are not. Where the current documentation disagrees with this page, the documentation is right.

Feynman test Before every tool call, the harness asks a single question: may this run? The answer comes from a fixed decision order, your explicit rules first, then a small set of always-safe actions, then whatever the current mode says about everything else. If you can state where a given command lands in that order, you can predict whether you will be interrupted, and you can stop being interrupted without giving anything away.
What's beyond the syllabus The interesting design question is who the permission model is protecting you from. It is not primarily the model's malice, which is not the failure mode in practice. It is protecting you from two other things: the model's confident errors, and content it reads. The second is the deeper problem. A file, a web page, or an issue comment can contain text engineered to read as an instruction, and the model has no reliable way to distinguish data from directive. Every serious agent security architecture is a variation on the same answer: constrain the action space so that following a hostile instruction is not catastrophic, because detecting the hostile instruction cannot be relied upon. Lecture 20 takes this properly.
Step 2

Why this matters

The first reason is diagnostic. When something goes wrong, knowing the harness's four responsibilities tells you where to look, and the answer is rarely the model. The agent ignored an instruction: that is context assembly, and the instruction is probably buried in a file too long to be salient. The agent could not do something obvious: that is the action space, and the tool it needed is not connected. The agent stopped to ask about something trivial: that is the permission model, and the rule is missing. The agent forgot a decision from earlier: that is session management, and the context has been compacted. Four symptoms, four different fixes, none of them "use a better model".

The second reason is that permission configuration is where convenience and safety trade against each other explicitly, and the trade is easy to get wrong in both directions. Configure nothing and you approve so many prompts that you stop reading them, which is strictly worse than approving none, because you have the illusion of oversight without the substance. Configure a blanket allow on shell access and you have removed the last enforced boundary between a confidently wrong model and your file system. The right configuration is neither: a specific allowlist covering the commands you genuinely run all day, and prompts preserved for everything else.

The third reason is that the harness is where your team's practice becomes portable. An instruction file, a settings file with an allowlist, a hook that runs the linter, a subagent definition: these are text files that live in the repository and apply to whoever opens it. That is the difference between one engineer having a good workflow and a team having one. It also means the configuration is reviewable, which is worth insisting on, because a settings file that grants broad execution rights is a security change and should be treated like one.

Step 3

The mental model

The action space

Tools are the agent's verbs, and they fall into three classes with very different risk profiles. Read-only tools, reading a file, globbing, grepping, listing, cost context and nothing else; a wrong call wastes tokens. Mutating tools, editing a file, writing a file, running a shell command, change your machine; a wrong call costs work. External tools, web fetches, MCP calls to a service, network requests, change or reveal things outside your machine; a wrong call can be irreversible and can involve other people. The permission model exists almost entirely to draw a line between the first class and the other two, which is why read-only actions are auto-approved in every mode and everything else is negotiated.

Two properties of tool design matter enough to state now, because they explain configuration choices later. First, every connected tool's schema occupies context on every turn, whether or not it is ever called, which is the argument for connecting servers per project rather than globally. Second, a tool's description is the only thing the model has to decide when to use it, so a vague or overlapping description produces exactly the failure you would expect: the wrong tool, called confidently. Anthropic's guidance on writing tools reduces to making each one self-contained, unambiguous about its purpose, and robust when misused.

The permission decision order

Every proposed tool call runs through a fixed sequence, and the first matching step wins. Holding this order in mind is what makes permission behaviour predictable.

A small set of paths sits outside this order entirely. Writes to .git, to shell configuration files, to hook and package-manager configuration, and to the agent's own .claude directory are treated as protected paths and are never auto-approved by an allow rule, because a rule granting the agent permission to edit the file that defines its permissions is a rule that grants everything. The design principle is worth taking away even if the specific list changes: the configuration that constrains the agent must not itself be inside the agent's unconstrained reach.

Advisory versus enforced. Instruction files are advisory: they influence the model's choice. Permission rules and hooks are enforced: they act on the call after the choice is made. If a requirement must hold every time without exception, it belongs on the enforced side, and putting it in an instruction file is a category error.
Permission mode. The default disposition towards calls that no explicit rule resolved. It sets the baseline; rules layer on top and are evaluated first.
Protected path. A file or directory whose modification is never auto-approved, because it governs repository state or the agent's own configuration. Allow rules do not override the protection.

Configuration precedence

Settings come from four scopes, and the precedence runs from organisation-managed policy at the top, through command-line arguments, then local repository settings, then shared project settings, and finally your user-level settings at the bottom. The mental model is the familiar one from any layered configuration system: the more specific and the more authoritative the source, the later it is applied. Permission rules are the exception that catches people out. They merge across scopes rather than overriding, and a deny anywhere in the stack beats an allow everywhere else. That is the correct behaviour for a safety mechanism: a project cannot quietly grant itself a permission your user settings withheld.

ScopeTypical locationApplies toShared with the team
ManagedDeployed by IT policyEveryone in the organisationYes, and cannot be overridden
User~/.claude/settings.jsonYou, in every projectNo
Project.claude/settings.jsonEveryone who clones the repositoryYes, via git

The split that matters in daily use is between project and local. Project settings are a team artefact and should be reviewed like code: they are the place for the linter hook everyone should run and the allowlist covering the repository's own build commands. Local settings are a scratchpad: they are where the harness records the one-off approvals you granted during a session. Treating the second as if it were the first is how allowlists rot, which is the subject of this lecture's worked example.

Step 4

The detail

The permission modes

Modes sit on a spectrum from reviewing everything to reviewing nothing. The names below are current at the time of writing; the shape is what to remember.

ModeRuns without askingUse it for
default (shown as Manual)Reads onlyUnfamiliar repositories, anything touching production
acceptEditsReads, file edits in scope, common filesystem commandsIterating on code you will read as a diff afterwards
planReads and exploration; edits blocked until you approve a planUnderstanding before changing. The default for anything non-trivial
autoMost things, with a separate classifier model vetting each actionLong tasks where prompt fatigue is the bigger risk
dontAskOnly what your allow rules pre-approve; everything else is deniedCI and scripts, where there is nobody to prompt
bypassPermissionsEverythingIsolated containers and virtual machines, and nowhere else

Two of these deserve comment. Plan mode is the one to make habitual, because it enforces the separation between research and execution that Lecture 1 argued for: the agent explores and proposes, you argue with the proposal, and only then does anything get written. The documentation is honest that it adds overhead and is not worth it for a typo, and the test it offers is a good one: if you could describe the diff in one sentence, skip the plan.

Auto mode is a different design idea and worth understanding rather than merely using. Rather than asking you about each action, a separate classifier model reviews the proposed action against the conversation and blocks the categories that constitute escalation: downloading and executing code, sending sensitive data outward, destroying things that existed before the session, force-pushing, touching production. Notably, it also treats boundaries you state in conversation as blocks, so telling the agent "do not push until I have reviewed" is honoured by the classifier and not merely by the model's good intentions. The honest limitation is stated in the documentation and worth repeating: it reduces prompts, it does not guarantee safety, and it is not a substitute for reviewing sensitive operations.

Permission rules

Rules are patterns matched against tool calls, sorted into three lists. An allow entry runs the matching call silently. An ask entry forces a prompt even in permissive modes. A deny entry refuses outright, in every mode, including the permissive ones. The syntax names the tool and, optionally, constrains its argument.

{
  "permissions": {
    "allow": [
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Bash(pytest -q:*)",
      "WebFetch(domain:docs.python.org)"
    ],
    "ask": [
      "Bash(git push:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(curl:*)"
    ]
  }
}

The deny list is the part people underuse. It is the only mechanism that holds in every mode, so it is where secrets belong: environment files, credential directories, key material. Writing Read(./.env) into a deny list costs one line and removes an entire category of accident, including the accident where a well-meaning agent reads a credential in order to help and thereby writes it into a transcript that syncs somewhere. That is worth doing in a repository long before it is worth tuning anything else.

Sessions, checkpoints, and the reset habit

The session is the fourth responsibility, and it is context management wearing different clothes. Four controls do most of the work. Clearing resets the window between unrelated tasks and is the single most underused command in the interface: a session carrying an hour of unrelated history starts every new task already impaired. Compacting summarises rather than discards, and takes an instruction, so you can tell it what to preserve. Rewinding restores a previous conversation and code state, which converts risky experiments into cheap ones, though it only tracks changes made through the editing tools and is therefore not a substitute for git. Resuming reopens a named session later, which makes long-running work survivable across days.

The habit worth building from these is the reset. The documented failure pattern is exact and recognisable: you correct the agent, it is still wrong, you correct again, and the context is now full of failed approaches that make the next attempt worse. After two failed corrections, clearing and rewriting the initial prompt with what you learned beats a third correction almost every time. This feels like giving up and is actually the cheapest available move, because it removes the accumulated wrong turns rather than adding to them.

Common pitfall The most consequential misconfiguration is running in bypassPermissions on a machine that matters, usually adopted after a frustrating afternoon of approvals. It removes every enforced boundary at once, and it offers no protection against the failure mode that boundaries exist for: content the agent reads containing text that reads as an instruction. If prompt fatigue is the problem, the proportionate answers are a specific allowlist for the commands you actually run, or auto mode with its classifier, or a sandbox. If you genuinely need everything permitted, the correct venue is a container or virtual machine with nothing in it you would miss.

Worked example: how an allowlist rots

Worked example: the local settings file in this repository

The docs/lectures/ folder in this repository carries a .claude/settings.local.json with about fifteen allow entries, accumulated over many sessions by approving prompts as they appeared. It is a good specimen because it is real, and because almost every entry in it is useless.

What is in it. Entries such as a PDF text extraction naming one specific input file and one specific output file, both by absolute path. A Python one-liner that imports three libraries and prints their versions, recorded character for character. A directory listing with a hardcoded substring operation on a hardcoded path. Each was granted once, in one session, to unblock one command.

Why they are dead. A rule earns its keep by matching a future call. An entry naming a specific file that was converted once will never match again, because the next PDF has a different name. The allowlist has grown by fifteen entries and reduced future prompting by approximately zero, while becoming long enough that nobody will read it to check what it grants.

What the same file should contain. The pattern the sessions actually repeat, which is reading anything under the docs tree and running the ordinary read-only git commands. Three or four entries of the form Read(docs/**) and Bash(git log:*) would have covered the great majority of the prompts that the fifteen specific entries were each approved to silence. Generality is the whole point of an allowlist: a rule that matches one historical invocation is a record of the past, not a permission for the future.

The wider lesson, and the honest cost. Approving prompts as they arrive produces an allowlist optimised for what already happened. Periodically rewriting it towards the patterns you repeat, and moving the genuinely shared ones up into a reviewed project settings file, is a five-minute maintenance job that nobody ever schedules. The cost of not doing it is not primarily security, since the dead entries grant nothing reachable; it is that the file becomes unreadable, and an unreadable permission file cannot be audited, which means that when a broad entry does eventually appear in it, nobody notices.

Step 5

Synthesis and what's next

The harness assembles context, defines the action space, gates every action, and owns the session, and those four responsibilities account for nearly everything people attribute to the model. Permission resolution follows a fixed order: your explicit rules first, then the automatic approval of reads and in-scope edits, then whatever the mode says about the remainder, with protected paths sitting outside the order entirely. Rules are enforced and instructions are advisory, so anything that must hold every time belongs in a rule or a hook. Settings layer across four scopes, with permissions merging rather than overriding and deny beating allow. And the session controls, clear, compact, rewind, resume, are context management by another name, with clearing after two failed corrections the highest-value habit among them.

The wider point is that configuring a harness is the act of deciding, in advance and in writing, what you are prepared not to look at. That is a genuine engineering decision with a genuine cost on both sides, and it deserves the same care as any other. The next lecture takes the last of the four foundational choices: which model to put inside the harness, and how much thinking to buy, given that the answer changes with the phase of the work rather than with your budget.
