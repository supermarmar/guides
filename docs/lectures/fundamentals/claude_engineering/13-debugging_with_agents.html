Systematic debugging: hypothesis before fix

An agent shown an error will produce a fix within seconds, and it will be the fix that error usually needs. Usually is the problem. Debugging discipline is the practice of refusing to act on a diagnosis you have not yet earned, and it matters more now precisely because the unearned diagnosis arrives so fast and so plausibly.

Step 1

The 30-second version

The discipline is four steps and the order is the whole of it. Reproduce: make the failure happen on demand, because a bug you cannot summon is a bug you cannot confirm you have fixed. Isolate: narrow it until the failing surface is small, by bisection, by deletion, by binary search through the input. Explain: state the mechanism in a sentence that accounts for every observed symptom. Then fix, and verify by watching the reproduction stop failing.

The agent's characteristic failure is to compress all four into one. It reads the stack trace, recognises the shape, and emits the fix that shape normally requires. Often that is right, which is exactly what makes it dangerous: a technique that works most of the time trains you to skip the check that catches the rest. The documented framing puts it as addressing root causes rather than symptoms, and pairs the instruction with an explicit prohibition on suppressing the error, because suppression is the most available wrong fix.

The counter-discipline is a rule you can state in one line and enforce with a prompt: no fix without an explanation that predicts the symptoms. If the account of the mechanism does not explain why the failure is intermittent, or why it only happens on that one machine, or why the log line appears twice, then the account is incomplete and the fix built on it is a guess wearing a diagnosis.

Feynman test Before applying any fix, answer: what did I believe about this system that was wrong? A real diagnosis always identifies a false belief. If you can describe the fix but cannot name the misconception it corrects, you have found a change that makes the symptom go away, which is a different and much weaker thing.
What's beyond the syllabus This is the scientific method with a shorter feedback loop, and the failure mode is the one Popper cared about: a hypothesis that cannot fail is not doing any work. "There is a race condition somewhere" is unfalsifiable and therefore useless; "the cache is read before the write completes, which is why it only fails under load and always on the first request after a deploy" makes predictions you can test. The reason agents are prone to the unfalsifiable version is structural rather than a defect of reasoning: they are trained to produce the most probable continuation, and the most probable explanation for a stack trace is the one that most often accompanies it, not the one that is true this time.
Step 2

Why this matters

The first reason is that a symptom fix does not merely fail to solve the problem; it conceals it. A clamp on an out-of-range value, a retry around a flaky call, a broadened exception handler: each removes the evidence that something is wrong while leaving the wrongness in place. The next person to encounter the underlying defect will find it harder, because the signal that would have led them to it has been suppressed by a change that looks like a fix and passes review.

The second reason is that speed inverts the usual economics of care. When a fix took an hour to write, the ten minutes spent confirming the diagnosis were obviously worth it. When a fix takes twenty seconds, the same ten minutes feel disproportionate, and the temptation is to try the fix and see. Trying is sometimes right, but it is a different activity from debugging and it needs to be a decision rather than a drift.

The third reason is that intermittent failures are exactly where the shortcut fails and exactly where they are most common. A bug that reproduces every time survives a bad diagnosis, because the wrong fix visibly does not work. A bug that fails one run in five will be declared fixed after one clean run, and the declaration will be sincere. Any debugging practice that does not explicitly handle intermittency will keep producing confident wrong conclusions about the hardest bugs you have.

Step 3

The mental model

Four steps, and the gate between three and four

Where the agent genuinely helps

Three parts of this are much faster with an agent, and it is worth being specific so the discipline does not read as a general slowdown.

Reproduction. Turning a vague report into a failing test is mechanical, tedious, and exactly the sort of thing to delegate. "Users say login fails after session timeout" becomes a test that logs in, advances the clock, and asserts the failure. This is the highest-value delegation in debugging because the artefact it produces is the thing everything else depends on.

Isolation. Bisection is a search, and searches are cheap to automate. git bisect against a reproduction script finds the introducing commit in a logarithmic number of steps, and an agent can drive the whole loop. Equally, narrowing an input by repeated halving until the smallest failing case remains is pure mechanism.

Surveying the surface. "Every place this value can be written" is a search across the codebase with a short answer, which is the delegation shape from Lecture 10. What comes back is not a diagnosis, it is the candidate list a diagnosis will be chosen from.

What the agent should not do unsupervised is step three, and the reason is not competence. It is that step three is where a wrong answer is indistinguishable from a right one until much later, so it is the step that most needs a second party.

Root cause versus symptom. A root-cause fix changes the thing that was wrong; a symptom fix changes what you observe. The test is whether the fix would still be needed if you could see the system perfectly. A clamp would not be; a corrected transform would.
Bisection. Binary search over a dimension that separates working from broken: commits, inputs, configuration, or code paths. Converts an unbounded search into a logarithmic one, and requires only a reliable reproduction and an ordering.
Step 4

The detail

Prompts that enforce the order

The discipline can be built into the request, which is more reliable than intending to apply it afterwards.

Do not propose a fix yet.

1. Write a test that reproduces this failure. Run it and show me the output.
2. Tell me the mechanism: what is happening, in one or two sentences, and
   why that explains (a) why it is intermittent and (b) why it only affects
   the batch path.
3. Wait for me to agree before changing anything outside tests/.

The numbered structure matters less than the two constraints inside it. Naming the specific symptoms the explanation must account for is what converts a plausible story into a falsifiable one, because a generic race-condition answer cannot satisfy a demand to explain why only the batch path is affected. And the explicit hold before implementation prevents the compression of steps three and four, which is the failure this whole lecture is about.

Intermittency, handled honestly

Intermittent bugs need a different verification standard and it is worth stating numerically rather than by feel. If a bug reproduces one run in five, a single clean run after a fix is close to no evidence: you would expect that outcome four times in five with no fix at all. Twenty clean runs is evidence. The rule is to know your base rate and require enough passes that the observed result would be unlikely under the null hypothesis of no change, which is the same logic as any other test of a proportion.

The related discipline is to state up front what result would count. "Run the reproduction fifty times and report the failure count before and after" is a specification an agent can execute and you can read. "Check it is fixed" is an invitation to a single run and a confident conclusion.

Knowing when to stop

Debugging has a failure mode of its own, which is the loop that will not terminate: attempt, fail, adjust, fail, adjust. Two rules cut it short. The first is Lecture 6's counting rule, applied here: after two failed corrections the context is full of dead ends, and clearing it and restarting with what you learned beats a third attempt. The second is escalation by kind rather than by effort. If three attempts have failed, the next move is not a fourth attempt but a change of approach: a different tool, a fresh pair of eyes, a subagent with a clean context, or a decision that the bug is not worth this today.

Recognising a non-terminating loop is a skill and the signal is specific: you are trying variations rather than testing hypotheses. Variations mean you have run out of theory and are searching, and searching by hand is the least efficient available method.

Common pitfall "It works now" after a change you do not fully understand is the most expensive sentence in debugging. Sometimes the change fixed it. Sometimes it perturbed the timing, or the ordering, or the cache state, and the bug is still there and will return in a worse place. The distinguishing question is whether you can explain why the change fixed it. If not, you have not fixed it, you have moved it, and the honest record is a note saying so rather than a commit message claiming a fix.

Worked example: a failure in this session that was not debugged

Worked example: the browser render check, and the decision to stop

Verifying the first four lectures included opening them in a browser to confirm the stylesheet resolved and the inline SVG figures rendered. The Chrome extension timed out twice on the first call, with an error suggesting the page might be loading, unresponsive, or waiting on a permission prompt. After the second attempt the browser check was abandoned and the limitation reported: everything structural verified, the visual render unconfirmed.

Why stopping was defensible. The tooling guidance is explicit that repeated browser-automation failures should end in a report rather than a third attempt, and there was a real cost to continuing: the failure was in someone else's process, the diagnosis would have involved a permission dialog nobody could see, and the remaining risk was low because the path and class checks cover the plausible causes of a broken render. Reporting the gap rather than papering over it was the right call.

Why it was still not debugging. No step of the four was performed. The failure was never reproduced deliberately, never isolated, and never explained. The error message offered three distinct hypotheses, loading, unresponsive, or awaiting a permission prompt, and no attempt was made to distinguish them, which would have cost one lighter call to a different tool as the error message itself suggested. What happened was a decision to abandon, correctly made, and it should not be mistaken for a diagnosis. The honest statement is "unknown cause, accepted risk", not "the extension was unavailable".

What the systematic version would have cost. Two or three minutes. Reproduce: call the tool a third time and observe whether the failure is consistent. Isolate: call a lighter operation on the same connection, which separates "extension unreachable" from "this operation is heavy". Explain: if the light call succeeds, the hypothesis is a heavy operation timing out and the fix is a different verification route entirely rather than a retry of the same one. That path might well have produced a render check by a different means, which is the thing that was actually wanted.

The general lesson. There is a real difference between stopping and concluding, and reports blur them constantly. Stopping is a resource decision and is often correct. Concluding requires the four steps. When a report says a thing failed because of some named cause, ask which of the two happened, because an accepted unknown that has been quietly written up as a known cause is how a recurring problem becomes invisible.

Step 5

Synthesis and what's next

Reproduce, isolate, explain, then fix, with the gate between the third and fourth steps carrying the discipline. Delegate reproduction, bisection, and surveying, which are mechanical and fast; keep explanation supervised, because a wrong explanation is indistinguishable from a right one until much later. Demand that the account predict every symptom, especially intermittency and specificity of scope, since a generic story cannot. Set the verification bar by the base rate rather than by feel. And distinguish stopping from concluding, because a resource decision written up as a diagnosis is how a problem gets lost.

The wider point is that all three lectures in this part are the same argument in different settings: the model produces plausible output at high speed, plausibility no longer tracks correctness, and the remedy is a procedure that does not depend on the output looking right. Tests provide it mechanically, review provides it deliberately, and debugging provides it by demanding an explanation. The last lecture in this part turns the argument on the conversation itself, where the same fluency problem appears as agreement, and where the thing you need checking is your own reasoning.
