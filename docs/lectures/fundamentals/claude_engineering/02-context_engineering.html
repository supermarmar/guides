Context engineering: the window is the program

Everything the model knows on a given turn is the token sequence in front of it. That sequence is finite, it degrades as it fills, and every file you paste competes with every tool schema and every previous turn for the same budget. Curating it is not a preliminary to the work. It is the work.

Lecture 2 of 22 Reading time, 50 minutes Part I: foundations
Step 1

The 30-second version

Context engineering is the practice of curating the set of tokens the model sees at inference time. Anthropic draws the distinction against prompt engineering sharply: prompt engineering is about writing good instructions, while context engineering covers the whole evolving universe of information that might land in the window, instructions, tool definitions, retrieved files, tool results, and the conversation so far, and the question of which subset of it should be there on this turn. The governing principle they state is worth memorising: find the smallest possible set of high-signal tokens that maximise the likelihood of the outcome you want.

The reason this is a discipline rather than a preference is that context is finite and lossy. A transformer lets every token attend to every other token, which means $n$ tokens create $n^2$ pairwise relationships, and models are trained on distributions weighted towards shorter sequences. The consequence, which Anthropic calls context rot, is that as the window fills, the model's ability to recall any particular thing in it falls. You are not working with a container that holds a fixed number of facts equally well. You are working with an attention budget that thins as you spend it.

Karpathy's version of the same idea is the more memorable one: in this new mode of programming, the context window is the RAM and the model is the CPU. You are writing a program whose source is a paragraph, and the window is the working memory it executes in. Nobody would load a 400-megabyte file into memory to read one field from it. That is nonetheless what most people do the first time they hand a repository to an agent, and it is why their sessions get slow, expensive, and vague at exactly the point where the task gets interesting.

Feynman test Ask, of any token in the window: what decision does this token help the model make? If the answer is "none, but it seemed relevant", it is costing you twice, once in money and once in the attention it draws away from the tokens that do matter. Good context is not comprehensive. It is the briefing you would give a competent colleague who has one hour: the goal, the constraints, the two files that matter, and where to look for the rest.
What's beyond the syllabus The quadratic attention cost is a property of the architecture, not a bug awaiting a patch, and the engineering responses to it, sparse attention, sliding windows, linear-attention variants, state-space models, are among the most active areas of the field. But note what does not follow. Even with an arbitrarily long window and perfect recall, curation would still pay, because the model must locate the relevant signal among the noise you supplied. A larger window changes the cost of a mistake, not the value of precision. This is the same reason a bigger disk never fixed a badly organised filing system.
Step 2

Why this matters

The first reason is that context is the one resource every other technique competes for. A skill you load is tokens. A tool you connect is tokens, because its schema sits in the window whether or not it is ever called. An instruction file is tokens on every single turn of the session. A subagent exists chiefly to keep tokens out of your window. Almost every design decision in the rest of this course is a decision about what to spend the budget on, and it is impossible to reason about those decisions well without holding the budget in mind.

The second reason is that the symptom of a badly managed window looks like a model failure, which sends people to the wrong remedy. A session that started sharp and became vague, an agent that forgets a constraint you gave it forty minutes ago, an agent that re-reads a file it already read, an agent that contradicts a decision made earlier in the same conversation: none of these are the model being unreliable. They are context rot, and the fix is to reset and re-brief rather than to argue with the model or to escalate to a larger one. Recognising the signature saves both money and an hour of increasingly frustrated prompting.

The third reason is economic and it compounds. Tokens are billed, and in a long agentic session the conversation history is re-sent on every turn, so a wasteful early decision is paid for repeatedly for the rest of the session. Pasting a 3,000-line file at turn three does not cost you 3,000 lines once; it costs you 3,000 lines on every subsequent turn until the context is compacted or cleared. The habit of retrieving the twenty lines that matter is worth an order of magnitude over a long session, and the discipline it builds happens also to be the discipline that produces better answers.

Step 3

The mental model

What is actually in the window

Five categories of token compete for the budget, and it is worth knowing their relative weights because people's intuitions are usually wrong about which one dominates.

The two lines to watch are the last two, because they are the ones that grow without anyone deciding that they should. A single unlucky command whose output runs to thousands of lines, a search that returned forty files, a stack trace pasted in full: each is a permanent deduction from the budget for the remainder of the session. This is the practical argument for tools that return summaries rather than dumps, and for the habit of piping noisy commands through something that trims them before the agent ever sees the output.

Altitude: the Goldilocks problem

Anthropic frames instruction-writing as a problem of altitude, and it is the most useful single idea for anyone writing a CLAUDE.md. Fly too low and you hardcode brittle logic: a long if-this-then-that script that covers the cases you thought of and breaks on the first case you did not. Fly too high and you write vague encouragement, "write clean code", "follow best practices", which gives the model no concrete signal at all and consumes budget doing it. The target is the middle: specific enough to guide behaviour, general enough to function as a heuristic in situations you never anticipated.

The test for altitude is whether a competent new colleague could act on the instruction without asking a follow-up question, and whether it would still make sense in a part of the codebase you were not thinking about when you wrote it. "Use double quotes for strings" passes both. "Write good docstrings" fails the first. "In src/pricing/loan.py, always call _validate_term() before _discount()" passes the first and fails the second, which means it belongs in the code as an assertion rather than in an instruction file.

Context rot. The observed decline in a model's ability to recall any given item from its context as the total number of tokens in that context grows. It follows from quadratic attention and from training distributions weighted towards shorter sequences, so it is a property of the architecture rather than a defect to be waited out.
Attention budget. The finite pool of effective attention available across a context window. Spending it on low-signal tokens does not merely waste money; it measurably degrades recall of the high-signal ones.
Just-in-time retrieval. Holding lightweight identifiers (file paths, queries, links) in context and loading the underlying content only at the moment it is needed. The opposite of preloading everything that might conceivably be relevant.

Two retrieval strategies, and the hybrid that wins

There are two ways to get information into a window. Upfront loading puts everything the agent might need into context before it starts: whole files, a full directory listing, an entire schema. It is simple, and it is correct when the material is small and certainly needed. Just-in-time retrieval keeps only references in context, file paths and search commands, and lets the agent pull content in as it discovers it needs it. It scales, because the window only ever holds what turned out to matter, and it mirrors what a human does when they navigate a codebase with grep rather than by reading it end to end.

Claude Code is deliberately a hybrid, and understanding the split explains a great deal about how to configure it. Instruction files are loaded upfront, because they apply to everything and are meant to be small. Everything else is just-in-time: the agent has glob, grep, and file reading, and uses them to discover the codebase as it goes. The design implication is direct. Your instruction files should be small and general, because they are paying rent on every turn. Your repository should be navigable, because navigability is what makes just-in-time retrieval work: clear names, predictable layout, and a structural map that lets an agent find the right file in one search instead of five.

Step 4

The detail

Three techniques for work that outlasts a window

Any task worth using an agent for will eventually exceed one context window. Anthropic identifies three techniques for surviving that, and they compose rather than compete.

Compaction takes a conversation approaching the limit, summarises it, and restarts the window from the summary. The engineering question is what the summary keeps. The right answer preserves architectural decisions, unresolved problems, and constraints that were established by argument, and discards tool outputs, superseded drafts, and file contents that can be re-read on demand. A compaction that keeps the last twenty messages verbatim and drops the decision made at message four has optimised the wrong quantity. When a harness compacts automatically, the useful habit is to state durable constraints explicitly at the point of compaction rather than trusting them to survive.

Structured note-taking has the agent write to a file outside the window and read it back later. This is the cheapest form of persistent memory there is: a progress file, a decision log, a plan on disk. The pattern's virtue is that it inverts the persistence problem. Rather than trying to keep everything in a window that forgets, you keep almost nothing in the window and one path to a file that does not. The plan file this course was written from is exactly this pattern; so is the memory directory that survives between sessions.

Subagent architectures delegate a bounded piece of work to a separate agent with its own clean window, which returns a distilled summary, typically a thousand or two thousand tokens, rather than everything it read. A search across forty files might consume a hundred thousand tokens in the doing and return two hundred words of conclusion. The parent window pays only for the conclusion. This is why "explore the codebase and tell me where X is handled" is a natural subagent task and "write the patch" usually is not: the first has a large read-to-conclusion ratio and the second does not.

Progressive disclosure, and why skills are folders

The same principle explains the design of Agent Skills, which Lecture 8 covers properly. A skill is a folder containing a SKILL.md plus whatever scripts and reference files it needs. Only the name and the one-line description sit in context by default; the body loads when the agent judges the skill relevant, and the deeper reference files load only if the body points at them. This is progressive disclosure: three tiers, each paid for only when reached. It is the reason a machine can have fifty skills installed without fifty skills' worth of tokens in every window, and it is a pattern worth copying in your own documentation. A directory of one-line summaries with paths beneath it will beat a single long document, because the agent can pay for the paragraph it needs rather than the chapter it does not.

Practical habits

Six habits do most of the work, and none of them require any configuration.

Start a fresh session for a new task rather than continuing a stale one, because a session carrying an hour of unrelated history begins already impaired. Point at files by path instead of pasting them, and let the agent read the parts it needs. Constrain noisy commands before their output reaches the window, so pytest -q --tb=line rather than a full verbose run, and git log --oneline -20 rather than the whole history. Ask for the conclusion rather than the workings when the workings are not the point. Put durable facts into files, not into chat messages, because chat is the only part of the window guaranteed not to survive. And when a session has gone vague, reset it and re-brief from the notes rather than repeating yourself, because repetition inside a rotting window is the least effective intervention available.

Common pitfall Connecting every available MCP server "so it's there if I need it" is the most common self-inflicted context wound, and the most invisible, because tool schemas are charged on every turn before a single tool is called. Twenty servers can occupy a substantial share of the window permanently, in exchange for capability you use once a week. The remedies are to connect servers per project rather than globally, and to prefer harnesses that defer tool schemas until a tool is actually needed. If a tool has not been called in your last ten sessions, it is not free to keep connected; it is charged rent on every turn of every one of them.

Worked example: an instruction file as a context artefact

Worked example: the coverage map in this repository's CLAUDE.md

The root CLAUDE.md in this repository contains a table mapping each F107 syllabus area to the folders that cover it, with a status of present, partial, or absent for each. It is a few hundred tokens, it is loaded on every turn of every session, and it is worth examining as a piece of context engineering rather than as documentation.

What it replaces. Without it, an agent asked to file a note on liquidity coverage must discover the layout: list directories, guess at conventions, read three or four index files, and infer where the material belongs. That is five or six tool calls, several thousand tokens of directory listings and file heads, and a decent chance of a wrong guess that only surfaces at review. With it, the routing decision is a lookup.

Why the altitude is right. The table gives coverage status and folder paths, and stops. It does not attempt to describe the contents of each file, which would be both enormous and immediately stale. It gives the agent enough to navigate, and delegates everything below that to just-in-time retrieval. That split, a map upfront and the territory on demand, is the hybrid pattern applied at the level of a single artefact.

What it costs, honestly. It is paid for on every turn, including the many turns that have nothing to do with routing. It is also the part of the file most likely to drift out of date, because folders change and tables do not update themselves. The break-even is easy to state: an upfront artefact earns its rent when the sessions that use it outnumber the sessions that do not, and when the discovery it replaces would have cost more than the artefact costs to carry. A routing map in a repository with twenty top-level areas clears that bar comfortably. The same map in a five-file project would not.

The generalisation. Before adding anything to an instruction file, ask what discovery it saves and how often that discovery would otherwise happen. If the answer is "rarely", the material belongs in a file the agent can find, not in the context it carries everywhere.

Step 5

Synthesis and what's next

The context window is the program, and it is both finite and lossy, so curation beats accumulation at every scale. Five categories compete for the budget, and the two that grow on their own, conversation and retrieved content, are the ones to watch. Instructions should be written at the middle altitude: concrete enough to act on, general enough to survive a situation you did not foresee. Retrieval should be a hybrid, with a small navigable map loaded upfront and the territory pulled in just in time. When work outgrows a window, compaction, note-taking, and subagents extend it in different directions, and they combine well.

The wider point is that context engineering is the discipline that makes every later technique legible. Skills, hooks, subagents, MCP servers, and memory files are all, underneath, answers to the same question: what should be in the window right now, and what should merely be reachable from it? That question is why the next lecture opens up the harness itself. Having established what the agent can see, the natural next question is what it can do, and who gets to decide.
