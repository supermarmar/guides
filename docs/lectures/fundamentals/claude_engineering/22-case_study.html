Lectures / Claude engineering

Case study: this repository, and where the practice is heading

A course about verification that ended without examining its own production would be an odd artefact. This lecture audits the building of the previous twenty-one against the standards they set, finds the gaps, and then separates what is likely to still be true in three years from what is already going stale.

Lecture 22 of 22 Reading time, 45 minutes Part V: judgement and governance
Step 1

The 30-second version

This course was built inside the system it describes: a git repository that is simultaneously an Obsidian vault, an exam-preparation knowledge base, and a lecture source tree, on a machine with a layered instruction stack, a permission configuration, two personal skills, and eighteen connected MCP servers. That made the worked examples honest and it made the failures visible, which is the only reason this retrospective is worth writing.

The verdict is mixed in a specific and instructive way. The steering layer worked well: research before writing, a plan argued over before execution, conventions read from an existing file rather than invented. The verification layer worked only at the mechanical level: paths, classes, tags, and prose rules were checked thoroughly, and nothing checked whether the content was true. The gap between those two sentences is the single most useful thing in this lecture, because it is the gap that every team building with these tools currently has.

The forward-looking half separates two categories that are constantly conflated. Some of this course is about a product and will age in months: mode names, flag spellings, event names, price tables. Some is about a constraint and will outlive several product generations: finite attention, plausibility decoupled from correctness, the instruction-versus-enforcement distinction, and the fact that a system cannot audit its own agreement. Knowing which is which is what makes any of this durable.

Feynman test For any practice in this course, ask what it is compensating for. If the answer names a model limitation, it will erode as models improve. If it names a structural property, a finite window, a shared channel for data and instructions, an optimiser pointed at a proxy, it will not, because better models make those problems arrive faster rather than more slowly.
What's beyond the syllabus The most reliable prediction about a technology is that its interfaces change and its constraints do not. The specific commands in Kernighan and Pike's The Unix Programming Environment are largely obsolete; the argument for composable single-purpose tools reads as though written last year. Every technical book that survived did so by being about a constraint rather than a product. This course has tried to sit on that side of the line and will only partly have succeeded, which is worth knowing when you read it in a year and find the flag names wrong.
Step 2

Why this matters

The first reason is that a retrospective on real work beats a summary. Restating twenty-one lectures would produce agreement and no learning. Auditing what actually happened produces findings, and the findings are more transferable than the principles, because everyone's practice fails in roughly the same places.

The second reason is that this course is itself evidence about the thing it describes. It was produced by the workflow it recommends, so its quality is a data point about that workflow, and pretending otherwise would be the sycophancy failure from Lecture 14 applied to a whole document. The honest reading is that the process produced something structurally sound with an unverified semantic layer, and that is exactly what the process was configured to produce.

The third reason is that anyone adopting this needs to know what will still be true when they finish reading. A course that presents version-volatile detail and durable principle in the same register leaves the reader unable to tell which parts to trust in six months, and that is a failure of the writing rather than of the reader.

Step 3

The mental model

The audit, against the course's own standards

What worked, and why

Research before generation. The first action was reading an existing lecture and the stylesheet rather than inventing a format. That single decision is why every file renders: an agent generating markup from its own priors would have produced invented class names and pages that display as unstyled text, confidently. The cost was two file reads.

Documentation fetched rather than recalled. Permission mode names, hook event names, skill frontmatter fields, and model prices were all retrieved before being written about. Several would have been wrong from memory: the skill lifecycle rule, that an invoked body persists for the session, is not something a prior would reliably produce, and it is load-bearing in Lecture 8.

Real material as worked examples. Every example that carries weight came from measuring something: 566 lines of always-loaded instruction, fifteen dead allowlist entries, eighteen MCP servers of which fourteen are unauthenticated stubs, eight deny rules that cover local destruction and nothing else. Invented examples would have illustrated; measured ones found things nobody knew.

What did not, and why it is the same failure four times

No enforcement. The course argues in Lecture 9 that anything which must hold every time belongs in a hook. The build had no hooks. The house-style rules it wrote about were checked by a grep at the end rather than enforced at the point of writing.

No stop condition. Lecture 19 lists four things an unattended run needs, and this run had one of them. Continuation was decided each turn by the process doing the writing.

Checks written after the artefact. Lecture 11 argues that a test never observed to fail is not yet a test. The four verification scripts were written after the first four lectures and passed on first run, which is the configuration that lecture warns about.

No independent reviewer. Lecture 12 argues that the fresh-context reviewer is the highest-leverage addition available, and Lecture 14 argues that separation is the only reliable defence against a system grading its own output. Neither was used at any point.

These are one failure wearing four hats. Every one is a piece of setup that would have cost a few minutes and was skipped because the work appeared to be going well. That is the specific mechanism, and it is worth naming precisely: the perceived quality of the output is what suppresses the impulse to verify it, which is exactly backwards, and exactly what fluency decoupling predicts.

Setup asymmetry. Steering costs thought and pays immediately; enforcement costs setup and pays only when something goes wrong. Practitioners reliably do the first and skip the second, which is why mature practices are strong on prompting and weak on gates.
Step 4

The detail

What ages fast

Named modes and their spellings. Hook event names. Skill frontmatter fields. Flags. Price tables and model names, which Lecture 4 already flagged as the most volatile content in the course. Anything counted, including the eighteen servers and the 566 lines, since those are true of one machine on one day. Treat all of it as illustrative of a shape rather than as reference, and check the documentation when it matters.

What does not

Finite attention. Larger windows change the threshold and not the principle; curation beats accumulation at every scale, because the model must still locate signal among what you supplied.

Plausibility decoupled from correctness. This gets worse as models improve, not better. A more capable model produces output that is harder to distinguish from correct output, which raises rather than lowers the value of a procedure that does not depend on how the output reads.

Instruction versus enforcement. A request is a request whatever is receiving it. No improvement in compliance turns an advisory mechanism into a guarantee, and anything that must hold every time will always need a gate.

The optimiser and the proxy. Point anything capable at a measurable target and the measure degrades. Assertion weakening, reward hacking, and metric gaming are one phenomenon, and it is a property of optimisation rather than of language models.

Sycophancy needs a target. As long as training incorporates human preference, agreement will be selected for, and a system cannot audit its own agreement because compliance and correctness produce identical text. Separation remains the only reliable answer.

Irreversibility. A sent message has arrived. No model capability changes this, which is why the reversibility sort from Lecture 18 will outlast every product decision in this course.

What is genuinely uncertain

Three things this course has taken positions on that could reasonably go the other way. Whether the CLI remains the centre of gravity, or whether desktop, web, and multi-agent surfaces displace it, in which case Part IV ages faster than Part II. Whether review scales, since the bottleneck argument in Lecture 21 assumes human review remains necessary and a sufficiently trustworthy automated reviewer would change the economics entirely. And whether the practice consolidates into something teachable in two pages, as Lecture 21's own worked example suspected, in which case the right artefact was never a course.

Common pitfall Reading a retrospective as a confession and stopping there. Naming failures is easy and is not the same as fixing them, and a document that catalogues its own gaps while leaving them open has bought the appearance of rigour at no cost. The four failures above are each an afternoon of work: a hook enforcing house style, a Stop hook running the checks, a fixture the checks are tested against, and a claim-checking subagent. If they are still absent when the next thing gets built here, this section was decoration.

Worked example: what a second attempt would change

Worked example: the same course, built properly

Not a hypothetical improvement list but the specific configuration this build should have had, in the order it would have been set up.

Before writing anything. A check-lecture.sh covering the four mechanical properties, run against a deliberately broken fixture, with each check observed to fail with the message expected. Fifteen minutes, and it converts the verification report from an assertion into evidence.

Wired into the loop. That script as a Stop hook, so no turn could end with a failing check, plus a PostToolUse hook on writes running the house-style grep. Lecture 9's argument applied to Lecture 9's own production.

Scope and budget. An --allowedTools list permitting writes only under the course directory, and an iteration cap so the loop terminated on its own. Two lines that would have made the run genuinely unattended rather than nominally so.

The layer that was missing entirely. A claim-checking subagent per lecture: given the lecture and the fetched documentation, list every factual claim and mark it supported, contradicted, or not addressed. High read-to-conclusion ratio, fresh context, no commitment to the text. This is the single largest gap, and it is the one the course's own Lecture 12 predicted would be missing.

What it would have cost. Perhaps an hour, against a build of several. And the honest reason it did not happen is the one in the diagram: setup pays only when something goes wrong, the output looked good, and looking good is exactly what this course spends twenty-one lectures explaining you cannot use as a signal. The failure was not ignorance of the principle. It was writing the principle down while not applying it, which is the most common way good practice fails and the reason this lecture exists.

Step 5

Synthesis and what's next

Built inside the system it describes, this course got the steering right and the enforcement wrong, in a pattern that is not accidental: thought-shaped practices get adopted and setup-shaped ones get skipped, and the better the output looks the more thoroughly they get skipped. The durable content is about constraints rather than products: finite attention, plausibility decoupled from correctness, advisory versus enforced, optimisers and proxies, sycophancy needing a target, and irreversibility. The volatile content is every name, flag, and number, and it should be checked rather than trusted.

If the whole course reduces to one sentence, it is this: generation became cheap and verification did not, so every worthwhile technique is a way of making verification cheaper or earlier. Tests, plans, hooks, subagents, fresh-context reviewers, deny rules, and the reversibility sort are all that idea in different clothes. The practice will keep changing shape and that constraint will not, because it is arithmetic rather than a limitation anyone is working to remove.

The next thing to do is not to read more. It is to pick the one gap in your own setup that this course made visible, and close it before the appeal wears off. For the machine this was written on, that is four lines of permission configuration and one hook, and it will take less time than reading the lecture that argued for them.
