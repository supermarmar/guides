Skills: when a folder of instructions beats a prompt

A skill is a procedure that lives in a file and loads only when it is needed. That last clause is the whole design: the description is always in context, the body is not, and the difference is what lets a machine carry fifty procedures without carrying fifty procedures' worth of tokens.

Lecture 8 of 22 Reading time, 50 minutes Part II: steering the agent
Step 1

The 30-second version

A skill is a directory containing a SKILL.md with YAML frontmatter and a markdown body, plus any supporting files it needs. The frontmatter's description sits in context from the start of the session so the agent knows the skill exists and when it applies. The body loads only when the skill is invoked, either by you typing /name or by the agent judging it relevant. This is progressive disclosure, and it is the mechanism that makes a large library of procedures affordable.

The documented trigger for creating one is a good test: when you keep pasting the same instructions, checklist, or multi-step procedure into chat, or when a section of CLAUDE.md has grown into a procedure rather than a fact. Both symptoms point at the same thing. The material is real, it is not needed every turn, and it is currently either being retyped or paying rent it does not earn. A skill is where it belongs.

One property matters more than any other and is routinely missed: once a skill is invoked, its rendered content stays in context for the rest of the session. Skills are not paid for per use; they are paid for once and then carried. That reframes the design constraint completely. The body is not a document you visit, it is a document you adopt, and every line in it becomes a recurring cost from the moment of invocation. The same conciseness test that applies to CLAUDE.md applies here, just deferred.

Feynman test Three tiers, three costs. The description is cheap and always present, so it must be excellent at answering "does this apply?". The body is expensive from the moment it loads and permanent thereafter, so it must be short and prescriptive. Supporting files are free until read, so that is where anything long belongs. Put material in the wrong tier and you either pay for what you do not use or fail to be found when you are needed.
What's beyond the syllabus Progressive disclosure is an old interface principle, from Nielsen's usability work and before that from technical writing: show the summary, let the reader descend. What is new is that the reader is a system with a hard budget and a documented recall decay, which turns a courtesy into an architecture. Notice also that skills follow an open standard rather than a vendor format, which changes what you are writing when you author one. A well-written skill is a portable artefact describing how your team does something, and that is a more durable thing to own than a configuration file for one tool.
Step 2

Why this matters

The first reason is that it resolves the tension Lecture 5 left open. Instruction files decay because people put procedures in them, and procedures are long, conditional, and relevant to a small fraction of sessions. There was previously nowhere else to put them. Skills are that place, and moving procedural content out of CLAUDE.md is usually the single largest available reduction in always-loaded context.

The second reason is that a skill is executable institutional knowledge. The deployment checklist that lives in one person's head, the review process nobody wrote down, the eight steps for cutting a release: as a skill, each becomes something the agent performs consistently rather than something a human remembers imperfectly. It is checked into the repository, reviewable, and versioned, which is more than can be said for the wiki page it replaces.

The third reason is that skills are where the model's own judgement gets to participate in retrieval. You do not have to know that a procedure applies; the agent reads the descriptions and decides. That is a genuine capability, and it fails in a specific and diagnosable way when the description is written for a human index rather than for a matching decision. Most skill problems are description problems, which is why the description gets a section of its own below.

Step 3

The mental model

Three tiers

Where skills live

ScopePathApplies to
EnterpriseManaged settings locationEveryone in the organisation
Personal~/.claude/skills/<name>/SKILL.mdYou, in every project
Project.claude/skills/<name>/SKILL.mdThis repository, shared via git
Plugin<plugin>/skills/<name>/SKILL.mdWherever the plugin is enabled

On a name collision, enterprise beats personal beats project, and any of them overrides a bundled skill of the same name, which is how you replace a built-in with your own. Plugin skills are namespaced as plugin:skill and so cannot collide. Skills also load from nested .claude/skills/ directories below the working directory, appearing under a directory-qualified name such as apps/web:deploy, which lets a monorepo package carry procedures that apply only when working inside it.

The frontmatter that matters

The field list is long; six fields account for nearly all practical use.

FieldWhat it does
descriptionWhat the skill does and when to use it. The matching signal. Put the key use case first
disable-model-invocationtrue stops the agent triggering it automatically. For side-effectful workflows you want to fire yourself
allowed-toolsTools pre-approved for the turn that invokes the skill. Clears on your next message
pathsGlobs limiting automatic activation to sessions touching matching files
context: forkRuns the skill in its own subagent context rather than inline
model, effortOverride the model or effort level while the skill is active

Two of these deserve emphasis. disable-model-invocation: true is the right default for anything with side effects, because a deployment skill that the model may invoke on its own judgement is a deployment that can happen without you asking. And context: fork is the answer to the lifecycle problem: a forked skill runs in a separate context and returns a result, so its body never enters your window at all, which makes it the correct choice for long procedures whose output you want but whose steps you do not need to carry.

Progressive disclosure. Loading a description always, a body on invocation, and reference material only on demand. The pattern that lets a skill library scale without its token cost scaling with it.
Skill lifecycle. Invoked content enters the conversation once and persists for the session. Re-invoking with identical content adds a note rather than a second copy; compaction re-attaches recent skills within a bounded budget, so older ones can be dropped entirely.
Step 4

The detail

Writing a description that gets matched

The description is doing retrieval, not documentation, and the two are written differently. It has to answer one question from the agent's position: given what the user just said, does this apply? That means naming the situation rather than the artefact.

# Weak: describes what it is
description: Deployment documentation

# Better: describes what it does
description: Deploys the application to production

# Best: names the situations that should trigger it
description: Use when deploying to production, cutting a release, or promoting
  a build from staging. Covers the pre-flight checks, the migration order, and
  the rollback procedure.

Two documented constraints shape this. The combined description text is truncated at 1,536 characters in the skill listing, so the key use case must come first or it may not survive. And the two failure modes are opposite and both diagnosable: a skill that never triggers has a description that does not name the user's actual words, while a skill that triggers too often has one that is too broad. Both are fixed in the same place, and neither is fixed by editing the body.

Keeping the body short, and where the rest goes

Because the body persists for the session, length is a recurring cost rather than a one-off. The documented guidance is to state what to do rather than narrating how or why. Rationale is for humans reading the file; the agent needs the steps.

Anything long goes into supporting files that the body references by path. A reference table of forty error codes, a worked example that runs to two pages, a script the procedure invokes: all of these belong beside the SKILL.md rather than inside it. The body then says "for the full error mapping see references/errors.md", and that file costs nothing until the situation arises. This is the same map-and-territory split from Lecture 2, applied one level down.

Choosing between a skill, a rule, and a hook

UseWhenCost profileEnforcement
CLAUDE.mdA fact true in every session in scopeEvery turn, foreverAdvisory
Path-scoped ruleA fact true for part of the codebaseEvery turn once matchedAdvisory
SkillA procedure, invoked sometimesDescription always, body once invokedAdvisory
HookSomething that must happen every timeNone in contextEnforced

The row people misuse is the third. A skill is not a way to make something happen reliably; the agent still has to decide to invoke it, and the documentation is explicit that if a skill seems to stop influencing behaviour, the content is usually still present and the model is simply choosing otherwise. If reliability is the requirement, the answer is the fourth row, which is the next lecture.

Common pitfall Invoking a large skill early in a session for a small piece of information costs you that skill's entire body for the remainder of the session. Because the content persists, a reference-heavy skill consulted once at turn three is still occupying the window at turn sixty, competing with everything since. Where you only need a fact, read the underlying file directly; where you need the procedure, invoke the skill; and where the procedure is long but its output is small, put context: fork in the frontmatter so the body runs elsewhere and only the conclusion comes back.

Worked example: two skills on this machine, and one loaded in this session

Worked example: anti-sycophancy, save-memory, and the cost of a large skill

This machine carries two personal skills, and this session invoked a third that ships with the tool. All three illustrate different points.

save-memory is the pattern working correctly. Its description names the triggering situations in the user's own likely words: "asks to save, remember, capture, record, or persist takeaways, lessons, decisions, or session findings". That is a retrieval description rather than a documentation one, and it will match. The content is genuinely a procedure, with a file format, a directory convention, and curation rules, so it is the right kind of material for a skill rather than a rule. And it is invoked rarely, so the deferred cost is the correct trade.

anti-sycophancy shows the boundary problem. The same content exists twice: as a 51-line always-loaded rule file and as a skill. The rule file says the split is deliberate, with the skill carrying the worked examples. But as Lecture 5 argued, the division sits in the wrong place. The skill's own description already identifies exactly when the behaviour is load-bearing, "when the user shares a decision, plan, opinion, or piece of their own work" — which is precisely the condition under which the rule's forty lines of detail matter. Almost all of the rule could move into the skill and be paid for only when the situation arises.

The claude-api skill shows the cost side honestly. Writing Lecture 4 required accurate model names and prices, so this session invoked the bundled claude-api skill. It returned an enormous body: the model table, per-language SDK documentation for seven languages, migration guides, caching guidance, managed-agents reference. It answered the question precisely, and under the lifecycle rule every line of it has been resident in this session's context ever since, through six subsequent lectures that have nothing to do with the API.

What that costs, and what would have been better. This is not a criticism of the skill, which is well built and whose tiering is mostly right. It is an illustration of the pitfall above: the need was one table of four model prices, and the invocation delivered a reference manual. Reading the model table directly, or a version of the skill with context: fork so the lookup happened elsewhere and returned four rows, would have cost a small fraction of the same session. The general rule is worth stating plainly: match the granularity of the invocation to the granularity of the need, because with skills the invocation is the commitment, and there is no way to un-invoke one.

Step 5

Synthesis and what's next

A skill is a folder with a SKILL.md, disclosed in three tiers: a description always in context, a body that loads on invocation and then persists for the session, and supporting files read only on demand. Create one when a procedure is being retyped or when a CLAUDE.md section has stopped being a fact. Write the description to answer a matching question rather than to document, and keep the body prescriptive because its cost recurs. Put length in supporting files. Use disable-model-invocation for anything with side effects and context: fork when the procedure is long but the answer is short. And remember what a skill is not: it is advisory, so it cannot make anything reliable.

Which is the seam this part of the course has been running along since Lecture 3. Instruction files, prompts, plans, and skills are all ways of asking well, and asking well is most of the practice. But some requirements are not requests: the linter that must run, the secret that must never be read, the test that must pass before a turn can end. The next lecture crosses to the other side of the line and covers the mechanisms the model does not get a vote on.
