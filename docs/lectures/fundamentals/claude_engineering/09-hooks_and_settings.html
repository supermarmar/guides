Slash commands, hooks, and settings: automation the model cannot skip

Everything so far has been a request. A hook is not. It is a shell command the harness runs at a fixed point in the lifecycle, and it fires whether or not the model agrees, remembers, or has room in its context to have noticed the instruction.

Lecture 9 of 22 Reading time, 50 minutes Part II: steering the agent
Step 1

The 30-second version

A hook is a handler configured in settings.json under a named lifecycle event. When the event fires, the harness runs the handler, and for the blocking events the handler's exit code or JSON output decides whether the action proceeds. The documented distinction is the whole point: instruction files are advisory, hooks are deterministic and guarantee the action happens. If a requirement must hold every time with no exceptions, it belongs here and nowhere else.

The event surface is large, and the shape is more useful than the catalogue. Events cluster around the agentic loop (PreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest), the turn (UserPromptSubmit, Stop), the session (SessionStart, SessionEnd), subagents (SubagentStart, SubagentStop), and context (PreCompact, PostCompact). Four of them cover the overwhelming majority of real use: run something before a tool call, run something after a file changes, inject context when a session starts, and refuse to let a turn end until a check passes.

The blocking mechanism is simple enough to memorise. A command hook exiting 2 blocks the action and feeds its standard error back to the agent as the reason; any other non-zero exit is a non-blocking error; zero is success. For finer control, a hook can emit JSON, and for PreToolUse the field that matters is hookSpecificOutput.permissionDecision, set to allow, deny, or ask. That single field turns a shell script into a policy engine sitting in front of every tool call.

Feynman test Ask of any requirement: what happens if the model simply does not do it? If the answer is "a slightly worse result", an instruction is fine. If the answer is "a secret leaks", "the build breaks silently", or "we ship untested code", then you have written a hope rather than a control, and a hope in an instruction file will eventually be crowded out by the sixty lines above it.
What's beyond the syllabus A hook is a reference monitor: a component that mediates every access, cannot be bypassed, and is small enough to be verified. That is Anderson's 1972 formulation, and it is the design pattern underneath every operating system kernel and every access-control system since. Its relevance here is exact. You cannot verify a language model, but you can verify a forty-line shell script, and placing the script between the model and the file system gives you a property you can actually reason about. This is also why the argument that better models will remove the need for hooks is confused: hooks are not compensating for the model's unreliability, they are supplying a guarantee that no amount of reliability provides.
Step 2

Why this matters

The first reason is that it is the only honest answer to a class of requirement everyone has and most people mis-file. Secrets that must never be read, formatters that must always run, tests that must pass before a claim of completion: each of these gets written into a CLAUDE.md, obeyed for a while, and then quietly dropped once the file grows or the context fills. The failure looks like the model becoming careless. It is actually a design error, made at the moment the requirement was written as a sentence rather than as a script.

The second reason is that hooks cost nothing in context. An instruction competes for the attention budget on every turn; a hook lives in a configuration file and consumes no tokens at all. For any requirement that can be expressed as a check, moving it from the instruction file to a hook is strictly better on both axes: it becomes reliable and it stops crowding out the instructions that cannot be automated. That is a rare trade with no downside worth naming.

The third reason is that hooks are the mechanism by which a team's standards stop depending on who is at the keyboard. A project-level settings.json checked into git applies to everyone who clones the repository, including the colleague who has never read the contributing guide and the agent running in CI at three in the morning. That is a different kind of guarantee from a documented convention, and it is the difference between a standard and an aspiration.

Step 3

The mental model

Where hooks sit in the loop

The configuration shape

Hooks live under a hooks object in settings.json, keyed by event name. Each entry has an optional matcher selecting which tools it applies to, and a list of handlers.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "./.claude/scripts/check-house-style.sh",
            "timeout": 30,
            "statusMessage": "Checking house style..."
          }
        ]
      }
    ]
  }
}

The matcher is an exact string when it contains only ordinary characters, and an unanchored regular expression otherwise, which is why Edit|Write matches both tools. MCP tools follow the pattern mcp__<server>__<tool>, so mcp__github__.* matches everything from one server. Beyond command handlers, a hook can be an HTTP call, an MCP tool invocation, a prompt sent to a fast model, or a full subagent, which is a wider range than most people realise: a policy question too fuzzy for a regular expression can be answered by a small model rather than a script.

How a hook blocks

MechanismEffect
Exit 0Success; any JSON on stdout is processed
Exit 2Blocks. Standard error is fed to the agent as the reason
Other non-zeroNon-blocking error; execution continues, stderr is logged
"decision": "block" with "reason"Blocks on the events that support it
hookSpecificOutput.permissionDecisionOn PreToolUse: allow, deny, ask, or defer
hookSpecificOutput.additionalContextInjects text into the agent's context rather than blocking

The detail that makes hooks useful rather than merely obstructive is that the block carries a message. Exiting 2 with a diagnostic on standard error does not just refuse the action; it tells the agent why, in terms it can act on. A hook that rejects a write with "line 42 contains an em dash, which house style forbids" produces a corrected write on the next turn. One that exits silently produces confusion and a retry of the same thing.

Hook. A handler run by the harness at a named lifecycle event, configured in settings.json. Deterministic, invisible to the context budget, and on blocking events able to refuse an action outright.
Blocking versus advisory event. Some events can stop what they observe (PreToolUse, PostToolUse, Stop, UserPromptSubmit); others can only observe and inject (SessionStart, PostCompact, Notification). Attaching a guarantee to a non-blocking event yields a log, not a control.
Step 4

The detail

Four hooks worth having almost everywhere

Format and lint after every edit. A PostToolUse hook matching Edit|Write that runs the project formatter removes an entire category of instruction from CLAUDE.md and an entire category of review comment from pull requests. It is the highest-value first hook for most repositories because the check is fast, the fix is mechanical, and the requirement is genuinely absolute.

Refuse to end the turn on a failing check. A Stop hook that runs the test suite and blocks while it fails converts "please run the tests" from a request into a gate. This is the mechanism behind the strongest row of Lecture 6's verification hierarchy, and it is what makes an unattended run trustworthy. The harness overrides the hook after eight consecutive blocks, which is the right design: a genuinely stuck loop terminates rather than spinning.

Guard the paths that must not be touched. A PreToolUse hook returning permissionDecision: "deny" for writes matching a pattern protects migration directories, generated files, and vendored code more reliably than a deny rule can when the condition is conditional rather than static. Where the rule is static, the deny list from Lecture 3 is simpler and should be preferred; hooks earn their place when the decision needs logic.

Inject state at session start. A SessionStart hook emitting additionalContext can supply the current branch, the open ticket, the last deploy, or anything else that is true now and false next week. This is strictly better than writing volatile facts into an instruction file, where they go stale silently and are re-sent forever.

Slash commands are skills now

One point of vocabulary that saves confusion. Custom slash commands have been merged into skills: a file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both produce /deploy and behave the same way. Existing command files keep working. What the skill form adds is a directory for supporting files, frontmatter to control invocation, and the ability for the agent to load it automatically. If you are writing a new one, write it as a skill; there is no reason left to prefer the older form.

Two cautions

A hook is arbitrary code running automatically on your machine, triggered by a model's actions. That is a meaningful trust boundary, and it is why hook configuration in a project's settings file sits behind a workspace trust dialog. Reviewing hooks in a repository you have just cloned is not paranoia; a PostToolUse handler is a shell command that runs every time a file changes.

The second caution is about latency. Every blocking hook sits in the critical path of the action it guards, and a slow one is felt on every single edit. A formatter that takes 200 milliseconds is invisible; a full test suite on PostToolUse makes the agent unusable. Put fast checks on the frequent events and slow checks on Stop, which fires once per turn rather than once per tool call.

Common pitfall Writing hooks that block without explaining why. A handler that exits 2 with nothing on standard error refuses the action and gives the agent nothing to act on, so it retries something similar, gets refused again, and burns turns until it gives up or the override fires. The block message is not a courtesy, it is the repair instruction. Every blocking hook should print what failed and, where possible, what would pass.

Worked example: making the writing rules real

Worked example: an advisory rule that a hook would enforce

This machine's global instruction file states two absolute writing rules: British English throughout, and no em or en dashes as punctuation. They appear in the organisation-level instructions, again in the user-level CLAUDE.md, and are referenced in the repository's own style guide. They are stated three times, which is itself a signal.

Why they get stated three times. Because they are advisory, and because the writing rules sit inside a 109-line file that sits inside a 566-line always-loaded stack. Lecture 5 covered what happens to a rule in that position: it is obeyed early in a session and progressively less reliably as the window fills, which is exactly the situation in which someone adds it to a second file. Repetition is the symptom of an enforcement problem being treated as an emphasis problem.

What the hook looks like. Both rules are mechanically checkable, which is the qualifying condition. A PostToolUse handler matching Edit|Write, greping the changed file for the two dash characters and for a short list of American spellings, exiting 2 with the offending line numbers when it finds any:

#!/usr/bin/env bash
# .claude/scripts/check-house-style.sh
f="$CLAUDE_TOOL_FILE_PATH"
case "$f" in *.html|*.md) ;; *) exit 0 ;; esac

bad=$(grep -nE '—|–' "$f")
sp=$(grep -nEi 'behavior|organiz|analyz|color|favor|defense' "$f")

if [ -n "$bad" ] || [ -n "$sp" ]; then
  echo "House style violations in $f:" >&2
  [ -n "$bad" ] && echo "Em/en dashes (use commas, colons, or parentheses):" >&2 && echo "$bad" >&2
  [ -n "$sp" ]  && echo "American spellings (British English required):"     >&2 && echo "$sp"  >&2
  exit 2
fi

What changes. The rules now hold on turn sixty as reliably as on turn three, because nothing about them depends on salience. They can be deleted from two of the three places they are currently written, reclaiming context. And the failure mode inverts usefully: instead of a violation shipping silently and being caught in review, the write is refused with the line number, and the agent fixes it before you ever see the file.

The honest limitation. A grep for six American spellings is not a British English checker. It catches the common cases and misses the rest, which means the advisory rule still has a job and cannot be deleted entirely, only shortened. This is the general shape of the trade and worth internalising: hooks convert the mechanically checkable fraction of a requirement into a guarantee and leave the judgement-dependent remainder where it was. That fraction is usually larger than people assume and never all of it, so the right move is almost always to enforce what you can and keep a much shorter instruction for the rest.

Step 5

Synthesis and what's next

Hooks are handlers run at named lifecycle events, configured in settings.json, deterministic where instructions are advisory, and free in context. Four events carry most of the value: PreToolUse to gate, PostToolUse to check what changed, Stop to refuse an incomplete turn, and SessionStart to inject volatile state. Blocking is exit code 2 with the reason on standard error, or JSON for finer control, and the reason matters as much as the block. Put fast checks on frequent events and slow ones on Stop. Review hooks in repositories you did not write, because they are arbitrary code triggered by a model.

The deeper point is the one this lecture shares with Lecture 3: you cannot verify a language model, but you can verify a small script, so the engineering move is to put the verifiable thing where the guarantee is needed. That completes the enforcement side of the steering layer. The last lecture of Part II turns to the remaining structural lever, which is not about constraining one agent but about running several: what subagents are actually for, why the answer is almost always context rather than speed, and when fanning out costs more than it saves.
