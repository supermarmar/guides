Prompting for code: the request, the constraint, the definition of done

A good coding prompt has three parts, and the one people omit is the third. Without a stated definition of done, the agent stops when the work looks finished, and "looks finished" is the only signal it has. You then become the verification loop, which is the bottleneck the whole practice exists to move.

Step 1

The 30-second version

Three parts make a coding prompt work. The request says what should change, scoped to specific files and a specific scenario. The constraints say what must not change, which is the half nobody writes and which is what stops a two-line fix becoming a hundred-line diff. The definition of done says what the agent should check before claiming success, and it is the part that decides whether you get a session you can walk away from or one you have to watch.

Anthropic's guidance puts the third part first among all recommendations, and the reasoning is exact: Claude stops when the work looks done, and without a check it can run, "looks done" is the only available signal. Give it something that produces a pass or fail, a test suite, a build exit code, a linter, a script that diffs output against a fixture, and the loop closes on itself. The agent works, runs the check, reads the result, and iterates without you. That single change converts you from the verifier into the reviewer, which is a different and much smaller job.

The rest is specificity, and the pattern is consistent across every documented example. "Add tests for foo.py" becomes "write a test for foo.py covering the edge case where the user is logged out, avoid mocks". "Fix the login bug" becomes "users report login fails after session timeout, check the token refresh in src/auth/, write a failing test that reproduces it, then fix it". The transformation in both cases is the same: name the file, name the scenario, name what finished looks like.

Feynman test Before sending a prompt, answer one question: what will the agent do to convince itself it is finished? If the answer is "re-read its own work", you have written a prompt that ends with your review. If the answer is "run the test I named", you have written one that ends with a signal. The difference is a single clause, and it is worth more than every other refinement combined.
What's beyond the syllabus There is an old idea underneath this. A specification precise enough to verify mechanically is, in the limit, a program; this is the observation behind formal methods, property-based testing, and Dijkstra's insistence that a program and its proof are written together. What has changed is who does the translation. You now write the specification and something else writes the implementation, which makes the quality of specifications the binding constraint on output in a way it has never quite been before. The engineers who get most from these tools are, almost without exception, the ones who were already good at saying precisely what they wanted.
Step 2

Why this matters

The first reason is that the cost of a vague prompt is not paid at prompt time. It is paid in the review, where you read a diff you cannot evaluate because you never said what right would look like, and then in the correction round, and often in a second correction round after that. The forty seconds spent naming the file and the acceptance test is the cheapest forty seconds in the whole workflow, and it is skipped because vagueness feels faster in the moment.

The second reason is that this is the lever that decides whether autonomy is safe. Lecture 1 argued that the autonomy slider should be set by how mechanical the verification is; this lecture is about manufacturing that mechanicalness. A task with a named check can run at high autonomy because the check does the supervising. The same task without one cannot, regardless of how capable the model is. Prompt quality and safe autonomy are the same variable seen from two sides.

The third reason is that vagueness has a legitimate use, and conflating the two wastes it. A deliberately open prompt, "what would you improve in this file?", surfaces things you would not have thought to ask about, and the documentation says so explicitly. That is exploration, and it is valuable. The failure is not vagueness; it is vagueness applied to execution, where you needed a specification and wrote an invitation instead.

Step 3

The mental model

The three parts

The request is the change you want, and its quality is measured in how few readings it admits. "Improve the error handling" admits dozens. "Every public function in this module should raise ValueError on malformed input rather than returning None" admits one. The mechanical fix is to name three things: which file or module, which scenario or input, and which observable behaviour should differ afterwards.

The constraints are the boundary, and they exist because of the scope-sprawl weakness from Lecture 1. Left unbounded, an agent asked to fix one function will reformat the file, add type hints to its neighbours, and improve three unrelated docstrings, each defensible and collectively turning a reviewable diff into an unreviewable one. Constraints are how you keep the diff the size of the change. They are also where you encode the things a newcomer would get wrong: no new dependencies, do not touch the migration files, keep the public signature.

The definition of done is the check, and it has a hierarchy of strength. Weakest is stating criteria in the prompt and asking the agent to run them. Stronger is a session-level goal condition that gets re-checked after every turn. Stronger still is a hook that runs your check as a script and blocks the turn from ending until it passes, which is enforcement rather than request. Strongest for judgement-shaped work is a second opinion: a verification subagent in a fresh context that never saw the reasoning which produced the change and therefore evaluates it on its own terms.

Four specificity moves

The documented before-and-after pairs reduce to four repeatable transformations, and they are worth learning as moves rather than as examples.

MoveBeforeAfter
Scope the task"add tests for foo.py"Name the file, the scenario, and the testing preference
Point at the source"why is this API so weird?""look through its git history and summarise how it came to be"
Reference the pattern"add a calendar widget"Name an existing widget as the model to follow
Describe the symptom"fix the login bug"Symptom, likely location, and what fixed looks like

Pointing at the source is the most underused of the four. An agent asked why a piece of code is strange will speculate plausibly from the code alone; the same agent told to read the git history will find the commit that explains it. The move generalises: whenever a question has a documentary answer somewhere in the repository, naming the document converts an inference into a lookup, and lookups do not hallucinate.

Definition of done. A check the agent can run and read the result of, stated in the prompt. Distinguished from an acceptance criterion you hold privately, which cannot close the loop because the agent cannot evaluate it.
Evidence over assertion. Asking for the test output, the command run, or the screenshot, rather than for the claim that it worked. Reviewing evidence is faster than re-running the verification yourself, and it works for sessions you were not watching.
Step 4

The detail

Getting context in without pasting it

Lecture 2 argued against pasting files. The practical alternatives are all cheaper. Referencing a file by path has the agent read it, and read only what it needs. Images can be pasted directly, which matters more than it sounds: a screenshot of a broken layout or a design to match communicates in one step what a paragraph of description communicates badly. URLs work for documentation, and frequently used domains can be allowlisted so they stop prompting. Data can be piped straight in from the shell. And the option people forget is to let the agent fetch its own context: telling it to go and find what it needs, rather than assembling a briefing yourself, is usually both faster and more accurate, because it retrieves what turned out to matter rather than what you predicted would.

Asking for the failing test first

One phrasing deserves singling out because it changes the character of a bug fix: write a failing test that reproduces the issue, then fix it. It appears in the documented symptom-description example and it is doing more work than it appears to.

Without it, the agent forms a hypothesis about the cause and writes a fix for that hypothesis. If the hypothesis is wrong, the fix is wrong, and you will not find out until later, because nothing in the loop tested the hypothesis independently. With it, the reproduction has to succeed before any fix is written, which means the hypothesis is confirmed before it is acted on. It also leaves behind a regression test, which is the thing you wanted anyway. The same instruction defends against the stopping-too-early failure from Lecture 1: an agent told only to make the tests pass may weaken an assertion, whereas one told to first write a test that fails for the right reason has committed to the failure being real.

The instruction that prevents sprawl

Scope discipline has to be asked for explicitly, because the model's default is to be helpful and helpfulness looks like improving what it passes. The instruction that works is concrete about what not to do:

Only make the change I described. Do not reformat surrounding code, do not add
type hints or docstrings to functions you did not change, and do not add error
handling for cases that cannot occur. If you notice something else worth fixing,
list it at the end instead of fixing it.

The last clause matters as much as the rest. Suppressing the observation entirely wastes it; the agent often is noticing something real. Redirecting it into a list at the end keeps the diff clean and keeps the finding, and it converts a review problem into a backlog item.

Correcting, and knowing when to stop correcting

Correct early. The documented pattern is a tight loop: interrupt as soon as the direction is wrong, because context is preserved and redirecting costs a sentence. Letting a wrong approach run to completion out of politeness costs the whole run.

Then the harder rule, which is a counting rule and therefore easy to follow: after two failed corrections on the same issue, stop correcting and start over. By the third attempt the context is full of failed approaches, and each one makes the next attempt worse rather than better, because the window now contains a record of things that did not work presented as things that were tried. Clearing and rewriting the initial prompt with what you learned beats a third correction almost every time. It feels like conceding. It is the cheapest move available, and the fact that it feels like conceding is exactly why people do not make it.

Common pitfall "Make the tests pass" and "fix the build" are the two most dangerous instructions in common use, because both name a signal rather than a state, and signals can be satisfied without the state being reached. A weakened assertion makes tests pass. A suppressed warning fixes a build. Neither is what you meant, and neither announces itself in the diff. The remedy is to name the invariant alongside the signal: "the build fails with this error, fix the root cause and do not suppress it", or "make the suite pass without weakening any existing assertion".

Worked example: two prompts for the same defect

Worked example: a PD model producing scores above one

The reported problem: a probability-of-default scoring function occasionally returns values greater than 1.0, which downstream code silently accepts and which shows up as impossible capital numbers three steps later.

The prompt most people write. "The PD scores are coming out above 1 sometimes, can you fix it?" The agent reads the scoring module, finds the most likely culprit, applies a clamp at the output, and reports that it has fixed the issue. It has. The scores are now all in range, the symptom is gone, and the underlying defect, a logistic transform applied twice on one code path, is still there and now permanently masked. Nothing about the diff announces this. It is four lines and it looks correct.

The prompt with all three parts. "Scores from score_pd() in src/pd/scoring.py sometimes exceed 1.0. Write a failing test that reproduces it before changing anything, then find the root cause. Constraints: do not clamp or otherwise bound the output, the function's signature must not change, and no new dependencies. Done means the new test passes, pytest -m "not slow" is green, and you can tell me which code path produced the out-of-range value."

What each clause bought. The reproduction requirement forced the defect to be located rather than hypothesised. Naming the file and function removed a search. The no-clamping constraint specifically forbade the plausible wrong fix, which was the entire risk in this task. The signature constraint kept the diff reviewable. And the last clause, asking which code path was responsible, is the evidence requirement: it cannot be satisfied by a fix that masks the symptom, because a clamp has no code path to name.

The general move. When you can predict the plausible wrong fix, forbid it by name. That single sentence is worth more than any amount of general instruction about quality, because it targets the specific failure this task invites rather than the failures tasks invite in general. Ask yourself, before sending: what is the cheap fix that would make the symptom go away without solving anything? Then rule it out.

Step 5

Synthesis and what's next

A coding prompt is a request, a set of constraints, and a definition of done, and the third is the one that decides whether you can walk away. Verification strength runs from a clause in the prompt through a session goal and a blocking hook to a fresh-context reviewer, and each step trades setup for attention. The four specificity moves, scope the task, point at the source, reference the pattern, describe the symptom, cover most of what separates a prompt that works from one that produces a diff you cannot evaluate. Ask for the failing test before the fix. Forbid the plausible wrong fix by name. Correct early, and after two failures clear and rewrite rather than correcting a third time.

The wider point is that the prompt is where the autonomy slider actually gets set, whatever you believe about it beforehand. A prompt with a machine-checkable definition of done can safely run unattended; the same task without one cannot, and no amount of trust in the model changes that. The next lecture takes the case where the specification is too large to fit in a prompt at all, and the discipline that handles it: separating research from planning from execution, so that the wrong understanding gets caught while it is still one sentence.
