Lectures / Claude engineering

Obsidian as the knowledge substrate

The best integration is the one you do not need. A vault is a folder of markdown files, which means an agent already has full read and write access to it using tools it was built with, no protocol, no server, no authentication, and no schema cost. That property is worth more than any feature.

Lecture 16 of 22 Reading time, 45 minutes Part IV: the wider stack
Step 1

The 30-second version

An Obsidian vault is a directory of plain markdown files plus a .obsidian folder of local configuration. There is no database and no proprietary format; the links between notes are text, the metadata is YAML frontmatter, and the whole thing is greppable. For an agent this is the ideal shape, because every tool it already has, read, write, glob, grep, works on it directly and at full fidelity.

Compare that with the alternative. A knowledge base behind an API requires a connector, which requires authentication, which costs schema on every turn, and which returns content already rendered and paginated by someone else's decisions. A vault costs nothing, returns exactly what is on disk, and can be searched with a regular expression. The lesson generalises past this one tool: plain files in version control are the most agent-legible storage there is, and choosing them is an architectural decision with compounding returns.

What the vault then needs is not integration but navigability, which is the just-in-time principle from Lecture 2 applied to a knowledge base. A vault the agent can traverse cheaply, clear names, index files, one idea per note, wikilinks that form a real graph, is a vault where the right three notes get read. A vault that is a flat directory of two thousand files with names like Untitled 47 is a vault where the agent reads everything or nothing.

Feynman test Ask how many tool calls it takes to get from "I need to know about X" to the note about X. If the answer is one grep, the vault is working. If the answer is a directory listing, then three speculative reads, then a search, the structure is doing no work and the agent is paying for the disorganisation on every question.
What's beyond the syllabus Obsidian's design descends from a specific tradition: Luhmann's Zettelkasten, atomic notes densely linked, where the value lives in the connections rather than the documents. That was always a claim about how human thought benefits from associative structure. It turns out to be an equally good claim about retrieval, for an unrelated reason: a dense link graph gives a reader who lands anywhere a path to everywhere nearby, which is exactly what an agent doing just-in-time retrieval needs. A format designed in the 1960s for index cards happens to be close to optimal for a machine that reads by following references.
Step 2

Why this matters

The first reason is that most of what an agent needs to know about your work is not in the code. Why an approach was rejected, what a regulator said, which assumption the model rests on, what was decided in a meeting: none of it is derivable from a repository, and all of it is the context whose absence Lecture 1 named as a structural weakness. A vault is where that lives, and if it lives somewhere the agent can read, the weakness is substantially closed.

The second reason is that the same substrate serves both readers. A note written for you is readable by the agent without translation, and a note the agent writes is readable by you without a viewer. That is not true of anything stored in a database or behind an API, where a second interface always stands between the content and one of its audiences. Removing that interface removes a whole class of friction and a whole class of drift.

The third reason is durability. Markdown in git will be readable in twenty years, by tools that do not exist yet, and it survives you changing editors, vendors, or agents. Every other option on this course's Part IV list is a bet on a company continuing to exist and continuing to offer an API. That is a reasonable bet for a workflow and a poor one for a decade of accumulated thinking.

Step 3

The mental model

Three layers of a navigable vault

Wikilinks as a machine-readable graph

The double-bracket link is the feature that most distinguishes this format, and its value to an agent is different from its value to you. To a reader it is a click. To an agent it is a declared relationship in plain text: greppable, countable, and traversable without parsing anything. Three consequences follow.

A link is a retrieval hint. An agent reading a note about IFRS 9 staging that encounters [[significant-increase-in-credit-risk]] knows both that a related note exists and what it is called, which is a stronger signal than a search would return. A link is also a completeness check: greping for links whose target does not exist finds the notes you meant to write, which is a to-do list generated from your own thinking. And link density is a health metric, since an orphan note with no inbound links is one that retrieval will never reach except by direct search.

Frontmatter as the queryable layer

YAML frontmatter gives each note structured fields alongside its prose, and the useful discipline is to keep it small and consistent. A handful of fields, a type, a status, a date, a few tags, turns the vault into something you can filter with a grep rather than read. The failure is elaborate schemas nobody maintains: six fields that are always filled in beat sixteen that are filled in for the first month.

Vault. A directory of markdown files treated as a single knowledge base, with links between notes expressed as text. Distinguished from a wiki or a document store by having no server: the files are the database.
Map note. An index for one area, listing its notes with a line of context each. The cheapest possible substitute for exploration, and the thing an agent should read before deciding what else to read.
Step 4

The detail

Writing notes an agent can use

Four properties matter, and they are the same properties that make notes useful to you six months later, which is the convenient part.

One idea per note. A note covering three topics is retrieved for all three and is mostly noise for each. Splitting is the single highest-return change to an existing vault.

A title that is a claim or a topic, not a label. lgd-downturn-adjustment.md is findable; notes-3.md is not, and neither is meeting.md. The filename is doing retrieval work before anything is opened.

A first paragraph that says what the note contains. An agent reading the first few lines of a candidate note is deciding whether to read the rest. Opening with context rather than with the summary wastes that decision point, which is the same argument as leading with the conclusion in ordinary prose.

Links out, deliberately. When you mention a concept that has its own note, link it. This is where the graph comes from, and it accrues only if it is a habit rather than an occasional tidying exercise.

The agent as a vault maintainer

Because the vault is plain files, the agent can maintain it as well as read it, and three jobs are worth handing over. Ingestion: turning a PDF, a transcript, or a long article into notes that follow your conventions, which is mechanical and tedious and exactly what should be delegated. Link repair: finding broken wikilinks, orphan notes, and duplicate coverage across notes that should be merged. Index maintenance: regenerating a map note from the folder it describes, which is the piece that always rots first because nobody wants to do it by hand.

What should not be delegated is deciding what a note says. A vault is a record of your thinking, and a vault of agent-written summaries is a record of nothing, pleasant to look at and useless to consult, because the value was in the act of working out what you thought.

The automatic memory directory is this pattern

Worth noticing because it is the same idea shipped as a feature. The per-project memory directory holds a MEMORY.md index whose first 200 lines are loaded every session, plus topic files that are read on demand. That is a map note plus a vault, with the loading behaviour made explicit, and the documented guidance for it, keep the index to one line per entry, move detail into topic files, merge or drop stale entries, is exactly the guidance this lecture gives for a map note. If you understand one, you understand the other.

Common pitfall Pointing an agent at a large vault with an open-ended question is the unscoped-investigation failure from Lecture 10 in a new setting, and it is worse here because a vault has no compiler and no tests to bound the search. "What do my notes say about credit risk?" against two thousand files reads until something stops it. Scope the question to a folder, ask it to consult the map note first, or delegate the survey to a subagent whose window absorbs the reading. The vault being cheap to read is what makes it dangerous to read carelessly.

Worked example: this repository is a vault

Worked example: a knowledge base that has been agent-native the whole time

The repository these lectures live in has a .obsidian directory at its root, a git history punctuated with commits titled vault backup: 2026-05-12 16:43:41, and wikilinks throughout the markdown under docs/wiki/. It has been an Obsidian vault and a git repository and a lecture source tree simultaneously, and no part of that arrangement required an integration.

What that has bought, mostly invisibly. Every session in this repository has had full read and write access to several hundred notes on banking, credit risk modelling, and regulation, at zero schema cost and with no authentication. The root CLAUDE.md's coverage map, dissected back in Lecture 2, is a map note in the sense used here: an index that turns a routing decision into a lookup. The structure is genuinely navigable, with folders that describe their contents and filenames like bcbs_239.md and ifrs9_staging.md that a glob can find.

Where it is weaker than it looks. The wiki is organised by folder hierarchy far more than by link graph. Wikilinks exist, but the dominant navigation structure is the tree, and a tree gives an agent one path to each note rather than many. The practical effect is that retrieval depends heavily on guessing the right folder, which is why the coverage map in CLAUDE.md is carrying so much weight: it is compensating for a graph that is thinner than the hierarchy.

The interesting tension. This vault has two consumers with different needs, and the course has been quietly favouring one. Obsidian's own strength is the graph, and the wiki's strength is the tree, and the reason is that the tree was designed for an exam syllabus while the graph would serve retrieval. Adding links from each A-IRB lifecycle stage to the IFRS 9 stage that mirrors it, or from each regulation note to the notes that apply it, would cost an afternoon and would give an agent landing anywhere a path to everything adjacent. That is the single change most likely to improve how well any future session answers a question here.

The general point. Being agent-legible is not a property you install, it is a property of how the content is arranged, and it is mostly free if you decide on it early. This repository got the format right by accident of choosing Obsidian, and got the structure half right by organising for a human curriculum. The half that is missing is the half that only matters when something reads by following references rather than by browsing.

Step 5

Synthesis and what's next

A vault is plain markdown on disk, which makes it the cheapest and most faithful substrate an agent can read: no protocol, no authentication, no schema cost, and no rendering between the file and the reader. What it needs instead of integration is navigability, in three layers: structure that a glob can narrow, map notes that replace exploration with a lookup, and a link graph that gives a path from anywhere to everything adjacent. Write one idea per note with a title that describes it and a first paragraph that says what it contains. Delegate ingestion, link repair, and index maintenance; do not delegate what the notes say. And scope questions against a large vault, because cheap to read is not the same as free.

The wider point is that storage format is an architectural decision with a long tail. Plain files in version control keep working when the tool changes, the vendor changes, or the agent changes, and every layer between the content and the reader is a cost paid forever. The next lecture is about the case where that cost is worth paying, because some things need to be seen by people who will never clone your repository.
