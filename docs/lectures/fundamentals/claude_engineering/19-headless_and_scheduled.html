Headless and scheduled: CI, cron, and background agents

Every technique so far has assumed someone was there to answer a prompt. Remove that assumption and two things must be settled in advance instead of in the moment: what the agent is allowed to do, and what counts as done. Neither can be improvised at three in the morning.

Lecture 19 of 22 Reading time, 45 minutes Part IV: the wider stack
Step 1

The 30-second version

Non-interactive mode is claude -p "your prompt". It runs once, prints a result, and exits, with output available as plain text, a single JSON object, or a stream of JSON lines for programmatic consumption. That one flag is what turns an interactive tool into something you can put in a CI pipeline, a pre-commit hook, a shell loop, or a cron entry.

What changes is not the model but the failure handling. Interactively, an unexpected permission request becomes a prompt and you resolve it. Headless, there is nobody to ask, so the permission strategy has to be declared up front. --allowedTools scopes a run to specific tools; dontAsk mode auto-denies anything not already pre-approved, which is the right posture for CI because the session never waits for input. Auto mode is available too, but with a documented caveat that matters: in non-interactive runs it aborts when the classifier repeatedly blocks, because there is no user to fall back to.

The second thing that has to move upstream is verification. Lecture 6's hierarchy ended with a hook that refuses to let a turn end until a check passes, and that is not a refinement here, it is the load-bearing element. An unattended run with no gate produces output nobody watched, checked by nobody, reported by the thing that produced it. Getting that right is the difference between automation and a machine that generates work for you to audit.

Feynman test Ask what happens when the run goes wrong at step four of nine. Interactively you notice and interrupt. Headless, the answer must already exist: a check that blocks, a permission that denies, a budget that expires, or a human who reads the evidence afterwards. If your answer is "it would probably be fine", you have not automated anything, you have removed the supervision and kept the risk.
What's beyond the syllabus This is the automation irony, described by Lisanne Bainbridge in 1983 and never bettered. Automating a process removes the easy cases and leaves the human responsible for the hard ones, while simultaneously destroying the practice that would let them handle those cases. Worse, the operator now monitors rather than acts, and humans are extremely poor at sustained monitoring of reliable systems. Every conclusion in this lecture follows from taking that seriously: prefer narrow scopes over broad ones, prefer a machine gate over a human reviewer for anything that runs often, and design the output so a person can check the result without reconstructing the process.
Step 2

Why this matters

The first reason is that a large class of work is genuinely better done without you. Triaging overnight failures, sweeping a codebase for a pattern, keeping documentation in step with code, running a migration across two thousand files: each is mechanical, bounded, and verifiable, and each is a poor use of an hour of attention. This is the shape of task the whole practice has been building towards.

The second reason is that unattended runs are where the earlier disciplines stop being optional. An instruction that is usually followed is fine when you are watching and dangerous when you are not. A test that usually runs is not a gate. A permission model that mostly prompts is not a boundary if nobody is there to answer. Headless operation takes every advisory mechanism in this course and exposes exactly how much you were relying on being present.

The third reason is that this is where cost and blast radius stop being bounded by your patience. An interactive session ends when you close it. A loop over two thousand files does not, and a scheduled job that fails badly fails repeatedly on a timetable. Budgets, caps, and scopes are not bureaucracy in this setting; they are the only thing standing between a bug and an invoice.

Step 3

The mental model

Four things to settle before the run

Output formats and what each is for

# Human-readable, for a quick one-off
claude -p "Explain what this project does"

# One JSON object with a result field — for scripts
claude -p "List all API endpoints" --output-format json

# One JSON object per line, starting with an init event — for live processing
claude -p "Analyse this log file" --output-format stream-json --verbose

The JSON forms are what make this composable. A run whose output is parsed rather than read can feed a dashboard, open a ticket, or gate a deploy, and the choice between the two is about whether you need the answer when it arrives or as it arrives. Use --verbose while developing the pipeline and turn it off in production, which is the documented advice and holds for the same reason it does everywhere else.

Permission posture, chosen deliberately

PostureBehaviour with no human presentFits
--allowedTools listOnly the named tools run; everything else is refusedFan-out loops and pipelines with a known tool set
dontAskAuto-denies anything not pre-approved; never waitsCI and locked-down automation
autoClassifier vets each action; aborts on repeated blocksLonger exploratory runs where the tool set is not known upfront
bypassPermissionsEverything runsIsolated containers with nothing in them you would miss

The first two are the workhorses and the difference between them is whether you can enumerate the tools in advance. If you can, enumerate them: an explicit list is the tightest scope available and it documents the run's intent in its own invocation.

Headless run. A non-interactive invocation that completes without any opportunity for a human to answer a prompt. Defined by what it cannot do rather than by where it runs.
Evidence output. A result formatted so a person can verify the outcome without re-running the work: the command and what it returned, the test output, the diff. Distinguished from an assertion of success, which is what an unverified run produces by default.
Step 4

The detail

Fan-out, done carefully

The migration pattern is a loop over a work list, and the documented sequence has a step people skip. Generate the list of targets. Write the loop. Run it on two or three items and read the results. Then run the full set. That third step is the difference between a migration and two thousand identically wrong edits, and it costs a minute.

for file in $(cat files.txt); do
  claude -p "Migrate $file from React to Vue. Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

Three properties of that command are worth naming. The prompt demands a short, parseable answer, so the loop's output is checkable at a glance rather than being two thousand paragraphs. The tool list is minimal and includes a scoped Bash pattern rather than blanket shell access. And each item is its own invocation, which means one failure does not poison the rest, unlike a single session attempting all of them with an increasingly polluted context.

Scheduling, and what recurring changes

A scheduled run adds one property to a headless one: it happens again. That turns a tolerable failure into a recurring one and a small cost into a standing charge. Three consequences follow.

Idempotence matters. A job that opens a ticket should not open the same ticket every night. Either the action is naturally idempotent or the job checks state first, and "check whether this already exists" is a clause worth putting in every scheduled prompt.

Failure needs a route to a human. A job that fails silently every night for three weeks is worse than no job, because the thing it was supposed to be doing is not being done and nobody knows. Notification on failure is not optional for anything recurring.

Drift is the real risk. The repository changes, the branch changes, the API changes, and a prompt written against last quarter's assumptions keeps running confidently. Scheduled jobs should be reviewed on a cadence, and the honest default is that any job nobody has looked at in three months should be turned off rather than trusted.

Getting evidence rather than assertions

For a run you did not watch, "done" is not information. The documented instruction is to have the agent show evidence rather than assert success: the test output, the command it ran and what that returned, a screenshot of the result. Reviewing evidence is faster than re-running the verification yourself, and it is the only thing that distinguishes a run that worked from a run that reported working.

Build that into the prompt. "Return the number of files changed, the test command you ran, and its exit code" produces something checkable. "Migrate these files" produces a claim.

Common pitfall Reaching for bypassPermissions because a headless run kept stopping on prompts. The stopping was the system telling you the scope was wrong, and the correct response is to widen the allowlist by one specific entry, not to remove the boundary. On an unattended run this matters more than interactively, because there is nobody to notice the consequence: the mode offers no protection against prompt injection, and an unattended session reading untrusted content with every permission granted is the worst configuration in this course. If you genuinely need everything permitted, the venue is a container with nothing valuable in it.

Worked example: this course was written in an unattended loop

Worked example: a self-paced loop with self-administered verification

Lectures 5 through 19 were written under a recurring instruction to continue with the remaining lectures, self-paced, with a wakeup scheduled between turns. That is a scheduled agentic loop in exactly the sense of this lecture, and it is worth auditing against the four rows of the diagram.

Scope: fine, by accident. The run stayed within one directory and wrote only HTML files, and no permission was needed that was not already granted. But nothing enforced that. No --allowedTools list bounded it, no deny rule protected anything, and a prompt that had drifted towards editing source code or configuration would have been able to. The scope held because the task was well-behaved, which is not the same as the scope being configured.

Stop condition: absent. There is no Stop hook, no goal condition, and no gate of any kind. The loop's continuation is decided each turn by the same process doing the writing. That is the exact configuration Lecture 12 identified as failing: the grader is the generator. If a lecture had been poor, nothing in the loop would have caught it, and the turn would have ended with a report saying it was done.

Budget: only the human's patience. No token cap, no iteration cap, no timeout. The bound on this run is that someone is reading the output and would say stop. That is the interactive safeguard surviving into a nominally unattended setting, and it means the run is not really unattended, which is fortunate given the other two rows.

Evidence: strong on one layer, absent on another. Each turn ran the mechanical checks and reported them, which is genuine evidence in the sense this lecture means. But as Lecture 12 already conceded, no check verifies that the factual claims match the documentation they were drawn from, and the loop's self-report cannot supply that, because the same process wrote both the claims and the report.

What the configured version looks like. A --allowedTools list permitting writes only under the course directory. A Stop hook running the four checks and blocking the turn while any fails, so verification is enforced rather than remembered. A claim-checking subagent per lecture, which is the fresh-context reviewer this loop conspicuously lacks. And a cap, so the loop terminates on its own rather than on somebody noticing. None of that is expensive; all of it was skipped because the run was going well, which is precisely when these things get skipped and precisely why the automation irony has a name.

Step 5

Synthesis and what's next

Headless mode is one flag, and everything difficult about it follows from the absent human. Four jobs they were doing implicitly, scoping, judging completion, bounding cost, and watching, must move into configuration: an explicit tool list or dontAsk, a Stop hook or goal condition, caps and timeouts, and output that carries evidence rather than assertions. Fan out over a list only after testing the prompt on two or three items. For scheduled work, add idempotence, a failure route to a human, and a review cadence, because a job nobody has checked in three months is a liability rather than an asset.

That closes Part IV and, with it, everything about capability. The course has covered what an agent is, how to steer it, how to check it, and how to connect it to the systems where your work actually lives. What remains is judgement: the threats this capability creates, whether any of it is paying for itself, and when the right answer is to close the laptop.
