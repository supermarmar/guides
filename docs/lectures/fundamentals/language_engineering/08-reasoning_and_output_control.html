Lectures / Language engineering

Reasoning and output control

Two problems close out Part II. A model that answers immediately gets multi-step questions wrong, and the fix is to make it produce the intermediate steps, which works for a reason that has nothing to do with introspection and everything to do with lecture 4. Separately, every generative example since lecture 5 has ended with fragile string parsing, and that problem has a real solution: because something outside the model chooses each token, you can forbid the choices that would break your format, and get output that is valid by construction rather than by hope.

Step 1

The 30-second version

Chain-of-thought prompting makes the model write its working before its answer, either by demonstrating worked reasoning in the examples or, in the zero-shot variant, by appending a phrase such as "let's think step by step". It helps because each generated token is another forward pass conditioned on everything already written, so a model that states an intermediate result can then condition on it, whereas one that answers immediately has to reach the conclusion in a single pass. Self-consistency runs the same prompt several times with sampling on and takes the majority answer, trading n times the cost for robustness against an unlucky sample. Tree-of-thought generates several candidate steps at each stage, scores them and prunes, which is powerful and expensive; a cheap approximation asks a single prompt to simulate several experts debating. On output, four things can go wrong, so there are three ways to control it: show the exact format as an example, which usually works; constrain the sampling with a grammar, which cannot fail because invalid tokens are removed from the distribution before a token is chosen; or fine-tune, which is Part V. Only the second gives a guarantee, and the guarantee is syntactic, never semantic.

Feynman test Ask someone for the answer to a three-step arithmetic problem and they'll often get it wrong; ask them to say each step out loud and they usually get it right, because having said "twenty-three minus twenty is three" they no longer have to hold it in their head. A model gains the same thing for a mechanical reason: what it has already written is part of its input for the next word. Now the other half. Suppose you need the answer on a form with specific boxes. You could show them a filled-in form and ask them to copy the layout, which works most of the time. Or you could hand them a form where the only thing they can physically write in the "amount" box is a digit, because the box only accepts digits. The second approach cannot produce a malformed answer. It can still produce the wrong number.
Where this sits in the track This closes Part II. The constrained-sampling section is where lecture 4's framing pays off: because the model emits a distribution and a separate decoding step picks from it, you can intervene between the two. It also removes the fragile parsing that lectures 5, 6 and 7 all had to live with, which is a precondition for Part III, since a chain or an agent that parses an intermediate result badly fails silently and expensively.
Step 2

Why this matters

Three reasons.

First, chain-of-thought is nearly free and the gains on multi-step tasks are large. Appending one sentence to a prompt costs a few tokens and turns a class of consistently wrong answers into consistently right ones. It has a real cost in output length, and therefore latency and money, but as an intervention-to-benefit ratio nothing else in this lecture comes close.

Second, reasoning output is auditable in a way a bare answer is not. A model that returns "9" gives you nothing to check. A model that returns "23 minus 20 is 3, plus 6 is 9" gives you a chain you can inspect, and in a regulated setting that difference matters more than the accuracy gain. The caveat is important and comes up again below: the stated reasoning is not a transcript of a hidden process, it's generated text that happens to correlate with the answer, and it can be plausible and wrong.

Third, unconstrained output is the most common cause of production failures in generative pipelines. Every generative example so far has ended in a line like 0 if text == "negative" else 1, and every one of those lines is a defect waiting for the model to reply "Negative." with a capital and a full stop. At the scale of one interactive query this is invisible. At the scale of a batch job it's a silent corruption of your results. Grammar-constrained sampling removes the failure mode rather than mitigating it.

Vignette from the field An extraction pipeline pulling structured fields out of policy documents was specified to return JSON, and the prompt said so clearly, with an example. In testing over a few hundred documents it returned valid JSON every time. In production it failed roughly one document in four hundred, and the failures had no pattern anyone could see: the same document would sometimes parse and sometimes not. Two things were happening. Sampling had been left on, so the output was not deterministic, and on the rare occasions the model wrapped its JSON in a markdown code fence or prefixed it with "Here is the JSON:", the parser threw. The team's first fix was a regular expression to strip fences and preambles, which reduced the failure rate without eliminating it and added a second thing to maintain. The eventual fix was to turn sampling off and switch on the model server's JSON mode, after which the failure rate was zero by construction rather than by defensive coding. The lesson is that "the prompt says to return JSON" is a request, and a request is not a constraint.
Step 3

The mental model

Hold two pictures. The first is a ladder of reasoning techniques, each buying accuracy with model calls.

The second picture is the difference between asking for a format and enforcing one, which is developed properly below. Two slogans hold both. Thinking out loud is thinking with more forward passes. And a request is not a constraint: only intervening in the token selection makes a format guaranteed.

Step 4

The detail

A framing worth holding loosely

The usual framing for this material borrows the psychological distinction between fast, automatic, intuitive thinking and slow, deliberate, self-reflective thinking. A model generating tokens straight out looks like the first; the techniques below are attempts to induce something resembling the second.

Take the analogy as a mnemonic and not as a claim. What these models do is generally understood to be pattern completion over an enormous training corpus rather than reasoning in any strong sense, and the field calls the output "reasoning" because of what it resembles, not because of what is established about the mechanism. That distinction matters practically: it is why a chain of thought can be internally consistent, fluent, and wrong, and why it should be read as evidence rather than as proof.

Chain-of-thought

The original form supplies examples that include the working, so the model continues the pattern of working-then-answer.

cot_prompt = [
    {"role": "user", "content": "Roger has 5 tennis balls. He buys 2 more cans of "
        "tennis balls. Each can has 3 tennis balls. How many does he have now?"},
    {"role": "assistant", "content": "Roger started with 5 balls. 2 cans of 3 tennis "
        "balls each is 6 tennis balls. 5 + 6 = 11. The answer is 11."},
    {"role": "user", "content": "The cafeteria had 23 apples. If they used 20 to make "
        "lunch and bought 6 more, how many apples do they have?"},
]

# "The cafeteria started with 23 apples. They used 20 apples, so they had
#  23 - 20 = 3 apples left. Then they bought 6 more, so they now have
#  3 + 6 = 9 apples. The answer is 9."

Note the structure: this is the few-shot pattern from lecture 7, with the demonstrated reasoning rather than just the demonstrated answer attributed to the assistant. What's being taught by example is the shape of the response, not the arithmetic.

The mechanism is worth restating because it demystifies the whole family of techniques. From lecture 4: one forward pass produces one token, and that token is appended to the input before the next pass. So a model that writes "23 - 20 = 3" has, on the following pass, the number 3 sitting in its input, and can condition on it. A model asked to produce the final answer directly has to get from the question to the conclusion within a single pass, with no intermediate state to rely on. Chain-of-thought is, quite literally, giving the model more computation and somewhere to put its working.

Supplying reasoning examples requires having reasoning examples. The zero-shot variant does not.

zeroshot_cot_prompt = [
    {"role": "user", "content": "The cafeteria had 23 apples. If they used 20 to make "
        "lunch and bought 6 more, how many apples do they have? Let's think step-by-step."},
]

# Step 1: Start with the initial number of apples, which is 23.
# Step 2: Subtract the apples used for lunch: 23 - 20 = 3 remaining.
# Step 3: Add the apples bought: 3 + 6 = 9.
# The cafeteria now has 9 apples.

One appended sentence produces the same behaviour. The exact wording isn't sacred; "let's work through this step by step" and various other phrasings do the same job, and the literature contains a certain amount of enjoyable folklore about which incantation performs best. Treat the specific phrase as a hyperparameter worth one afternoon of testing on your own task, not as a magic formula.

Do not confuse the stated reasoning with the actual computation A chain of thought is generated text. It is produced by the same next-token process as everything else, and there is no guarantee it faithfully describes whatever the network did internally. Models can produce correct answers with faulty stated reasoning, and confident, well-formed reasoning that leads to a wrong answer. The output is genuinely useful as an audit artefact, because a human can spot a bad step, but it is not a proof and should never be presented to a regulator as one. The machine learning track's responsible use lecture develops this point.

Self-consistency

With sampling switched on, the same prompt gives different answers on different runs, and some of that variation is simply luck. Self-consistency exploits it: ask the same question n times, each with chain-of-thought and sampling enabled, then discard the reasoning and take a majority vote over the final answers.

The argument is that there are many valid reasoning paths to a correct answer and comparatively few paths that converge on the same wrong one, so agreement across independently sampled paths is evidence. It works, and it costs exactly n times as much and takes n times as long unless you parallelise the calls.

Two practical notes. Sampling must be on, since with greedy decoding all n runs are identical and you have paid n times for one answer. And it needs an extractable final answer to vote over, which is a good motivation for the output control in the second half of this lecture: majority voting over free text requires you to first decide whether "9 apples" and "The answer is 9" are the same vote.

Tree-of-thought

Chain-of-thought commits to one line of reasoning. Tree-of-thought does not: at each step it generates several candidate next steps, scores them, keeps the promising ones and prunes the rest, then continues from the survivors. It's a search over reasoning paths rather than a single walk down one.

This suits problems with genuine branching, where an early choice determines what's reachable later: planning, creative work with structural decisions, puzzles with backtracking. It is expensive, needing many calls to generate candidates and more to evaluate them, and the orchestration is real code rather than a prompt.

There's a much cheaper approximation that captures some of the benefit in a single call: ask the model to simulate the search itself.

zeroshot_tot_prompt = [{"role": "user", "content":
    "Imagine three different experts are answering this question. All experts will "
    "write down 1 step of their thinking, then share it with the group. Then all "
    "experts will go on to the next step, etc. If any expert realises they're wrong "
    "at any point then they leave. The question is '...'. Make sure to discuss the results."}]

The model produces a transcript of three experts working through the steps and checking each other, arriving at a cross-checked answer. Be clear about what this is: no actual search is happening and no branch is actually pruned, because it is one generation of a document that resembles a debate. It works better than a bare question mainly because it induces more intermediate tokens and some self-checking language, which is chain-of-thought with extra structure. That's still worth having, and it costs one call.

Output verification: what can go wrong

Now the second half. Four distinct things can be wrong with generated output, and conflating them leads to applying the wrong fix.

Not structured You need JSON and got prose, or JSON wrapped in a markdown fence, or JSON with a friendly preamble. A parsing failure, and the one most likely to take down a pipeline.
Structured but invalid Valid JSON, but the sentiment field says "mixed" when your schema allows only three values. Nothing throws; a bad value flows downstream and appears in a report.
Unsafe Open models frequently ship without guardrails. If the output is customer-facing or logged, profanity, personal data reproduced from the input, or stereotyped content are live risks that no amount of formatting control addresses.
Inaccurate Well-formed, valid, safe and false. The hardest of the four, and not solvable by output control at all: the answers are grounding the model in retrieved sources (lecture 11), verification against an external check, and honest evaluation (lecture 18).

Three mechanisms address the first two. Show the format as an example. Constrain the sampling with a grammar. Or fine-tune the model on data in your format, which is Part V. They are not equivalent, and the difference is whether you get a guarantee.

Control by example

Ask for JSON with no example and you get something JSON-shaped, at whatever length and with whatever fields the model fancies. Asked to "create a character profile for an RPG game in JSON format", a small model produces a deeply nested object with a dozen fields and runs into the token limit part-way through the attributes, leaving output that is not parseable because it's truncated.

Supplying the exact skeleton fixes both problems at once.

one_shot_template = """Create a short character profile for an RPG game.
Make sure to only use this format:
{
  "description": "A SHORT DESCRIPTION",
  "name": "THE CHARACTER'S NAME",
  "armor": "ONE PIECE OF ARMOR",
  "weapon": "ONE OR MORE WEAPONS"
}
"""
# {"description": "A cunning rogue with a mysterious past, skilled in stealth
#   and deception.", "name": "Lysandra Shadowstep",
#   "armor": "Leather Cloak of the Night", "weapon": "Dagger of Whispers, Throwing Knives"}

Exactly the four requested fields, short enough to complete, and parseable. This is the few-shot technique of lecture 7 applied to structure rather than content, and it's cheap, portable across providers, and effective most of the time.

Most of the time is the problem. The model is still choosing every token freely; you have made the desired format overwhelmingly probable, not mandatory. At a few hundred documents you will not notice. At a few hundred thousand you will.

Control by grammar: constrained sampling

The real fix follows directly from lecture 4. The model does not choose a token; it produces a score for every token in the vocabulary, and a decoding step chooses. That decoding step is code you control, so it can be made to ignore tokens that would produce invalid output.

In practice you rarely write the mask yourself. Local inference through llama-cpp-python exposes a grammar interface with a JSON mode built in, and hosted providers offer equivalents, typically a JSON mode and a stricter schema-constrained mode.

from llama_cpp.llama import Llama

llm = Llama.from_pretrained(
    repo_id="microsoft/Phi-3-mini-4k-instruct-gguf",
    filename="*fp16.gguf",
    n_gpu_layers=-1,     # all layers on the GPU
    n_ctx=2048,          # context size
)

output = llm.create_chat_completion(
    messages=[{"role": "user", "content": "Create a warrior for an RPG in JSON format."}],
    response_format={"type": "json_object"},   # applies a JSON grammar internally
    temperature=0,
)["choices"][0]["message"]["content"]

json.loads(output)   # parses, every time, by construction

Note the model format: GGUF, which is the quantised format llama.cpp consumes, and the entry point to the local-model tooling that lecture 9 uses throughout. If you're switching between transformers and llama-cpp-python in one session, free the first model's VRAM before loading the second, since both will happily try to occupy the whole card.

Choosing among the three controls Use examples when you're prototyping, when portability across providers matters more than a guarantee, or when the structure is loose. Use grammar constraints whenever the output feeds a parser in a pipeline that runs unattended: the cost is one configuration line and the benefit is the removal of an entire class of failure. Use fine-tuning when the format is elaborate and constant and you're generating enough volume for the training cost to amortise, which is lecture 17. And in every case remember what the grammar buys you. Constraining the tokens guarantees the shape of the answer. It says nothing about whether the answer is right, and a pipeline that treats successful parsing as successful extraction has simply relocated its blind spot.

A related pattern worth knowing, since it needs no special tooling: generate only the parts you don't know. If the structure is fixed, write the scaffolding yourself in code and call the model once per field with a narrow prompt. You get correct structure by construction because you built it, each call is small and focused, and each field can be validated independently. It costs more calls and it is often the most robust option for a small, fixed schema.

Step 5

Synthesis and what's next

Making a model write its working improves multi-step answers for a mechanical reason: each token it generates enters its input for the next pass, so stated intermediate results become something to condition on. Chain-of-thought does this by demonstration or by a single appended instruction, and it's the best value in the lecture. Self-consistency samples several reasoning paths and votes, buying robustness at n times the cost. Tree-of-thought searches over paths and prunes, which suits genuinely branching problems, and its single-prompt imitation is chain-of-thought with a debate structure rather than an actual search. Treat all stated reasoning as an audit artefact rather than as a faithful account of the computation. On output, distinguish unstructured from invalid from unsafe from inaccurate, because only the first two are format problems. Examples make the right format very likely; a grammar makes the wrong format impossible, by zeroing illegal tokens before selection; fine-tuning is the third route and belongs to Part V. Nothing here makes the content true.

Part II is complete: you can classify, cluster, prompt, reason, and get output a parser can trust. Part III makes systems out of these pieces. Lecture 9 takes the chain prompting sketched at the end of lecture 7 and turns it into a proper construct with templates, then confronts the fact that a model has no memory at all, so any conversation that appears to remember something is a program that re-sends it.
