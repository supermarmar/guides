Agents and ReAct

An agent is the chain from lecture 9 with two additions: it can call something that is not a model, and it decides for itself when to stop. Those two changes are what make it able to do things a chain cannot, and they are also the entire source of its expense, because a loop whose length the system chooses inherits a quadratic cost curve with no upper bound written anywhere.

Lecture 10 of 18 Reading time, 40 minutes Part III: building systems
Step 1

The 30-second version

The ReAct pattern, from Yao and colleagues in 2022, interleaves two things the previous lectures kept separate: reasoning, which is the chain-of-thought from lecture 8, and acting, which is calling a tool and reading what comes back. The loop is thought, action, observation, repeated until the model emits a final answer instead of another action.

Everything difficult follows from the model choosing the number of iterations. Reliability compounds: at 95 per cent per step, a ten-step trajectory succeeds 59.9 per cent of the time and a twenty-step one 35.8 per cent, and the agent picks which of those you get.

Cost compounds harder, because each step re-sends the whole scratchpad. With a 600-token system prompt and steps of 150 tokens of thought and action plus 800 of observation, a five-step task consumes 12,500 tokens and a ten-step task 48,750. Doubling the steps multiplies the cost by 3.9, not by two.

Which produces the result worth carrying out of this lecture. Since cost grows with the square of the step count, expected cost depends on $\mathbb{E}[k^2] = \text{Var}(k) + \mathbb{E}[k]^2$, so the variance in how many steps an agent takes is itself a cost. At a mean of eight steps with a standard deviation of six, the true expected cost is 56 per cent above the figure you get from budgeting on the average. That term is almost always omitted.

Feynman test Let the model think out loud, then let it ask for something: a search, a calculator, a database. Show it the answer, let it think again. Repeat until it says it is done. The only hard question is what stops it.
Step 2

Why this matters

The first reason is that tool use removes the two limits that everything so far has run into. A model cannot know a fact that postdates its training and cannot reliably do arithmetic, and both are solved by letting it ask something that can. For tasks with either property the comparison against a single call is not cost against cost, it is possible against impossible.

The second reason is that the same mechanism removes the guarantees. A chain has a step count you fixed, so you can test it, price it and reason about its failure rate. An agent has a step count it chooses at runtime from information you have not seen, so none of the three is available in advance.

The third reason is that the failure modes are specific and predictable rather than mysterious, which means they can be designed against. Loops, tool misuse, malformed calls, and observations that overflow the context are the four that matter, and step 4 handles each.

And a fourth reason about where agents are actually appropriate. The decision rule in step 5 is short and unfashionable: if the task can be decomposed in advance, write a chain, because fixed steps are cheaper and testable. Reach for an agent only when the sequence genuinely depends on what is discovered along the way. The expensive mistake is using an agent for work whose shape was already known.

Step 3

The mental model

One loop, three token types, and a scratchpad that grows with every pass.

ReAct
Reasoning and acting interleaved in one loop, from Yao and colleagues (2022). The reasoning step decides what is needed; the acting step gets it. Neither alone is sufficient: reasoning without acting cannot obtain facts, and acting without reasoning cannot decide what to obtain.
Tool
Any function the runtime can execute on the model's behalf, described to the model by name, purpose and argument schema. Search, calculator, database query, code execution, an HTTP call. The model never runs anything; it emits a request and your code decides whether to honour it.
Scratchpad
The accumulated transcript of thoughts, actions and observations, resent in full on every pass because the model is stateless. It is lecture 9's full-buffer memory strategy, applied by default, to content the model did not write and whose size you do not control.

The scratchpad makes the cost quadratic

Lecture 9's full-buffer strategy is the default here and it is applied to material the model did not write. A search result or a page of documentation can be an order of magnitude larger than the thought that requested it, and its size is set by the tool rather than by you.

Truncating or summarising tool output before it enters the scratchpad is therefore the single highest-value optimisation available, and it is a change to your runtime rather than to the model.

Four failure modes, and what each needs

The loop
The agent repeats an action that failed, or oscillates between two, because nothing in the pattern penalises repetition. Needs a hard iteration cap and a check for repeated action signatures.
The malformed call
The action does not parse, or names a tool that does not exist, or omits a required argument. This is lecture 8's problem exactly, and constrained decoding against the tool schema makes it structurally impossible rather than merely rare.
The oversized observation
A tool returns a whole document and the scratchpad jumps by thousands of tokens. Needs truncation, extraction or summarisation at the runtime boundary, before the observation is appended.
The confident wrong action
A well-formed call to the right tool with plausible but incorrect arguments, whose result the agent then reasons from. Nothing in the loop detects it, which is why write actions need confirmation and read actions need provenance.

A longer context makes an unbounded agent MORE expensive to get wrong, not less. THE CAP IS THE FIX, AND IT SHOULD BE LOW most successful trajectories are short. A cap set near the 90th percentile of observed successful lengths costs almost nothing in completed tasks and truncates the tail that produces the bills.

Tools: description is the interface

The model chooses a tool by reading its description, so the description is not documentation, it is the interface. Three properties make the difference between a tool that is called correctly and one that is not: a name that says what it does rather than what it is implemented with, a one-line purpose that includes when not to use it, and an argument schema tight enough to constrain generation.

{
  "name": "lookup_policy_document",
  "description": "Retrieve the current text of an internal policy by its "
                 "reference code. Use for questions about what a policy says. "
                 "Do NOT use for questions about how a policy is applied in "
                 "practice; use search_case_notes for those.",
  "parameters": {
    "type": "object",
    "properties": {
      "code": {"type": "string", "pattern": "^POL-[0-9]{4}$"}
    },
    "required": ["code"]
  }
}

The negative instruction in that description does more work than the positive one. Most tool-selection errors are a plausible tool chosen for an adjacent purpose, and the fix is to say in each description which neighbouring cases belong elsewhere. The pattern on the argument then makes a malformed code impossible under constrained decoding rather than merely unlikely.

Step 5

Synthesis and what's next

An agent is a chain with a loop and a tool call, and both additions come from the model rather than from you. Reasoning without acting cannot obtain a fact it does not hold; acting without reasoning cannot decide what to obtain; ReAct interleaves them and lets the model decide when it is finished. Reliability then compounds over a step count you did not choose, so 95 per cent per step gives 59.9 per cent over ten steps and 35.8 over twenty, and improving the per-step figure is worth more than it looks because the exponent magnifies it. Cost compounds harder still, because the scratchpad is resent in full and observations are 84 per cent of what each step adds: doubling the steps multiplies the bill by about four.

The result to carry out of this lecture Cost is roughly proportional to the square of the step count, so expected cost depends on $\mathbb{E}[k^2] = \text{Var}(k) + \mathbb{E}[k]^2$. At a mean of eight steps with a standard deviation of six, the expected cost is 56 per cent above what the average step count implies, and at a standard deviation of ten it is 156 per cent above. Budgeting an agent on its average trajectory length omits the variance term, and the variance term is frequently the larger one. The practical consequence is that reducing the spread of trajectory lengths, through caps, better tool descriptions and constrained actions, saves more money than reducing the mean.

The decision rule is short. If the task can be decomposed in advance, write a chain: fixed steps, fixed cost, testable before deployment. If the sequence genuinely depends on what is discovered along the way, use an agent, cap it near the 90th percentile of successful lengths, constrain every action against its schema, and truncate observations at the runtime boundary. The expensive mistake is reaching for an agent for work whose shape you already knew.

Lecture 11 takes the most common reason agents are reached for, which is that the model does not hold some fact, and solves it without a loop. Retrieval fetches the relevant passage and puts it in the prompt, which is the fourth memory strategy from lecture 9: instead of re-sending a transcript, fetch a small part of a large store. It is cheaper than an agent, bounded in steps, and it is the right answer whenever the task is really a lookup wearing a loop.
