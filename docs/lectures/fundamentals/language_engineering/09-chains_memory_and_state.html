Chains, memory and state

Part III begins by building systems out of the pieces from Part II, and the first thing to confront is that there is no state anywhere. A model has no memory of your previous message. Every conversation that appears to remember something is a program re-sending it, and once you see that, the three standard memory strategies stop being library features and become what they actually are: three answers to a cost problem with a quadratic shape.

Step 1

The 30-second version

A transformer forward pass, as lecture 4 set out, conditions on exactly one thing: the sequence of tokens it is given. Nothing persists between calls. So a chatbot that remembers your name is not a model with a memory, it is a program that puts your name back into the prompt every single time, and every design question in this lecture follows from that.

Running models locally becomes practical through quantisation, and the arithmetic is simple enough to do in your head. Weights dominate memory, so bytes equal parameters times bytes per parameter. A seven-billion-parameter model at sixteen-bit precision needs 14.0 GB and will not fit an eight-gigabyte consumer card; the same model at four bits needs 3.5 GB and does.

A prompt template is a string with holes, which sounds trivial and is the unit that makes composition possible: once a prompt is a function of variables, the output of one call can be the input to the next, and that is all a chain is.

Memory is where the real engineering sits, because re-sending the history has a cost that grows. Sending everything means turn $n$ carries $n$ turns of text, so cumulative tokens follow $T \cdot n(n+1)/2$, which is quadratic. Over thirty turns at 150 tokens each that is 69,750 tokens against 24,750 for a six-turn window, and the full buffer breaks the 4,096-token context window at turn 27. Summarising is cheaper still but costs an extra model call per turn, and on these figures it does not pay for itself until turn 24.

Feynman test The model forgets everything the instant it replies. If a conversation seems to remember, some code kept a transcript and pasted it back in. The only real questions are how much of the transcript to paste, and who pays for the pasting.
Step 2

Why this matters

The first reason is that statelessness is the most consequential fact about these systems and the one most thoroughly hidden by the interfaces built on top of them. Frameworks offer a memory object; hosted chat products keep a thread; both create the impression of an entity that remembers. Every debugging session on a conversational system that goes badly wrong ends at the same realisation, which is that the model saw a different prompt from the one the developer imagined.

The second reason is cost, and it is the reason the memory strategies exist at all. If re-sending history were free there would be one strategy: send everything. It is not free, it grows quadratically, and it eventually hits a hard wall rather than a soft one.

The third reason is that quantisation is what puts a capable model on a laptop, and the trade is understandable rather than mysterious. Fewer bits per weight means less memory and faster arithmetic, at some cost in fidelity. Knowing the byte arithmetic tells you immediately which models are available to you and which are not.

And a fourth reason that carries into the rest of Part III. A chain is just function composition over prompt templates, and an agent, in lecture 10, is a chain with a loop and a branch. Nothing in either is conceptually harder than what this lecture builds; the difficulty is entirely in what happens when the pieces fail, which is why lecture 10 spends its length on failure modes.

Step 3

The mental model

One stateless function, one template that makes it composable, and three ways to decide what to feed it.

Prompt template
A string with named holes, filled at call time. Turning a prompt into a function of its variables is what allows one call's output to become another call's input, and therefore what makes chains possible at all.
Chain
Two or more calls where the output of one is an input to the next. Function composition, with a language model as the function and a template as the calling convention. Nothing more.
Quantisation
Storing weights at reduced numerical precision, typically eight or four bits instead of sixteen. Cuts memory proportionally and speeds arithmetic, at some cost in output quality. GGUF is the file format that made four-bit local inference routine.
Step 4

The detail

Quantised local models: the arithmetic that decides what you can run

Model weights dominate the memory footprint, and the calculation is one multiplication: bytes equal the parameter count times the bytes per parameter. Sixteen-bit precision is two bytes, eight-bit is one, four-bit is a half.

THE TRADE fewer bits means a coarser representation of each weight. Modern 4-bit schemes quantise in small blocks with their own scale factors, which keeps the damage small, and the honest summary is that 8-bit is close to lossless for most uses while 4-bit is usually acceptable and occasionally is not. Test on your own task rather than trusting a benchmark average.

The practical route is the GGUF format with a runtime such as llama-cpp-python, introduced in lecture 8 for the same reason it matters here: a local model makes iteration free, which matters a great deal when a chain calls a model five times per user request.

Templates, and why they are the unit of composition

A prompt template is a string with variables. That is genuinely all it is, and it is worth being clear about why it deserves a name. Once the prompt is a function of its inputs, three things become possible that were not: the same prompt can be applied to many inputs, the output of one call can be substituted into another, and the prompt itself becomes a versionable artefact separate from the code that calls it.

summarise = "Summarise the following in one sentence:\n\n{text}"
classify  = "Classify the sentiment of this sentence as positive, "
            "negative or neutral. Answer with one word only.\n\n{sentence}"

# a two-step chain: the second call consumes the first call's output
brief = model(summarise.format(text=document))
label = model(classify.format(sentence=brief))

That is a chain. Frameworks add error handling, retries, streaming, parallel branches and tracing, all of which are worth having in production and none of which changes the shape. When a chain misbehaves, the diagnostic is always the same and always sufficient: print the fully rendered prompt that was actually sent.

The failure this creates Chains compound errors. If each step is right nine times in ten, a three-step chain is right about seven times in ten, and a five-step chain about six. That is not a criticism of chaining, it is the arithmetic of independent steps, and it is the reason lecture 8's constrained output matters so much here: a step whose format is guaranteed cannot fail in the way that breaks the step after it.

Memory: three strategies and their cost curves

Since the model holds nothing, the program must decide each turn how much of the conversation to include. The three standard answers differ in what they keep and, more importantly, in how their cost behaves as the conversation lengthens.

What summarisation actually costs

Summarisation looks strictly better than the alternatives in the table above, and the table is incomplete: it counts only the main call. Each turn also needs a second model call to fold the latest exchange into the running summary, and that call has both input and output tokens, with output typically priced several times higher.

WHICH GIVES A CLEAN DESIGN RULE for short interactions, send everything: it is cheaper, simpler, and loses nothing. for long ones, the quadratic term dominates and the extra call is worth paying. for interactions of unknown length, the window is the safe default because its cost is bounded and it needs no extra call. AND A CAVEAT ON THE FIGURES the exact break-even depends on the token prices, the summary length and the turn size, all of which vary. The SHAPE does not: a quadratic curve always eventually crosses a linear one, so the only question is where.
Step 5

Synthesis and what's next

The organising fact is that the model is a pure function of its input tokens and holds nothing between calls, so every appearance of memory is a program re-sending text. Quantisation is what makes running that function locally practical, and the arithmetic is one multiplication: a seven-billion-parameter model needs 14.0 GB at sixteen-bit precision and 3.5 GB at four, which is the difference between impossible and routine on consumer hardware. A prompt template is a string with holes, and it earns its name because turning a prompt into a function of its variables is exactly what allows one call to feed another; a chain is that composition and nothing more, with the caveat that independent steps multiply their failure rates.

Memory strategy is a cost decision with a shape. Re-sending the whole transcript gives perfect recall at quadratic cost and hits a hard context wall at turn 27 on the worked assumptions. A sliding window bounds the cost linearly and forgets abruptly. A running summary bounds it too and forgets gracefully, at the price of an extra call per turn that does not pay for itself until turn 24. Choose by expected conversation length, and default to the window when the length is unknown.

Lecture 10 keeps everything here and adds two things to the chain: a loop, and the ability to call something that is not a model. That is an agent, and the reasoning-acting pattern that structures it is a direct descendant of the chain-of-thought from lecture 8. The lecture is mostly about failure modes, because a loop that can act is a loop that can act wrongly, repeatedly, and expensively.
