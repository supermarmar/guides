Lectures / Language engineering

Prompt engineering

The previous two lectures wrote instructions to generative models and hoped for the best, which is how most people use them. This lecture replaces the hoping. Three things are worth knowing before you write another prompt: what the model actually receives, which is not what you typed; what the two sampling parameters everybody sets do to the distribution, which is not what their names suggest; and which components a prompt is made of, so that improving one is an experiment rather than a rewrite.

Step 1

The 30-second version

Instruction-tuned models expect a chat template, a specific arrangement of special tokens marking who is speaking and where each turn ends, and your library silently applies it; the model was trained on that exact format and departing from it degrades output in ways that look like model failure. Two parameters then govern how a token is chosen from the distribution lecture 4 described. Temperature reshapes the distribution before sampling, flattening it so unlikely tokens become plausible or sharpening it so the top token dominates. top_p, or nucleus sampling, instead truncates it, keeping only the smallest set of tokens whose probabilities sum to p and discarding the rest. Neither does anything unless sampling is switched on at all. On the prompt itself, the minimum useful structure is an instruction plus the data it applies to, plus an output indicator that constrains the shape of the reply; beyond that, a prompt decomposes into persona, instruction, context, format, audience, tone and data, and treating those as separable components is what turns prompt writing into something you can iterate on. Two techniques do the heavy lifting. In-context learning shows the model worked examples rather than describing the task, in zero-shot, one-shot and few-shot variants. Chain prompting splits a hard task across several calls, so the model does one thing at a time and you can set different parameters for each.

Feynman test Think of a very well-read assistant who has one peculiarity: they only respond properly to notes written on a particular printed form, with boxes marked "from" and "to" and a line ruled at the end of each message. Hand them the same words on plain paper and the quality drops, for no reason they could explain. Your software fills in the form for you, which is why you have never seen it. Separately, the assistant has a dial marked "how adventurous", and a second control that says "only consider your top few ideas, discard the rest". The first changes how seriously they weigh their unlikely thoughts; the second decides how many thoughts are on the table at all. Turning the first up while turning the second down gives you someone imaginative but still on-topic, which is a genuinely different setting from turning both up.
Where this sits in the track Lecture 4 explained that the model returns a distribution and something else chooses from it. This is that something else. Lectures 5 and 6 both wrote instruction prompts and both hit the same wall, that the reply is free text you must parse; this lecture builds the prompt properly and lecture 8 fixes the parsing. Chain prompting, introduced at the end here, becomes a formal construct in lecture 9 and grows into an agent in lecture 10.
Step 2

Why this matters

Three reasons, and the first is invisible until it bites.

First, the chat template is a hard requirement dressed up as a convenience. An instruction-tuned model was fine-tuned on text in one exact format, and the special tokens in that format are how it knows a turn has ended and a reply is expected. Use a high-level helper and it's applied for you. Drop to raw string concatenation, which people do the moment they need something the helper doesn't support, and you get a model that rambles, answers its own questions, or fails to stop. The symptom looks like a bad model and the cause is a missing token.

Second, temperature and top_p are set carelessly more often than any other parameter in this field. They're commonly described as "creativity", which is close enough to be misleading. They do different things to the distribution, they compose, and the right values depend entirely on the task: a classification prompt wants no sampling at all, whereas a brainstorming prompt wants both turned up. Setting a nonzero temperature on an extraction task is a common and expensive mistake, because it makes your pipeline non-reproducible for no benefit.

Third, treating a prompt as a single blob makes it impossible to improve systematically. If your prompt is one paragraph, every change is a rewrite and every comparison is confounded. If it's seven named components assembled by concatenation, you can add, remove and reorder them one at a time and actually attribute the effect. That's the difference between prompt engineering and prompt fiddling.

Vignette from the field A summarisation service produced good output in testing and inconsistent output in production, with occasional summaries that contradicted the source document. The team suspected the model and started evaluating alternatives. The actual cause was two settings nobody had revisited. The prototype had been built interactively while exploring what the model could do, so temperature had been left at a value chosen to make the demo outputs feel less robotic, and it had been carried into production unchanged. A summariser has no use for creativity: it should say what the document says, the same way, every time. Setting temperature to zero removed the contradictions and, incidentally, made the output cacheable, which cut the bill. The broader point is that generation parameters are part of the specification of the task, not a presentation preference, and a value that improves a demo can be actively wrong in production.
Step 3

The mental model

Hold one picture: the gap between the prompt you write and the token sequence the model receives.

Two slogans. You are not writing the prompt; you are writing part of the prompt. The template, and in a conversation the accumulated history, are the rest of it, and both count against the context window. Reshaping and truncating are different operations. Temperature changes how much the model's preferences matter; top_p changes how many options exist at all.

Step 4

The detail

Choosing a model, briefly

Start small. A 3.8-billion-parameter instruction-tuned model such as Phi-3-mini runs on 8 GB of VRAM, responds fast enough to iterate on, and fails often enough to teach you what your prompt is actually doing. Scaling a working prompt up to a larger model is usually pleasant; scaling one down, having tuned it against a model that forgave your ambiguity, usually is not. Build against the small model and treat the large one as headroom.

The chat template

Here's the thing nobody sees. Load an instruction-tuned model, pass a messages list, and the library converts it before the model gets anywhere near it.

messages = [{"role": "user", "content": "Create a funny joke about chickens."}]

# what actually reaches the model:
print(tokenizer.apply_chat_template(messages, tokenize=False))
# <s><|user|>
# Create a funny joke about chickens.<|end|>
# <|assistant|>

Those markers are vocabulary entries, the chat special tokens catalogued in lecture 2, and they are doing three jobs. They tell the model who is speaking, which is what makes multi-turn conversation possible at all. They mark where each turn ends, which is what the model emits when it has finished, so the software knows to stop generating. And the trailing <|assistant|> puts the model in the position of having to continue as the assistant, which is what converts a text completer into something that answers.

Every model family has its own template. Phi-3's is not Llama's is not Mistral's. Call apply_chat_template and you get the right one automatically, because the template ships with the tokenizer. Concatenate strings yourself and you will get it wrong, and the failure will present as poor model quality rather than as a formatting error.

Two consequences worth internalising A base model has no chat template because it was never instruction-tuned; feeding it a chat-formatted prompt is meaningless and it will simply carry on completing the text, which is what it does. Check whether the model you have loaded is the base or the instruct variant before blaming the prompt. And in a conversation, every previous turn is re-sent with its markers on every request, so a long chat consumes context and, on a hosted model, is re-billed each turn. That is the problem lecture 9 addresses with memory strategies.

Controlling the output: sampling

Lecture 4 established that the model returns a distribution over the whole vocabulary and a decoding strategy picks from it. Three settings control that pick.

do_sample The master switch. With False, the model takes the highest-probability token every time: greedy decoding, fully deterministic, and temperature and top_p are ignored entirely. This is the correct setting for classification, extraction, and anything you need to be reproducible. Setting temperature=0 on a hosted API achieves the same thing.
temperature Rescales the model's scores before they're turned into probabilities, so it changes the shape of the distribution. Below 1 it sharpens: the leading token takes even more of the mass and the output becomes focused and repetitive. Above 1 it flattens: unlikely tokens become genuinely reachable and the output becomes varied and, eventually, incoherent. Around 0.2 is conservative, around 0.8 is lively. Nothing is ever excluded, so at high enough temperature the model can pick anything at all.
top_p Nucleus sampling. Sort the tokens by probability and keep adding them to the candidate set until their cumulative probability reaches p; discard everything else and renormalise. At 0.9 the improbable tail is simply gone. At 1.0 nothing is excluded. Unlike temperature, this adapts to the model's confidence: where the model is certain the nucleus might hold two tokens, and where it is uncertain the same setting might admit fifty. A related parameter, top_k, fixes the candidate count instead, keeping the k most probable tokens regardless of how the probability is distributed. 
output = pipe(messages, do_sample=True, temperature=0.8, top_p=0.9)

Because they act differently, the combinations are meaningfully distinct rather than redundant.

What a prompt is made of

At its most minimal a prompt is a few words and the model completes them, which is all a base model can do. Useful prompts have more structure, and the structure is worth naming because it's what you iterate on.

The smallest useful unit is an instruction plus the data it applies to: "Classify the sentiment of the following review" and then the review. Add an output indicator and the reply becomes usable: prefixing the review with Text: and ending the prompt with Sentiment: signals that a single word is expected, rather than a paragraph of discussion. That trick is worth more than it looks, because it's the cheapest form of the output control lecture 8 develops properly.

Beyond that, seven components recur often enough to be worth keeping as a checklist.

persona     = "You are an expert in large language models. You excel at breaking down complex papers.\n"
instruction = "Summarise the key findings of the paper provided.\n"
context     = "Your summary should extract the points a researcher needs to understand it quickly.\n"
data_format = "Create a bullet-point summary of the method, then one paragraph on the results.\n"
audience    = "The summary is for busy researchers tracking new trends.\n"
tone        = "The tone should be professional and clear.\n"
data        = f"Text to summarise: {text}"

query = persona + instruction + context + data_format + audience + tone + data

Written this way, improving the prompt is an experiment rather than a rewrite: drop one variable from the concatenation, rerun, compare. That is the entire methodology, and it's why the decomposition is worth the slight awkwardness of the code.

Three techniques that reliably help

Specificity is the one that matters most. "Write a description for a product" leaves everything open; "write a description for a product in under two sentences using a formal tone" leaves almost nothing. Every unspecified dimension is one the model fills in itself, differently each time. Most disappointing output is under-specified rather than beyond the model.

Give it an exit. Models produce fluent, confident, wrong answers, and they do it because a confident answer is the most probable continuation of a question, whatever the truth. Explicitly permitting "I don't know" makes that a licensed continuation and measurably reduces invention. It doesn't eliminate it, and the real fix for factual questions is supplying the facts, which is lecture 11.

Put the instruction at an end, not in the middle. Models attend disproportionately to the beginning and the end of their input, and material in the middle of a long prompt is measurably more likely to be ignored, a documented effect sometimes called "lost in the middle". If your prompt has a long document in it, the instruction belongs before or after that document, not embedded in it. This one is easy to violate accidentally, because inserting the data in the middle of a nicely-structured prompt feels tidy.

In-context learning: show rather than tell

Everything so far describes the task. The alternative is to demonstrate it, which is in-context learning, and it comes in three sizes: zero-shot with no examples, one-shot with one, and few-shot with several.

The mechanically important part is that the examples must be formatted as a conversation, with the demonstrated answers attributed to the assistant. Put them all in one user message and you are showing the model a user who talks to themselves.

one_shot_prompt = [
    {"role": "user",
     "content": "A 'Gigamuru' is a type of Japanese musical instrument. "
                "An example of a sentence that uses the word Gigamuru is:"},
    {"role": "assistant",
     "content": "I have a Gigamuru that my uncle gave me as a gift. "
                "I love to play it at home."},
    {"role": "user",
     "content": "To 'screeg' something is to swing a sword at it. "
                "An example of a sentence that uses the word screeg is:"},
]

pipe(one_shot_prompt)
# "During the intense duel, the knight skillfully screeged his opponent's shield,
#  forcing him to defend himself."

Two invented words, one demonstration, and the model produces a correct usage of the second. Applying the chat template to this reveals alternating <|user|> and <|assistant|> blocks, which is exactly the structure of a real conversation, and that is the point: you're fabricating a history in which the model has already done this task well, so continuing that history means doing it well again.

Examples are worth more than description when the task has a shape that's easier to show than to state, which covers most formatting requirements and most edge-case handling. They cost context, they can bias the model toward the specific examples you chose, and they do not bind: the model can still ignore them, especially with sampling on. The machine learning track's prompting and reasoning lecture covers the competing theories of why in-context learning works at all, which remains genuinely unsettled.

Chain prompting: split the problem across calls

The components above break a prompt up internally. Chain prompting breaks the task up externally, running several calls where the output of one becomes input to the next.

# call 1: name and slogan
product_prompt = [{"role": "user",
    "content": "Create a name and slogan for a chatbot that leverages LLMs."}]
product_description = pipe(product_prompt)[0]["generated_text"]
# "Name: 'MindMeld Messenger'  Slogan: 'Unleashing Intelligent Conversations...'"

# call 2: the pitch, using call 1's output
sales_prompt = [{"role": "user",
    "content": f"Generate a very short sales pitch for: '{product_description}'"}]
sales_pitch = pipe(sales_prompt)[0]["generated_text"]

Three benefits, in increasing order of importance. Each call gets the model's full attention on one subproblem instead of a compound one. Each call gets its own parameters, so the name generation can be short and creative while the pitch is longer and more conservative. And, decisively, each intermediate result is a thing you can inspect, validate, cache, or replace with something that isn't a model at all. A one-shot prompt that does three jobs is a black box; a chain of three is a pipeline with test points.

The same structure supports several patterns worth knowing by name. Response validation feeds a generated answer back for checking. Parallel prompts run several independent calls and merge the results, for instance generating several recipes and then producing one shopping list. Progressive construction builds a long artefact in stages, writing a summary, then characters, then beats, then dialogue.

The costs are real and worth stating. Latency is additive, since each call waits for the last. Errors compound, because a poor intermediate result is faithfully built upon. And the whole thing costs more, since you're paying for several generations. Lecture 9 turns this pattern into a named construct with proper templating, and lecture 10 removes the fixed sequence altogether by letting the model decide what to do next.

Step 5

Synthesis and what's next

What reaches an instruction-tuned model is not your text but your text wrapped in a chat template of role and end-of-turn tokens, which is the format it was trained on and the mechanism by which it knows to stop. Downstream, sampling is off by default and should stay off for anything you parse; when it's on, temperature reshapes the distribution so that unlikely tokens become reachable, while top_p truncates the tail so they cannot be reached at all, and the two compose into genuinely different behaviours. A prompt is best built as named components, persona, instruction, context, format, audience, tone and data, because that makes improvement an experiment rather than a rewrite; and the three techniques with the best return are being specific, licensing "I don't know", and keeping the instruction out of the middle. Showing examples often beats describing the task, provided the demonstrated answers are attributed to the assistant. And when one prompt is doing too much, splitting it across several calls buys attention, per-call parameters, and inspectable intermediate results.

Two problems remain open, and lecture 8 closes both. The reasoning problem: a model that answers immediately gets multi-step questions wrong, and there are prompting techniques that fix this by making it work through the steps. And the output problem, visible since lecture 5, that a generative model returns free text your pipeline has to parse and might get anything at all.
