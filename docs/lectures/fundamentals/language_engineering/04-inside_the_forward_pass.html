Lectures / Language engineering

Inside the forward pass

The machine learning track derives what attention computes. This lecture is about what happens when you actually run the thing: that a paragraph is not one computation but hundreds, each a full pass through the network; that the model's real output is a probability over every token in its vocabulary and something else entirely decides which one you get; and that the single optimisation making generation tolerable, caching the attention keys and values, is also the reason serving a long conversation costs so much memory. Nearly every architectural change since 2017 has been an attack on one of those costs.

Step 1

The 30-second version

A generative model produces one token per forward pass, appends it to the input, and runs again; that loop, and not the network, is what produces a paragraph. Three components make up the pass: the tokenizer, a stack of transformer blocks, and the language modelling head, a single linear layer projecting the final hidden vector onto one score per vocabulary entry. What the model returns is therefore a distribution over the whole vocabulary, and a separate decoding strategy chooses from it, either greedily by taking the maximum or by sampling. Every input token gets its own computation stream and the number of streams available is the context length, a hard architectural ceiling; only the last stream's output reaches the language modelling head, but all of them must be computed because attention reads them. Recomputing them at every step would be ruinous, so the key-value cache stores each position's attention keys and values once, turning a quadratic amount of repeated work into a linear amount of stored memory. That memory is the binding constraint on serving, which is why the significant architectural changes since 2017, sparse attention, multi-query and grouped-query attention, flash attention, and rotary positional embeddings, are almost all attacks on the cost of attention rather than improvements to what it computes.

Feynman test Imagine a scribe who can only ever write one word, and to do it must reread the entire document from the beginning. Write a word, hand the page back, and the scribe rereads everything and writes one more. That's the generation loop, and it explains why output arrives at a steady drip rather than all at once. Now notice the obvious inefficiency: the scribe is rereading identical text hundreds of times. So the scribe keeps notes about each sentence already read, and on each new pass only reads the newest word and consults the notes for the rest. That is the key-value cache, and it's the difference between a paragraph taking twenty seconds and taking four. The catch is that the notes keep growing. On a very long document they eventually fill the desk, which is precisely the constraint that decides how many conversations a server can hold at once.
Where this sits in the track This closes Part I. Lectures 2 and 3 took you from text to token IDs to vectors; this one follows the vectors through the network and back out to text. It deliberately does not re-derive attention, which the machine learning track's transformers lecture does properly. Everything here is what that lecture leaves out because it only becomes visible once a model is running: the loop, the head, the cache, and the engineering that has grown up around their costs.
Step 2

Why this matters

Four consequences that shape how you design, cost and debug anything built on a generative model.

First, generation cost is per output token, not per request, and the two behave completely differently. Reading a long prompt is one pass over many positions, done in parallel and therefore fast. Writing a long answer is many sequential passes, each of which must wait for the last. A request with a 10,000-token prompt and a 50-token answer is far cheaper and faster than one with a 100-token prompt and a 2,000-token answer, which is the reverse of most people's intuition. When you're optimising latency, the first question is always how many tokens you're asking the model to write.

Second, the model's actual output is a distribution, and the thing that turns it into text is not the model. Understanding that the same model with the same prompt can give different answers, or perfectly reproducible ones, purely by the choice of decoding strategy is what makes the temperature and top_p parameters of lecture 7 comprehensible rather than magical. It's also what makes constrained generation possible in lecture 8: if you can see the distribution before a token is chosen, you can forbid choices that would break your output format.

Third, the key-value cache is usually what limits how many users you can serve. Model weights are a fixed cost, loaded once. The cache is a per-conversation cost that grows with every token, and on a busy server it can exceed the weights. This is why context length is priced the way it is, why providers meter it so carefully, and why grouped-query attention was adopted so quickly across the industry: it reduces cache size directly.

Fourth, the context length is a hard ceiling and not a soft one. There are only as many computation streams as the architecture provides. Text beyond the limit is not attended to weakly, it is not part of the computation at all, and the usual symptom is silent truncation rather than an error. Any pipeline handling documents of unpredictable length has to count tokens explicitly, which is the direct reason chunking and retrieval exist as disciplines.

Vignette from the field A team deployed an internal assistant on a single GPU and load-tested it with short questions. Throughput looked comfortable, so they released it. Within a week it was falling over at a fraction of the tested concurrency, and the pattern made no sense at first: the failures came in the afternoons, and restarting the service fixed it for a while. The cause was that real users held long conversations rather than asking one-off questions, and each conversation's key-value cache grew with every turn. Model weights had been sized carefully against available memory; the cache had not been budgeted at all, because in the load test every conversation was two turns long. The eventual fix was three unglamorous changes: a cap on conversation length, eviction of idle sessions, and moving to a model using grouped-query attention, which cut cache per token substantially. None of that is visible from the model card, and all of it is predictable from the picture in this lecture.
Step 3

The mental model

Hold one picture: a loop around a three-part pipeline, in which the network runs once per output token and the last thing it does is score every word it knows.

Two slogans. The model predicts one token; the loop writes the text. Almost every property of generation that surprises people, the drip-feed latency, the cost asymmetry between reading and writing, the way a single bad token derails everything after it, follows from that separation. Attention is where the money goes. The feedforward layers hold most of the parameters, but attention is what scales badly with sequence length and what consumes the memory, so it's what every optimisation since 2017 has targeted.

Step 4

The detail

The three components, read off a real model

Printing a loaded model gives you its architecture directly, and it is worth learning to read.

print(model), lightly trimmed: Phi-3-mini

Phi3ForCausalLM( (model): Phi3Model( (embed_tokens): Embedding(32064, 3072) ← the embedding matrix, lecture 3 (layers): ModuleList( (0-31): 32 x Phi3DecoderLayer( ← 32 identical blocks (self_attn): Phi3Attention( (qkv_proj): Linear(3072 -> 9216) ← queries, keys, values: 3 x 3072 (o_proj): Linear(3072 -> 3072) (rotary_emb): Phi3RotaryEmbedding() ← RoPE, discussed below ) (mlp): Phi3MLP( (gate_up_proj): Linear(3072 -> 16384) ← the feedforward layer: (down_proj): Linear(8192 -> 3072) wider than the model, then back (activation_fn): SiLU() ← not ReLU ) (input_layernorm): Phi3RMSNorm() ← normalisation before, not after (post_attention_layernorm): Phi3RMSNorm() ) ) ) (lm_head): Linear(3072 -> 32064) ← one score per vocabulary entry )

Read it top to bottom and you have the whole pipeline. An embedding matrix of 32,064 rows by 3,072 columns, matching the tokenizer's vocabulary. Thirty-two identical decoder blocks, each with an attention layer and a feedforward layer. Then lm_head, a single linear layer from the model's 3,072-dimensional hidden space to 32,064 outputs, one per vocabulary entry.

That last layer is the language modelling head, and calling it a head is meaningful: it's one of several things you can bolt onto the same stack of blocks. Attach a sequence classification head instead and you get a document classifier; attach a token classification head and you get an entity recogniser. Lecture 16 does exactly this. The stack of blocks is the general-purpose part; the head is what determines the task.

What the head returns, and who chooses

You can run the stack and the head separately and look at what sits between them.

prompt = "The capital of France is"
input_ids = tokenizer(prompt, return_tensors="pt").input_ids.to("cuda")

model_output = model.model(input_ids)          # the stack, without the head
lm_head_output = model.lm_head(model_output[0])  # the head

model_output[0].shape    # torch.Size([1, 6, 3072])   6 positions, 3072 dims each
lm_head_output.shape     # torch.Size([1, 6, 32064])  6 positions, one score per token

token_id = lm_head_output[0, -1].argmax(-1)    # 0 = batch, -1 = last position
tokenizer.decode(token_id)                      # 'Paris'

The shapes tell the story. Six tokens went in, six vectors of 3,072 came out of the stack, and the head expanded each into 32,064 scores. The indices [0, -1] select the batch's only item and its last position, because the last position is the one whose continuation you want. Taking argmax over those 32,064 scores gives "Paris".

Taking the maximum is greedy decoding, and it's one choice among several. Because the head's output is a distribution, you can instead sample from it: if "Dear" carries 40% of the probability mass, pick it 40% of the time. Greedy decoding is deterministic and tends towards repetitive, flat text. Sampling introduces variety at the cost of reproducibility. Neither is part of the model, and switching between them changes nothing about the weights. Lecture 7 works through what temperature and top_p do to the distribution before the sample is drawn.

Why this matters more than it looks Two facts follow directly from the head returning a full distribution rather than a token. The model always has an opinion about every token in its vocabulary, including the ones it considers absurd, so there is always a probability attached to a wrong answer and the interesting question is how much. And because something outside the model does the choosing, you can intervene there: forbid tokens that would produce invalid JSON, force the next token to be one of a fixed set of category labels, or require the output to match a grammar. That's constrained generation, and lecture 8 shows what it buys you.

Streams, context length, and why all of them are computed

Inside a single forward pass every input position is processed in parallel along its own stream: in at one end as an embedding vector, out at the other as a vector of the same size. The model's context length is simply how many such streams the architecture provides, and the ceiling is architectural rather than configurable.

Only the last stream's output reaches the language modelling head, which raises the obvious question of why the others are computed at all. The answer is that they are consumed inside the stack rather than at the end. Attention in every block reads the intermediate representations of every earlier position, so the final position's vector can only be computed if all the earlier ones have been. Their outputs are discarded; their intermediate states were the point.

This is also where the reading-versus-writing asymmetry comes from. Processing a long prompt happens in one pass with all positions computed in parallel, which GPUs are extremely good at. Writing a long answer requires one sequential pass per token, and no amount of parallel hardware removes the dependency between them.

The key-value cache

Now put the loop and the streams together and the waste becomes obvious. To generate token 101, you append token 100 to the input and run the whole pass again, recomputing every stream from position 1 onwards, all of which produced exactly the same intermediate values last time because their inputs have not changed. The causal mask guarantees this: earlier positions cannot see later ones, so nothing about them changes when a token is appended at the end.

The key-value cache exploits that. Each attention layer computes a key vector and a value vector for every position; store them the first time and reuse them on every subsequent step. Then generating the next token requires computing just one new stream, for the newly appended token, plus reading the cache for everything before it.

The difference is not marginal. Generating 100 tokens from the same prompt on a Colab T4 takes about 4.5 seconds with caching enabled and about 21.8 seconds with it disabled, a factor of roughly five, and the factor grows with sequence length because the wasted work grows quadratically while the cached work grows linearly.

generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=100,
    use_cache=True,     # the default. Setting False is a useful demonstration
)                       # and a terrible idea in production.

The cost is memory, and it's the cost that bites. The cache holds two vectors per position, per attention head, per layer, and it grows with every token generated. For a model with many layers and many heads, a long conversation's cache can rival or exceed the model weights, and unlike the weights it's paid per concurrent conversation rather than once. Everything about how long contexts are priced and rationed traces back to this.

One more observation from the numbers. Even 4.5 seconds is a long time to watch a blank screen, and the wait scales with answer length. This is why essentially every provider streams tokens to the client as they're generated rather than returning the completed answer: the total time is unchanged, but the first token arrives in a fraction of a second.

Inside the block: two layers with two jobs

Each of the thirty-two blocks contains an attention layer and a feedforward layer, and the division of labour between them is worth naming even though the mechanics belong to the machine learning track.

Attention layer Brings in information from other positions. Two steps: score how relevant each earlier position is to the current one, by multiplying the current position's query vector against the keys of all previous positions and normalising with a softmax; then combine, by taking the weighted sum of those positions' value vectors. This is what resolves "the dog chased the squirrel because it" by pulling information from whichever noun the training data suggests. Run several times in parallel as attention heads, so different heads can track different kinds of relationship at once.
Feedforward layer Holds most of the parameters and most of what the model knows. It's the component that supplies "Redemption" after "The Shawshank", and it does more than lookup: the same machinery interpolates between things it saw in training, which is what generalisation to unseen input actually consists of. Note in the printout that it widens 3,072 to 16,384 before projecting back down; that expansion is where the capacity lives.

A useful shorthand: attention decides which information is relevant, and the feedforward layer decides what to do with it. The machine learning track's transformers lecture derives the query, key and value projections properly, including why the scaling factor is there and how multi-head attention is implemented.

Making attention cheaper: three approaches

Attention is quadratic in sequence length, because every position may attend to every previous position, and it's the dominant cost at long contexts. Three families of fix have stuck.

Sparse and local attention attacks the problem directly by restricting which earlier positions a given position may attend to, typically a sliding window of recent tokens rather than everything. Restricting every layer this way degrades quality badly, since the model then genuinely cannot see far back. The workable pattern, used by GPT-3, is to interleave: alternate blocks use full attention and sparse attention, so information can still propagate a long way through the stack while most layers pay the cheaper cost.

Multi-query and grouped-query attention attack the cache rather than the computation. In standard multi-head attention, each head has its own query, key and value projections, so a model with 32 heads caches 32 sets of keys and values per position per layer. Multi-query attention shares one key and value set across all heads, cutting the cache by a factor equal to the head count. That turns out to be too aggressive at scale, costing noticeable quality, so grouped-query attention takes the middle position: divide the heads into groups and share keys and values within each group. It's the default in the Llama family and most current open models, for the straightforward reason that it retains nearly all the quality for most of the memory saving.

Flash attention attacks neither the computation nor the cache but the movement of data. A GPU has a small, very fast on-chip memory and a much larger, much slower one, and a naive attention implementation shuttles large intermediate matrices between them repeatedly. Flash attention reorganises the calculation so intermediates stay in fast memory, producing a substantial speed-up in both training and inference. It computes exactly the same attention: the result is numerically the same, only obtained without the wasted traffic. It is worth knowing about mainly because enabling it is often a one-line configuration change with no downside.

Other changes in a current block

Comparing the 2017 block with the printout above shows three quieter changes that have become standard.

Normalisation moved from after each sub-layer to before it. Pre-normalisation makes training more stable and faster to converge, and it's why input_layernorm appears ahead of the attention layer rather than behind it. The normaliser itself changed from LayerNorm to RMSNorm, which drops the mean-centring step and is simpler and cheaper for no measured loss. And the activation function moved from ReLU to gated variants in the SwiGLU family, visible in the printout as SiLU paired with a gate_up_proj. None of these change what the architecture can express; all three make it cheaper or more stable to train.

Rotary positional embeddings

Attention has no inherent notion of order, so position must be supplied. The original transformer added an absolute positional vector to each token's embedding at the very start: position 1, position 2, and so on. That works, and it has a specific problem at scale.

Training a model with a 4,000-token context on documents that are mostly much shorter would waste most of every batch on padding, so documents are packed together, several per context window. Now consider a document that happens to start at position 50. Absolute positional embeddings tell the model this is the fiftieth token of something, implying forty-nine tokens of preceding context that in fact belong to an entirely unrelated document. The model is being told something false about its input.

Rotary positional embeddings, or RoPE, address this by encoding position as a rotation applied to the query and key vectors, in a way that makes the attention score between two positions depend on their relative distance rather than their absolute indices. Two tokens five apart interact the same way whether they sit at positions 10 and 15 or at 1,010 and 1,015. Two structural details are worth remembering: RoPE is applied inside the attention layer immediately before the relevance scoring step, not added to the embeddings at the start of the pass, which is why rotary_emb appears inside Phi3Attention in the printout; and because the encoding is relative, it extrapolates to sequence lengths beyond those seen in training far better than absolute schemes do. That property is a large part of why context windows grew as quickly as they did.

Extrapolation is graceful, not free RoPE degrading gracefully beyond its training length is not the same as working. A model advertised with a long context may have been trained on far shorter sequences and extended afterwards, and quality often falls off well before the stated limit. If a long-context capability matters to your application, measure it on your own data rather than trusting the number on the model card. Retrieval, in lecture 11, is frequently the better answer than a very long prompt even when the long prompt technically fits.

Beyond the transformer

Two directions are worth knowing by name even though they sit outside this track. Mixture-of-experts models replace the single feedforward layer in each block with many parallel expert layers and a router that activates only a couple per token; the model has a very large total parameter count but activates a small fraction of it per token, buying capacity without proportional compute. Several prominent current models are built this way. Separately, Mamba and RWKV revisit the recurrent idea with modern machinery, aiming for transformer-quality results with cost linear rather than quadratic in sequence length. Neither has displaced the transformer, and both are live enough that the shape of this lecture may need revisiting.

Step 5

Synthesis and what's next

Generation is a loop around a three-part pipeline, and the network runs once per output token. The tokenizer converts text to IDs, a stack of identical blocks turns embeddings into contextual vectors, and the language modelling head projects the last position's vector onto one score per vocabulary entry; a decoding strategy outside the model then picks a token, which is appended before the next pass. Every position gets a parallel stream and the number of streams is the fixed context length. The key-value cache removes the quadratic recomputation this loop would otherwise entail, at the price of memory that grows with every token and is paid per concurrent conversation, which is the real constraint on serving. Nearly every architectural refinement since 2017 targets one of those costs: sparse attention restricts what may be attended to, grouped-query attention shrinks the cache, flash attention removes wasted memory traffic, and RoPE encodes position relatively, which is what let context windows grow.

Part I is complete: you can now follow a string from your keyboard to token IDs, to vectors, through the stack, back to a distribution, and out as text. Part II turns to using this. Lecture 5 takes a single task, sentiment classification, and solves it five different ways, from a task-specific representation model to a hosted generative one, then compares the results. It's the lecture that makes the representation-versus-generative choice concrete rather than theoretical.
