Lectures / Language engineering

Tokenisation

A language model never sees your text. It sees a list of integers produced by a separate component that was trained before the model was, on a dataset chosen by somebody else, according to design decisions nobody documented in the model card. That component sets a hard floor on what the model can do with numbers, spelling and non-English script, decides how much of your document fits in the context window, and determines your API bill. Almost nobody thinks about it until it breaks something, at which point it explains a startling proportion of the failures people attribute to the model.

Step 1

The 30-second version

A tokenizer converts text into a list of integer token IDs, each indexing an entry in a fixed vocabulary established when the tokenizer was trained. It is a separate artefact from the model, paired with it permanently, and it operates in both directions: it encodes your prompt on the way in and decodes the model's chosen IDs into readable text on the way out. Three decisions determine its behaviour: the tokenisation method, most commonly byte pair encoding for GPT-family models or WordPiece for BERT; the parameters, chiefly vocabulary size, which special tokens exist, and whether capitalisation survives; and the training corpus, which is why a code model and a text model tokenise the same Python function completely differently. Modern tokenisers work at subword granularity, sitting between whole words, which cannot handle anything unseen, and individual characters, which handle everything but waste the context window. The consequences are concrete and constant: how digits are split determines whether the model can do arithmetic, how whitespace is handled determines whether it can write Python, and how well the vocabulary covers a language determines what that language costs you per API call.

Feynman test Imagine you must send a long document abroad using a telegraph code book, and the code book was printed years ago by someone who mostly wrote English business correspondence. Common English words have their own short codes. Rarer words have to be spelled out in fragments: "apologising" goes as "apolog" plus "ising". Words from other languages are not in the book at all, so they go letter by letter, or byte by byte, at several times the cost. Now notice the two things that follow. First, the receiving clerk never sees your document, only the codes, so anything the book cannot express is information the clerk will never have. Second, you're billed per code sent, so an identical-length message in a language the book covers badly costs you multiples of what it costs in English. That code book is the tokenizer, and both consequences are real.

Step 2

Why this matters

Four consequences, all of which you will hit.

First, tokenisation is the root cause of the arithmetic and spelling failures people blame on reasoning. When a model gets 870 and 871 confused, or cannot count the letters in a word, the usual explanation offered is that it "doesn't really understand". The more precise explanation is that the GPT-2 tokenizer gave 870 a single token and split 871 into "8" and "71", so those two numbers have no relationship in the model's input at all. The same applies to spelling: if "strawberry" is three tokens, the model has no direct view of its letters, and asking it to count the letter r is asking it to do something its input representation actively obscures.

Second, the tokenizer sets your context budget and therefore your bill. Context windows and API pricing are both denominated in tokens, not characters. English averages roughly four characters per token on a modern tokenizer. Languages poorly represented in the training corpus can run at one or two characters per token, so the same document in Thai or Amharic can cost several times what it costs in English and can overflow a context window that comfortably held the English version. If you're budgeting for a multilingual pipeline, measuring token counts per language is the first thing to do, not the last.

Third, the tokenizer decides whether the model can work with code at all. Python's meaning lives in its indentation. A tokenizer that represents four leading spaces as three or four separate tokens forces the model to track indentation depth by counting, which it does badly. A tokenizer with a single token for each whitespace run up to length 83, which is what GPT-4's has, hands the model the indentation level as one symbol. This is not a subtle effect, and it's why code models ship with their own tokenisers.

Fourth, the tokenizer and model are a matched pair, and mixing them produces silent nonsense rather than an error. Token ID 5281 means something specific to the model that was trained alongside the tokenizer producing it. Feed a model IDs from a different tokenizer with an overlapping ID range and nothing throws; you just get output that looks like the model has had a stroke.

Vignette from the field A team building a document-extraction pipeline over scanned policy schedules benchmarked two comparable open models and found one dramatically worse at pulling out sums assured. The natural conclusion was that the weaker model was simply less capable, and the team started planning a fine-tune. Someone checked the tokenisation first. The stronger model's tokenizer split every digit into its own token, so "1,250,000" arrived as a clean sequence of digit symbols. The weaker model's tokenizer had learned multi-digit chunks from its training corpus, so the same figure arrived as an idiosyncratic mixture such as "125" plus "0," plus "000", with the chunk boundaries shifting depending on the surrounding punctuation. The model was not failing to read the number; it was being shown a different, inconsistent number each time the formatting varied. No amount of fine-tuning would have fixed the representation, and the actual fix, normalising the numeric formatting in the input before tokenisation, took an afternoon.
Step 3

The mental model

Hold one picture: a round trip in which the model sits in the middle and never touches text at either end.

Two slogans. The tokenizer is a lossy compressor with opinions. It was trained to represent one particular corpus efficiently, and everything outside that corpus, other languages, unusual formatting, domain jargon, gets represented badly or not at all. Token boundaries are the model's atoms. The model can reason about relationships between tokens and has no direct access to anything inside one, which is why questions about letters inside a word and digits inside a number are structurally hard in a way that questions about words in a sentence are not.

Step 4

The detail

Watching it happen

Take a prompt and look at what the model actually receives.

prompt = "Write an email apologizing to Sarah for the tragic gardening mishap."

input_ids = tokenizer(prompt, return_tensors="pt").input_ids
# tensor([[    1, 14350,   385,  4876, 27746,  5281,   304, 19235,   363,   278,
#          25305,   293, 16423,   292,   286,   728,   481, 29889]])

for token_id in input_ids[0]:
    print(token_id.item(), repr(tokenizer.decode(token_id)))

Decoded one at a time, with Phi-3's tokenizer, that prompt comes out as:

What the model is given

1 '<s>' ← special: beginning of text 14350 'Write' 385 'an' 4876 'email' 27746 'apolog' ← a stem, not a word 5281 'izing' ← a suffix, glued to the stem 304 'to' 19235 'Sarah' 363 'for' 278 'the' 25305 'trag' 293 'ic' 16423 'garden' 292 'ing' 286 'm' 728 'ish' 481 'ap' ← "mishap" cost three tokens 29889 '.'

Four things to notice. Common words get one token each. Less common words are split into a stem and a suffix, so "apologizing" is "apolog" plus "izing" and shares its stem with "apology" and "apologetic". Rarer words fragment badly: "mishap" costs three tokens. Punctuation is its own token. Spaces have no token of their own; instead, tokens that continue a word carry a hidden marker, and tokens without it are assumed to have a space in front. This is why tokenizer.decode on a single ID can look subtly wrong and why you should decode the whole sequence when you want to see real text.

The output side works identically in reverse. When the model generates, it emits IDs, and it emitted 3323 then 622 then 29901 to produce "Subject:", because "Sub" and "ject" are separate vocabulary entries. Nothing about "Subject" exists as a unit anywhere in the model's output.

Four granularities

Subword tokenisation is standard now, but it is one point on a spectrum, and understanding the ends explains why the middle won.

How the three methods build a vocabulary

Byte pair encoding builds the vocabulary from the bottom up. Start with every individual character (or byte) as a token. Count every adjacent pair in the training corpus, merge the most frequent pair into a new single token, and add it to the vocabulary. Repeat until the vocabulary reaches its target size. The ordered list of merges is the tokenizer: encoding new text means applying the same merges in the same order. Frequent sequences therefore become single tokens and rare ones stay fragmented, which is exactly the behaviour you want and also exactly why the numeric splits are so arbitrary.

WordPiece, used by BERT, works the same way but chooses which pair to merge differently: rather than the most frequent pair, it picks the merge that most increases the likelihood of the training corpus under a simple language model. It marks continuation pieces with a ## prefix, so "capitalization" becomes capital plus ##ization, and the prefix doubles as the record of where the spaces were.

SentencePiece, used by the T5 family, is better thought of as a wrapper that fixes a different problem. It treats the input as a raw character stream including the spaces, encoding a space as a visible marker character, which means it never needs a language-specific pre-tokenisation step and decoding is exactly reversible. That matters for languages such as Mandarin and Thai that do not delimit words with spaces at all. Inside, it can run either BPE or a unigram language model, which works top-down instead: start with a large candidate vocabulary and repeatedly prune the candidates that cost the least likelihood when removed.

Read down the "CAPITALIZATION" column and you can watch tokenisers get better at English between 2018 and 2023, from eight tokens to two. Read the whitespace column and you can see the field discovering that code matters: GPT-2 spends three tokens on four spaces, GPT-4 spends one. Read the digit column and you see the deliberate correction of a known defect. StarCoder2 and Galactica force every digit into its own token specifically so that arithmetic becomes tractable, accepting longer sequences as the price. Read the last column and you see the difference between a tokenizer that discards what it cannot represent, as BERT and Flan-T5 do by emitting an unknown token, and one that falls back to raw bytes, as the BPE tokenisers do, and can therefore reconstruct the original exactly.

Why every-digit-its-own-token helps Under GPT-2's tokenizer, 870 happens to be a single token while 871 is two, 8 and 71. Nothing in the input tells the model those numbers are adjacent, and their embeddings are unrelated vectors that happened to be learned from different contexts. Splitting every digit gives the model a consistent, positional, base-ten representation, which is what arithmetic needs. This is a good example of a general principle: when a model is bad at something, check whether the input representation is making it hard before concluding the model is incapable.

Special tokens

Alongside pieces of text, the vocabulary holds tokens that carry structural meaning. Which ones exist tells you what the model was designed to do.

TokenPurposeWhere it appears
<s>, <|endoftext|>Marks the start of a sequence, and the point at which generation should stopUniversal
[PAD]Fills unused positions so a batch of different-length inputs can be one rectangular tensorAny model trained in batches
[UNK]Stands in for anything not representable. A tokenizer with byte fallback never needs itWordPiece, SentencePiece

The last three rows make the general point. Special tokens are how a model builder encodes domain structure directly into the input format. StarCoder2's repository and filename tokens exist because a function call in one file often refers to a definition in another, and the model needs to know which files share a repository. Galactica's <work> token is a dedicated marker for chain-of-thought working, baked into the vocabulary rather than prompted for. If you're ever training a tokenizer for a specialised domain, this is the lever with the highest return.

The three design choices, restated

Everything above reduces to three decisions made before the model was trained.

Method BPE, WordPiece, or SentencePiece with BPE or unigram inside it. Determines the algorithm that selects the vocabulary and, with byte fallback, whether anything can ever be truly unrepresentable.
Parameters Vocabulary size, typically 30,000 to 50,000 historically and increasingly 100,000 or more; which special tokens exist; and whether capitalisation is preserved. A larger vocabulary means shorter sequences and a larger embedding matrix, so it is a direct trade of memory against context efficiency.
Training corpus The dataset the merge statistics were computed on. Two tokenisers with an identical method and identical parameters trained on English prose and on Python will produce entirely different vocabularies, and each will be inefficient on the other's domain.

The corpus point deserves emphasis because it is the one people forget. Every token spent on an over-represented language is a token unavailable for an under-represented one, which is the mechanism behind the cost asymmetry noted earlier. It is also why a text-focused tokenizer applied to a Python file wastes a substantial fraction of its tokens on indentation that carries one bit of information per level.

Practical checks worth running before you trust a model on your data Tokenise a representative sample of your actual text and look at the characters-per-token ratio; anything much below three in English means the vocabulary is a poor fit for your domain. Tokenise your numeric fields under their real formatting and check the splits are stable when the formatting varies. Round-trip a sample through encode then decode and diff it against the original, because a tokenizer that emits unknown tokens is silently destroying data. If you're paying per token, measure the ratio separately for every language you handle before you set a budget.
Step 5

Synthesis and what's next

The tokenizer is a frozen, lossy lookup table sitting on both sides of the model, and the model's entire experience of language is the integer sequence it produces. Its behaviour follows from three choices made before you arrived: the method, most often byte pair encoding; the parameters, chiefly vocabulary size and which special tokens exist; and the corpus its merge statistics were computed on. Subword granularity won because it keeps frequent words compact while still decomposing anything unfamiliar. The practical consequences are the ones to remember: digit splitting determines arithmetic competence, whitespace handling determines code competence, vocabulary coverage determines what a given language costs you, and mismatching a tokenizer to a model produces nonsense rather than an error.
