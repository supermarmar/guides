Feature engineering: reduction and transformation

From a thousand raw MRD columns to a few dozen model-ready features. Two pipelines run in series: reduction strips down the candidate set by predictive power, correlation and collinearity; transformation conditions the survivors so each one is well-behaved in log-odds space. Both pipelines are explicit, auditable and reproducible.

Step 1

The 30-second version

A typical retail MRD ships with around 1,000 candidate features once you count behavioural roll-ups, bureau attributes and engineered trend variables. The PD scorecard ends up using 20 to 40. Feature engineering is the disciplined funnel between the two: a five-step reduction pipeline (data quality, predictive-power screening, correlation clustering, variable clustering via PCA, collinearity assessment) followed by a five-step transformation pipeline (special-value treatment, missing-value imputation, outlier capping, scaling, monotonising transformation). Both pipelines have explicit thresholds and produce auditable artefacts at every step.

The work is anchored in two ideas. Reduction protects model stability: keeping highly correlated features destabilises coefficients (multicollinearity) and inflates variance; keeping weak features adds noise without adding signal. The reduction pipeline drops, in order, the obviously broken (quality), the weak (predictive screening), the redundant (correlation clustering), the over-similar (PCA clustering) and the destabilising (collinearity). Transformation enforces the modelling assumption: logistic regression assumes a linear relationship between features and the log-odds of default. Most raw features do not satisfy this assumption out of the box. Transformation maps each surviving feature into a form where the assumption holds, using Tukey's Ladder of Power and the Bulging Rule as the diagnostic.

Both pipelines are run per segment. The PiT model is segmented (delinquency, MoB, utilisation; see lecture 13) and feature behaviour can differ materially across segments. Running a single feature-engineering pipeline over the whole portfolio and then segmenting downstream is a common modelling shortcut that produces silently sub-optimal scorecards.

Feynman test Feature engineering is what separates "this is the data we have" from "this is what the model is allowed to see". A junior modeller's instinct is to feed everything in and let the regression sort it out; the regression then over-fits, multicollinearity destabilises the coefficients, and the resulting scorecard fails the validator. The five-step reduction pipeline is the discipline of removing material before it reaches the model. The five-step transformation pipeline is the discipline of making sure what survives is in a form the model can use. Skipping either is the most common cause of scorecard failure at validation.
Step 2

Why this matters

Multicollinearity is the silent killer of logistic regression. Two features that are 95% correlated will have unstable coefficients: small changes in the training sample produce large swings in the relative weights. The supervisor's challenge is then mechanical: rebuild the model on a different random sample of the same data, observe that coefficients have moved, and require a rebuild. The collinearity-assessment step (Step 4 of reduction) exists to stop this happening before the model is fit.

The transformation pipeline addresses the related problem of linearity. Logistic regression models log-odds as a linear function of features. A feature that has a U-shaped relationship with the observed default rate (low ODR at both extremes, high ODR in the middle) cannot be used directly: the linear fit averages out to a flat coefficient and the variable looks insignificant when in fact it is informative. The transformation pipeline detects this and either splines the variable, transforms it, or splits it into two monotone half-features. None of this happens by accident.

Both pipelines are also where the use test gets enforced operationally. Every transformation, every drop, every cap is documented; the same documentation is used by the credit-risk-control unit when explaining the model to the credit committee. If a feature is dropped because it has a non-monotone relationship with ODR, the bank must be able to explain that to a credit officer in plain terms. The documentation discipline that emerges from this work is what passes supervisory review.

Step 3

The mental model

The two pipelines form a funnel. Raw MRD features enter at the top; model-ready features emerge at the bottom. At each step, an explicit criterion either drops a feature or transforms it. The diagram traces the flow.

Three properties to hold. First, both pipelines are run per segment, not over the whole portfolio. A feature that is highly predictive in the transactor segment may be uninformative in the revolver segment; running the pipeline once on a pooled sample averages out segment-specific signal. Second, each step has a documented justification per feature dropped or transformed: the development document records which step the variable failed at, what the metric value was, and why the threshold applies. Third, the order matters: reduction strictly precedes transformation, because there is no point conditioning a feature you are about to drop, and a transformation applied to a feature that fails reduction in a later iteration is wasted effort.

Step 4

The detail

Reduction Step 1: data quality screening

Some features fail the most basic quality checks and need not enter the rest of the pipeline. The screening rules:

  • No variance. A feature with a single unique value carries no information; drop unconditionally.
  • Excessive cardinality. Categorical features with more than around 100 categories (some banks set 50) cannot be encoded into a stable logistic regression without dimension reduction; drop or aggregate.
  • Date / time fields. Raw dates are not predictors and should not enter the model; drop or replace with derived age / vintage features.
  • High missingness. Numeric features with more than around 20% missing values are dropped, because imputation at high missingness rates introduces enough noise to outweigh the variable's signal.

Certain features are protected from the reduction pipeline entirely on business grounds: the default flag and its components (target / target-derived), account identifiers (needed for joins), product type (needed for segmentation), external bureau scores (highest single-feature predictive power; supervisory expectation), and application-form variables (use-test alignment with origination). Protected features bypass Steps 1 to 5 and go straight to transformation.

Reduction Step 2: predictive-power screening

Each surviving feature is scored on its bivariate relationship with the target. Three metrics dominate:

Information Value (IV). For a binned feature with k bins, with good-rate g_i (1 - default rate) and bad-rate b_i in bin i:

WoE_i = ln( g_i / b_i )

IV = sum_i (g_i - b_i) * WoE_i

Standard interpretation: IV < 0.02 weak; 0.02 to 0.10 medium; 0.10 to 0.30 strong; > 0.30 very strong (occasionally too strong, indicating leakage). The Weight of Evidence (WoE) per bin is what some banks use directly as the transformed feature; we keep IV for screening and re-derive the transformation in the transformation pipeline.

Gini coefficient. The bivariate Gini for a numeric feature against the binary target is the ratio of the area under the Lorenz curve to the maximum possible area. Gini = 2 * AUC - 1, and for a binary target with a numeric predictor it is computed by ranking the predictor, accumulating the bad-rate, and comparing to a uniform diagonal. Typical retail bureau features score 0.15 to 0.40 Gini against the 12-month default flag.

R-squared. The univariate R-squared from regressing the target on the feature; complementary to Gini and IV. Use as a cross-check rather than a primary criterion.

The standard cut-off: drop features below the 50th percentile of the predictive-power distribution within the segment. Where two features score identically, one is dropped to avoid duplicate information. The choice of which to drop is documented (typically the one less stable across time or less explainable to credit officers).

Reduction Step 3: correlation clustering (three iterations)

The standard reduction approach is iterative, with progressively looser thresholds. The reason: a single hard threshold either keeps too many correlated variables (loose threshold) or drops too many small but informative ones (tight threshold). Iterating addresses both ends.

IterationPearson correlation cutKeep per cluster
1> 99%1 (highest Gini)
2> 85%2 if cluster > 10 variables; 1 otherwise
3> 70%3 if cluster > 10; 2 if 5 to 9; 1 if < 5

Within each cluster the highest-Gini variable is retained; ties are broken on IV. Variables removed at each iteration are determined independently of previous iterations (the cluster is re-formed each time). For segments with low default counts or unusual structure, IV may be used alongside Gini as the ranking criterion, and the independence assumption may be relaxed.

Pearson correlation is the standard. Some banks supplement with Spearman (for non-linear monotone relationships) or distance correlation (for general dependence). The choice is documented and stays consistent across iterations within a single model build.

Reduction Step 4: PCA-based variable clustering

Pearson correlation only captures pairwise linear association. Variables can be jointly redundant without being pairwise highly correlated: three variables that all reflect "customer's overall financial health" may each pairwise correlate at only 60% but share most of their information. PCA-based clustering catches this.

The procedure: run PCA on the remaining feature set; form clusters that maximise within-cluster correlation and minimise between-cluster correlation; iterate by splitting any cluster whose second eigenvalue exceeds 1 (a sign that two underlying factors are present); continue until at most around 35 clusters remain.

Within each cluster, four metrics are computed for each variable: RS Own (1 - R-squared with own cluster, where lower is better because it indicates the variable is well-explained by its cluster), IV, Gini, R-squared. Variables are ranked on a combined IV-Gini score; the top variable per cluster is kept. A second variable is kept where it provides complementary information:

  • If the top variable has a low RS Own rank (well-explained by the cluster), keep a second variable that has a high RS Own rank (less typical of the cluster) plus high IV and Gini.
  • Reverse case: if the top variable has high RS Own (atypical), keep a second variable that has low RS Own (typical) plus high IV and Gini.

This ensures both the most representative and the most informative-but-divergent variables survive. Judgemental adjustments are also permitted: where multiple variables share a business meaning (different roll-up windows of the same underlying signal, for example "balance trend 3-month" versus "balance trend 6-month"), the development team picks the most predictive one and drops the rest.

Reduction Step 5: collinearity assessment

The final reduction step targets multicollinearity that survived Steps 3 and 4. Two related diagnostics:

Variance Inflation Factor (VIF). For each feature, fit it as a function of the others and take VIF = 1 / (1 - R-squared). Standard threshold: VIF > 10 indicates severe multicollinearity; some banks use a stricter VIF > 5. Drop the feature with the highest VIF first, refit, repeat.

Condition index and variance decomposition. The more diagnostic approach for collinearity. Compute the eigenvalues of the standardised correlation matrix; the condition index for the k-th eigenvalue is sqrt(lambda_max / lambda_k). Values above 30 indicate severe multicollinearity. For each high condition index, the variance decomposition matrix shows how much each variable's coefficient variance is associated with that eigenvalue. Where two or more variables contribute more than 0.5 to the same condition index, the variable with the highest variance proportion is removed. Iterate until no condition index exceeds 30.

After Step 5 the candidate feature set is typically down to 30 to 50 variables. A final univariate review (sometimes called Step 6) examines each survivor for distributional anomalies, univariate predictive strength, bivariate monotonicity with ODR, and stability across time and segments. Variables with non-monotone or unstable ODR relationships are flagged for either transformation (next pipeline) or removal.

Transformation Step 1: special-value treatment

Many external data feeds encode missing data and "no hit" results as specific sentinel values rather than nulls. Experian's 997 / 998 / 999 series is the classic example. These values are syntactically valid numbers but semantically not part of the variable's range; including them untransformed pulls regression coefficients in the wrong direction.

The treatment rule:

  • If the special value occurs in less than 1% of the sample, treat as immaterial and proceed.
  • Otherwise: bin the valid range into deciles, compute the ODR per decile, and inspect the trend.
  • If the ODR is monotonic across deciles, leave the special value as-is (the regression will sort it out).
  • If the ODR is non-monotonic, replace the special value with a negative value outside the valid range (for an Experian variable with valid range [0, ...], use 998 → -1, 999 → -2) to force the special-value rows to fall outside the trend.

Validate by re-plotting the post-imputation ODR series and confirming monotonicity is restored.

Transformation Step 2: missing-value imputation

Three missingness mechanisms call for different treatments:

  • Missing at random (MAR): missingness is unrelated to the value but may correlate with other variables. Impute into the nearest decile of non-missing values, where "nearest" means the decile whose ODR is closest to the missing-group ODR (or the more conservative decile if multiple are tied).
  • Missing not at random (MNAR): missingness is informative (high-risk customers more likely to leave the field blank). Impute with 0 (or a distinguishing sentinel) and rely on the regression to pick up the differential.
  • Structurally missing: the field is genuinely undefined for some obligors (LTV for unsecured loans). Treat as MAR with explicit documentation; alternative is to add a presence indicator as an auxiliary feature.

Validate post-imputation ODR series for monotonicity and absence of imputation-induced discontinuities.

Transformation Step 3: outlier treatment

Standard rule: examine values below the 1st percentile and above the 99th percentile of each variable's distribution. For each tail, decide whether the values are:

  • Data errors (impossible values, input mistakes): cap at the 1st / 99th percentile unconditionally.
  • Genuine but sparse extremes: cap if their small count creates instability in coefficient estimation, retain if they represent meaningful risk patterns with consistent ODR.

The decision is judgemental and documented per variable. A frequent source of false outliers in retail data: balance values immediately after a large purchase or a credit-line increase, which are unusual but not erroneous and carry genuine information.

Transformation Step 4: scaling and normalisation

Some variables have a concentrated mass at an extreme value (zero balance, maximum utilisation, hundreds of recent enquiries) where the values are not outliers but where the raw scale produces unintuitive coefficients. Scale the variable down by a constant factor or apply log / square-root to compress the tail without distorting rank-ordering.

Monotonic transformations do not change discriminatory power: a Gini computed on the raw variable equals the Gini computed on the log of the variable. What changes is the regression coefficient: a one-unit change in the log of a count is a doubling, which is a more meaningful "unit" than a one-count increase. Coefficient interpretability matters for the use test.

Transformation Step 5: monotonising transformation

The final and most important step. The logistic regression assumes a linear relationship between the feature and the log-odds of default. Most raw features satisfy this only approximately. Three diagnostics drive the transformation choice:

  1. Plot the variable against ODR or against log-odds. The visual is the primary tool.
  2. Apply Tukey's Ladder of Power: try x^p for p in {-1, -0.5, log, 0.5, 1, 2, 3} and pick the one that produces the best linearity in log-odds space.
  3. Apply the Bulging Rule. If the plotted ODR-vs-feature curve bulges upwards (rises and then flattens), apply a transformation in the lower half of Tukey's ladder (log, square-root) to compress the right tail. If the curve bulges downwards (flat then rising), apply a transformation in the upper half (square, cube) to expand the right tail.

Where no power transformation produces a monotonic linear relationship in log-odds, the feature is either spline-transformed (piecewise linear in log-odds with knots chosen by ODR breakpoints), binary-encoded (indicator of exceeding a threshold), or dropped. Splining preserves more information than binary encoding and is the standard for variables with a clean non-monotone but interpretable relationship (utilisation rate has a well-known U-shape in some portfolios because both zero-balance and at-limit obligors are higher risk).

Validate by re-fitting the univariate logistic regression on the transformed variable and confirming the residuals are approximately normal and the relationship is monotone.

Step 5

The grandmaster's perspective

The single most consequential lesson in feature engineering is that more variables do not produce better models. Past the point of diminishing returns (typically around 30 to 50 variables for a retail PD scorecard), adding features increases multicollinearity, instability and over-fit faster than it adds discrimination. A scorecard with 25 well-chosen, well-transformed features outperforms one with 100 raw features at every metric the validator looks at. The reduction pipeline is the discipline that gets you to the sweet spot; the temptation to skip steps "because we have so much data" is the most common cause of scorecard failure at validation.

The second lesson is on over-compression versus over-expansion. The transformation pipeline can damage data as easily as it can fix it. A log transformation applied to a variable that does not need it compresses meaningful variation into a narrow range; a square transformation applied to a roughly-linear variable expands noise. The Bulging Rule and Tukey's Ladder are not formulas to apply blindly; they are visual diagnostics that read the data. A modeller who applies log() to every variable because "log() usually helps" is producing transformations on autopilot rather than on the data.

The third lesson is on monotonicity. Logistic regression is a linear model in log-odds; if a feature has a U-shape relationship with the target, the linear fit averages to flat and the variable looks insignificant when it is in fact informative. The standard fixes are splining (piecewise monotone) or binary encoding (indicator of being on the high-risk side). Both are valid; the choice depends on whether the underlying relationship has meaningful gradations (split) or just two regimes (binary). Examination questions on this should test understanding of why monotonicity matters, not just memorisation of the bulging rule.

The fourth lesson is operational: the documentation that emerges from feature engineering is what the supervisor reviews first. Every drop, every cap, every transformation has a row in the development document. The development document is what the validator marks up, the credit-risk-control unit signs off, and the supervisor reads at SREP. Banks that treat feature engineering as a coding task to be cleaned up "later" end up with documentation that does not match the production scorecard, which fails review. The discipline is to write the document as you go.

Test yourself

  1. List the five steps of the reduction pipeline and the five steps of the transformation pipeline, in order.
  2. Why is the reduction pipeline run per segment rather than over the whole portfolio?
  3. Write the IV formula. State the four standard interpretation bands (weak, medium, strong, very strong / suspicious).
  4. The correlation-clustering step uses three iterations with progressively looser thresholds. Why iterate rather than apply a single threshold?
  5. What is the difference between VIF and the condition index as collinearity diagnostics? Which is the more rigorous?
  6. An Experian feature has 4% of rows coded as 998 (no-hit). The ODR by decile across the valid range is monotonic. What treatment applies?
  7. Distinguish MAR, MNAR and structural missingness. What imputation rule applies to each?
  8. Explain the Bulging Rule. Given an ODR-vs-feature curve that bulges upwards, what side of Tukey's Ladder should the transformation come from?
  9. A feature has a U-shaped relationship with ODR. Why is using the raw variable in the logistic regression a problem? Name two fixes.
  10. A junior modeller's instinct is to include all 1,000 raw features and let regularisation sort them out. State three reasons this is a bad approach for IRB capital.
